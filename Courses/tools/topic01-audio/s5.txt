[focus] 上一节我们用三个数，给 MLA 这一步收了尾。注意力那场仗打完了，token 继续往下走，来到第三步：Dense MLP。

[friendly] 这一节看着是全课最简单的一节。但它有一个特殊身份：它是后面整个 MoE 的对照组。所以请大家跟着我，把它仔细记住。

[casually] 这个对照组不是假想的。V3 的配置里写着，前三层用普通的 MLP，从第四层开始才换成 MoE。它就是模型里实实在在的三层。

[focus] 先看结构。请看这张图。一个七千一百六十八维的向量进来，先被撑宽到一万八千四百三十二维，大约二点五七倍，再压回七千一百六十八维。就这么一件事。

[curiosity] 唯一需要解释的地方是：撑宽这一步，做了两份。上面那一份，过一个叫 SiLU 的激活函数，变成阀门。下面那一份，什么都不过，原样不动，是水流。

[thinking] 阀门和水流逐个元素对位相乘。每个通道上，阀门开多大，就放多少水过去。最后第三个矩阵，把结果压回七千一百六十八维。

[friendly] 这个结构叫 SwiGLU。三个矩阵，每个都是七千一百六十八乘一万八千四百三十二。一层大约三亿九千六百万个参数，三层加起来大约十一亿九千万。

[seriously] 还要记住一点：这一步的形状完全固定。跟输入的内容没关系，跟序列有多长也没关系。后面那四条好处，全都从这一句长出来。

[curiosity] 讲到这里，几乎每次都有人问，而且问得对。经典的 MLP 只有两个矩阵：撑宽，过一个非线性，再压回来。第三个矩阵图的是什么？

[thinking] 图的是让那个非线性活起来。经典写法里，非线性是死的。不管什么输入、哪个通道，都按同一个规则压一遍，训练也改不了它。换一个更好的激活函数也没用，它依然是一个固定的函数。

[realization] SwiGLU 把哪些通道该放行、放多少，变成了学出来的，而且跟着输入变。同一个通道，这个 token 来的时候阀门全开，下一个 token 来，可能就关上了。

[seriously] 所以这一节最容易讲偏的一句是：真正买到表达力的，不是 SiLU，是那个乘号。

[focus] 这件事有实验钉死。请看这张八根条的图，来自提出 SwiGLU 的那篇论文。八种写法，参数量和算力全部对齐，训一样多的步数，比 perplexity，这个数越小越好。先别看数字，看它分成了哪两堆。

[thinking] 上面一组，只换激活函数，还是两个矩阵。基线 ReLU 是一点六七七，GELU 一点六七九，Swish 一点六八三，两个都比基线还差一点。

[realization] 下面一组，加一个乘号，变成三个矩阵。五个变体全都赢了。两组之间的差距，比组内任何两个的差距都大。分界线在有没有乘号，不在用了哪个激活函数。

[excitement] 最说明问题的是这一根，Bilinear。它两条路都不过任何激活函数，就是两个线性变换直接相乘，一点六四八，照样赢过那两个精心挑过激活函数的写法。连激活函数都不要，光靠一个乘号，就赢了。

[casually] 顺带一句：SwiGLU 一点六三六，GEGLU 一点六三三，基本打平。所以 V3 选 SwiGLU，不是因为它最好，而是这一组里挑哪个都差不多，重要的是进了这一组。

[contemplative] 还得补一句诚实的话。这篇论文的作者自己说，他解释不了门控为什么管用，只能归于老天赏饭。所以乘法带来交互，是一个说得通的直觉，不是被证明的因果。这张表撑住的只有一件事：门控这一组确实赢，而且赢的不是激活函数。

[curiosity] 第二个必被问到的问题：多了一个矩阵，听起来像多了百分之五十的参数，真的多花钱了吗？

[thinking] 没有。请看这张三行的图，格子长度就是参数量。经典写法两个矩阵，惯例撑到四倍，也就是两万八千六百七十二维，一层四亿一千一百万参数。

[thinking] 那篇论文定了一条规则：三个矩阵的写法，把中间宽度乘以三分之二。这样三个矩阵的总参数，跟原来两个矩阵完全持平，算力也持平。刚才那张表就是在这条规则下比的。

[realization] V3 实际用的一万八千四百三十二，比这条规则还再低一点，一层三亿九千六百万。多了一个矩阵，参数反而少了百分之三点五七。门控那点表达力，在参数账上是白送的。

[excitement] 一万八千四百三十二这个数，还藏着一个伏笔。九乘以两千零四十八，正好等于它。两千零四十八是后面 MoE 里一个专家的宽度，而 V3 每个 token 激活的专家，正好是九个。这件事下一节会兑现。

[contemplative] 不过要说清楚：相等是能验算的事实，所以他们是照着这个定的，是解读，论文没写。

[focus] 好，下面是这一节真正要留下的东西：dense 的四条好性质。请看这张表，大家记一下。

[friendly] 第一，每个 token 走完全相同的一条路，形状静态、可预测。第二，它就是一个大矩阵乘，算力利用率天然高，是 TPU 矩阵单元 MXU 最喜欢的形状。

[friendly] 第三，不需要任何通信来决定谁算什么，没有调度，没有商量。第四，编译器能提前把一切排好，运行时没有不确定性。

[seriously] 这四条，MoE 一条都没有。

[focus] 到第四步，它们会分别变成：形状要等路由跑完才知道；一个大矩阵碎成两百五十七个小矩阵，单个喂不饱 MXU；每层多出两趟 all-to-all 通信；编译器只能按最坏情况留位置，留少了就得丢 token。

[warmly] 所以千万别把 MoE 理解成白捡的便宜。它确实省算力，省得很多。但省下来的那部分，就是拿这四条换的。下一步讲的每一个麻烦，都能对回这里的某一条。

[curiosity] 最后一个必来的问题：为什么偏偏是前三层不做 MoE？

[thinking] 有一个流传很广的答案：靠近输入的层做的是通用活儿，基本词法、局部句法，每个 token 都要用，没什么可分工的。这个说法听起来非常顺。问题是，它不是 DeepSeek 给的理由。

[focus] 请看这张三个方框的图。去翻论文，会看到一条链。最早是 DeepSeekMoE，保留第一层 dense，而且给了理由：他们观察到，第一层的负载均衡收敛得特别慢。

[seriously] 这是一个训练稳定性的理由，跟通用还是专用一点关系都没有。

[casually] 接下来 V2，同样保留第一层，只写了一句沿用上一篇。再到 V3，改成了前三层，这一次只陈述事实，没给任何理由。为什么从一层变成三层，公开资料里查不到。

[seriously] 所以能说的是：最初的公开理由是训练稳定性。不能说的是：V3 选三层，是因为前三层最通用。后面这句是猜测，论文里没有依据。

[contemplative] 把负载均衡收敛慢，讲成前几层比较通用，就是把一个训练现象，偷换成了一个语义故事。两者都可能对，但只有前者能查证。而且这远不是共识：同期的主流 MoE 里，有留三层的，有留一层的，也有一层都不留的，说明这是各家试出来的经验值。

[warmly] 好，对照组立好了，四条好性质也摆在这儿了。下一步，我们进入 MoE，看它省下了多少，又拿走了哪几条。

[friendly] 这一节就到这里，大家有问题吗？
