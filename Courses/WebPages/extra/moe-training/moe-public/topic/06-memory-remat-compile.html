06 · 显存、remat 与编译：远低于上限的理论账怎么变成 92 GiB

这章解决什么：每个 device 可用显存上限 94.74 GiB。按「权重 + 梯度 + 优化器 + 激活」算，大号模型的理论账远低于上限，实测却顶到 92 GiB。差出来的是三样账本外的东西：在途通信 buffer、碎片、被留得太久的临时量。贯穿全章：空出来的显存是调度器藏通信的地方（有前提，见 §1 末）。术语查 README 术语表。

步时指数：大号模型以单片 BF16 最初基线 = 100，小号模型以开发期起点 = 100（越小越快）。只在单个 A/B 里出现的数只给百分比；显存给 GiB / GB 原值。

  • 92 GiB 实测（算上碎片）；理论账远低于上限
  • 2.7 GiB 离可用上限的余量
  • 84 GiB 10+ 片大号 FP8 JIT 基线的编译估计（每 device）
  • 约 42 min 数千芯片 JIT 到 step 0 结束

1.显存账本：94.74 GiB 里住着谁

先占后用：通信一发起，接收 buffer 就占上显存，发得越早同时占着的越多。理论账只数正在用的东西，没数这些接收区、碎片和留得太久的临时量；逐项见住户表，机理见本节末动图。

  • 每 device 96 GiB HBM（192 GiB ÷ 2，官方 TPU7x 规格表），可用上限 94.74–94.75 GiB。
  • 日志「94.74 GB」其实是 GiB（max_utils 除 2**30，XLA 也是 1024 进制）。

92 和 94.74 别混：92 GiB 有三种意思

数 是什么 拿来干什么
94.74 GiB 运行时每 device 可分配的上限：jax.local_devices()[k].memory_stats()["bytes_limit"] 换成 GiB，MaxText 启动日志「Using (GB) x / 94.74」的分母 硬上限。实机峰值过了它就 RESOURCE_EXHAUSTED
92 GiB 实测峰值（本章开头） 一次观测：大号模型早期 BF16 基线（1 片 256 芯片、PDB 2、context 存 device）一次 profile 的实机峰值约占上限八成，算上碎片约 92 GiB（这次 profile 的碎片没单独拆出；下表「4 → 9 GiB」是另一组对照）。和 §10.4 阶梯第 0 级（FP8 满配，含碎片约 80 GiB）不是同一配置 不是门，只说明碎片能吃掉多少
92 GiB placement 准入线 placement 自己的显存准入上限：96 − 4（4 GiB 是它的显存安全余量配置），比的是它在调度后的显存估算，不是最终 temp，也不是实机峰值（02 §13.2） 只决定 placement 接不接受一次提前；超了它，那次移动被拒，编译照常通过
92 GiB 每日 AOT 闸（§7 表） 试过的每日 AOT 显存检查门槛，量的是编译期 CompiledMemoryStats 的总量（arg + out − alias + temp），未进生产 只借判据。总量比 temp 多出输入那一截，所以这个门比「temp ≤ 94.74」严得多，会拦下实机放得下的产物（§10 的 10+ 片 AOT 中间档就超了它，照样跑通）

新模型用哪个：编译期先用 temp ≤ 94.74 GiB 初筛（§10），终判看实机峰值 ≤ 94.74 GiB。要不要再加一道 92 GiB 的每日 AOT 闸，看你们能不能接受它误拦。

常驻那一项自己怎么估（通用口径，按自己的精度配置改；书里模型的参数量不公开，这里也不代入）

  • 常驻 ≈ 参数量 × 每参数字节 ÷（FSDP × CP × EP）；有 TP 切的再 ÷ TP。MaxText 默认切分规则里，非专家权重的 embed 维也切到 context / expert 轴，专家权重则 embed 维切 fsdp / context、专家维切 expert，两类分母一样——不是只有专家那部分 ÷ EP。
  • 每参数字节，按「权重 fp32、梯度按 grad_dtype（默认 float32）、优化器状态 fp32」这一常见配置（MaxText weight_dtype 默认 float32，mu_dtype 不设时跟随它）：
    • AdamW：权重 4 ＋ 梯度 4 ＋ 一阶矩 m 4 ＋ 二阶矩 v 4 ＝ 16 B；
    • Muon：权重 4 ＋ 梯度 4 ＋ 一个动量 4 ＝ 12 B。MaxText 的 Muon 对没标 Muon 维度的叶子仍走它内带的 Adam（1D / 标量、norm 的 scale、嵌入、输出头；KDA 类模型的 A_log、dt_bias、conv1d 也归这边；muon_include_routers=false 时路由器同样走 AdamW），这部分按 16 B 算；
    • 权重存 bf16、或动量降精度时，按实际字节改。
  • 常驻再加激活（§2.2）就是上表第一行的「理论账」；要和 94.74 GiB 比，还得留出下面这些账外住户。所以它只作开编前的初筛，终判同 §10。

HBM 余量 = 调度余量（下图）。有前提：瓶颈得是「显存不够、调度器没法提前发 collective」；成立条件、反例（含本章 §2 的 mlpwi_0/1 变成正收益）和判据（换存法前后比暴露的 RS async-done 等待）见主场 05 §2。

示意。看右侧 HBM 竖条：上行住得下两个在途 AG，下行只放得下一个。

为什么：空出来的显存不会闲着，调度器会自动把它换成通信的提前量（上图；实例：context + kda_residuals 上再多存 mlpwi_0/1 反而变慢，§2）。

  • 调度器怎么用显存：开源调度器（LHS）的目标是让计算盖住通信的估计延迟，不是越早越好；显存用量过上限一半后，显存才进入它的打分，把在途窗口往短里推（细节见下方折叠）。
  • 多片的硬门：真正卡住提前量的，更可能是 placement 准入线 96 − 4 = 92 GiB（02 §16.2；和 §1 表里那道 92 GiB 每日 AOT 闸数值相同，但不是一回事）[推断]。
  • 单片另算：单片 temp 约 93 GB（约 87 GiB），在准入线以下；单片满配下要是提前量也被它卡住，那就得是 placement 自己的估算比 temp 高 [推断]。
  • TPU 后端是否用同一份代码、上限怎么设，未公开。

GPU 上相当于：FSDP1 的 forward_prefetch／backward_prefetch 与 limit_all_gathers——PyTorch 让用户手调在途 AG 数，XLA 的调度器按 HBM 余量自动调（类比）。

把握：源码证实 · 出处：openxla/xla xla/service/latency_hiding_scheduler.cc（开源 XLA；TPU 后端未公开）；PyTorch torch/distributed/fsdp/fully_sharded_data_parallel.py 的参数说明

  • 若开了重排（rerun，开源默认 0），整张排完仍超限就按 0.9 倍上限重排。

  • minimal 系列 OOM。
  • mlpwi=offload 撞 scan+offload bitcast bug；decoder_layer_input=offload 编译崩溃。
  • 优化器卸 host：搬走的字节约 35% 被 temp 反涨吃回；JAX_MEMORY_FITTING_LEVEL=O3 字节级无变化。口径：多模态版 BF16、10+ 片 DP10+ / FSDP512、PDB 2，CPU AOT。
  • 同一组里关掉 latency-hiding scheduler 省一大截：张量没变小，是 logits 和梯度不再同时活着——「显存余量＝调度余量」的反面证据（代价是性能，没测）。
  • 激活全卸 host（minimal_offloaded）比 full 慢约 60%（指数 50 对 31）：小号模型 64 芯片、PDB 2。
  • 在 context + kda_residuals 上再加 mlpwi_0/1 存设备，反而慢约 9%（按原始步时、以 context + kda_residuals 基线折算；05 §2 的指数 28 → 31 是取整后的值，直接相除约 +11%，两处是同一组数）：多存的激活挤掉 RS 的异步余量（机理见 05 §2）；PDB≤2 新基线上又成正收益（上表第 2 行）。
  • 开 mlpwi remat 时 GMM 输出必须先 mask 再打 checkpoint_name，否则梯度 NaN。
  • KDA 17 个残差全存设备：OOM；只存三个局部量（Aqk/Akk/g_cumsum）就是上表约 −10% 那一档。
  • --xla_tpu_enable_ag_backward_pipelining=true 想降 HBM：小号模型 64 芯片 step 1 起 loss / grad norm 全 NaN，不能用。另一个坑：看 flag 实验先核对实际生效的值（编译日志 / LIBTPU_INIT_ARGS），不信实验标签里写的值——标签与实际传入值可能不一致。

  • 判据：先看暴露的集合通信占比；通信受限时别指望减 remat——省掉的重算本来藏在通信底下，不缩短关键路径，多存的激活还吃掉调度余量。
  • 同一组对照里，每个 device 的两颗 SparseCore（每芯片 4 颗、每 device 2 颗，官方 TPU7x 规格）执行时间比从约 3:4 偏成约 6:1（physical_core_indices 放置失衡）：换 remat 会连带改 SC 分工，要一起看。

示意。RS 两行等长；看重算变短、红色等待变长。

为什么 SC 分工会跟着 remat 偏：通信活按核分派，一次 RS 不拆到两颗核上，RS 的数量和先后一变，活就可能挤到一颗核上，成了尾巴（上框 3:4 → 6:1）。分派规则未公开，「一次 RS 不拆到两颗核上」也是推断；判据：在 xprof 里看同一个 RS 是否同时出现在两条 SC 轨道上。

GPU 上相当于：SC 卸载类似把搬运交给独立的 DMA 引擎／copy engine、不占 SM（NCCL 的 RS 默认以 kernel 形式跑在 SM 上，不算这一类）；这里是两台引擎分活不均（类比，推断）。

2.1 换模型怎么重扫 remat 档位

本章和 05 §2 的 remat 结论换模型、换基线正负都会翻（多存 mlpwi_0/1 在小号先慢后快；大号多存 context 反而 RS 多暴露），所以在新模型上按这个顺序重扫：

  1. 先 remat_policy=full，保证跑得起来，记下基线。
  2. 看 profile 里暴露的集合通信占多少。通信受限时别指望靠少 remat 提速（§2 WARN）。
  3. 给自定义 kernel 的残差命名（§3）：custom_vjp 里的残差要在 f_fwd 内部打 checkpoint_name，否则 remat 策略看不见（05 §2）。GQA 用 Splash attention 时不用自己打：
    • 上游 layers/attention_op.py 的 tpu_flash_attention 构造 Splash kernel 时传了 residual_checkpoint_name="context"，JAX 的 Splash kernel 内部把输出和 logsumexp 都打上这个名字。要存就在 policy 里留 context（预设 minimal_with_context，或 custom 下 context: device）。
    • 投影在 layers/attentions.py 里另有名字：query_proj／key_proj／value_proj／out_proj；还有 custom 专用的 attention_out（attention 输出、out_proj 之前），预设档里没有它。
    • 怎么验证：每档用 jax.ad_checkpoint.print_saved_residuals 列出存下的残差，看有没有名为 context 的两项。再看编译后 HLO 里 Splash 前向 kernel 出现几次：存下来时反向不该再调一次前向 kernel，不存时会多一次 [推断：按 remat 机制推，没在 Splash 上实测]。
  4. 一次只开一个键，大致从小到大 [推断：各键大小没有逐项实测]：attention 残差 → MoE 路由索引（上游没有这个键；上游相邻键是 moe_routing_maps，存 top-k 专家 id 和排序置换，未测）→ decoder_layer_input → 最后才是 mlpwi_0/1。mlpwi 最大，也是收益正负翻过的那个。
  5. 每档记四个数：编译期 temp、实机峰值、步时、暴露的 RS。只留在当前基线上确实变快的。
  6. 改了 placement / FP8 / PDB 之后重扫：基线一换，同一刀的收益正负可能翻过来。

判断做对了：最终档位相对 full 步时确实下降，实机峰值离 94.74 GiB 还有余量，暴露的 RS 没有明显变长。

2.2 序列拉到 32K：激活怎么估、什么时候开 CP

激活显存的通用估法（每 device，scan 层，BF16 按 2 字节）

  • 记 t ＝ 每 device 的 token 数 ＝ PDB × S，L ＝ 层数，D ＝ hidden。
  • full 档：每层只存层输入，约 L × t × D × 2 字节；另加反向时正在重算的那一层的全部中间量（随 t 线性涨）。
  • 每多存一个键，加 L × 该键大小：
    • q／k／v 投影：t × (q 头数 ＋ 2 × kv 头数) × 每头维度 × 2；
    • context：t × q 头数 × 每头维度 × 2，外加 fp32 的 logsumexp（t × q 头数 × 4）；
    • 稠密 mlpwi_0／mlpwi_1：各 t × F × 2；路由专家的 moe_mlpwi_*：各约 t × top-k × 专家宽 × 2（不计 padding）；
    • 有 TP 切 hidden 或头时，对应那一维再除以 TP。
  • 上面 q／k／v 那行按 GQA 写，MLA 要换量：MLA 先把输入压成低秩 latent 再展开成每头的 q／k／v，所以多出两个带名字的中间量，展开后的每头维度也不一样（键名与形状按源码推，没在 MLA 上逐项量过 [推断]）：
    • mla_q：q 的 latent，t × q_lora_rank × 2；mla_kv：kv 的 latent，t × kv_lora_rank × 2（kv 压缩时另切出一段各头共享的 rope 维 qk_rope_head_dim，不在 mla_kv 里）；
    • query_proj／key_proj：t × q 头数 ×（qk_nope_head_dim ＋ qk_rope_head_dim）× 2；value_proj 和 context：t × q 头数 × v_head_dim × 2（MLA 的 k／v 展开到每个 q 头，没有 kv 头数这一项）；
    • 这套方案的 MLA Splash 残差放置开关（11 C04）存的是 MLA Splash 的 output 与 logsumexp，大小同上面 context 那项；
    • 套用前用 jax.ad_checkpoint.print_saved_residuals 核一遍实际存下的形状。
  • 注意力用 Splash 时没有 S² 项；不用 flash 类 kernel 才会有 PDB × 头数 × S² 的打分矩阵，32K 下它先爆。
  • loss 头的 t × 词表那一项也随 t 涨，见 §6。
关键一步：S 涨了，先看 t 变没变
  • 8K → 32K 时把 PDB 降到原来的 1/4，t 不变，上面每一项都不变 [推断：公式里只出现 t，没有单独的 S]。所以先降 PDB，不急着开 CP。
  • CP 本身不减少 t：PDB 固定时 t ＝ PDB × S 和 CP 无关 [推断：和下面那组「HBM 不变」一致]。CP 的用处是让一个 device 只拿一条序列的一段。
  • 上游 PDB < 1 是按 PDB ＝ 1 读数据、只训其中一部分（configs/types.py 的 calculate_global_batch_sizes），读进来的有浪费。

什么时候才该开 CP

  1. 全局 batch 的序列条数少于 device 数，每个 device 分不到一整条序列；或者
  2. PDB 已经是 1，单层重算时的瞬时峰（随 S 线性涨）还是放不下。

开之前过三道：

  • 11 B04 的计数修复在不在；有线性注意力层的，状态跨 rank 传没传（13 §5.1）。
  • Splash 的 block_q 能不能整除每分片长度（05 tile 扫描规矩第 2 条）。
  • CP 收 K/V 的通信在 profile 里能不能藏住。

估算只作初筛，之后同 §10：temp 再筛，实机峰值终判。

书里唯一的 CP 证据，和它的局限

  • 来源：11 「试过不行」表：另一个模型、256 device、seq 32k，CP=2 对 CP=1，HBM 不变，步时略慢，结论是「不需要 CP」。
  • 局限：
    • 单次对照；
    • 不是这本书的两个模型；
    • 同时撞上 B04 的 GLA（门控线性注意力）状态静默错误，那组的数值本身就不对；
    • 只说明 PDB 不变时 CP=2 不省显存，没测「PDB 降不下去」的场景。

2.3 序列变短（如 8K → 4K）：remat 往哪调

书里没在短序列上测过，下面是判据和测法 [推断]。

先分清 S 变短时 t 变不变（t 同 §2.2）

  • PDB 加倍、t 不变：§2.2 那些按 t 算的激活项都不变；变的是注意力核心——每 token 的 softmax 注意力乘法随 S 线性缩，MLA 那份计算占比下降，打开 MLA Splash 残差放置开关能省的重算也跟着变少。KDA 每 token 的开销和 S 无关，基本不变。
  • PDB 不变、t 减半：激活减半，HBM 多出余量；但 FSDP 下每步搬权重的量和 t 无关，算的时间减半、通信不变，更容易变成通信受限。
往哪调的判据
  • 新基线先跑 remat_policy=full（§2.1 第 1 步），看 profile 里暴露的集合通信占比。
  • 暴露通信变大（t 减半时最可能）：多出来的 HBM 先别拿去多存激活，留给 placement／异步 collective 当调度余量（§1）；减 remat 很可能不降反升（§2 WARN）。
  • 暴露通信没变、计算是大头：才按 §2.1 第 4 步的顺序逐个多存，每档记四个数。
  • 8K 上调好的档位不能直接搬：基线一换同一刀的收益正负可能翻过来（§2.1 第 6 步）；MLA 那刀和 Splash 块参数尤其要重扫（05 §8 的 4K 起点）。

3.自定义 kernel 的残差要显式命名（fused MoE 反向不再重放前向）

前置：§2。后续：§2.1 第 3 步。

收益：未量化（没有修前对照）；trace 里 fused 前向和 fused 反向次数一一对应，没有反向触发的重放；稳态无 OOM、无 hang。

怎么考虑的：fused MoE 前向是 remat 看不透的 custom call，full 下反向要它的中间结果就把整个 fused 前向再跑一遍。

原理：full remat 下只额外保存 route IDs 和 routing weights（Linen / NNX 两套 policy 都覆盖），反向直接跑 fused 反向。

示意。看反向段开头那块前向重放。

怎么开：这套方案的 fused MoE 路径里已默认带上（上游 MaxText 的 fused MoE 只在推理侧，vllm_rpa 路径调 tpu-inference 的 kernel，没有这条训练路径）。

坑（通用规则）：自定义 kernel 一碰 remat，要显式命名它的 residual（checkpoint_name / 专门的 remat 键）。不命名，full 会重放整个 kernel，custom 会静默不生效（同类坑见 13 O09）。

4.专家权重 all-gather 占的显存：五种修法

FSDP 下专家权重每层先 AG 再算；这块 buffer 活多久、同时活几份由 XLA 决定，不由模型代码决定。下面五种修法前两种针对 GA > 1，后三种针对一层内 / 跨层的 buffer 寿命。

4.1 GA 循环里的权重外提屏障（默认关）

  • 前置：GA > 1，且配逐层 remat（prevent_cse=True）。大号模型生产是 GA=1，用不上（11 B05）。
  • 现象：XLA 的循环不变量外提（LICM）发现专家权重的 AG + concat 每个微批都一样，就提到 GA 循环外整份常驻（下图左）。
  • 怎么开：打开防权重 AG 上提开关，用 jax.lax.optimization_barrier 给权重注入对循环变量的假依赖。
  • 收益：被外提的 concat 缩到原来的一个零头；另一个模型 16 芯片 loss 校验的 OOM 消失。

4.2 同一个问题的梯度侧：dW 的 RS 被挪出 GA 累加（默认关）

  • 前置：同 4.1，只在 GA > 1 时有意义。
  • 现象：XLA 利用线性（先 RS 再累加 ＝ 先累加再 RS）把专家权重梯度的 RS 移到 GA 累加之外，carry 变成整份未切分，高 GA 下 AOT OOM（下图右）。
  • 怎么开：打开防梯度 RS 上提开关，在权重梯度 RS 之后插 optimization_barrier。覆盖 FP8 / QAG 与 BF16 显式 gather 两条路径。
  • 收益：让大号模型 BF16 高 GA 配置 AOT 编得过；无步时数据。小号模型 1000 步 loss 校验是 GA=1、开关关着，GA > 1 路径没做数值对拍。
  • 坑：
    • 静默无效：shard_exp_on_fsdp=false，或者既没开 QAG 也没开 force gather 时，开关什么都不做、也不报错；两阶段 AG 路径和 megablox 非 Tokamax 分支也不受保护（13 §2.2）。
    • 和 use_batch_split_schedule 互斥，同开直接报错。

示意。上排编译器外提，下排加屏障；红色整份块是多出来的显存。

4.3 两阶段 AG（试过，没留下）

  • 怎么开：moe_fsdp_use_two_stage_all_gather，专家权重 AG 拆两段 with_sharding_constraint + optimization_barrier，禁止跨层异步流水 AG。
  • 收益（小号模型 64 芯片）：
    • GA=1 单开：峰值约 −20%（86 → 67 GiB），但每 device 吞吐约 −15%——AG 不能提前发，全暴露。
    • GA=2 配合：吞吐持平、显存约 −20%；PDB 2 + GA=1 配合两阶段 AG 吞吐约 +20%（对照组未记录），峰值贴到 90 GiB 级，可能 RESOURCE_EXHAUSTED（碎片整理重试能救回）。
  • 坑：代码和编译器升级后省显存效果基本消失（GA=2 版 70 → 87 GiB），原因未定位到单个改动。判据：「禁止流水」换显存是拿步时付账；效果依赖 XLA 的调度，用之前要在当前版本上复测。

4.4 前缀层改四段 nn.scan（生产配置里有）

  • 怎么开：dense 前缀和 MoE 前缀原来是 Python for 循环，改成四个 nn.scan。
  • 收益（小号模型 64 芯片）：峰值约 −15%（91 → 77 GiB），步时约 −5%，8 步 loss 一致。拆项是 AG buffer 和 copy buffer 各省一大截，MLA splash 反向 buffer 涨一截。
  • 原理：scan 后 XLA 跨迭代复用同一份 AG 后的专家权重 buffer（下图），不是「scan 轴上做了 FSDP」（那条规则映射为空）。

示意。数右侧同时活着的 AG buffer 份数。

为什么：循环体只排一次，AG 输出 buffer 只有一份、每轮复用。「复用」是结果，循环边界才是原因：跨层预取最多由 collective pipeliner 往前剥一轮。代价是跨层藏通信的余地变小。在本例上是推断，没比过两版 schedule。

把握：公开资料 · 出处：JAX 文档 jax.lax.scan（「lowered to a single WhileOp」）；openxla/xla xla/service/collective_pipeliner.h

  • 坑：
    • 层数如果刚好让 dense 前缀与周期对齐，会静默构造出错的 attention 类型；
    • 检查点转换映射要跟着改；
    • nn.scan(length=1) 会被 XLA 当单次 while 内联，scan 结构丢了，调度和显存管理跟着变。所有 length=1 的 scan 都要包 set_xla_metadata(skip-simplify-while-loops_trip-count-one=true)（数值惰性，小号模型 1000 步对拍通过）。

4.5 分片权重直接传进 GMM 的 custom VJP（只有 AOT 验证，未进生产）

  • 怎么开：BF16 显式 gather（GMM 内强制权重 gather 开关）原来先 AG 出完整权重再进 GMM，反向残差存完整权重。改成把 FSDP 分片权重传进 megablox GMM 的 custom VJP：残差只存分片，反向算 dlhs 前重新 AG，dW 由 TGMM 算完直接 RS 回分片。
  • 原理：用一次额外 AG 换掉「整层完整权重从前向活到反向」。
  • 收益：大号模型 AOT 峰值明显下降（仅模拟编译）。
  • 坑：
    • 只有 AOT 数字，没有运行时步时、没有数值验证。
    • 开 remat 后每层完整权重 AG 多出一半，而 remat 本已限制权重存活期，省下的显存在真实配置里可能打折。
    • 依赖 ICI AG pipelining 的配置。

前置：§1（Muon 常驻 12 B/参数）。后续：§7 第一行 JAX 0.11 OOM 的修法在这里；§8 表里的 Muon 编译惩罚。

Muon 的 Newton–Schulz（NS）正交化每步要做几次矩阵乘，本身就是一个小循环。通信那条（NS 前复制矩阵轴，optimizer 段约 −15%）主场在 02 §3。

5.2 编译

  • 编译友好化：NS 迭代默认不展开（loop lowering）、同形叶子分桶批量做（打开 Muon 批量 NS 开关，每批 16 个），HLO 里 dot / while 个数不再随叶子数增长（同形叶子 1 个和 8 个编出来一样多）。收益见 §8 表（无前后实测）。
  • Muon NS 展开开关打开后没生效：带按分量切分配置和 scan_axis 的参数（如 MLA 投影）递归 vmap 时漏传了这个开关，仍走 scan。修后小号模型再快不到 1%，是整体打开 Muon NS 展开开关（单项快 1–2%，按小号模型 64 芯片步时折算）的前置。开关类优化要在 HLO 里确认每类参数都走了新路径。
  • 分块从 Python for 改 lax.scan：所有块共用一个 NS 体，HLO 指令数大降；但接着撞上下一个坑 ↓
  • 同形矩阵 concat 超 int32：scan 版把一大组同形矩阵 concat 成一个 buffer，word offset 超 INT32_MAX → RET_CHECK allocation_size_words <= INT32_MAX。修法：按 2 GB 上限分桶，外层 Python for、内层 scan。全用 lax.scan 会让 slice-of-concat 折叠失效，所以外层保留 for。
  • JAX 0.11 下 NS 被复制到 OOM（§7 表第一行），修法是一条窄保护：
    • 只对 CP > 1、且 NS batch 轴复制后工作集超 256 MiB 的叶子不复制、保留原分片，叶子内用 lax.scan 按每块 ≤16 个矩阵顺序做 NS；CP=1 时图完全不变。
    • 大 Gram 中间量和它引出的 all-to-all 一起消失，小号模型 CP8 编译 heap 降约 60%（§7 的 115 → 44 GiB 是同一思路的另一实现测的）。
    • 未进生产，修改后没再长跑。

批量做的显存方向（§10 两张表第 10 级与「关 Muon 批量」行）：Muon 批量在阶梯和 knockout 两种拆法里显存方向相反，步时同号（09 §4.9）。「批量」＝把同形矩阵拼成一批一起做 Newton-Schulz 正交化。

为什么：批量做和逐个做各有一股抬峰的力，哪股赢看峰值落在哪段。整组同形矩阵拼起来做，整组中间量同时活着，会抬峰；逐叶子做时调度器把很多叶子交错并发，在途中间量反而更多。哪股赢看峰值落在哪段：两级的峰值若落在不同段，批量的中间量只在其中一级碰上峰值时刻 [推断]。换配置要重看峰值位置；没逐级找过峰值指令，判据同 §2 末框，比两版峰值时刻的活集。

8.3 坑

⛔AOT 与运行时对不上：都能干净加载然后静默跑错

  • AOT 带 --xla_tpu_num_sparse_cores_for_gather_offloading=1 等 flag，JobSet 没有 LIBTPU_INIT_ARGS。
  • AOT 验证开了 HLO pass，训练脚本不用。
  • pickle 名只编码模型、拓扑，remat / Muon 不同照样加载。
  • AOT 静默编出 BF16、选成 JAX 参考 kernel（慢 2–3%；大号模型 FP8 256 芯片、GBS 1024、20 步）。
  • 配置指纹（pickle 名加配置 hash、旁挂 fingerprint 文件、加载时 assert）有设计，没进生产。上线前自己比对：AOT 时叠加的配置覆盖文件（overlay）和 flags 算一个 hash 写进产物旁，训练侧加载前重算一遍对上再跑。学习率曲线、步数这类配置是烘在 HLO 里的，对不上时训练跑的是编译时的配置。

AOT 加载两个坑（细节见 11 A01）：

  • GA > 1 时 params_shardings 算成 None（报 Expected dict, got None）：上游 maxtext#3872 已修，用 maybe_update_params_sharding_with_opt 算。
  • load_compiled 必须包在 jax.set_mesh 里，否则 Muon 报 … requires an active mesh context（来自 NS 矩阵复制开关）。

版本钉死：生产版本 jax 0.11.0 / libtpu 0.0.48；升 jax 或 libtpu 都要重量显存和数值。

副作用：0.0.47 改 batched-dot 数值（NS 最大差千分之几，§5.1）；jax 0.11.1 BF16 谱范数失败；0.0.48 在 2x4x4 AG 带宽减半。

  • 参照：阶梯第 0 级（大号模型 FP8、1 片 256 芯片、PDB 2、指数 37）在 XProf memory viewer 里的 HBM 峰值约 76 GiB（含碎片约 80 GiB）。§1 表里「含碎片约 92 GiB」是早期 BF16 基线那次 profile，不是同一配置。

11.还没解决的

  1. 0.0.48 的显存与速度是否一笔交易，只跑单次（口径见 §7）；复测 A/B 只在微型多模态版 4 芯片上起过。
  2. 多模态版 10+ 片只有关 LHS 能过；多模态版 FP8 在 2 片上差约 10 MB OOM（§7）。
  3. HLO placement 的碎片没有正式修法（大号模型 BF16 AOT 256 芯片，指数 55 的配置）；把反向 AG 流水做成 HLO pass 的实现，在完整层数上 OOM（单片 4×8×8；同一改动在 4×4×4 小配置上能过）。
  4. MoE 路由索引存不存 device 未定：大号模型 FP8 256 芯片上两边的数都只差不到 1%，在单次波动以内（PDB 未记录）。device 那边只有 profile 证据，remat 那边只有一次端到端对比，还混着别的配置改动，都不能当胜负。生产配置和 10+ 片 JIT 基线都用 device。怎么按自己的 HBM 余量取舍、怎么测见 05 §7.5。
  5. AOT/运行时指纹没落地（§8.3）；JIT 首步编两遍、每遍 trace + lowering 约 15 min（§9 坑），两处修法都没验证。

这五件有个共同点：很多修法是拿显存换调度（多留几块缓冲，通信才叠得进计算），显存一紧最先被砍的就是这些缓冲；而验证大多只跑过一次，且常在小配置上。

考考自己

max_utils 打印「Total memory size 112 GB」（量级），而 v7x 每 device 只有 94.74 GiB，作业却正常跑着。矛盾吗？ 答：不矛盾。logical 数不计 buffer 复用；同配置 XProf 峰值约 74 GiB。看 memory-usage report 或 XProf。
