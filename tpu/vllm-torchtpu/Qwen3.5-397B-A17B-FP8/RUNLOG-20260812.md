## R0 · 拿到 4 芯片测试环境　✅

**先试的路（失败）**：在自有项目 `tpu-launchpad-playground` 的 `chrisya-tpu` 集群上用 DWS
flex-start（node pool `hy3-v7-4-dws`，2x2x1）。

- ProvisioningRequest `Accepted=True / SuccessfullyQueued`，但 **排队 4 小时未拿到节点**。
- 结论：自有项目上的 v7 flex-start 容量不可预期，不适合有时限的验证。

**踩坑 1 — DWS node pool 有两个 taint，少容忍一个就永远 Pending**

```
taints:
  google.com/tpu=present:NoSchedule
  cloud.google.com/gke-queued=true:NoSchedule   ← 容易漏
```

只加前者时 autoscaler 一直回 `Pod didn't trigger scale-up: 1 node(s) didn't match Pod's
node affinity/selector`。两个都容忍后仍不触发 —— 因为 `gke-queued` taint 表示这是
**排队式 DWS**，必须先提 `ProvisioningRequest`，Pod 再用注解去消费它：

```yaml
annotations:
  cloud.google.com/consume-provisioning-request: <pr-name>
  cloud.google.com/provisioning-class-name: queued-provisioning.gke.io
```

**踩坑 2 — TPU Pod 的 nodeSelector 不能精简**

想只留 `gke-nodepool` 一条时被准入控制器拒绝：

```
Workload included the 'cloud.google.com/generate-allowlist: "true"' annotation,
but the constraint(s) {tpu-accelerator-topology-constraints} cannot be bypassed
```

`gke-tpu-accelerator` 与 `gke-tpu-topology` 两条**必须都写**。顺带确认 v7x 的值是
`tpu7x`（不是 `tpu-v7x-slice` 那种 v5p/v6e 风格），topology `2x2x1`。

**成功的路**：共享集群 `bodaborg-tpu7x-nap` 提 JobSet，**22 秒** Kueue admit + Pod Running。

```yaml
metadata:
  namespace: priority-dev
  labels:
    kueue.x-k8s.io/queue-name: multislice-queue
spec: ... 
        priorityClassName: medium
        nodeSelector:
          cloud.google.com/gke-tpu-accelerator: tpu7x
          cloud.google.com/gke-tpu-topology: "2x2x1"
          cloud.google.com/reservation-name: cloudtpu-20260710003900-159478293
        resources:
          limits: {google.com/tpu: 4}
```

提交前实测的容量（19:07 HKT，**off-peak**）：

| 指标 | 值 |
|---|---|
| `priority-dev` 队列 nominal | 119（off-peak；peak 为 375） |
| 队列 used | 64 → **剩 55** |
| 物理 tpu7x 节点 | 29 台 / 116 芯片 |
| 物理 Running 占用 | 116 芯片 → **物理 0 空闲** |

> **判断**：物理 0 空闲**不代表拿不到**。这是 NAP 集群，pending 的 workload 会触发自动扩节点，
> 上限 375 芯片。判据是 `min(队列余额, 375 − 已开)`，不是 `min(队列余额, 当前已开 − Running)`。

**拿到的环境**：

```
node        : gke-tpu-bdaf394b-4s86
/dev/vfio   : 0..7          → 8 device = 4 chip（chip:device = 1:2）
TPU_TOPOLOGY: 2x2x1         TPU_CHIPS_PER_HOST_BOUNDS: 2,2,1
host        : 224 vCPU / 944 GB RAM / 95 GB 根盘（可用 76 GB）
```

8 个 device 正好对上 Qwen3.5-397B 三种布局的 `TP × DP = 8`。

**踩坑 3 — 后台 watch-task 会抢 kubeconfig 的 current-context**

盯 DWS 的那个 watch 任务每 3 分钟跑一次 `gcloud container clusters get-credentials chrisya-tpu`，
把默认 context 改走，导致这边 `kubectl exec` 报 `namespaces "priority-dev" not found`。

修法：本次会话所有命令走独立文件，不碰默认 kubeconfig。

```bash
export KUBECONFIG=/tmp/kc-bodaborg.yaml
gcloud container clusters get-credentials bodaborg-tpu7x-nap \
  --region=us-central1 --project=cloud-tpu-shared-capacity
kubectl config set-context --current --namespace=priority-dev
# 验证 server 必须是 https://35.253.203.133
```

## R2 · torch_tpu 本体验证　✅

镜像自带的关键包：

| 包 | 版本 | 说明 |
|---|---|---|
| `torch` | **2.11.0+cpu** | 注意是 **CPU 版** torch |
| `torch_tpu` | 0.1.1 | |
| `torchax` | 0.0.11 | torch ↔ JAX 桥接 |
| `jax` / `jaxlib` | 0.9.2 | |
| `libtpu` | 0.0.41 | |
| `numpy` | 2.0.0 | |

`import torch, torch_tpu` 的输出暴露了接入机制，值得记：

```
PyTorch PrivateUse1ProfilerRegistry not found. Native TPU profiling will be disabled
    (this is expected on PyTorch < 2.12).
PjRt runtime initialization deferred for tpu
Successfully renamed PrivateUse1 backend to 'tpu'. Device: device(type='tpu')
Registered Python module for 'tpu'.
Initializing TPU distributed runtime
```

**结论**：torch_tpu 走 PyTorch 官方的 **PrivateUse1 第三方设备接入点**，把它改名成 `tpu`，
底下接 PJRT。所以 torch 本体是 CPU 版并不矛盾——TPU 能力整个由 PrivateUse1 后端提供。
import 耗时 **8.5 秒**（每次进程启动都要付）。

### 最小计算验证

```python
import torch, torch_tpu
print(torch.tpu.device_count())          # 8
d = torch.device("tpu")
a = torch.randn(4096,4096, device=d); b = torch.randn(4096,4096, device=d)
c = a @ b; float(c.sum().cpu())
```

| 项 | 实测 |
|---|---|
| `device_count()` | **8**（= 4 chip × 2，与 `/dev/vfio` 的 0..7 一致） |
| 首次 matmul（含编译） | **3.10 s** |
| 稳态 4096³ matmul | **0.289 ms/次** |
| 编译缓存命中 | `num_cache_hits=23 {85.1%}` |

> ⚠️ **不要**把 0.289 ms 直接换算成 MFU 去跟峰值比。输入是 `torch.randn` 的 **float32**，
> XLA 在 TPU 上对 fp32 matmul 有自己的降精度策略（bf16 多趟等），这个数字的精度口径未确认，
> 且只用了 device 0。作为「环境活着、算得动」的冒烟足够，作为性能数据不合格。
> 真实性能以后面 vLLM benchmark 为准。

## R3 · 安装 vllm_torchtpu

**踩坑 5 — `vllm_torchtpu` 不是预编译包，registry 里没有**

```
$ pip3 index versions vllm_torchtpu
ERROR: No matching distribution found for vllm_torchtpu
```

私有 registry `torch-tpu-virtual-registry` 提供的是 **torch-tpu 及其依赖**，
`vllm_torchtpu` 本身必须**从源码 editable 安装**（`pyproject.toml` 里 `name = "vllm_torchtpu"`，
但不发布 wheel）。README 的 Installation 第 2 步写的就是 `uv pip install --pre -e .`。

**踩坑 6 — `TOKEN_FAIL` 的真因是镜像里没有 curl**

一开始想在 pod 内用 metadata server 拿 token，脚本报 `TOKEN_FAIL`，第一反应是
Workload Identity 没配。实际是 **`curl` 命令不存在**。改用 `python3 urllib` 后 metadata 正常：

```
node SA: cloud-tpu-shared-capacity.svc.id.goog
```

> 教训：在精简镜像里，「命令不存在」和「权限不足」的报错长得很像。诊断顺序应该是
> 先 `command -v`，再谈权限。

**镜像内工具链实测**：

```
git:N   uv:Y   pip3:Y   python3:Y   gcc:N   g++:N   make:N
网络   pypi 200   github 200   us-python.pkg.dev 200
磁盘   74 GB 可用
```

`uv` 有（官方推荐路径可用），但 **`git` 和编译器都没有**。所以：

- 不能 `git clone vllm` → 改用 `urllib` 直接下 GitHub 的 tag tarball
- 若 vLLM 安装过程需要编译 C 扩展，会失败（`VLLM_TARGET_DEVICE=tpu` 理论上跳过 CUDA kernel，待验证）

**采用的安装流程**（无 git 版）：

```bash
export UV_TORCH_BACKEND=cpu
export UV_INDEX_TORCH_TPU_REGISTRY_USERNAME=oauth2accesstoken
export UV_INDEX_TORCH_TPU_REGISTRY_PASSWORD="$(gcloud auth print-access-token)"

# 1. 下 vLLM v0.26.1rc0（无 git，用 urllib 拉 tarball）
python3 -c "import urllib.request,shutil;u='https://github.com/vllm-project/vllm/archive/refs/tags/v0.26.1rc0.tar.gz';open('/work/vllm.tgz','wb').write(urllib.request.urlopen(u,timeout=120).read())"
tar xzf vllm.tgz && mv vllm-0.26.1rc0 vllm

# 2. 关键一步：删掉 tpu-inference 依赖，否则会跟 vllm-torchtpu 装到一起冲突
sed -i '/tpu-inference/d' vllm/requirements/tpu.txt

# 3. 装 vLLM（editable，TPU target，锁版本防 .dev 预发布错配）
SETUPTOOLS_SCM_PRETEND_VERSION=0.26.1rc0 VLLM_TARGET_DEVICE=tpu \
  uv pip install --system -e /work/vllm

# 4. 装 vllm_torchtpu
uv pip install --system --pre -e /work/vllm-torchtpu
```

> 用 `--system` 而不是建 venv：镜像里的 `torch_tpu` / `libtpu` 装在系统 python 下，
> 新建 venv 会把它们隔离掉。

```

```

| | 版本 |
|---|---|

### plugin 激活确认（本轮最关键的一步）

```
INFO [__init__.py:54] - torchtpu -> vllm_torchtpu.platforms:register_tpu_platform
INFO [__init__.py:18] TPU info: node_name=None | tpu_type=tpu7x-8 | worker_id=0
                      | num_chips=8 | num_cores_per_chip=2
INFO [__init__.py:237] Platform plugin torchtpu is activated
current_platform: TpuPlatform tpu
```

注册到的两个 entry point：

| group | name | target |
|---|---|---|
| `vllm.platform_plugins` | `torchtpu` | `vllm_torchtpu.platforms:register_tpu_platform` |
| `vllm.general_plugins` | `torchtpu_layers` | `vllm_torchtpu.layers:register_layers` |

**这证实了架构分析：vllm-torchtpu 是纯 plugin，vLLM 上游代码零改动。**

> ⚠️ **口径注意**：vLLM 报的是 `num_chips=8 | num_cores_per_chip=2`，但我们申请的是
> **4 chips**（2x2x1）。真实硬件是 4 chip × 2 core = 8 device，`/dev/vfio` 里也是 8 个，
> `torch.tpu.device_count()` 也是 8。**vLLM 这里的 `num_chips` 实际是 device 数**，
> 按字面理解会把规格记成两倍。配置 `TP × DP = 8` 指的是 8 个 **device**，对应一台四芯片机器。

> `ERROR [tpu_info.py:26] Unable to poll TPU GCE Metadata. Got status code: 404` —— GKE pod
> 里拿不到 TPU GCE metadata，会 fallback 到环境变量推断，**不影响运行**，别被 ERROR 级别吓到。

### ❌ 阻塞 C（本轮终点）：jax 版本与主干 kernel 不兼容

依赖补齐后，`LLM(model="Qwen/Qwen3-0.6B")` 报：

```
AttributeError: module 'jax.experimental.pallas.tpu' has no attribute 'BufferType'.
Did you mean: 'BufferedRef'?
```

**这条推翻了我在 R3 里的推测。**当时看到 `--no-deps` 能装能 import，我写的是
「钉死的 dev 版本号更像 CI 复现性要求，不一定是硬性 ABI 约束」——**错了，那是硬约束**：

| | |

## R8 · 真实推理：Qwen3-0.6B 冒烟

模型加载后进入 TPU 编译阶段，日志清楚展示了**静态形状税**的实景：

```
[tpu_runner.py:4029] Compiling gather_logprobs with different input shapes.
[tpu_runner.py:4029] Compiling substitute_placeholder_token with different input shapes.
[tpu_runner.py:4029] Compiling model backbone with different input shapes.
[tpu_compiler.py:287] [TpuCompilerAdaptor] Compiling FX graph for range (16, 16)
[backends.py:393]     Compiling a graph for compile range (16, 16) takes 6.55 s
[tpu_compiler.py:342] Saved compiled executable to
    /root/.cache/vllm/torch_compile_cache/798870e724/rank_0_0/backbone/artifact_compile_range_16_16_subgraph_0
[backends.py:378]     Cache the graph of compile range (16, 16) for later use
[tpu_compiler.py:287] Compiling FX graph for range (32, 32)
```

要点：

- **每个 token 数桶单独编译一次**，单个 backbone 图约 **6.5 秒**。桶越多冷启动越久，
  这正是 `_get_exponential_token_paddings` 存在的原因——用指数分桶压桶的数量。
- 除 backbone 外，`gather_logprobs`、`substitute_placeholder_token` 等**采样侧算子也各自编译**。
- 编译产物落盘 `/root/.cache/vllm/torch_compile_cache/<hash>/rank_0_0/...`，**可复用**。
  → **在 60 分钟窗口里跑大模型，第一件事应该是把这个 cache 目录挂到持久卷或同步到 GCS**，
  否则每轮 pod 都要重新付一遍编译时间。397B 的桶数远多于 0.6B，这笔钱很贵。

### ✅ 推理成功

```
MODEL_READY_SEC 201.2
GEN_SEC 0.2
OUTPUT: ' Paris. The capital of Italy is Rome. The capital of Spain is Madrid.'
SMOKE_OK
```

| 项 | 实测 |
|---|---|
| 从 `LLM(...)` 到就绪 | **201.2 s**（含 HF 下载 + 权重加载 + 全部 shape 桶编译） |
| 16 token 贪心生成 | **0.2 s** |
| 输出正确性 | ✅ `The capital of France is` → ` Paris. ...` |

**`vllm-torchtpu` 在 TPU v7 上的端到端推理链路，本轮全部打通。**

201 秒里绝大部分是编译，不是加载——0.6B 的权重只有 1.2 GB。这更凸显了上面那条：
**编译缓存必须持久化**，否则 397B 的每一轮都要重付一次，而它的桶数和图规模都远大于 0.6B。

### ❌ 阻塞 D：`/dev/shm` 只有 64 MiB

第一次跑，server 起不来，runner 只报 `Engine core initialization failed. See root cause above.`
——这是二手信息。去 `benchmark_runs/<ts>/server.log` 里翻才看到真凶：

```
File "vllm/distributed/device_communicators/shm_broadcast.py", line 242, in check_shm_free_space
RuntimeError: Insufficient space in /dev/shm: 160 MiB required, 64 MiB free.
                Increase /dev/shm (e.g. --shm-size or --ipc=host).
```

**K8s pod 的 `/dev/shm` 默认只有 64 MiB**，而 vLLM 的 multiproc executor（TP>1 时用）
要用共享内存做 RPC broadcast，至少 160 MiB。TP=1 时不走这条路，所以 R8 的 0.6B 冒烟没撞上。

**修法：给 pod 挂一个内存介质的 emptyDir 到 `/dev/shm`**

```yaml
volumes:
- name: dshm
  emptyDir:
    medium: Memory
    sizeLimit: 64Gi
...
        volumeMounts:
        - name: dshm
          mountPath: /dev/shm
```

挂上后 `df -h /dev/shm` → `tmpfs 64G`。已固化进 `manifests/v7-4chip-dev.yaml`。

> `sizeLimit` 记在 pod 的内存配额里，不是额外白送的内存。本机 944 GB RAM，给 64 GB 很宽裕；
> 内存紧张的机型上按需调小，但不要低于 vLLM 要求的 160 MiB 太多——TP 越大需求越高。

> **排障顺序的教训**：runner 抛的 `Engine core initialization failed ... Failed core proc(s): {}`
> 是**转述**，而且连 proc 集合都是空的，看起来像"没有更多信息"。真正的 traceback 在
> `benchmark_runs/<timestamp>/server.log` 里。**遇到 vLLM 起不来，第一动作是去翻 server.log，
> 不要在 runner 的输出里找答案。**

## R10 · 一整轮 57 分钟白跑：日志写在容器里，pod 一死全没

修好 `/dev/shm` 后重跑，pod 到点 `Completed`（exitCode 0），然后发现**什么都没留下**：
`kubectl logs` 里只有 JobSet 启动时那几行 echo，benchmark 的输出、报错、进度一概没有。

**这不是"日志神秘丢失"，是我自己的设计错误**，而且是两层：

**错误 1：把输出重定向到容器内文件**

```bash
nohup bash /work/all.sh > /work/all.log 2>&1 &     # ← 全部进容器文件系统
```

pod 一 `Completed`，容器文件系统就没了，`kubectl exec` 也进不去，`/work/all.log` 读不到。
`kubectl logs` 只能拿到**容器主进程的 stdout/stderr**，而我的脚本是 nohup 挂在旁边的后台进程，
它的输出根本没进容器日志。

**错误 2：benchmark 不是容器主进程，是 `sleep` 旁边的挂件**

pod 的 command 是 `sleep 3300`，benchmark 靠 `kubectl exec` 启动。后果：

- `sleep` 一到点，容器退出，**不管 benchmark 跑到哪都被砍**，而且退出码是 0，看起来「正常完成」
- 监控看到 `Completed / exitCode 0` 会误判成成功

**修法**（改动很小，效果决定性）：把输出 tee 到 PID 1 的 stdout。

```bash
nohup bash -c 'bash /work/all.sh 2>&1 | tee /work/all.log > /proc/1/fd/1' >/dev/null 2>&1 &
```

`/proc/1/fd/1` 就是容器主进程的 stdout → 进容器日志 → **`kubectl logs` 既能实时看，
pod 死后也能读**（只要 pod 对象还在）。同时 `tee` 保留一份容器内文件供 exec 时查。

另外加了 `PYTHONUNBUFFERED=1`，避免 python 缓冲导致日志滞后。

> **可推广的教训**：在有生命周期上限的容器里跑长任务，**日志必须走容器 stdout**。
> 写进容器内文件 = 跟容器同生共死，而恰恰是「容器死了」那一刻你最需要日志。
> 判断标准很简单：**pod 消失之后你还能不能拿到它？** 不能就得改。
>
> 同理，结果文件也不能只留在容器里，要落 GCS。

### 顺带修正 watch 报告

监控当时报的是「日志输出丢失或者未被写入 stdout/stderr，可能是脚本误把输出重定向到了挂载卷」。
方向对，但把它当成一个待查的谜团了。实际原因确定且简单——**是我写脚本时把输出重定向到了容器内文件**。
自己造成的问题，不该当成外部现象去排查。

### 本轮的真实代价

第 2 次尝试（22:39–23:36 的前身）整整 57 分钟，**没有产出任何可用数据**：
不知道权重下到没有、不知道编译走到哪、不知道 benchmark 有没有开始。

## R11 · 阻塞 E：节点 ephemeral-storage 被撑爆，pod 被 evict

修好日志后重跑，pod 跑了 9 分钟被 **evicted**：

```

```

`df -h /` 在容器里看是 95 G total / 74 G 可用，很容易以为够。**但那是容器视角**——
ephemeral-storage 是**整个节点共享**的，同一节点上别人的 pod 也在吃。35 GB 权重下载过程中

被 evict 时容器是**强杀**，`kubectl logs` 也取不到 —— 又是一轮无产出。

### 修法：把 `/work` 整个挂成内存盘

这台机器有 **944 GB 主机内存**，而权重只有几十 GB。与其跟节点磁盘抢，不如直接放内存：

```yaml
volumes:
- name: dshm
  emptyDir: {medium: Memory, sizeLimit: 32Gi}      # vLLM multiproc 只要 160 MiB，32 Gi 绰绰有余
- name: workdir
  emptyDir: {medium: Memory, sizeLimit: 320Gi}     # 权重 + HF cache + 编译缓存全在这
...
        volumeMounts:
        - {name: dshm,    mountPath: /dev/shm}
        - {name: workdir, mountPath: /work}
        resources:
          requests: {google.com/tpu: 4, cpu: "8", memory: 48Gi, ephemeral-storage: 16Gi}
          limits:   {ephemeral-storage: 32Gi}
```

三个作用：

1. **权重、HF cache、编译缓存全部落内存盘**，不碰节点磁盘 → 不会再被磁盘压力驱逐
2. **顺带提速**：从内存盘加载权重比从容器 overlay 快得多
3. **显式声明 `ephemeral-storage` request/limit**，让调度器把这份消耗算进账，也给自己设了刹车

> `emptyDir: medium: Memory` 是**按实际用量计费**的 tmpfs，不是预先占掉 320 GB。
> 但它计入容器内存使用，所以别把 memory limit 设得比它小。这里干脆不设 memory limit。

### 这条顺带解决了 397B 的落地问题

之前判断「pod 本地盘只有 74 GB，397B 的 400 GB 权重放不下，必须走网络存储」——
**有了内存盘这条路，判断要修正**：944 GB RAM 装 400 GB 权重绰绰有余。

| 方案 | 397B 可行性 | 并行友好 | 备注 |
|---|---|---|---|
| 容器本地盘 | ❌ 74 GB 放不下 | — | 还会撞节点 ephemeral-storage 上限 |
| **内存盘 `emptyDir: Memory`** | ✅ 944 GB RAM | 每 pod 一份 | 最快；但每个 pod 都要重下一次权重 |
| GCS + gcsfuse (RWX) | ✅ | ✅ 多 pod 共享 | 省下载；但 gcsfuse 读性能待实测 |
| hyperdisk PVC (RWO) | ✅ | ❌ 单 pod | 并行时每个 pod 一份，退化成方案 2 |

**串行跑单个大模型 → 内存盘最简单；并行铺开多配置 → 还是要 GCS 共享**，否则每个 pod
重下 400 GB。两者不冲突，可以叠加：GCS 存一份，pod 启动时拷进内存盘。

### 教训归纳：这一轮连续三个坑都是"容器边界"问题

| # | 坑 | 共同点 |
|---|---|---|
| D | `/dev/shm` 默认 64 MiB | 容器默认值远小于宿主能力 |
| — | 日志写容器内文件，pod 死即丢 | 产物生命周期 = 容器生命周期 |
| E | ephemeral-storage 按**节点**共享，不按容器 | 容器里看到的可用量不是你能用的量 |

**共同教训：容器里 `df` / `free` 看到的数字，都不等于你实际能用的配额。**
真正的约束在 pod spec 和节点层面。在有硬时限的环境里，这类问题每踩一个就废掉一个窗口。

## R12 · 队列 9 个任务全跳过：又是我自己改坏的 pod spec

修完内存盘后启动测试队列，结果 10 个任务里 9 个报「pod 没起来」，整夜无产出。
监控给的结论是「GKE TPU 集群系统性故障」。

**先说结论：不是集群故障，是我改 yaml 时制造的 YAML 键覆盖。**

### 排查路径（值得照抄）

| 层 | 查什么 | 结果 |
|---|---|---|
| 1. 节点 | `kubectl get nodes -l ...gke-tpu-accelerator=tpu7x` | **69 台正常** → 不是集群挂了 |
| 2. YAML | `kubectl apply --dry-run=server` | **通过** → 看起来没问题（**这里被骗了**） |
| 3. Kueue | `kubectl get workload` | `ADMITTED=True` → 配额没问题 |
| 4. JobSet | `kubectl get jobset -o json` | `conditions: []`、`replicatedJobsStatus: None`、**一个 Job 都没创建** |
| 5. **JobSet controller 日志** | `kubectl logs -n jobset-system -l control-plane=controller-manager` | **真因在这** |

第 5 层的原文：

```
ERROR Reconciler error {"controller":"jobset", "JobSet":{"name":"chrisya-ttpu-q10"},
 "error": "job \"chrisya-ttpu-q10-slice-0\" creation failed with error:
  Job.batch \"chrisya-ttpu-q10-slice-0\" is invalid:
  spec.template.spec.containers[0].resources.limits:
  Required value: Limit must be set for non overcommitable resources"}
```

### 根因：一个 YAML 文件里出现了两个 `limits` 键

我用脚本给 resources 加 `ephemeral-storage` 时，只替换了 `requests` 那一行并在后面追加了
一行 `limits`，于是变成：

```yaml
resources:
  limits: {google.com/tpu: 4}                                    # ← 被下面覆盖
  requests: {google.com/tpu: 4, cpu: "8", memory: 48Gi, ephemeral-storage: 16Gi}
  limits: {ephemeral-storage: 32Gi}                              # ← 生效的是这个
```

YAML 后出现的同名键覆盖前面的，于是 **`google.com/tpu` 失去了 limit**。而扩展资源
（extended resource）属于 non-overcommittable，K8s 强制要求 limit 必须存在 → Job 创建被 API server 拒绝。

正确写法是合并成一行：

```yaml
  limits:   {google.com/tpu: 4, ephemeral-storage: 32Gi}
  requests: {google.com/tpu: 4, cpu: "8", memory: 48Gi, ephemeral-storage: 16Gi}
```

### 三条教训

**① `kubectl apply --dry-run=server` 校验不到 JobSet 的内层 Job 模板。**
JobSet 作为 CRD 本身是合法的，非法的是它将来要生成的 Job。dry-run 通过给了我虚假信心。
**要验证 JobSet 能不能真正起来，只能真 apply 然后看有没有生成 Job。**

**② 排障要逐层往上走：pod → job → jobset → controller 日志。**
在 pod 层看只有「不存在」这一个信息量为零的事实；真正的报错在 controller 日志里，
而那需要主动去 `jobset-system` namespace 捞。driver 原来把 `apply` 的输出
`>/dev/null 2>&1` 吞掉了，等于把最有用的线索扔了——已修成记录 apply 输出，
并在 pod 起不来时自动打印 jobset conditions / job 数 / controller 报错 / Kueue workload。

**③ 不要把"我这层看不出问题"当成"外部故障"。**
监控报「集群系统性故障」，我第一反应是"节点还有 69 台，这判断是错的"——
这个反驳同样过快：节点活着不等于 JobSet controller 在干活。**双方都停在了自己能看到的那一层。**
真相在第 5 层，而且是我自己造成的。

> 用脚本改 YAML 时，**替换后一定要 grep 一遍改动区域**确认没有产生重复键。
> 这次如果改完立刻 `grep -n "limits\|requests"`，一眼就能看出两个 `limits`——
> 代价是整夜 9 个任务空转。

### 核心缺陷：runner 的超时比 pod 寿命还长

`run_benchmarks.sh` 等 server 的逻辑：

```bash
local max_wait=$(( ${SERVER_READY_WAIT_MIN:-90} * 60 ))    # 默认 90 分钟
while ! curl -s .../health; do
    if [ "$waited" -ge "$max_wait" ]; then
        echo "========== Last 200 lines of server.log =========="
        tail -200 "$RESULTS_DIR/server.log"                # ← 唯一会打印 server.log 的地方
    fi
    ...
done
```

**pod 只活 60 分钟，`max_wait` 是 90 分钟** → 那段打印 server.log 的代码**永远执行不到**。
所以连续三轮我们只能看到一串 `Waiting for server...`，而 server 到底为什么起不来，
答案一直躺在那个从没被读出来的文件里。

> 397B 的 config 更极端：`SERVER_READY_WAIT_MIN=120`（120 分钟），是 pod 寿命的两倍。
> 在有 60 分钟上限的环境里跑那个 config，注定拿不到任何诊断信息。

### 四处修复

```bash
# ① 超时压到小于 pod 寿命，让 runner 有机会把 server.log 吐出来
export SERVER_READY_WAIT_MIN=25

# ② 不等超时，直接把 server.log 实时接到 stdout（加 [srv] 前缀好区分）
( while true; do
    L=$(ls -t benchmark_runs/*/server.log 2>/dev/null | head -1)
    [ -n "$L" ] && { echo "=== tailing $L ==="; tail -F "$L" | sed 's/^/[srv] /'; }
    sleep 10
  done ) &

# ③ setup 失败立刻停，不要带着残缺环境往下跑
if ! bash /work/setup.sh ... ; then echo "SETUP_FAILED"; exit 1; fi
python3 -c "import vllm" || { echo "SETUP_FAILED: vllm 不可 import"; exit 1; }

# ④ pytest 去掉 | tail -N，让输出实时流出来
python3 -m pytest tests -q --timeout=300 2>&1
```

### 归纳：这一整晚所有的失败都是同一类问题

| 轮次 | 表面现象 | 本质 |

在有硬时限的环境里，可观测性不是锦上添花：**看不到失败原因，就得再花一个完整窗口去重现它**。

## R14 · 第 5 个自制 bug，以及为此加的启动前自检

修完 R13 的四处可观测性缺陷，队列第 1 个任务就死了：

```

```

**又是我自己写的。**driver 用 `<<TASKEOF`（**未加引号**）生成 pod 内的 task.sh，
未加引号的 heredoc 会在 **driver 这一层**展开 `$变量`。我新加的 server.log tail 段里

```bash
L=\$(ls -t .../server.log | head -1)
```

> heredoc 用不用引号是有取舍的：`<<TASKEOF` 能展开 `$TASK`（我需要），

> 既然选了前者，**每加一行新代码都要问一句：这里的 `$` 该在哪一层求值？**

397B-A17B-FP8 权重约 **400 GB**，而 manifest 里 `sizeLimit: 320Gi`（≈343 GB）。
**照文档跑 397B 会在下载中途爆掉。**跑 397B 必须把 workdir 提到 **560Gi** 以上
（节点有 944 GB RAM，够）。这条在文档里完全没提——因为我此前只跑过 0.6B。

**❌ 文档错误 3：冷启动时间估计严重偏低。**

QUICKSTART 写「首次约 35 分钟（装环境 5 + 拉模型 2 + 编译 7 + 跑 benchmark 3）」，
那是 **0.6B / TP=1** 的数。35B / TP=4 实测：

| 阶段 | 0.6B TP=1 | 35B TP=4 |
|---|---|---|
| 权重下载 | ~1 分钟（1.2 GB） | **约 2 分钟（35 GB）** — hf_transfer + 内存盘，很快 |
| backbone 编译 | 41.5 s | 15.7 s（每 worker） |
| 到 `Application startup complete` | ~7 分钟 | **> 15 分钟，本轮未等到** |

关键差异在**大 range 的图编译**：

```
[backends.py:393] Compiling a graph for compile range (8192, 8192) takes 50.12 s
```

0.6B 每个 graph 约 12 秒，35B 的 8192 range **单个就要 50 秒**，而且 TP=4 时
4 个 worker 各编一份。等待期间 `EngineCore` 每 60 秒打一次
`No available shared memory broadcast block found` —— 那是**编译期的正常提示**，不是故障。

**推论：60 分钟窗口对 397B 基本不可行。**35B 光启动就吃掉 15 分钟以上，
397B 的参数量是它的 11 倍、图更大更多。这把「编译缓存必须持久化」从优化项变成了前置条件。
