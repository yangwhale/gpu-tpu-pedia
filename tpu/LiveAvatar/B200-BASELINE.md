# B200 基线 —— TPU v6e 的优化目标

这是 LiveAvatar 在 **5×B200** 上的实测基线，**作为 TPU v6e 的对标目标**。
本页自带完整测量口径 —— **TPU 侧必须用同一套口径量，否则数字不可比**。

> **只看视频生成时间。启动/加载/编译一律不计。**
> 数字人是常驻服务，那笔只在部署时付一次，进不了性能指标。

数据来源：2026-09-17 在 8×B200 机器上（实际用 5 张）的流水线内插桩实测，非估算。
完整过程见 [`../../gpu/inference/LiveAvatar/`](../../gpu/inference/LiveAvatar/)。

---

## 一 · 配置（对标时必须对齐的变量）

| 项 | 值 |
|---|---|
| 硬件 | 5 × NVIDIA B200（183 GB HBM3e / 卡），4 卡跑 DiT + 1 卡跑 VAE |
| 模型 | `Wan-AI/Wan2.2-S2V-14B` + `Quark-Vision/Live-Avatar` LoRA |
| 精度 | DiT **fp8**（`_scaled_mm` + absmax），VAE **bf16** |
| 采样 | euler，**4 步**，`sample_guide_scale=0` |
| 分辨率 | `--size "720*400"` → 实际输出 **704×384**（横）/ **384×704**（竖） |
| 帧率 | 25 fps |
| `infer_frames` | 48（每 clip 4 个 block，**每 block 12 帧**） |
| 并行 | 4 级流水线（TPP），`ulysses_size=1`（**序列没切**） |
| 编译 | `torch.compile(mode=None, backend="inductor")`，inductor cache 持久化 |
| attention | cuDNN sm_100 flash（**不是** FlashAttention） |

> ⚠️ **`ulysses_size=1` 很重要**：GPU 侧从没试过 >1，所以这个基线是
> **完全没做序列并行**的数字。TPU 侧如果上了序列并行再对比，属于不同配置。

## 二 · 核心指标（★ 就冲这两个数去）

| 指标 | B200 基线 | v6e 目标 | v6e 实测 |
|---|---|---|---|
| ★ **生成 1 s 视频需要** | **0.604 s** | ≤ 0.604 s | 待填 |
| ★ **实时倍数** | **1.66×** | ≥ 1.66× | 待填 |
| 等效 FPS | 41.4 | ≥ 41.4 | 待填 |
| 每 block 周期（12 帧 = 0.48 s 视频） | 0.290 s | ≤ 0.290 s | 待填 |

**表里全部是纯生成时间。** 启动、权重加载、图编译都不在内 —— 不是指标，不用填。

**为什么 ≥1.0× 就够**：数字人是交互式服务，超过 1.0× 实时之后再快只增加缓冲余量，
不改变体验。真正的硬指标是 **≥ 1.0×**，1.66× 是 B200 已经达到的水位。

参考：官方宣称「多卡 H800 45 FPS」= **1.80× 实时**。B200 没跑赢 H800。

## 三 · 分项拆解（定位瓶颈用）

每 block = 12 帧 = 0.48 s 视频：

| 组件 | 优化前 | 优化后（当前基线） | v6e 对应物 |
|---|---|---|---|
| **DiT 单级前向** | 0.206 s | 0.206 s | **主瓶颈**，先打这个 |
| VAE decode | 0.1930 s | **0.0912 s** | `channels_last_3d` 换来的，XLA 上不适用 |
| VAE → host 拷贝 | 0.0198 s | 0.0198 s | 不是问题 |
| **每 block 周期** | 0.318 s | **0.290 s** | |
| VAE 占周期 | 61% | 31% | |

**理论下限**：VAE 若完全隐藏，周期 = DiT 单级 0.206 s → **2.33× 实时**。
当前 1.66×，中间约 0.08 s 是流水线重叠损耗。

**显存**：DiT 卡各 47.6 GB，VAE 卡 38.8 GB。B200 单卡 183 GB ——
**容量远不是约束**，卡数由流水线切分决定。这条对 v6e 有参考意义：
v6e 单芯 32 GB HBM，**47.6 GB 装不下单卡**，切分方式必须变。

## 四 · kernel 级分解（判断「同类工作在 TPU 上该多快」）

### DiT 一次前向：206 ms，**26,617 个 kernel**

| 项 | 耗时 | 性质 |
|---|---|---|
| cuDNN sm_100 flash attention（40 次） | 32.9 ms | 算 |
| fp8 GEMM · nvjet Blackwell kernel（344 次） | 27.2 ms | 算 |
| **copy / mul / add / cat / elementwise（1,900+ 次）** | **~58 ms** | **搬** |
| fp8 absmax 量化（40 次） | 2.9 ms | 量化开销 |

平均每 kernel **7.7 µs**。真正算数的约 29%，纯搬数据约 28%。

> **这一条对 TPU 是利好。**GPU 上这 58 ms 的 elementwise 碎片是 launch 粒度问题，
> 而 XLA 的融合能力强得多 —— **如果 v6e 能把这部分吃掉，就是白捡的收益**。
> 反过来说，如果 v6e 上同样出现大量未融合的 elementwise，说明 lowering 写得不对。

### VAE 一次解码：189 ms（优化前），**7,120 个 kernel**

| 项 | 占比 |
|---|---|
| `triton_poi_fused__to_copy_cat_constant_pad_nd_convolution`（57 次） | 51.9% |
| `cudnn_convolution`（115 次） | 26.3% |
| cutlass `sm100_tensorop` implicit gemm（45 次） | 14.8% |
| NCHW↔NHWC 布局转换（312 次） | 8.6% |

那个占一半的 kernel 是 **CausalConv3d 的流式 cache 拼接**（`cat` + `constant_pad_nd`）。
**TPU 侧这一块是重点**：变长 `cat` 会触发反复重编译，必须改成固定形状 ring buffer。

## 五 · 测量口径（⚠️ TPU 侧照抄这一节，否则数字不可比）

1. **只量视频生成，启动一概不算。** 常驻服务只在部署时付一次启动成本，
   把它摊进吞吐是没有意义的 —— 也没人会为了出一段实时视频去等启动。
2. **周期取稳态**：在每次 VAE 解码处打绝对时间戳，取**连续两次的差**，
   **丢掉前 2 个 block**（预热 / 编译），对剩下的取均值。
3. **换算**：`每秒视频耗时 = 周期 ÷ 0.48`，`实时倍数 = 0.48 ÷ 周期`。
4. **分项计时必须夹 `synchronize()`**（TPU 上对应 `block_until_ready()`），
   否则量到的是入队时间不是执行时间。

### ⛔ 三个已经踩过的坑，别再踩

**① 不要拿采样进度条下吞吐结论。**
那个条稳态显示 22 it/s，看着飞快 —— 但它**只量 DiT 去噪那一段**，
不含 VAE 编解码、音频特征、motion frame 拼接。据此得出的「比实时快」是错的。
**吞吐只认 `生成循环耗时 ÷ 产出视频长度`。**

**② 不要用整跑时间去反推生成速度。**
最早用 9 条视频（10.6–21.4 s）拿「整跑耗时 vs 视频长度」做线性回归想把启动摊掉，
得到 1.39 s/s = 0.72× 实时。**那个数错了一倍以上**（R²=0.64，残差 ±5 s）——
跨度太窄、点太少，启动开销把斜率带偏了。
**正确做法是一开始就别把启动放进来：直接在生成循环里量稳态周期。**

**③ 探针本身会改变被测对象。**
中途用子类包 `Upsample` 做计数探针，**那个子类打断了 `torch.compile`**，
基线从 189 ms 变成 1035 ms。在那个瘸腿基线上，`channels_last` 测出来是「慢 5.4 倍」——
**跟真相完全相反**。加探针后**第一件事是核对 baseline 有没有变**。

## 六 · 两条不能照搬到 TPU 的结论

| GPU 侧结论 | 为什么不能照搬 |
|---|---|
| `channels_last_3d` 让 VAE 快 2.51× | 它解决的是 cuDNN 内部 NDHWC 与外部 NCDHW 来回转（一次解码 312 次）。**XLA 有自己的 layout assignment，没这个中间层** |
| DiT 上 CUDA Graph 被 KV cache 的原地修改堵死 | TPU 侧对应的是 **donation / aliasing**（`donate_argnums` / `input_output_aliases`）。**这是要提前设计的，不是事后调优** —— 不做的话滚动 cache 每步复制一整份 |

## 七 · 什么算成功

| 档位 | 判据 |
|---|---|
| **能用** | ≥ 1.0× 实时，且长时（≥ 2 分钟）身份不漂 |
| **追平** | ≥ 1.66× 实时（B200 当前水位） |
| **超过** | ≥ 2.33× 实时（B200 在当前并行策略下的理论上限） |

长时稳定性 B200 侧已验证：**118 秒连续生成，跨 6 个采样点身份零漂移、无色偏**。
这条 TPU 侧也要复验，不能只看吞吐。
