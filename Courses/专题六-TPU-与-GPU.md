## 这个专题要回答的一个问题

TPU 和 GPU，到底差在哪？

网上最常见的答案是罗列参数：多少 TFLOPS、多少 GB HBM、多少 TB/s 带宽。
**那种对比没用** —— 它解释不了为什么同一个模型在两边要用完全不同的方式去跑，
也解释不了为什么有些优化在这边是神器、到那边就没意义。

真正的答案要从**出身**说起：

> **GPU 从图形渲染长出来 —— 基因是「大量独立的小核 + 运行时灵活调度」。**
> **TPU 一开始就是为神经网络造的 ASIC —— 基因是「少数巨大的矩阵单元 + 编译期把一切排好」。**

这一条差别会一路向下贯穿：芯片结构 → 内存层次 → 互联 → 编程范式 →
软件栈 → 什么样的优化有效。**这个专题就是把这条链走一遍。**

---

## 一 · 出身：两条进化路径

### GPU

- 起点是**图形渲染**：屏幕上几百万个像素，每个像素的计算彼此独立
  → 天然需要**大量独立的、能各干各的小核**
- 后来发现这套东西能算通用并行任务 → CUDA → 科学计算 → 深度学习
- 再后来才**反过来**为 AI 加专用单元（Tensor Core）
- ⭐ **关键遗产**：上百个 SM，每个 SM 有自己的调度器、寄存器、共享内存。
  **灵活是刻在骨子里的** —— 每个 SM 可以做完全不同的事

### TPU

- 起点是**一个具体的工程问题**：神经网络推理太贵，做个 ASIC
- 一开始就知道要算什么：**矩阵乘 + 少量向量运算**
- 于是把绝大部分晶体管给了一件事：**巨大的脉动阵列（MXU）**
- ⭐ **关键遗产**：芯片上没有那么多独立调度单元，
  **一切靠编译期安排好** —— 因为要算什么本来就是已知的

### 一句话对照

| | GPU | TPU |
|---|---|---|
| 出发点 | 像素并行 → 通用并行 → AI | 矩阵乘 |
| 组织形式 | **上百个独立 SM** | **少数巨大的 MXU** |
| 谁做决定 | **运行时**（硬件调度器） | **编译期**（XLA） |
| 优先什么 | 灵活性 | 效率 / 能效 |

**下面每一节，都是这四行的展开。**

## 二 · 芯片内部

- **计算单元**：SM / Tensor Core 对 TensorCore / **MXU**
  - MXU 是脉动阵列 —— 数据流过一个固定的阵列，天然适合规整的大矩阵
  - 一个直接后果：**矩阵形状要对齐到 MXU 的尺寸**，不对齐就白白浪费
- **SparseCore**：TPU 上专门处理稀疏/嵌入的单元，GPU 上没有对应物
- **标量 / 向量 / 矩阵**三类单元的配比差别

**要算的**：给一个不对齐的矩阵形状，在两边各浪费多少

---

## 三 · 内存层次：这是最容易踩坑的地方

| | GPU | TPU |
|---|---|---|
| 片上 | 寄存器 → shared memory → L1/L2 | 向量寄存器 → **VMEM** |
| 片外 | HBM | HBM |
| 谁管 | 程序员管 shared memory，L2 自动 | **VMEM 由编译器管** |

⚠️ **对 TPU 用户最重要的一条**：**HBM 和 VMEM 是两层完全不同的内存**。

- VMEM OOM 和 HBM OOM 是**两回事**，报错不同、解法也完全不同
- ⚠️ **降 batch 治不了 VMEM OOM** —— batch 通常是 fusion 的最外层循环维，
  进 VMEM 的 tile 大小不随它变。这是个反复有人踩的坑
- 对应的旋钮也不同：VMEM 看 tile / block size 和 scoped vmem 上限

---

## 四 · 互联：拓扑的形状不一样

| | GPU | TPU |
|---|---|---|
| 机内 | **NVLink 域**（全连接或近似全连接） | **ICI**，构成 2D/3D **torus** |
| 机间 | InfiniBand / RoCE | ICI 继续延伸 + DCN |
| 拓扑性质 | 域内均匀，跨域断崖 | **规则的网格，有明确的距离概念** |

这带来的差别很实在：

- **all-to-all 在全连接域里很自然，在 torus 上要绕** ——
  这就是为什么 MoE 的分组限制路由在 TPU 上尤其重要
- **torus 上相邻通信极快** → ring 类算法天然合适
- **TPU 的切片形状不是随便选的** —— 拓扑是硬约束，
  接回[专题四](专题四-并行策略.md)那句「先选对拓扑再调参」

## 五 · 性能指标：怎么比才有意义

**先说怎么比不对：**

- ❌ 直接比峰值 TFLOPS —— **精度口径常常不一致**（稠密 vs 稀疏、
  FP16 vs FP8 vs FP4），而且峰值只是分母
- ❌ 只看 HBM 容量 —— 得同时看带宽，还得看每卡还是每芯片
- ⚠️ **单位陷阱**：TPU v7 是 **2 device / chip**，
  而框架日志一律按 device 报。同样 `per_device_batch_size`，
  v7 的 global batch 是 v5p 的两倍。**跨平台比 loss 曲线之前先对齐 global batch**

**该怎么比：**

1. **MFU** —— 实际吃到峰值的多少。但要说清楚 FLOP 公式的口径
2. **同一个模型、同一个规模，两边各自调到最好之后比** ——
   这才是有意义的对比，也最贵
3. **每美元 / 每瓦** 的口径

> ⭐ **我们有真东西**：混元 3 295B 在 **GB300** 和 **TPU v7** 上都完整跑过。
> 同一个模型、同一个规模、两边都调过 —— 这种对比数据很少有人有。

## 六 · 编程范式：静态 vs 动态

**这一节是软件栈所有差别的根**。

| | GPU / CUDA | TPU / XLA |
|---|---|---|
| 心智模型 | **写一个 kernel，描述一个线程干什么**（SIMT） | **写整个计算图，描述数据怎么变换**（SPMD） |
| 形状 | 运行时可变 | **编译期必须确定** |
| 控制流 | 随便写 | 数据相关的控制流很贵 |
| 优化在哪发生 | 主要靠人写 kernel + 库 | **编译器做全局优化** |
| 调试 | 打印、单步 | 看 HLO、看 profile |

**静态的代价**：
- 形状一变就**重编译**，而编译可能要十几分钟
- 动态形状（变长序列）要靠**分桶 + padding** 绕
- 数据相关的操作（比如 MoE 路由）实现起来别扭

**静态的红利**：
- 编译器能看到整张图 → **跨算子融合、通信与计算重叠、内存复用**都能自动做
- 显存规划是确定的 → **能提前算出会不会 OOM**（AOT 编译）
- 不需要手写大部分 kernel

> **一句话**：CUDA 把控制权交给你，XLA 把控制权交给编译器。
> **各自的痛苦也就完全不同** —— 一边是"写不出足够快的 kernel"，
> 一边是"编译器不听话，而我插不上手"。

## 七 · 软件栈全景

| 层 | GPU | TPU |
|---|---|---|
| 主力框架 | PyTorch | JAX（PyTorch 走 torchax / PyTorch-XLA） |
| 编译 | Inductor / TorchDynamo | **XLA** |
| 手写 kernel | CUDA C++ / **Triton** / CUTLASS | **Pallas** / Mosaic |
| 训练框架 | **Megatron-LM** | **MaxText** |
| 推理引擎 | **vLLM** / **SGLang** / TensorRT-LLM | vLLM-TPU / SGLang-JAX / tpu-inference |
| 通信 | **NCCL**（+ DeepEP 等专用库） | XLA 内建 collective |
| Profile | Nsight / nvprof | **XProf** |
| 显存诊断 | torch memory snapshot | HLO 里的 `temp_size` |

### 7.1 训练框架：Megatron vs MaxText

| | Megatron-LM | MaxText |
|---|---|---|
| 并行怎么表达 | **手工切**：显式写 TP/PP/EP 的通信 | **声明式**：给张量标 sharding，编译器生成通信 |
| 心智负担 | 要理解每一处 all-reduce 在哪 | 要理解 mesh 与 partition spec |
| 灵活性 | 高，什么都能改 | 受编译器约束 |
| 出问题时 | 看得见每一步 | **要会读 HLO** |
| 配置复杂度 | 参数极多，MoE 还有独立的一套 | 参数少，但一个 sharding 标错全盘皆输 |

> ⭐ 这两者的差别正是第六节那条「谁做决定」在框架层的复现。

### 7.2 推理：vLLM 与 SGLang 在两边

- 两个引擎都起于 GPU，**都在往 TPU 上移植**
- 移植的难点集中在一处：**动态性**
  - 连续批处理、变长序列、KV cache 的动态分配 ——
    全都是 XLA 最不喜欢的东西
  - 解法：**静态形状 + 分桶 + 预编译**
- ⭐ 我们**部署过其中好几个**（`tpu/tpu-inference/` 下六个模型），
  踩过的坑可以直接摆出来

### 7.3 kernel：Triton 与 Pallas

- 两者定位相似：**用 Python 写高性能 kernel**
- 差别在底下：Triton 编译到 PTX，Pallas 编译到 Mosaic → TPU
- 什么时候不得不自己写 kernel：编译器生成的不够好、或者算子根本不存在
- ⭐ 我们写过：**KDA 的 Pallas kernel**（Tokamax），有第一手经验

## 八 · 各自擅长什么（这一节要克制，不吹不黑）

**GPU 更合适的场景**
- 需要**灵活性**：研究阶段、频繁改结构、奇怪的算子
- **动态性强**的负载：变长、稀疏、数据相关的控制流
- 生态：绝大多数开源代码首发在 CUDA 上

**TPU 更合适的场景**
- **大规模、规整**的训练：形状固定、跑很久
- 需要**编译期确定性**：AOT 能提前算出装不装得下
- 拓扑规整带来的**大规模扩展性**
- 能效 / 成本

**中立的一句话**：
> 两边的差别不是"谁更强"，而是**"把控制权交给谁"**。
> 交给人，就得有人有能力写；交给编译器，就得接受它的脾气。
