一、问题：十几列车一起开，怎么知道它真在跑（4′）

🖥️ 屏幕06c §6.6.1 ① 日志里程碑，连同最右「这一段在干什么」那列一起遮住，只指 jax.devices 那行和 Total memory size 那行之间那个「约 22 min」。

「前面留的问题，说具体点：pod 全起来了，日志停在一行不动，二十二分钟没有新输出，你杀不杀？在这个 pod 上跑数千芯片的训练，从提交到第一步，实测四十多分钟，中间有两段各二十分钟左右一行日志都没有。先别答，这一章讲到第三节再揭晓。」

🖥️ 屏幕06c 开头那张「06c 和 06b / 06 / 06a 怎么分工」表。

「先交代身份：这一章原样复现一个大号 MoE 模型训练，开卡现编，是判读样板，教你认出跑对了是什么样。你们自己的 DeepSeek V3 配方有专章；大规模建议提前编译，也就是 AOT，Google 可以协助。」

「为什么是十几列车？一个 ICI 切片按公开文档最多三十二节车厢，没有整段一百四十四节的单列车。所以大训练是一个旅行团分乘十几列同型号的列车，每列四乘八乘八，四节车厢，列车之间靠无线电，也就是 DCN，协调。」

💬 互动一列 4x8x8 是两百五十六个芯片，每台主机四个芯片，这一列要起几个 pod？等台下说出「六十四」再切下一屏（下一屏的图上就写着答案）。

🖥️ 屏幕06c 任务画像下面那张 f08 布局图，先指一片内部，再指片与片之间的线。

「六十四个，一个 pod 占一台主机。乘上片数：pod 数是片数乘六十四，device 数是片数乘五百一十二；日志里 jax.devices 报出这个数，才说明所有人都进了同一个集群。读配置只记一条：带 ici 前缀的管列车内部，走贯通道；带 dcn 前缀的管列车之间，走无线电。这里片内把参数切成五百一十二份，叫 FSDP，片间数据并行 N 路（N 为片数）。列车之间怎么找到彼此，平台建 pod 时自己注入。」

🖥️ 屏幕06c §6.1 末尾「读写路径」那张表，逐行指。

「再看它碰哪些路径，都在同一个数据桶里：环境包，每台机器启动时读一次；配置覆盖文件，按运行名一个目录；输出目录，只有零号 worker 往回同步日志；JAX 编译缓存，所有运行共用一份。前两样提交前你要备好，后两样跑起来自己长出来。那现在都备好了，按下提交，会在哪儿出错？」

二、为什么难：哪一环不对，都可能「看起来在跑」（4.75′）

🖥️ 屏幕06c 路线图下面「每级 5 条」那张表，指第 1 行和第 3 行。

「难在它同时用到切片、DCN、共享存储和一长串 libtpu 参数，好几种错还是静默的。训练出错，退出码也可能是零，JobSet 照样显示 Completed。显存也一样：有人把梯度累积设成二，编出来一百零一 GB，超了，它不报内存不足，第一步挂了六分钟才被看门狗杀掉。这正是第二条暗线的后半句：永远别信单一的健康信号，绿色的 Completed 只是其中一个。」

🖥️ 屏幕06c §6.1 第一个实测框（FAIL），指那行报错原文。

「具体看四个坑。第一个在挂桶。我们在实测集群上照模板建好卷，两个都显示已绑定，验证 pod 却一直卡在初始化，同一条事件反复出现：集群级开了 Workload Identity，系统池和少数单网卡池没开。所以建集群时系统池要显式打开，脚本末尾再核一遍。」

💬 互动配置覆盖文件里把层数改小，模型自己的配置文件里另写着一个层数，最后照哪个编？举手押覆盖文件还是模型配置，押完再切屏（下一屏的标题就是答案）。

🖥️ 屏幕06c §6.3 最后一条「overlay 管不到模型 yml 里已有的键」。

「照模型配置。合并顺序是基础配置加覆盖文件，再被模型自己的配置盖一遍，最后才轮到命令行。覆盖文件里的层数被静默盖掉，照模型配置的层数编完，报显存不够。模型结构类的参数要走命令行，改完去日志里核那一行 Config param。还有，覆盖文件不存在，启动脚本直接跳过，按默认配置照跑，所以提交前先查它在不在。」

🖥️ 屏幕06c §6.4 下面「flag 怎么生效」那张图；再指 §6.4.1 显存表的 XLA_FLAGS 行。

「第三个：两串参数合并规则不一样。libtpu 那串是追加，你写的接在默认值后面，同名的后出现的为准。XLA 那串是整个替换，你一设，脚本默认关掉的两个编译步骤就全回来了。我们试过只关其中一个，两片训练显存涨到一百零八点六 GB，加载时就不够，一步没跑。」

「第四个：第一级冒烟换小模型，别用小模型自带的启动脚本。它的权重路径写成带默认值的变量，JobSet 里设成空串也挡不住，空串被当成没设；桶里正好有那份权重，就静默加载了，loss 起点不再是随机初始化的值。用大模型的脚本，只换模型名。」

🖥️ 屏幕06c §6.2 标题。

「环境也别让大量机器各自去装：一个 CPU pod 装好打成包进桶，每台只解压，不到一分钟。代码提交、libtpu 版本和镜像每次钉死，一错配就起不来。」

⚠️ 最容易跑偏被问「验证 pod 放哪个 namespace」：本书 Kueue 开了 manageJobsWithoutQueueName，验证 pod 和环境构建 pod 放默认 namespace 会一直 SchedulingGated，要放进排除的 rb-inspect——按 Kueue 文档推断，没在本书配置下实跑。⛔ 不讲模型结构、精度、优化器这些训练方的旋钮，运维只对切片数、形状、device 数、镜像和 libtpu 版本、生效的 flag。

三、怎么做：四级阶梯，外加一张时间线（6′）

🖥️ 屏幕06c 路线图那张分级表，从第 1 级往下指到第 4 级。

「一次上数千芯片，出了问题分不清是环境、单片计算还是网络。所以分级爬：先一节车厢验管线，再一片真模型，再两片第一次过无线电，最后十几片。同一份 JobSet、同一个环境包，只换几个变量；每级五条都过了，才上下一级。」

「第一级为什么不用真模型？一片切五百一十二份，换到一节车厢只切一百二十八份，按份切的权重和优化器状态变成四倍。我们实测过：真模型在一节车厢上编了十八分钟左右，才报临时内存九十七点一二 GB，超过九十四点七四。超显存要编完才知道，所以大配置先在 CPU 上提前编一次。」

「第二级最重要：一片、同镜像、同参数，只少了 DCN。它的步时是你以后判断慢在片内还是片间的那把尺子。上第三、第四级之前，再跑一次同片数的 DCN 小基准，拿到网络本身的尺子。」

💬 互动回到开头那个问题：日志停在 jax.devices 之后，二十二分钟没新行，杀不杀？等台下押出「杀」或「不杀」再切屏（下一屏的标题就是答案）。

🖥️ 屏幕06c §6.5.1 时间预算表下面那张「apply 到第一步」横条图，先指 10+ 片那条的蓝段和橙段，再指最下面那条拆开的。

「不杀。灰段五分钟上下是编组、起 pod、连成集群；蓝段二十二分钟是训练步编译，编完会报出显存，八十四点三 GB，上限九十四点七四；橙段二十分钟左右，是同一个训练步又编了一遍，因为第零步喂进去的数据切法和编好的那份对不上。从一片到更大规模，横条几乎一样长。超过六十分钟还没新行，才按挂住去查。」

「最下面那条是一节车厢的小配置拆开看：真正的 XLA 编译只占两分钟出头，大头是降成中间表示十二分钟、Python 追踪三分钟。所以编译缓存帮不上大忙，同一配置冷启动三十多分钟，热启动也要将近半小时。」

「横条和片数无关，所以阶梯省的是卡时，不省墙钟：前三级光到第一步就要一个半小时以上。每一级还要留一次重跑：模板不重启、不存检查点，我们八个训练任务里就有一次，第零步之后十八秒掉了一台机器，四十多分钟全部作废。」

「两个小坑。覆盖文件开着 profiler，从第十步开始抓，所以短跑至少十四步，不然编完就报错退出。loss 不能跨片数比：同样五十步，一片降了一成五左右，十几片只降了百分之五左右，全局 batch 大、学习率还在预热。」

🖥️ 屏幕06c §6.5 验收，指 verify 那一段。

「停和删要分清。停是把 Workload 设成不激活：释放十几片，JobSet 留着，可不存检查点，恢复就是从头来。显示达到最大重启次数，先查有没有节点故障，掉了机器就直接重提。」

「跑完跑验收。它取最后一行的步号，五十步要看到四十九，因为从零数；loss 五十步降了百分之五左右。再对步时：快步比一片慢四成左右，每 device 一百五十 TFLOP/s 左右。最后存档生效的 libtpu 参数，再删掉 JobSet，跑完的 JobSet 不会自己消失。」

⚠️ 最容易跑偏容易说错：橙段不是「参数初始化」，日志那行写着 params initialized，其实是 step 0 输入切法对不上导致的第二次编译（实测）；改参数的规矩（追加参数、换运行名、只改一处、≥20 稳态步）在 §6.4.1，被问再讲。

四、代价和坑：跑通了，不等于跑快了（11.75′）

🖥️ 屏幕06c §6.6 那张双峰步时分布图，先指左边快步那一堆，再指右边慢步那一堆。

「跑通以后第一眼看步时。第一次跑，步时分成两堆：一大堆是快步，另一堆约四成，比快步慢三成多到一倍。平均数因此比中位数高出约两成。」

💬 互动「十几片在同一步一起变慢。是十几片都慢了，还是只有一片慢？」

🖥️ 屏幕06c §6.6.1 ④ 根因框下面那张两行流程图。

「是一片慢、其余各片等。那片里有一台机器整天在做 GCE 计划外维护，而节点状态、分区健康、看门狗全都显示正常。换掉那个 cube，慢步就没了。所以开跑前先排除正在维护的 cube；步时永远报中位和平均两个数。再见到双峰，先比十几片同一步的耗时，几片几乎一样，就是都在等同一片；然后先换 cube，再换参数。」

🖥️ 屏幕06c §6.6.1 ③ 弱扩展效率表和下面的曲线图。

「第二级那把尺子在这儿用：一片步时除以多片步时，就是扩展效率。我们实测两片百分之七十八到七十九，网络基准同期通过，所以低于大约百分之七十五再去查网络。效率不是匀着掉的：一片到两片掉二十个点出头，之后基本持平。」

🖥️ 屏幕06c §6.6.1 ⑥ 四行 PASS 的那张表。

「步时对上了，不等于算对了。loss 按参考实现逐步比：一片、真数据、同一份检查点起步，对照参考日志，平均相对差不能超过千分之一。我们实测已到阈值的近九成，过了，但离线很近，所以代码、数据、检查点都要钉死。再换一批完全不重合的六十四个节点重跑，五十步 loss 逐位相同，以后有偏差就可以先排除换了节点。」

「口径要说清：这一章的数都是现编的对照，不是生产配置。大规模训练建议提前编译，也就是 AOT，开头那段沉默会短很多，Google 可以协助。」

🖥️ 屏幕06c §6.10 第 8 条和第 10 条。

「经验清单里再挑两条。第一，初始化挂住没人会杀它：pod 全起来后六百秒内没报出 device 数，就删任务、收证据，正常一片一两分钟，十几片也就五分钟上下。第二，任务失败时 pod 先被删，报错要直接去 Cloud Logging 捞。」

「这一章留下一个问题：上面这套训练关了检查点，失败策略是不重启，要是跑到第三个小时，这么多台里坏了一台，会怎么样？下一讲讲怎么存、怎么接着跑。」

⚠️ 最容易跑偏⛔ 不逐行讲 §6.4.1 参数表、不当场教调参；⚠️ 容易说错：外部给的 TFLOP/s 先确认是每芯片还是每 device，一个芯片两个 device，口径不同不能直接比；被追问「能不能开更多片」：十几片以上有已知限制，大规模建议提前编译（AOT），Google 可协助，见 §6.9；公开模型配方看 06b，别的形状看 §6.8；P7 功耗档高负载下的稳定性仍在确认，先用默认档。
