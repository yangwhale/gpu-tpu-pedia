[thinking] 上一节说那个实习生只说对了一半，这一节就来兑现这句话。不过在看见那一幕之前，得先把上一节欠下的那笔债，换算成看得见的东西。所以这一节一个新招都不讲，只做一件事：定价。

[focus] 请看这张三行对照图，三行用的是同一把尺子。第一行是开篇那条 RNN 老链，每一步都要把权重重搬一遍。第二行是 Transformer 训练，一整段话一次喂进去，权重只搬一次，换来 n 倍的活，这是 2017 年那一刀赢下来的地方。第三行，是它给你吐字的时候，也就是你每天在用的样子。

[realization] 这一节真正要说的就是：它赢的是第二行，可你每天在用的是第三行。赢的那一栏和付钱的那一栏，不是同一栏。

[seriously] 看第三行的形状。吐第一个字，吐第二个字，吐第三个字，每一个都得等上一个吐完，因为上一个字得先变成新的存货，才能被下一个字看见。第一章那条链，在这里原封不动地回来了。只不过这一次是被迫的，没人想要它，它自己长回来了。到第七章我们还会再见到同一幕，那一次，是有人主动把它请回来的。

[thinking] 而且它比老链更重。两行每一步都要把整份权重搬一遍，这部分一模一样。不一样的是额外还要搬什么：RNN 额外搬的是一个固定大小的盒子，跟上下文多长无关；解码额外搬的是 KV cache，话越长，它越大。

[curiosity] 那加大 batch 能不能救？这里要把每一步读的东西拆成两半看。

[focus] 权重那一半，全 batch 共享一份，搬一次给所有请求用，所以攒 batch 有用，算术强度就等于 batch 大小。这是所有「加大 batch 提吞吐」的依据。KV 那一半不一样，每个请求各存各的，batch 一大，要读的字节和要算的 FLOPs 同比例一起涨。

[thinking] 算一下这一半。读的字节：K 和 V 各是历史长度乘以每头维度那么多个数，每个数两字节，合起来是四倍的长度乘维度。算的 FLOPs：共用这一份 K V 的有几个 query 头，每个头打分一次、加权求和一次，各是长度乘维度次乘加，一次乘加算两个 FLOP，合起来是四倍的长度乘维度，再乘以头数。两边一除，强度就等于几个 query 头共用一份 K V。

[seriously] 比如一组八个头共用一份，强度就是八，对着三百一十三那条屋脊线，差了将近四十倍，而且跟 batch 多大毫无关系。拿最朴素的多头注意力自检一下：一个头一份，强度是一，正好对上业界常说的，decode 阶段注意力的算术强度约等于一。加 batch 只救得了权重那半，救不了 KV 那半。后面所有的招，拧的都是这一半。

[curiosity] 那为什么偏偏是这两年？这个形状 2017 年就造出来了，2019 年就有人指着它说是问题，可全行业真正动手改，是 2024 年以后。中间那几年，技术一个字没变。答案不在论文里，在机房里。

[focus] 请看这两根柱子，是同一个模型，DeepSeek V3。左边是一个人、一段短对话，上下文四千；右边是六十四个人，各拿一份十二万八千长的文档。读三个数。灰色那段是权重，六百二十五个 GiB 到六百二十五个 GiB，一个字节没动。红色那段是 KV cache，从零点二七个 GiB 涨到五百四十九个 GiB，涨了两千零四十八倍，也就是长度乘了三十二、人数乘了六十四。它在总量里的占比，从百分之零点零四涨到百分之四十六点八。要几张卡，按每个 TPU v7 device 九十四点七四个 GiB 向上取整，从七张涨到十三张。

[realization] 什么都没改。模型没换，权重没动，技术一个字没变，是工作负载变了。而且这根红柱子，已经是 V3 压得很小的那种存法。

[thinking] 「突然」这两个字，就是这么来的。这几年有两样东西各自翻了几十倍：一样是话变长了，从几千字到几十万字；一样是同时伺候的人变多了。而这两样，都乘在同一项上，就是那堆存货。一样东西翻十倍，你会看着它一点点变贵；两样东西各翻几十倍、还乘在一起，你看见的就不是变贵，是某天早上它忽然成了最大的一块。

[contemplative] 技术没有变坏。是我们换了一种用法去用它。

[curiosity] 不过，如果只有「装不下」这一条理由，这件事最多做成一堆将就的权宜之计。真正让这么多人扑上来的，是还有第二条线，而且它跟显存一点关系都没有。

[focus] 请看这张图的左右两半。左边是硬件的账。还是 V3 的形状，一百二十八个头，每头一百二十八维，K 和 V 两份，每个 token 每层三万两千七百六十八个数；乘六十一层、乘两字节，一个 token 就是三点八一个 MiB；再乘十三万一千零七十二个 token，一个用户四百八十八个 GiB，要五点二个 device。结论是：必须省。

[thinking] 右边是数据自己露出来的破绽：十二万八千长的序列，真需要十二万八千份独立的 K 和 V 吗？有三个观察。第一，注意力实测极其稀疏，绝大部分权重集中在很少的位置。第二，有个现象叫 attention sink，注意力被大量停放在开头几个 token 上，跟内容无关。第三，远近有别，邻近几十个 token 要细看，几万个之外只要粗看。结论是：可以省，而且不太亏。

[seriously] 两条缺一不可。只有「必须省」，你得到的是一堆效果掉了只能认的有损压缩；只有「可以省」，你没有动力去付那么难写的 kernel 的代价。后面所有的方案，都活在这两条的交汇处。

[focus] 从下一节起，每出场一个新名词，我们都只拿一把尺子量它，问三句，顺序是死的。第一句，省的是哪一样，是显存、是带宽，还是算力？第二句，省了多少？第三句，亏了多少？第一句绝对不能省，因为一个漂亮的倍数最会干的事，就是让你忘了问它省的到底是哪一样。今天你会看到一个省了五十多倍的方案，它省的那一样，跟你以为的不是同一样。而真正决定一个方案有没有人用的，是最后那一句。

[seriously] 这一节最后一句，也是全讲最要紧的一条操作性结论。模型的权重，一台机器上只放一份，谁来都用它；可那份 KV cache，来一个人就得单开一份。所以它卡住的不是这台机器装不装得下这个模型，而是这台机器同时伺候得了几个人。

[thinking] 而且这笔账不是线性涨的，是一级一级往上跳的。能一张卡装下的，就别跨卡；能一台机器装下的，就别跨机。因为卡里面的带宽，比卡和卡之间快，卡和卡之间又比机器和机器之间快。每跨一级，整套推理就被最慢的那一段拖一次。
