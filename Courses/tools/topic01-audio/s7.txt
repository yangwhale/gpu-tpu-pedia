[focus] 上一节，路由已经选完了：每个 token 在这一层挑出了自己的八个专家。可选完之后，马上撞上一个很实际的问题：这八个专家，人在哪？

[seriously] 先说为什么专家一定散在很多张卡上。一个专家是三个矩阵，每个七千一百六十八乘两千零四十八。一层有两百五十六个路由专家加一个共享专家，一共两百五十七个。每个数两个字节，一层的专家权重就是二十一点零八个 GiB。

[realization] 五十八层 MoE，二十一点零八乘五十八，大约一千二百二十三个 GiB，也就是一点一九个 TiB，几乎就是整个模型的重量。一个 TPU v7 device 只有九十四点七四个 GiB，差着一个多数量级。所以每张卡放一整套专家，这条路不存在。

[focus] 于是题目就摆在面前了：token 在这张卡上，它要用的专家在那张卡上。谁去找谁？

[friendly] 请看这张图，两条路都能走通。第一条，把 token 送到专家那儿：把激活发到专家所在的卡上，算完再收回来，送去一次，送回一次，两次 all-to-all。第二条，把专家权重取过来：各张卡先把自己那份专家权重 all-gather 给大家，凑齐之后在本地算，token 一步都不动。

[curiosity] 先算第一条要搬多少。每个 token 每层：送去送回两次，乘以拷贝的份数，乘以七千一百六十八，乘以两个字节。份数取四，是一百一十二个 KiB。

[confusion] 为什么是四份？每个 token 不是选了八个专家吗？

[realization] 因为搬运的单位是目的地，不是专家。V3 的两百五十六个路由专家摊在八个节点上，上一节那个分组限制规定：一个 token 最多去四个节点。同一个节点上选中的两个专家，共用一份拷贝，到了节点里再走机内互联分发。所以倍数是四，跟挑几个专家无关。技术报告自己说过，每个 token 的专家数从八个加到十三个，通信代价不变。

[thinking] 反过来想一下就明白了：如果通信量跟专家个数成正比，多选五个不可能不要钱。它只能跟节点数成正比，而节点数被四焊死了。还能再抠一点：四个目的地里可能有一个正好是 token 自己所在的节点，那一份不用过网，所以跨机的期望份数其实是三点五。我们保守取四，算出来是个上界，不会把量算小。

[focus] 这样一层的总账就是：送去送回两次，乘以十三万一千零七十二个 token，乘以四份，乘以七千一百六十八，乘以两个字节，十四个 GiB。乘以五十八层，一次前向要搬八百一十二个 GiB。

[focus] 再看第二条。挪权重，一层就是那二十一点零八个 GiB。

[thinking] 关键不在两个数谁大，在两条线的形状。挪 token 的量，跟 token 数成正比，这是图上那条斜线。挪权重的量，跟 token 数完全无关：权重不认识 token，你这一批是十个 token 还是一千万个，要凑齐的都是那两百五十七份。这是那条水平线。

[seriously] 这一点是整张图能成立的全部原因。假如挪权重那条线也随 token 数往上涨，两条线就可能永远不相交，也就谈不上二选一了。

[realization] 一条斜率是一，一条斜率是零，所以它们一定相交。「要看场景」这句话在这里不是和稀泥，是从几何上看出来的。

[focus] 交点在哪？二十一点零八个 GiB，除以每个 token 一百一十二个 KiB，得到十九万七千三百七十六个 token，大约二十万。

[friendly] 拐点两边住着谁？推理的 decode，一步只有几十个 token，远在左边，挪 token 划算，差着好几个数量级。训练一个 step，动辄上百万个 token，远在右边，挪权重划算。同一个模型，这两件事给出了相反的答案。

[thinking] 那一次十二万八千的 prefill 呢？十三万一千零七十二个 token，一层搬十四个 GiB，还没到拐点，挪 token 仍然占优，但只差一点五倍左右。同一次推理请求里，prefill 紧挨着拐点，decode 却离得很远，这两段的性格很不一样。

[seriously] 边界要说清楚。十九万七千不是一个工程门槛，别拿去当阈值。它只比了每层搬多少字节，没算两种通信的效率差异；而且专家摊在越多张卡上，挪 token 那条线被分摊得越薄，拐点就越往右移。

[contemplative] 这个数真正的价值是告诉你：两个方案在同一个数量级上。要是差着一百倍，就没什么可选的。正因为咬得这么近，二选一才真的成立。前面每一笔账都有唯一答案，这一笔没有。真实系统里两种办法也经常混着用。

[suggestion] 再跟上一节接一下。那个「最多四个节点」的分组限制，把挪 token 这条线的斜率按住了，不让它更陡；这一段问的是更上层的问题：这条路本身该不该走。一个是先把代价压到能接受，一个是再问要不要走，同一条链上的两环。

[curiosity] 下面讲另一个问题。稠密 MLP 有一条好性质：形状是静态的。编译器开跑之前就知道每个矩阵多大、内存放在哪，才能把整张图排好。

[seriously] MoE 一来，这条断得最彻底。这一批里有多少个 token 落到第三十七号专家头上？路由跑完才知道，下一批又变了。可硬件要的是开跑之前就定死。

[thinking] 为什么硬件这么较真？因为整张图是开跑之前一次排好的：每个矩阵多大、每块内存放在哪，都要事先定下来。形状到运行时才知道，这套提前排好的前提就不成立了。

[casually] 老办法是给每个专家发一个固定大小的盒子，盒子多大由一个超参数决定，叫容量系数。形状又静态了，编译器满意了。

[focus] 但请看这张图，同一层同时在赔两笔钱。专家 A 来了六个 token，盒子只装四个，多出的两个直接丢掉。丢掉不是 token 消失了，而是它在这一层的专家输出被置零，只剩残差穿过去，这一层对它等于白过。专家 C 只来了一个 token，剩下三格拿零去填，照样占算力、占显存。

[seriously] 所以容量系数是个很难受的旋钮：开小了丢真数据，开大了白烧算力。更麻烦的是，你根本不知道该开多大。有研究测过，丢 token 的那版验证损失的下降只有不丢那版的一半多一点；有的模型要把系数开到十一才不丢，还有的会在训练中途突然飙上去。

[cheerfully] dropless 的思路很直接：不要盒子了。把 MoE 层改写成一种能处理大小不一的块的矩阵乘法，来六个算六个，来一个算一个。真正的收获不是省了那点算力，是那个旋钮直接不存在了。代价是要有一套处理不规整形状的算子。

[casually] 这也解释了为什么还有人用盒子：盒子那套只用最普通的稠密矩阵乘，形状静态，任何框架都能跑。dropless 是拿算子实现的复杂度，去换不用调那个旋钮。在大模型上这笔交易很划算。

[realization] 那 V3 呢？技术报告说：由于负载均衡策略有效，训练全程负载良好，所以训练时不丢弃任何 token。请注意它给的理由。上一节那个负载均衡的偏置，作用比当时说的还大：当时说负载不均会让大家一起等最慢那张卡；现在看到另一半，在有盒子的世界里，负载不均会让 token 直接丢掉。它不只是在防变慢，还在防数据凭空不见。

[thinking] 这里要说准一点。「V3 训练不丢 token」可以讲，但它的训练算子内部还留不留「容量」这个概念，公开资料里我没有查到，所以不能说成「V3 用的是 dropless 算子」。上线之后没有训练循环调偏置了，V3 靠在节点内复制热点专家来保证推理也不丢。

[focus] 好，现在把账合上。请看这张参数表，每个数前面都推过。

[casually] 单个专家，四千四百零四万个参数。一层两百五十七个专家，加上门控，一百一十三点二亿。五十八层 MoE，六千五百六十五点七亿。一层注意力一亿八千七百一十一万，六十一层一百一十四点一亿。三层稠密 MLP，十一点九亿。进门的嵌入表和出门的大矩阵，两张一共十八点五亿。

[excitement] 全部加起来：六千七百一十点三亿。官方口径六千七百一十亿，对上了。

[contemplative] 这一步的意义不是对上一个数字，而是把一路用过的每条公式一次性验了：隐藏维七千一百六十八，专家宽度两千零四十八，SwiGLU 三个矩阵，MLA 那几个秩，任何一条记错，总数都对不上。验算就该这样做：找一个能把一整套公式串起来的外部锚点。

[curiosity] 表里最扎眼的是这两条。上面是全部六十一层注意力加起来，一百一十四点一亿；下面是随便一层 MoE，一百一十三点二亿。两条一样长。六十一层注意力，等于一层 MoE。

[seriously] 注意力只占参数的百分之一点七，可在十二万八千的长度上，它吃掉百分之八十一点八的算力。为什么会这样？不是注意力小，是 MoE 一层实在太大。

[casually] 拿数比一下：注意力一层一亿八千七百万，一个稠密 MLP 层是三亿九千六百万，注意力也就它的一半。而一层 MoE 把两百五十七份 MLP 摞在一起放着，每次只用九份。注意力从来不是参数大户，它是算力大户。参数量和计算量是两本账，连排序都不一样。

[warmly] 再看最后这两条。蓝的是六百七十一点零三个 B，全部参数，显存要装下这些。绿的那一小截是三十六点六二个 B，一个 token 真正用到的，算力只花这些。差十八点三倍。三十六点六二是逐项加的：五十八层各九个专家，加全部六十一层注意力、三层稠密和出口那张大矩阵。把嵌入表也算成激活，是三十七点五五。官方的三百七十亿落在这两个数中间，怎么归的报告没细说。差这不到十亿，十八倍还是十八倍。

[seriously] 这一课最容易听错的就是下面这句：这十八倍全是算力，显存一个字节都没省。那六千三百多亿参数这一步确实闲着，但必须待在显存里，因为下一个 token 可能就要用其中某几个。

[contemplative] 六千七百一十亿参数像一座山压在显存上，一块都搬不走；每个 token 真正淌过的，只是山脚下那条溪，三百七十亿。那座山是显存要扛的，那条溪才是算力要付的。MoE 做的事，就是把山和溪分开。在它之前，你想要多大的山，就得付多大的水。

[realization] 所以「激活三百七十亿」不等于「跟三百七十亿的稠密模型一样好养」，你要的显存跟六千七百一十亿的稠密模型一模一样。MoE 是一笔用显存换算力的交易：同样的算力，装下更多知识。

[thinking] 换个问法就更清楚了。想要一个六千七百一十亿的稠密模型，每个 token 都得算满六千七百一十亿，这个算力账没人付得起。MoE 让你用三百七十亿的算力预算，拿到六千七百一十亿的容量，代价是显存按六千七百一十亿准备。值不值，取决于你手上显存和算力哪个更紧。

[thinking] 还要再拧一道。「只花三百七十亿」是每个 token 的账，可机器一次处理一批。单个 token 只过九个专家，这是稀疏；一批 token 够多时，两百五十六个专家全被点亮，这是稠密。所以权重一个字节都少不了要从显存读一遍，而乘法确实只做了二百五十七分之九。

[focus] 稠密到什么程度，是一个除法：每个专家分到的行数，等于这一步的 token 数乘八除以两百五十六，也就是除以三十二。TPU 上矩阵乘按一百二十八行一块来做。训练一步五十二万多个 token，每个专家一万六千三百八十四行，一百二十八个满块。decode 两百五十六个并发请求，每个专家只有八行，一块都填不满。decode 每个请求每步只出一个 token，上下文再长也不多贡献一行，所以训练受限于算力，decode 受限于带宽。

[warmly] 第四步到这里走完了。我们看清了三本账：参数、算力、显存。一个部件在一本账上微不足道，在另一本账上可能就是主角。不过到现在讲的全是一层里面的事，下一节我们看六十一层是怎么串起来的：一条贯穿全程的总线，残差流。

[friendly] 这一节就到这里，大家有问题吗？
