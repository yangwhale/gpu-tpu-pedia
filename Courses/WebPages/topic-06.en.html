The table still holds, but the emphasis shifts: TP's few all-reduces per layer carry little data, so latency is what hurts; and EP doesn't have to use all-to-all—the published TPU inference work does the expert step with all-gather plus reduce-scatter (Chinese full edition, §6.4).

Training does a batch per step; inference, one token. The cost: each token hauls the whole load from HBM.

Only two waits: first token, then each next

The cost: one full haul per token

  • How heavy. Each DeepSeek-V3 token passes through ~37B parameters (~37 GB in FP8), plus each user's KV (cached results of earlier text), reread every step: 8.58 GiB at 128K.
  • Why every step. One TPU v7 chip has only 128 MiB on-chip, ~1/1,500 of its HBM (192 GiB), so it all has to re-stream each step.
  • A bus. Weights are its cargo: fixed fuel per trip, about the same for one rider or full. KV is each rider's notes, growing with riders.
In one sentence Each decode step hauls the weights and KV once. Every technique shares the trip with more users or moves less.
One family leaves the trip alone: each kind of work gets its own hardware.

Section 1

A long prompt in one pass, but output one token at a time?

The same chip is flat out reading a prompt, mostly idle emitting tokens. The only difference: rows per pass.

Rows per pass decide: compute- or memory-bound

  • Prefill: thousands of rows a pass. The prompt is ready: 4K tokens enter the matmul at once; one weight read serves thousands.
  • Decode: one row per user per step. Each token needs the previous one, so nothing can be computed ahead; N users, N rows.
  • The line: 313. Reading 1 byte takes as long as 313 operations (v7, bf16: 2,307 TFLOP/s ÷ 7.37 TB/s). M rows ≈ M operations per byte; under 313 rows, compute idles.

One user, one token: 5 ms moving, 0.016 ms computing

37 GB ÷ 7.37 TB/s ≈ 5 ms; compute 0.32% used (ideal lower bound). Faster compute won't help; bandwidth sets the floor.

Back to the bus Fixed fuel per trip: prefill is a full bus, decode one rider. Up to 313, extra riders ride free.

More users: weights amortize, KV doesn't

MoE breaks the batch apart again

The 313 line holds only per whole matmul; to fill every expert, a step needs 9,000+ tokens a step (Chinese full edition, Section 3, for H100).

Takeaway Prefill is compute-bound; decode is bound by data movement. To earn back the fuel, carry more riders: keep the bus full (Section 2), free seats for KV (Section 3), regather users MoE scattered (Section 4).

Section 2

Just add users? How big can the batch get?

Riders don't board or leave together: one asks and goes, another wants 3,000 words. Scheduling sets how full a trip runs, seats set the cap, and fuller means slower per rider.

Old way: fill up, wait for the slowest

  • Static batching. All in, all out; early finishers' seats ride empty.
  • Interface-bound. Old engines only had “run the whole batch”: no swaps midway.

Stop at every step and reschedule

Orca (OSDI 2022), first idea: stop after every step and look again. Now called continuous batching; vLLM and SGLang both do it.

Still the same bus Static batching is a charter: fill it, arrive together. Continuous batching is a real bus: off and on at every stop.
  • Why requests merge (Orca's second idea). Weight matmuls ignore token owners: one strip; only attention (rereading notes) is per request.
  • New riders don't block the door. Long prompts board one chunk per step (chunked prefill), so riders mid-output aren't stalled.

Seats are KV: more seats, not always more tokens

One seat per request the KV pool can hold. Per-device throughput ≈ riders ÷ TPOT (time between tokens); full seats cap it.

Add seats? TPOT won't stay put:

Weights are already amortized; newcomers add only KV, lengthening every step.

So batch size starts with “how fast per user?”

  • One system, one curve. 68 tokens/s per user gives 9,759 per GPU; 173 leaves only 895.
  • Fix the tier, then compare. Per-user tokens/s is the tier; big claims may sit further left.
  • Production does pick the left. DeepSeek online: only 20–22 tokens/s per user, about 14,800 per 8-GPU node. Different hardware and model: don't compare to the per-GPU figures above.
Takeaway Continuous batching fills the seats; KV sets their number; more riders, slower each. The gain: at the same 190 ms per-token latency, Orca served GPT-3 175B at 36.9× the requests/s of FasterTransformer's static batching.

Section 3

KV cache: how big, how to shrink?

Seats are KV: each request keeps a notebook, one line per token. Seats = KV pool ÷ notebook thickness. Three steps seat more: thinner lines, no wasted paper, no redoing.

Step one: same model shape, line thickness differs over 50×

  • MHA: each head keeps a copy. At V3's shape (128 heads), about 4 MB a token; 128K: about 488 GiB, over a 192 GiB chip (our derivation).
  • GQA: each group of heads shares a copy. Llama-3.1-70B: 8 groups, 327,680 bytes a token.
  • MLA: one compressed summary. All heads read it: one KV head. V3: 70,272 bytes/token, ≈ 1/57 of same-shape MHA (our derivation).

Does thinning cost accuracy? The GQA paper converted T5-XXL to 8 groups: about 5.4× faster decoding (our derivation), average 47.1 vs. 47.2 originally. Only T5-XXL on TPU v4.

Thinner isn't enough: longer notes, fewer riders

Fewer riders per trip, each reading more KV per step. Long context pays on both.

Step two: no wasted paper, a page at a time

  • The old way reserves the maximum. Each holds one max-length block; unwritten slots stay taken: only 20.4%–38.2% used (measured).
  • PagedAttention is a loose-leaf binder. Take a page only when the last fills; return them on leaving. Utilization reaches 96.3%.
  • Sharing comes free. Two requests with the same opening map to the same page, no copies; step three builds on it.

Step three: reuse a shared opening and keep writing

  • Many requests share an opening: the same system prompt, earlier chat turns. Keep that KV and the next request picks up from it. SGLang's RadixAttention keeps prefixes in a tree; vLLM has enabled prefix caching by default since 2025.
  • Only an exact prefix counts. Each token's KV depends on all tokens before it: change one at the start and nothing after matches.
Takeaway Thinner lines (MLA/GQA), no wasted pages, reused prefixes: same memory, more riders, less recompute.
The gain: in the vLLM paper (SOSP 2023), 2–4× the baselines' throughput at equal latency, even against continuous batching (the authors' Orca reimplementation). Whole systems, not paging alone.
So far, one device. With many: one notebook each, or a copy per device?

Section 4

Many devices: TEP or DEP?

Too big for one device, V3 runs on several. Experts go EP either way; attention is the fork: one shared batch, or own users per device? This decides how many copies of each notebook exist.

Reading the names TEP = T + EP, DEP = D + EP. EP (experts) in both; the first letter is how attention splits: T = TP (by heads), D = DP (own users per device). dep8 = 8-way DEP.
In DCP/PCP (next section) the first letter is a phase, a different axis. Nor is either Megatron-LM's ETP/EDP.

How many notebook copies?

  • TP splits by heads. Fewer KV heads than devices? Devices sharing a head each copy its notes.
  • Copies = TP degree ÷ KV heads (min. 1). Each copy is stored and read every step.
  • DEP: own users per device. Notes stored once, read once.

Real models: MLA and V4-Pro have 1 KV head: TEP8 makes 8 copies. Qwen3.5-397B, 32 query heads on 2 KV heads: 4 copies. GQA with 8 KV heads: none, so DEP gains nothing.

Capacity vs. speed: empty seats earn nothing

V4-Pro (1 KV head), our own SGLang setup on GB300: prefill and decode on separate machines (why: Section 6), DEP on both, 14 prefill nodes at dep4, decode at dep8. 10,704 tok/s per decode GPU end to end: 95.6% of the official target (the PyTorch blog's ~11,200 per GPU; denominator unstated, we read it as decode GPUs).

  • Capacity: no copies, up to 4× users per device, a ceiling reached only once the pool fills.
  • How we cracked it. ① First run 6,887, only 727 users per GPU: the two notebooks (full / recent window) badly split, seats empty. ② Rebalanced: 886, +54%. ③ 999: just +0.8% (the Section 2 puzzle); slower steps ate it.
  • Speed, corroborated. vLLM, concurrency 512, decode TP4 → dep8: time between tokens 46.8 → 11.8 ms; per-GPU throughput 2.09× over all GPUs (our derivation), 1.31× over decode GPUs only (which also doubled).
  • The bottleneck moved. Decode dep8 → dep16 nearly halved step time, but the 12 prefill nodes left (of 16) starved it: output per decode GPU fell 40%. New topology, new P:D sweep.

DEP's cost: each device packs its own kit

  • Each device is a mini inference server: own attention weights, scheduler, state. Unsplit per-request state multiplies as DEP widens.
  • Some models won't start. Most Kimi K3 layers keep no verbatim notes: a fixed-size note per user, rewritten in place (linear-attention state). DEP puts the full pool on every device; DEP8 is out of memory at load (we measured it twice); SGLang's official K3 recipe also uses TP and DCP. Back on TP, the notes are copied again (next section).

Large-scale EP: regather the users

Section 1's gap: only 8 rows per expert on average. Fix: spread the experts beyond one 8-GPU machine (large-scale EP; TensorRT-LLM's line: EP above 8). Attention stays per-device: DEP scaled up.

DeepSeek's production decode: EP144 on 18 machines; 256 experts + 32 redundant = 288 copies; per GPU, 2 routed + 1 shared.

  • The bus fills. At 32 requests per device, rows per expert copy: 8 → ~128 (144 × 32 × 8 ÷ 288; our derivation, even load).
  • Less reading. Per device per layer, expert weights 1.41 GB → 88 MB; each byte used 128×, not 8.
  • Memory freed. Routed experts per device: 81.7 GB at EP8, over an 80 GB GPU; 5.1 GB at EP144, the rest for KV.

Why it works: waits, not volume

  • Small volume. Tokens go to their experts and back each layer: at most ~10 MB per token per step (our derivation), over 10× under the 288 MB of notes read per step at 4K.
  • The hard part: waiting. 58 expert layers × a round trip = 116 waits per token.
  • Plain 8-GPU machines suffice. DeepSeek used InfiniBand with GPU-initiated RDMA; NVL72's rack-wide NVLink domain adds headroom.

One more cost: a small batch can't fill the bus, yet pays the full transfer cost.

Why big domains like NVL72 suit inference

Takeaway DEP copies no notes, so steps shorten; large-scale EP fills the expert bus and frees memory for notes.
The gain: SGLang, DEP both sides, 95.6% of the official target; vLLM to dep8, 2.09× per-GPU throughput (all GPUs).

Section 5

Long context: DCP vs. PCP

Section 4's gap: K3-like models can't run DEP; falling back to TP copies notes several times, so long contexts exhaust memory. The other problem: long prompts mean a long wait for the first token. Both fixes split the sequence; the names differ by one letter.

Don't go by the letters DCP, PCP: framework names, after each one's usual phase: D is decode, P prefill. CP is context parallel: one long sequence across devices.
The mechanism isn't phase-bound: Meta names them by what moves (pass-KV, pass-Q) and passes Q in prefill too when cache hits are high and new input short. We track only who moves: PCP passes notes, DCP the question.

Who moves: notes or question?

Attention is a table: rows are new tokens' questions (Q), columns earlier notes (K, V); looking only back, a triangle. Split it: one side moves.

Same split: by token, each device holding its segment's KV. Only what travels differs.

  • PCP: questions stay, notes travel. Prefill's thousands of questions split by row; notes travel during compute, hiding the transfer.
  • DCP: notes stay, the question travels. Decode has one question per step, cheapest to send.

Why opposite: smaller side moves

  • Prefill: many questions, small KV under GQA, so move notes. Decode: one Q against 100K+ notes, so move the Q.
  • One paper uses both. Meta's prefill passes full K, V; Q if the cached prefix is long, new tokens few. Both match the unsplit result.

Combining: don't divide yet. Attention is a weighted average: devices send numerators and denominators; sum, then divide once.

The arithmetic: merging two devices' averages

Same 8-way split, different payoffs

  • DCP: decode is memory-bound; splitting helps twice. Fit: a 128K V3 request takes 1.07 GiB per device, not 8.58. Reads: each device reads just its segment, no eightfold rereads as under TP. Cost: an extra communication round per layer; net gain only if reads are a big share.
  • PCP: prefill is compute-bound; splitting buys an earlier first token. Meta: Llama 3 405B on 128 H100s, 1M-token prefill in 77 s. Each doubling from 1 to 8 nodes about halves it; 8 → 16 cuts only ~35% (our arithmetic from two paper numbers).

When DCP wins and when it loses

  • Long contexts win. K3, GB300, 128K input, concurrency 8: TP8 holds ~790K tokens by default; 8 users need over 1M. DCP8: 365 tok/s; best TP8: 108. The win is in queueing: median TTFT 32.1 s vs. 2.3 s (TP8 vs. DCP8, queueing included).
  • Short contexts lose. At 4K the notes fit; only the cost is left: extra collectives per layer. All four concurrencies lose, up to 26%.
  • Total notes matter, not just length. At 8K, concurrency 8 loses 11%; 32 gains 24%.
  • Ignore the compute crossover. Over all of Qwen3.5-397B, attention FLOPs catch the experts only at ~34K in decode, ~68K in prefill (our derivation). But decode is about bytes read: enable DCP when the notes don't fit.
  • TPOT: DCP's penalty shrinks with context, but starts higher. Concurrency 1, 4K → 128K: DCP8 15.2 → 15.3 ms, flat; TP8 11.1 → 12.0 ms. The ~4 ms gap is mostly DCP forcing symm-mem off (our inference from two rows). K3 has only 24 MLA layers, so it gains mainly in fit.

Before enabling: DCP doesn't stack on DEP

DCP covers only attention and adds no devices: on attention's TP, copies become shards. Experts can use EP or TP, so the usual setup is TEP + DCP (our K3 run: TP8 + DCP8, no expert EP). Today DCP borrows its degree from the attention TP group (at most TP degree ÷ KV heads); DEP attention has one device per group: nothing to borrow. EP is fine; DEP is not. It rescues exactly the models that can't run DEP and fall back to TP attention.

Takeaway Smaller side moves. PCP moves notes: compute-bound prefill gets its first token sooner. DCP moves the question, so memory-bound decode gains capacity; a net win only at long context, after per-layer communication.
The gain: K3 / GB300 / SGLang, TP8 over two machines, 128K in / 1K out, concurrency 8: DCP8 vs. tuned TP8, output 108 → 365 tok/s (+237%). Short inputs lose.
But prefill and decode still share devices; the more users, the more each long incoming prompt delays. Next: PD disaggregation adds a KV move; why does it serve more users?

Section 6

PD disaggregation: one more KV trip, yet more users?

Section 5's gap: prefill and decode still share devices; the fuller each one, the more users a long new prompt delays. Splitting them across machines costs one extra KV trip per request. So why more users?

Each job drags the other

One kitchen: prep and service Trip size isn't the problem; two jobs share one stove. Prefill preps the whole prompt at once; decode serves plate by plate, best several at a time. A big party orders, prep piles up, service halts.
Split: two stoves, prepped ingredients (KV) handed over once.
  • Chunked prefill only spreads the stall. Long prompts enter in chunks: shorter waits, devices still shared.
  • Splitting doesn't shrink decode's trip; it only stops interruptions, so batches can safely fill.

Why more users: each side at its own limit

  • Why only 1.6: two latency targets, fast first token and no stutter; colocated, a device guards both and admits fewer.
  • Each side hits its own limit: 2 prefill + 1 decode: 3 devices, 10 req/s; colocated, 7 for ~11. Per device, over double.

DistServe: up to 7.4× the unsplit per-device request rate (≥90% on target). Mooncake serves Kimi live; NVIDIA Dynamo 1.0 shipped March 2026. PD splitting is now standard.

What the extra trip costs

  • Cheap: a rounding error. One 8K Qwen3-Coder-480B prompt's KV hands over in ~100 ms, 5–10% of prefill (bandwidth estimate).
  • Cheap per trip, not in total. A prefill machine ships many requests' KVs a second; one dedicated link fits just a few (below). Thin KV lets prefill go off-site; thick KV stays in NVLink.

After the split: sharding, ratios, when not to split

Sharding: many narrow prefills, one wide decode Our V4-Pro on GB300 with SGLang, 16 machines, runs DEP on both sides (each attention device serves its own users; experts split by EP). They differ in width and replica count:
  • Prefill: 14 × dep4. 4-device groups on one machine, never talking. Compute-bound: one long prompt alone saturates it. Small groups, little cross-machine traffic; add replicas to serve more.
  • Decode: 1 × dep8, 8 devices on two machines. Movement-bound: needs a big batch to amortize each expert-weight read; large-scale EP gives each expert more users. DP attention: V4-Pro has 1 KV head, so each user's KV is stored once.
  • Wide needs feeding. Decode at dep16 left 12 prefill machines, too few; output per decode device fell ~40% (Section 4).
  • Not just us. SGLang's public GB200 NVL72 runs match: one 48-GPU decode instance (DP attention + EP48), 2–4-GPU prefill instances (Chinese full edition, §8.5).
  • New model, new mix. No DEP? Decode falls back to TEP + DCP (K3, Section 5). Slow first token? Prefill can add PCP. Both inferred from Sections 4–5, unused in our deployment.
  • Compute a starting ratio, then sweep. Start ≈ decode completions/s × input length ÷ tokens/s per prefill instance. On V4-Pro (GB300, 8 decode devices), formula, official recipe and our sweep disagree (~9.8, 8, 14); 14 → 16 adds just 2%: decode is fed. New topology? Re-sweep.
  • Another prefill machine buys first-token speed. Over a ~65 s request, the 0.67 s saved is invisible; total output doesn't rise.
  • Jobs don't collide? Splitting is pure cost. Qwen3-Coder, two v7x-8s, concurrency 1: as 1P1D, median TTFT 95 → 281 ms, output only +12%.
  • Don't copy ratios; measure your load.
Takeaway Splitting stops interruptions, not hauling; each side batches to its limit. The extra KV moves once per request, and one trip is cheap; each side shards its own way.
The gain: Mooncake's FAST '25 paper reports 115% (A800) / 107% (H800) more requests than prior systems.
Split or not, decode still emits one token per step. Next: several per trip?

Section 7

Speculative decoding: many tokens per trip?

Section 6's gap: split or not, decode makes one trip per token. Tiers needing fast tokens can't batch big; reasoning models write thousands of tokens. Can one trip yield several?

Guess, then verify: hits free, misses cheap

Apprentice drafts, master grades The apprentice (small model) drafts a few tokens; the master (big model) checks them as one input, in one trip.
Matches stay; the first miss becomes the master's token; the rest go. Worst case: one token, as without it.
  • Verifying more is almost free. Small batches haul weights (Section 1); dense models verify five as cheaply as one; drafts are ready input, like prefill. MoE isn't: each position picks experts; more verified, more read (left, below).
  • Same output. When sampling, rejection sampling keeps the distribution exact.
  • The payoff is one division: acceptance length (mean tokens/step) ÷ step slowdown.

K3 on GB300, one user: trips slow 11.1 → ~16 ms (back-calculated) but carry 6.96 tokens on average: 4.81× faster per token. Optimistic (temperature 0, random prompts): official temperature-1.0 acceptance is ~4.73 code, ~2.61 creative; different engine, don't divide.

More users, smaller gain

  • “Free” needs idle compute. More users fill it; then every draft token costs real compute. Throughput: 4.22× at one user, 1.74× at 64.
  • Drafts take memory too. DSpark: K3's KV pool 787,504 → 637,504 tokens (−19%).
  • DEP tuned for big batches can lose. V4-Flash, 8 B200s, vLLM DEP8 with its own MTP draft: 3–37% slower at all ten concurrency levels, 12% even at 1; no reason given.

So: low-concurrency, interactive tiers first; big batches: measure first.

Drafts: ever nearer the big model

  • Separate small model (2022-11): a small apprentice model.
  • Medusa adds heads, EAGLE reads hidden states (2024-01): drafts grow onto the big model.
  • MTP trained into the model (2024-12): DeepSeek-V3 ships a draft layer: one more token.
  • EAGLE-3 fuses shallow, middle and deep layers (2025-03): now in SGLang and vLLM.
  • DFlash (2026-02): a block per pass; slots can't see each other: “of course” and “no problem” make “of problem”; later slots err more.
  • DSpark (2026-07): DFlash backbone; confidence and load set how many to verify; replaced DeepSeek's live MTP-1.

Speedups use different baselines and models, so they don't compare; the Chinese full edition lists each (Section 11).

DSpark's fix: two cuts. Whole-block drafts start strong, fade fast; chat is inherently harder to guess than problem solving (paper data folded below). One cut each.

Paper data: which positions do one-by-one vs. whole-block drafts get right?
  • Cut one fixes the draft. The backbone still drafts the block in one pass; a tiny head then rescores each slot, left to right, from the one before: “of” lifts “course”. Avg. 16–18% more accepted per round, only 0.2–1.3% slower.
  • Cut two fixes verification. Another small head rates each slot; multiplied along, that's the odds of reaching it. The batch's candidates queue by those odds; load sets how many get verified: more when idle, fewer when busy. Unsure tokens get no place.

EAGLE and MTP: same shape, different trainer

  • EAGLE needs training, but little. Big model frozen; train just a compression layer and one decoder layer: 0.99B params for 70B, 1–2 days on one A100 server.
  • Nearly EAGLE's skeleton and drafting; MTP differs in who trains it. Vendors train MTP in pretraining and ship it with the weights; anyone can train and attach an EAGLE after release.
  • Multi-step guessing needs a chain-trained draft. MiMo-7B's MTP chained as is: acceptance about 70%, 10%, near zero at the three positions; FastMTP's chain fine-tune: 81%, 56%, 36%.
Takeaway One weight trip yields every right guess, at worst one token. Biggest with few users; shrinks as more join.
The gain vs. no speculation (K3, GB300, one user): 4.81× faster per token; 4.22× end to end, first token (not sped up) included; 64 users: 1.74×.
With many users speculation helps less; each trip stays as heavy. Next section, a new lever: lighten the load.

Section 8

Quantization: fewer bytes, accuracy drop?

Section 7's gap: more users, less help from speculation, trips as heavy. Mostly we added riders; now: same bus, lighter cargo, fewer bits for weights and KV. Savings? Accuracy loss?

Halve the bits, halve the floor

Same cargo, packed tighter Same bus; each item drops from 16 bits to 8 or 4.
Few users: steps are nearly all weight reads; half the bytes, half the floor.
  • The math (our derivation, weights only). DeepSeek-V3 reads 37B parameters a token; on 8 v7 chips, FP8 needs ≥0.63 ms, exactly 1/8 of Section 1's 5 ms on one chip.
  • Measured: close. With vLLM's FP8 weights (2024) on 2 H100s, dense Llama 3 70B's inter-token latency fell to as little as half; MoE Mixtral 8x7B's only to 1/1.6.
  • Many users? Still worth it. MoE experts each get only a few rows, so weight reads dominate; freed memory holds more KV.
  • 4 bits isn't another clean halving. 16 codes can't span the range, so several values share a scale, which costs bytes too.

4-bit experts, attention 8+ bits

gpt-oss-120b's model card lists experts 114.71B, attention 0.96B, embedding + output 1.16B: experts ≈98%, attention under 1% (our derivation). OpenAI put only experts in MXFP4; it fits one 80 GB GPU.

  • Attention stays above 4 bits: under 1% of weights, little to save; softmax amplifies its score errors exponentially (gate ④). Yet its bytes per step aren't small (below).
  • So: unquantized, or FP8. Kimi K2 Thinking: INT4 on routed experts only; DeepSeek-V4: FP4 experts, mostly FP8 elsewhere; R1 on TPU: FP4 experts, FP8 attention.
  • No FP4 compute? Still faster. TPU v7's public specs list no FP4 peak: the cost is reading HBM; unpacking on chip is cheap.
Our TPU v7 runs: fitting on one machine R1, GLM-5.1: official FP8, experts only; one scale per output channel, rounded to FP4, no calibration data; converted once offline, reused.
First win: it fits. R1's FP8 experts take ~101.8 GB per device (R1 FP4 README); the usable 94.75 GiB is only ~101.7 GB, no room for activations or KV; FP4, ~60.9 GB: one four-chip machine runs it. Accuracy didn't collapse (R1 ≈95% on GSM8K), but without a same-machine FP8 baseline the drop is unknown.

Net: quarter-size experts save only about half the step: attention is then about 38% of its bytes (our derivation), plus KV at long context.

Accuracy: error crosses four gates; method sets the loss

Error crosses four gates; softmax doesn't recover it. Follow one rounding error, weight to token (sources: Chinese full edition, §12):

  • ① Land somewhere flat. Trained: gradient ≈0; nudges cost quadratic loss; curvature mostly ≈0, a few axes steep. GPTQ aims error flat.
  • ② Errors cancel; outliers hurt. Ups/downs mostly cancel (our explanation); an outlier wrecks a group's scale, so use small groups.
  • ③ Only first place counts. It changes only if the top two are close. Answers may flip at equal accuracy: check flip rate.
  • ④ The amplifier: softmax. Score error δ scales probability by eδ (our derivation). Attention scores and routing use it: protect them. Expert outputs join the residual directly: linear error.

The method sets the loss. At the same 4 bits, plain rounding clearly trails searched scales:

  • Use a format built for 4 bits: FP8 → NVFP4, NVIDIA's blog reports DeepSeek-R1-0528 drops within 1% on main language tasks.
  • Or train for 4 bits; “lossless” versus what? Kimi K2 Thinking simulates INT4 in training; its card claims a “lossless 2x speed-up in low-latency mode,” with no baseline accuracy and INT4-only benchmarks.

Quantize the KV too

  • One flag. FP8 KV is one --kv-cache-dtype in both vLLM and SGLang. Kimi K3's high-throughput recipe requires it: BF16 KV for 128 requests per device group doesn't fit.
  • Already at 4 bits. NVIDIA released NVFP4 KV on Blackwell: roughly half of FP8 again.
Takeaway Saved: halve the bits, halve the floor; 4-bit experts, attention at 8+ bits: about half a step saved. Lost: most error dies en route, but softmax amplifies it, so protect attention; measure the loss.
The gain: vLLM's FP8 weights at best halved Llama 3 70B's inter-token latency on 2 H100s; expert-only quantization puts gpt-oss-120b on one 80 GB GPU.

Section 9

Day one: which questions first?

Toolkit done. Back to Section 0: model, devices in hand, what first on day one? Eight questions: four on paper, then four at the knobs.

Set the yardstick, weigh the trip

  • Yardstick: which tier (①), which devices count (②). A tier change can shift per-device throughput 10×+ (Section 2); Section 4's DEP: 2.09× over all devices, 1.31× over decode only.
  • The trip: cargo weight (③), riders (④). Bytes ÷ bandwidth floors a step; measured several times slower? Check layout, scheduling first (Section 1). KV caps the batch (Section 3).

Find the jam, pick a fix (⑤–⑦)

  • Too empty: add riders. Continuous batching; with MoE, DEP / large-scale EP (Sections 2, 4).
  • Too few seats: thinner notes, paging, prefix reuse; no copies across devices; very long contexts split by sequence (Sections 3–5).
  • Long inputs block output: PD disaggregation, size by throughput (Section 6).
  • Few users, fast tokens: speculative decoding; K3: 4.22× solo, less with more (Section 7).
  • Always: quantize, fewer bytes (Section 8).

Order matters: same vLLM tests as Section 4: DEP first, 2.09× per device; tuning concurrency alone (256 → 512), just +28% (Chinese full edition, §10).
