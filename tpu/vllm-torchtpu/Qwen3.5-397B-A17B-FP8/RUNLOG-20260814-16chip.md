# Qwen3.5-397B-A17B-FP8 on v7x 16 chips —— 实测记录

**日期**：2026-08-14
**集群**：`chrisya-v7x-v3`（us-central1，project `cloud-tpu-multipod-dev`）
**硬件**：节点池 `hy3-v7-16-dws-2`，4 节点 × `tpu7x-standard-4t` = **16 chips / 32 devices**，拓扑 2x2x4
**与前一份的关系**：[RUNLOG-20260812](./RUNLOG-20260812.md) 记录的是 bodaborg 共享集群上的 **4 chip 单机**验证。
本文是同一套软件栈搬到**专属 16 chip 多机 slice** 上的记录，两者的软件版本矩阵完全一致，
所以 4 chip 的数可以直接当 16 chip 的对照基线。

---

## 0. 一句话结论

搬到专属集群后，**准备阶段从「每轮重付」变成「一次性」**，这是最大的结构性变化。
bodaborg 有 60 分钟 pod 上限，每个 cell 都要重付一遍 13 分钟启动；这里 pod 长期存活，
18 个 cell 一轮铺开。

## 1. 两个集群的差异（决定了跑法必须改）

| | bodaborg-tpu7x-nap | chrisya-v7x-v3（本文） |
|---|---|---|
| 归属 | 共享，`priority-dev` 命名空间 | 专属 DWS flex-start |
| pod 寿命 | **60 分钟硬上限** | 无上限（sleep infinity 长期持有） |
| 规模 | 4 chip 单机 | 16 chip / 4 节点多机 slice |
| 权重落点 | hyperdisk PVC（EXT4） | 节点内存 tmpfs（963 GB/节点） |
| 编译缓存 | hyperdisk PVC，跨 pod 存活 | tmpfs，随 pod 存活 |
| 跑法 | 一个窗口一个 cell | 一次铺开整个矩阵 |

**跑法必须改的原因**：bodaborg 那套「单 cell 切分 + 结果立刻拷到持久盘」纯粹是为了绕开
pod 寿命，不是什么好设计。这里不需要，硬搬过来反而会为每个 cell 白付一次 13 分钟启动。

## 2. Lustre 在 TPU 节点池上不可用（单子里没写的坑）

集群里有两个 35Ti RWX 的 Lustre PVC（`lustre-pvc` / `lustre-uc1a-pvc`），
看起来是 397B 权重的理想落点。**实际挂不上。**

```
MountVolume.MountDevice failed for volume "lustre-pv":
  mount.lustre: mount 172.25.0.3@tcp:/lfs at ... failed: No such device
  Are the lustre modules loaded?
```

排查路径与结论：

1. `lustre-csi-node` daemonset 在 4 台 TPU 节点上都是 `2/2 Running` —— **这是假象**，
   CSI 进程活着不等于内核模块在。
2. 集群 `lustreCsiDriverConfig.enabled: true`，addon 没问题。
3. 进节点看真值：

```
lsmod  → lnet 667648 3 ko2iblnd,obdclass,ksocklnd
         libcfs 352256 4 lnet,...          ← 这两个在
modprobe lustre
  → FATAL: Module lustre not found in directory /lib/modules/6.12.68+   ← 客户端模块根本没有
grep lustre /proc/filesystems → 空
```

**结论**：TPU 节点的 COS 镜像装了 lnet/libcfs 但**没有 lustre 客户端模块文件**，
不是配置问题，使用方修不了。这是 GKE TPU 节点镜像的缺口，值得报给 GKE。

> **给后来人**：在 TPU 节点池上看到 `exit status 19 / No such device`，
> 别去查网络和 PVC 绑定，直接进节点 `modprobe lustre` 看模块在不在。

## 3. 节点 ephemeral-storage 只有 43.8 GiB

`tpu7x-standard-4t` 节点：内存 963 GB、CPU 223 核，但 **ephemeral-storage 只有 43.8 GiB**。

pip 编译 vLLM（`MAX_JOBS=64`）、`/tmp`、pip cache 都往容器盘写，会撞**节点级**驱逐。
危险之处在于容器里 `df` 看着一片宽裕 —— 因为 ephemeral-storage 是整节点共享的配额，
容器 `df` 根本看不见。

**处置**：`/work`、`/tmp`、`/root/.cache` 全部挂 tmpfs（`emptyDir: {medium: Memory}`），
容器盘只留镜像本身。

## 4. 接管被占位 Job 占住的 DWS 节点（可复用流程）

DWS flex-start 节点一旦 `BookingExpired=True`，空闲即是 autoscaler 的回收候选，
所以「删占位」和「提交真任务」之间不能有空窗。上一次重新排队等了 38 小时。

**做法 —— 把风险挪到删除之前，而不是靠手快：**

1. **先预热镜像**。拉镜像不需要 TPU 资源，可以和占位 Job 共存。
   在 4 台节点各起一个不请求 `google.com/tpu` 的 pod 把镜像拉下来。
   这一步把切换时最大的失败模式（镜像拉取慢/失败）提前消化掉。
2. **三层校验**，缺一不可：
   - 严格 YAML 解析抓重复键（见下）
   - `kubectl apply --dry-run=server` 校验 JobSet
   - **把 pod template 抽成独立 Job 再 dry-run** —— 只有这层才真正校验 pod spec
3. **delete 与 apply 写在同一条命令里**，中间不加 sleep、不加判断。

实测：切换 2 秒，10 秒后 4 个 worker 全部 Running。

> **为什么第三层不能省**：JobSet 的 `--dry-run=server` 只校验 JobSet CRD 本身，
> **不校验它生成的 Job**。上一轮 YAML 里出现两个 `limits` 键，后者覆盖前者导致
> `google.com/tpu` 丢掉限额，Job 被 API server 拒绝，而 dry-run 一路绿灯，
> 真因只在 `jobset-system` 控制器日志里。那次废掉一整夜 9 个任务。

## 5. 权重：同区 GCS → tmpfs

权重已存在于 `gs://chrisya-v7x-us-central1/models/qwen3.5-397b-a17b-fp8/weights/`
（94 分片 / 378.30 GiB / us-central1，与集群同区），不必走 HF。

镜像里没有 gcloud SDK，用 `google-cloud-storage` 自己控并发（见 `scripts/fetch-weights.py`）。

| 项 | 实测 |
|---|---|
| 单节点速率 | 231 MiB/s |
| 4 节点聚合 | 990 MiB/s |
| 单节点耗时 | 27.95 分 |
| 落盘一致性 | 4 台逐字节相同，406198639413 bytes / 94 分片 |

四台速率几乎完全相同（244–254 MiB/s），说明瓶颈是**共享的聚合上限**而不是单节点能力，
加线程没用。

**环境安装与权重下载并行跑**（一个打 pypi、一个打 GCS，不抢同一个瓶颈）：
安装只要 2 分 50 秒，完全被 28 分钟的下载掩盖。串行的话要白多花近 3 分钟。

### 进度条踩的坑（值得记）

`fetch-weights.py` 最初只在**文件完成时**计数。94 个 4 GB 分片、48 并发的场景下，
前 20 分钟一个都没完成，进度条一直显示 `6/106 · 0.0 GiB · 0 MiB/s`，看着像卡死，
ETA 也算得离谱。**`du -sh` 才是真值** —— 那时盘上已经有 359 GiB。

> 大文件批量下载的进度必须统计**已落盘字节**，不能统计**已完成文件**。

## 7. 两个上游问题

### 7.1 AOT 编译缓存有一部分永不命中

热启动时 88 个可执行体从缓存正常加载，但 **16 个失败后重新编译**，8 个 worker 每个中招 2 次：

```
WARNING [decorators.py:321] Compiling model again due to a load failure from
  /cache/vllm/torch_compile_cache/torch_aot_compile/<hash>/rank_N_0/model,
  reason: a bytes-like object is required, not 'BundledAOTAutogradResult'
```

序列化路径的类型错配 —— 写进去的是 `BundledAOTAutogradResult` 对象，
读出来时按 `bytes` 处理。这部分编译时间**每次启动都白付**，缓存做得再持久也没用。

### 7.2 权重 prefetch 的文件系统白名单太窄

```
INFO [weight_utils.py:892] Auto-prefetch is disabled because the filesystem (EXT4)
  is not a recognized network FS (NFS/Lustre). If you want to force prefetching,
  start vLLM with --safetensors-load-strategy=prefetch
```

白名单只认 NFS/Lustre。EXT4 和 tmpfs 都被排除，而这两个恰恰是本地盘场景的主力。
需要手动加 `--safetensors-load-strategy=prefetch`。

## 8. 多机（32 device 单一 mesh）的可行性

GKE 在 pod 里注入了完整的多机 mesh 环境：

```
TPU_ACCELERATOR_TYPE=tpu7x-32          ← 32 = device 数（16 chip × 2）
TPU_TOPOLOGY=2x2x4
TPU_WORKER_ID=0..3
TPU_PROCESS_ADDRESSES=ttpu16-s-0-{0..3}.ttpu16:8471
```

多机在代码里是**一等公民**，不是脚本层 hack：

- `envs.py` —— `TPU_MULTIHOST_BACKEND = env_with_choices("TPU_MULTIHOST_BACKEND", "", ["ray"])`
- `platforms/tpu_platform.py` —— 按 `multihost_backend` 分支走不同的 device 绑定
- `distributed/utils.py` —— ray 模式下 `get_kv_ips/ports` 收集全部节点

但上游只提供裸 VM + docker 的多机脚本（`scripts/multihost/run_cluster.sh`），**没有 GKE 先例**。

### 挖到的坑：`TPU_NODE_ID` 不会被注入

`distributed/utils.py` 的 `get_node_id()` 读的是 **`TPU_NODE_ID`**，默认 `0`：

```python
def get_node_id() -> int:
    id = os.getenv("TPU_NODE_ID", 0)
    return int(id)
```

而 GKE 注入的是 `TPU_WORKER_ID`，**不注入 `TPU_NODE_ID`**。不手工补这一行，
4 个节点会全都自认为 node 0，`get_kv_ips()` 收集到的 IP 表塌成一个。

处置：`export TPU_NODE_ID="${TPU_WORKER_ID:-0}"`（见 `scripts/ray-up.sh`）。

### 把 16 chip slice 当 4 个独立 4 chip 环境用

这不是虚拟化，也不是资源划分 —— **是「拒绝组队」。**

硬件本来就是 4 台机器，每台物理上插着自己的 4 颗芯片，通过 `/dev/vfio` 挂进容器。
所谓「16 卡是一个整体」，是 libtpu 在启动时**按环境变量去跟其他 3 台会合**才形成的。
把那组变量改掉，进程就不去会合，只初始化本机的 8 个 device。

不需要任何隔离机制，因为每台机器物理上本来就摸不到别人的芯片。

#### 六个变量，改前 vs 改后

| 变量 | GKE 注入（多机） | 改成（单机） | 作用 |
|---|---|---|---|
| `TPU_WORKER_ID` | `0` / `1` / `2` / `3` | `0` | 我是几号 worker |
| `TPU_PROCESS_ADDRESSES` | `ttpu16-s-0-0.ttpu16:8471,`<br>`…-1…,…-2…,…-3…:8471` | `localhost:8471` | 同伴地址表（带端口） |
| `TPU_WORKER_HOSTNAMES` | 同上四个 DNS 名 | `localhost` | 同伴主机名表 |
| **`TPU_HOST_BOUNDS`** | **`1,1,4`** | **`1,1,1`** | **主机在三维上的排布 —— 核心就是这一个** |
| `TPU_CHIPS_PER_HOST_BOUNDS` | `2,2,1` | `2,2,1`（**不变**） | 每台主机上芯片的排布 |
| `TPU_ACCELERATOR_TYPE` | `tpu7x-32` | `tpu7x-8` | 后缀是 **device 数，不是 chip 数** |

再加一个动作：

```bash
unset TPU_MULTIHOST_BACKEND
```

若之前设过 `ray` 不清掉，代码会走多机分支，与刚声明的单机拓扑打架。

#### 三个容易踩错的点

1. **地址表和主机名表必须一起改。** `TPU_PROCESS_ADDRESSES`（带端口）和
   `TPU_WORKER_HOSTNAMES`（纯主机名）是一对，只改一个会对不上。

2. **`TPU_CHIPS_PER_HOST_BOUNDS` 不用改。** 每台主机上永远是 4 颗芯片按 2x2x1 排布，
   单机多机都一样。真正变的只有 `TPU_HOST_BOUNDS`，从 `1,1,4` 变 `1,1,1`。
   脚本里显式写出来只是为了自我说明。

3. **`tpu7x-32` 的 32 是 device 数不是 chip 数。** v7x 上 **1 chip = 2 device**，
   16 chip × 2 = 32。所以单机 4 chip 要写 `tpu7x-8`。这个后缀写错会在初始化时
   报拓扑不匹配，而错误信息不会告诉你是单位搞错了。

#### 完整写法

```bash
export TPU_WORKER_ID=0
export TPU_PROCESS_ADDRESSES=localhost:8471
export TPU_WORKER_HOSTNAMES=localhost
export TPU_HOST_BOUNDS=1,1,1
export TPU_CHIPS_PER_HOST_BOUNDS=2,2,1
export TPU_ACCELERATOR_TYPE=tpu7x-8
unset TPU_MULTIHOST_BACKEND
```

见 [`scripts/run-config.sh`](./scripts/run-config.sh) 的 `single` 模式分支。

#### 怎么验证

```bash
python3 -c "import jax; print(len(jax.devices()))"
```

| 返回 | 含义 |
|---|---|
| **8** | 对了 |
| 32 | 变量没吃进去，仍在多机视图 |
| **卡住不返回** | 它还在等另外 3 台会合 —— 说明地址表没改干净 |

实测 `jax.devices()` 返回 8 个 `TPU7x`，`torch.tpu.device_count()` = 8，matmul 正常。

#### 代价

跨机的 ICI 链路在这个模式下**完全闲置**。
所以这招只适合**单机装得下**的模型：397B FP8 权重 378 GiB，单机 768 GB HBM 装得下，
可以这么玩。模型大到单机放不下时必须组 mesh，那时跨机链路才真正派上用场。

## 9. 测试矩阵

上游 397B 有 3 个 config，`DP × MAX_NUM_SEQS` 恒等于 512，都是 8 device：

| config | TP | DP | MAX_NUM_SEQS | MAX_NUM_BATCHED_TOKENS |
|---|---|---|---|---|
| tp1-dp8-ep | 1 | 8 | 64 | 1024 |
| tp2-dp4-ep | 2 | 4 | 128 | 2048 |
| tp8-dp1-ep | 8 | 1 | 512 | 8192 |

每个 config 6 个 cell（ISL/OSL 2 种 × 并发 3 档），共 18 个 cell。

本轮分派（4 节点并行）：

|---|---|---|
| node0 | tp8-dp1-ep | isl1024/osl8192 × 并发 64/256/512 |
| node1 | tp8-dp1-ep | isl8192/osl1024 × 并发 64/256/512 |
| node2 | tp2-dp4-ep | 全 6 cell |
| node3 | tp1-dp8-ep | 全 6 cell |

压测口径：`BENCHMARK_TEMPERATURE=0`（上游 config 自带，四台逐台确认）。

server 端 sampling（这些模型是 temp 0.7），在 decode-heavy 的 cell 上明显更慢。

## 11. 从数据里能总结出的规律

### 规律一：同一 slice 上多台单机 server 互不干扰

这是本次最有操作价值的一条。同一个 cell，两种跑法：

| | median TPOT | output tok/s |
|---|---|---|
| 单机独占（bodaborg 4 chip） | 39.62 ms | 5833.5 |
| 4 台同时跑（本轮，同一 2x2x4 slice） | 39.54 ms | 5877.9 |
| 差异 | **−0.22%** | **+0.76%** |

噪声级别。**一个 16 chip 的多机 slice 可以当 4 个独立的 4 chip 环境用，吞吐不打折。**

这条直接改变工程做法：需要跑并行实验矩阵时，不必申请 4 个小 slice 排 4 次队，
申请一个大 slice 切开用即可，而且拿到的是同一批硬件，横向对比没有机器差异。

### 规律二：低并发 TP 赢，高并发 DP 赢，翻转点随负载形状变化

> **修订**：本节初版只有 c64/c256 两档，据此写过「TP 越大越好，与并发无关」。
> 补齐 c512 后被证伪 —— 排序会翻转。以下是 18 格全跑完的结论。

**decode 重（ISL 1024 / OSL 8192）· output tok/s**

| 并发 | tp1-dp8 | tp2-dp4 | tp8-dp1 | 赢家 |
|---|---|---|---|---|
| 64 | 2510 | 2819 | **2953** | tp8-dp1 |
| 256 | 5550 | 5708 | **5878** | tp8-dp1 |
| 512 | 8355 | **8414** | 5907 | tp2-dp4 |

**prefill 重（ISL 8192 / OSL 1024）· output tok/s**

| 并发 | tp1-dp8 | tp2-dp4 | tp8-dp1 | 赢家 |
|---|---|---|---|---|
| 64 | 840 | 1067 | **1636** | tp8-dp1 |
| 256 | **2454** | 2368 | 2287 | tp1-dp8 |
| 512 | **3316** | 3057 | 2146 | tp1-dp8 |

三个 config 的 `DP × MAX_NUM_SEQS` 恒等于 512，总并发能力相同，差异纯来自策略。

**成因**：低并发时瓶颈是单请求执行速度，decode 是访存瓶颈，TP 把权重摊到更多 HBM 通道
直接加速；高并发时瓶颈转移到调度，而 `tp8-dp1` 是 **DP=1，只有一个 engine、
一个连续批处理循环**，请求全挤在一个队列里，`tp1-dp8` 则是 8 个 engine 各跑各的。

**翻转点**：prefill 重在 64→256 之间就翻转，decode 重要到 256→512。
prefill 单条开销大，更早把单一调度循环压满。

### 规律三：tp8-dp1 的饱和点与并发悬崖

decode 重上，tp8-dp1 从 c256 到 c512 吞吐只涨 **0.5%**（5878→5907），
而 median TTFT 从 335 ms 涨到 10,956 ms（**33 倍**）。

prefill 重上更极端：

| 指标 | c256 | c512 | 变化 |
|---|---|---|---|
| median TTFT | 2,305 ms | **108,536 ms** | **47 倍** |
| output tok/s | 2287 | 2146 | **−6.2%** |

> **归因修订**：初版把它归因于 `MAX_NUM_BATCHED_TOKENS / ISL = 1`（一步只装得下一条 prefill）。
> **这个归因是错的。** `tp1-dp8` 的 `MAX_NUM_BATCHED_TOKENS` 只有 1024，比 tp8-dp1 的 8192 更小，
> 按那个判据应该更惨，实际却是同档最好的（3316 tok/s）。
> 真因是 **DP=1 的单一 engine 调度饱和**，与 batched tokens 预算无关。

**判据**：看 `DATA_PARALLELISM`。DP=1 在高并发下会撞调度墙，
症状是「吞吐持平或下降 + TTFT 暴涨一个数量级」。
高并发要吞吐就用 DP，低并发要延迟就用 TP。

### 规律四：相对 baseline 的增益随并发升高而收窄

增益最大在 c64（+3.8% / +6.7% / +4.3%），到 c256 收窄到 +1.6% ~ +3.0%。
本版本的改进主要作用在**低并发、单请求延迟**路径上；
高并发下系统被批处理效率主导，改进被稀释。
**做版本对比时只测高并发会低估改进幅度。**

### 规律五：看吞吐必须分清 output 和 total，两者会给出相反结论

同样是 tp8-dp1：

| cell | output tok/s | total tok/s |
|---|---|---|
| isl1024_osl8192_c256 | 5878 | 6610 |
| isl8192_osl1024_c256 | 2287 | **20512** |

按 output 看，prefill 重的负载只有 decode 重的 39%；
按 total 看，反过来是 3.1 倍。
**脱离 ISL/OSL 谈「吞吐多少」没有意义** —— 这也是为什么本文每个数字都带完整形状标注。

## 13. 投机解码（MTP）实测

### 13.1 能不能用

397B checkpoint 里有 **3096 个 `mtp.*` 张量**，投机解码可用，实测接受率 **89.6–95.2%**。
但 `mtp.layers` **只有第 0 层**，所以 `num_speculative_tokens` 硬上限是 1，
理论每步产出 = 1 + 接受率 ≈ **1.9 token**，**2 倍就是天花板**。

### 13.2 收益曲线：峰值在并发 4–8，高并发转负

tp8-dp1 / ISL 1024 / OSL 1024 / 640 prompts（低并发档 64 prompts）：

| 并发 | base tok/s | MTP-1 tok/s | 吞吐 | base TPOT | MTP TPOT | TPOT 改善 |
|---|---|---|---|---|---|---|
| 1 | 125 | 144 | **+15.1%** | 7.91 ms | 6.81 ms | +13.8% |
| 4 | 426 | 529 | **+24.2%** | 9.20 ms | 7.32 ms | +20.5% |
| 8 | 729 | 907 | **+24.4%** | 10.55 ms | 8.44 ms | +20.0% |
| 16 | 1237 | 1397 | +12.9% | — | — | — |
| 64 | 2631 | 2406 | **−8.6%** | — | — | — |

> **只测两端会得出相反结论。** 先前只测了 16 和 64，看到的是「+13% 然后转负」，
> 据此差点判定 MTP 无用 —— 实际峰值在 4–8，被跳过了。
> **选型扫描必须覆盖低并发段，尤其是投机解码这类收益随批次衰减的特性。**

### 13.3 为什么只有 1.24 倍而不是 1.9 倍

理论增益只兑现了 **27%**。真因在权重结构里：

```
MTP 张量 3096 个，其中专家权重 3072 个，涉及 512 个专家
```

**MTP 草稿头不是轻量模型，它带着完整的 512 专家 MoE 层。**
起草一次的代价接近一次真实 decode，省下来的步数被起草成本吃掉大半。

这与 GPU 侧的公开结论**不可比**：那边（Google Cloud 实测 Qwen3.5-27B on B200）
是 dense 小模型配真正轻量的草稿头，且 B200 上算力大量闲置
（DCGM 实测 tensor core 活跃度 < 5%，HBM 带宽 < 11%），投机解码等于白捡闲置算力，
所以能报出「MTP 是单个最大吞吐杠杆、关掉掉三分之一」。
397B MoE 在 v7x 上草稿头本身就重，捡不到那么多。

> **要显著提升，方向是更轻的草稿头**（少量专家或 dense 化），不是调并发。
> 这是模型侧的事，配置层解决不了。

### 13.4 两个必须绕开的坑

**坑一：`/dev/shm` 撑爆。** `torch_tpu` 把编译产物写 `/dev/shm`，32 GiB 不够。
报出来是 **SIGBUS（信号 7）**、栈顶停在 `determine_available_memory`，**看起来像 HBM 不足**。
诊断先跑 `df -h /dev/shm`。不重启 pod 的修法：软链到 `/work`（同为内存盘但 640 GiB）。

**坑二：编译缓存全命中时 MTP 崩溃。** 详见 §14。

## 14. 编译缓存与 MTP 冲突的根因

**现象**：同一份 serve 配置，缓存状态决定成败。

| 缓存加载 | 新编图 | 动态形状告警 | 结果 |
|---|---|---|---|
| 8 | 20 | 8 | ✓ |
| **168** | **0** | 8 | ✗ |
| 全命中 | 0 | — | ✗（51 秒即崩） |
| 0 | 21 | 8 | ✓ |

报错 `NotImplementedError: TPU backend: does not support dynamic shape`。

**别被错误名带偏** —— 成功的两次同样报了 8 次该告警，它不是失败原因。

### 根因（源码坐实）

| 位置 | 内容 |
|---|---|
| `_backend.py:295` | `_raise_on_symint(example_inputs)` —— 扫到 `torch.SymInt` 就抛 |
| `_backend.py:263` | `dynamism: bool = False` —— **动态形状支持存在但默认关闭** |
| `compile/dynamic/compiler.py` | `DynamicCompiler` 确实存在，只是被上面那个开关挡在抛错点之后 |
| `_backend.py:186-188` | `AOTAutogradCache.generate_guards_expression = staticmethod(lambda *a, **kw: None)` |

**关键是最后一条：写缓存时 guard 生成被替换成返回 `None` 的空函数。**
guard 正是 torch.compile 用来判定「缓存图对当前输入形状是否有效」的依据 ——
被抹掉后，缓存条目加载时不做形状校验。

不开 MTP 时每步 token 数固定，形状不变，不出事；
开 MTP 后每步 token 数在 1 与 1+已接受之间变动，命中不匹配的缓存条目，
dynamo 重新 trace 时走 automatic-dynamic 产生 `SymInt`，
而 `_dynamism=False` 让它在到达 `DynamicCompiler` 之前就抛错。

**能重编时（新编 20–21 个图）会走回退路径重编；缓存全命中时一个图都不编，
回退路径没机会触发，告警就升级成致命错误。**

### 这是上游自己标记的临时状态

`_serialization_context` 的 docstring 原文：

> **TODO**: Once we bump torch past pytorch/pytorch#170443, replace this entire
> context manager with `bundled_autograd_cache: True, bypass_autograd_cache_key: True`
> and **remove the `_cache_inference_info` and `generate_guards_expression` patches**.

另有注释说明动态图根本进不了缓存：

> DynamicCompiler artifacts are not pickleable yet, so only static compilations
> can participate in AOTAutogradCache.

### 三条真修法（「清缓存」只是绕开，不是修）

1. **停止抑制 guard** —— 阻塞在 torch 升级（pytorch#170443），上游已列 TODO
2. **让 `DynamicCompiler` 产物可 pickle** —— 动态图就能进缓存，不必回退
3. **启用 `_dynamism`** —— 让 `SymInt` 走到已存在的 `DynamicCompiler` 而不是抛错；
   需配合 `torch_tpu._internal.dynamism.mark_dynamic` 显式标注可变维度

**顺带**：错误信息 `TPU backend: does not support dynamic shape` **措辞误导** ——
准确说是「未启用，且要求调用方显式 mark_dynamic」，而不是不支持。
