07 韧性：检查点、故障演练、恢复

要解决什么：06 的 JIT 基线作业没开检查点（ENABLE_CHECKPOINTING 为 "false"）、maxRestarts: 0，坏一台就从头再来。 为什么难

  • multislice 全有或全无：坏一台，全部切片重切（05 §5.2）。
  • 最慢的是「TPU 初始化挂住」（多次打断里有几次），根因是一片的 pod 撒到多个 cube（§7.4、经验教训第 42 条）。

演练规模：3 × 4x4x4 = 192 chip（缩小版 MoE 模型），不是 06c 的 10+ × 4x8x8。

  • 多次 打断（192 chip 演练）
  • 64–106 s 打断 → 重新切片、准入
  • ~6 min 顺利时打断 → 新 step
  • 半小时到一个多小时 掉进 TPU 初始化挂住时

读图：快慢取决于菱形那一步。

开工前（每个终端一次）：

bash
source ~/runbook-env.sh && rb_env_check PROJECT REGION ZONE CLUSTER MTC_BUCKET
  • 变量：$PROJECT $REGION $ZONE $CLUSTER $NS $STATE_DIR，MTC 的 $MTC_CONFIG_NAME $MTC_BUCKET $MTC_INMEM_SIZE（env.sh「K8s 侧」段）。
  • 工具与权限：kubectl（集群管理员）、gcloud、jq、envsubst；container.clusters.update、storage.buckets.create/setIamPolicy、compute.instances.stop/start。
  • 已完成：03、05、06。

7.1打开 Multi-Tier Checkpointing（MTC）

MTC 分两层存检查点：

读图：换 cube 时本地副本还在，被 MaxText 列校验拒收（见经验教训第 24 条）。

分六步，用词：

词 是什么
replicator 节点上的组件，备份写到 gs://<bucket>/<job-name>/<YYYY-MM-DD_HH-MM>/；初始化失败写 /local/replicator.failed

    • 实测集群实际：highscalecheckpointing-multitier-driver:v0.9.0-gke.2、replicator:v0.3.1-gke.0。

  2. 备份桶：HNS（建桶时就得开 源https://cloud.google.com/storage/docs/create-hns-bucket）。

    • 授权：给 ns/gke-managed-checkpointing/sa/gke-checkpointing-multitier-node 授 roles/storage.objectUser。
    • 保留：backup-interval-minutes ≥30；MTC 从不删 GCS 备份，自己做保留。

PNUM=$(gcloud projects describe $PROJECT --format='value(projectNumber)')
gcloud storage buckets add-iam-policy-binding gs://$MTC_BUCKET --role=roles/storage.objectUser \
  --member="principal://iam.googleapis.com/projects/$PNUM/locations/global/workloadIdentityPools/$PROJECT.svc.id.goog/subject/ns/gke-managed-checkpointing/sa/gke-checkpointing-multitier-node"

  • 回滚：remove-iam-policy-binding 同参数；gcloud storage rm -r gs://$MTC_BUCKET 会删掉所有备份。
  1. CheckpointConfiguration CR：driver DaemonSet 由它创建；升级前后删了重建。

  • 模板 scripts/07-checkpoint-configuration.yaml 含 ${…} 变量，别直接 apply，用 07-mtc-setup.sh 或 envsubst < "$RUNBOOK_DIR"/scripts/07-checkpoint-configuration.yaml | kubectl apply -f -：

建（第 1、3、4 步缺什么补什么；默认 dry-run）：

bash
"$RUNBOOK_DIR"/scripts/07-mtc-setup.sh              # 看现状与将执行的命令
"$RUNBOOK_DIR"/scripts/07-mtc-setup.sh --execute    # 最后一步 = envsubst < 07-checkpoint-configuration.yaml | kubectl apply -f -

卸载：07-mtc-setup.sh --delete --execute（不删桶、不关 addon）。报 no matches for kind "CheckpointConfiguration" = addon 没开 源公开文档 Troubleshoot。

  1. 内存：ramdisk 从 960 GB 主机内存扣；inMemoryVolumeSize ≈ 本地检查点 × 2.2（TPU）。缩小版 MoE 模型实测：31.5 GiB per host needed, ramdisk 100.0 GiB。

  2. 工作负载侧：用 07-jobset-mtc.yaml。未实测，T0（reservation 生效时刻）前的演练须在 2 片上验证。

    • 底子是 06-jobset.sh 生成的 JobSet；只从实测集群第一次演练（§7.4 共三次演练）的 JobSet借了结构（容错 failurePolicy、/local 卷、MTC 那组 env），模型参数没抄。
    • 不抄的原因：该演练是 3 × 4x4x4 的小模型，GA 2 编译要 101.0 GiB > 94.74 GiB HBM。
    • 周期默认照后两次演练：本地 20 步、持久 40 步。周期按步数定、按步数对使用方讲；10+ 片 AOT 生产步时比 JIT 口径（06c §6.6）短约 40%，同样步数的墙钟也短这么多，换算分钟要用生产口径，别用 JIT 口径。
    • 生产规模参考（10+ 片 / 更大规模，配置逐项见 07a §7a.3）：本地 save 阻塞（Orbax Finished blocking save … @ /local/N）10+ 片和更大规模都只有秒级，摊到本地周期里可以忽略；持久层（GCS，数 TiB 级检查点）一次阻塞 save 要几分钟；但同作业其余 GCS save 阻塞只有几秒，口径见 07a §7a.3。该作业持久层整个关了，所有片同时丢时没有回退点 —— 交付时不照抄，持久层周期按故障率定。
      • 生产规模 MTC 参数参考（10+ 片 / 更大规模）：
      • 本地层 LOCAL_CHECKPOINT_PERIOD：按自己的步时折成分钟级存一次。
      • GCS 备份 MTC_BACKUP_INTERVAL_STEPS：比本地层稀，取本地周期的整数倍，按自己的步时和能容忍的丢失量调。
      • 本地层每 host 要百余 GiB，ramdisk 给到约 2.6 倍（数百 GiB）。
      • 本模板默认 20 / 40 步是小规模演练的值，数千芯生产按上面重定；持久层仍建议开。
    • 存盘后那几步会变慢（已知问题，上游修复未合入）：持久层每次存盘阻塞几分钟（见经验教训第 23 条）；本地层存盘后第 1、2 步明显变慢。持久层周期按故障率定，别设太密。
    • MTC_DATA_PARALLELISM 和 replicas 由同一个 ${SLICES} 生成，必须等于片数（演练配置填的 3 是它自己的片数）。
    • 前提、渲染命令、2 片验证四步都在文件头。最要紧的一条：JIT 基线作业的 MaxText env tar 带不带 MTC 接线未核，不带时 env 被静默忽略。
    • dsv3（06b）没有 MTC 模板：本书唯一的 MTC 模板建在 06c 的训练 JobSet 上（要 env tar、代码仓库凭据、数据 PVC）。06b 公开镜像认不认这组 env 未核 [需确认：上游 MaxText 是否读 ENABLE_MTC 等 env]。要给 dsv3 开 MTC，把这组 env 和 /local 卷叠到 06a-jobset-dsv3.yaml 上，自己在 2 片上验证；这是本书的缺口。
yaml
# 节选：07-jobset-mtc.yaml 相对 06-jobset.sh 生成的 JobSet 的增量
failurePolicy: {maxRestarts: 10, restartStrategy: Recreate}
replicas: ${SLICES}
volumes:
- name: mtc-ramdisk
  csi: {driver: multitier-checkpoint.csi.storage.gke.io}   # 容器挂到 /local
env:
- {name: ENABLE_MTC, value: "true"}
- {name: LOCAL_CHECKPOINT_DIRECTORY, value: /local}
- {name: LOCAL_CHECKPOINT_PERIOD, value: "${LOCAL_CKPT_PERIOD}"}       # 默认 20
- {name: CHECKPOINT_PERIOD, value: "${PERSIST_CKPT_PERIOD}"}           # 默认 40
- {name: MTC_BACKUP_INTERVAL_STEPS, value: "${PERSIST_CKPT_PERIOD}"}
- {name: MTC_DATA_PARALLELISM, value: "${SLICES}"}                     # = 片数
- {name: MTC_PERSISTENT_CHECKPOINTING, value: "true"}
- {name: ENABLE_CHECKPOINTING, value: "true"}
- {name: ASYNC_CHECKPOINTING, value: "true"}
- {name: ENABLE_GOODPUT, value: "true"}

标签 managed-mldiagnostics-gke: "true" 开 ML Diagnostics（演练配置里有，模板保留）。

7.2JobSet / Kueue 的失败策略

设置 取值
backoffLimit 0（任一 pod 失败即 Job 失败）
failurePolicy.maxRestarts 恢复测试 10；一次性基准 0；约 4K pod 规模下 3–5
failurePolicy.rules RestartJobSet on BackoffLimitExceeded，restartStrategy: Recreate
Kueue waitForPodsReady 30m / recovery 10m；pod 掉线超过 recoveryTimeout 就驱逐——坏 cube 靠它
--activation-timeout 60m（先例）

核对命令（每次恢复测试前；出处 https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/ 、 https://jobset.sigs.k8s.io/docs/concepts）：

bash
# Kueue：waitForPodsReady 必须是生效的（没被注释掉）——期望 timeout: 30m / recoveryTimeout: 10m
kubectl get cm -n kueue-system kueue-manager-config -o jsonpath='{.data.controller_manager_config\.yaml}' | grep -A3 -E '^\s*#?\s*waitForPodsReady:'
# JobSet：失败策略与 backoffLimit
# JobSet 名：kubectl get jobset -n $NS；默认取 env.sh 的 $JOBSET_NAME
kubectl get jobset $JOBSET_NAME -n $NS -o jsonpath='{.spec.failurePolicy}{"\n"}{.spec.replicatedJobs[*].template.spec.backoffLimit}{"\n"}'
# 期望：{"maxRestarts":10,"restartStrategy":"Recreate","rules":[{"action":"RestartJobSet",...,"onJobFailureReasons":["BackoffLimitExceeded"]}]} 和 0
kubectl get jobset $JOBSET_NAME -n $NS -o jsonpath='{.status.restarts}'        # 已用掉的重启次数，到 maxRestarts 就终态失败

⚠️waitForPodsReady 可能是注释掉的

  • 实测集群的 kueue-manager-config 里整段 waitForPodsReady 是注释掉的（#waitForPodsReady: / # timeout: 5m / # recoveryTimeout: 3m）。
  • 以 # 开头即没生效，按 03 §3.2 改好重启 → 见经验教训第 34 条。
  • 改 failurePolicy = 删了重提；waitForPodsReady 集群级，改完 kubectl rollout restart deployment -n kueue-system kueue-controller-manager，影响集群上所有作业。

读图：被驱逐时 Kueue 重切全部切片；RestartJobSet 不重切（05 §5.2 修正）。

情况 要点
GKE 切片控制器不自愈 FAILED 切片 靠 Kueue 删了重建 → 见经验教训第 39 条
驱逐原因 kubectl get events 看不到 Evicted… 后跟 events is forbidden
交付前核 RBAC kubectl auth can-i create events -n $NS --as=system:serviceaccount:kueue-system:kueue-controller-manager 应为 yes
TAS 把 DiskPressure 当节点故障（EvictedDueToNodeFailures） → 见经验教训第 42 条
恢复路径已知 bug 要 kueue-slice-controller ≥v0.8.0-203 + kueue-tpu-ac 新版本（以 Google 确认为准）才修复。本章演练用的是 v0.8.0-200，不含这两项修复；交付前须升级并重跑本章恢复演练（待办），版本结论见 09 D10。本章所有 MTTR / 各段耗时都是在早期版本上测的，升级后须复测

各层超时：按触发先后排

一次故障要等负责它的那一层超时到了才暴露。各层超时互相不知道对方，没有谁短谁长的约定。下表是先例集群（一整个 TPU pod）上实测或工单里查到的值，按触发先后排（「无」排最后）：

# 超时 值（先例） 哪层 到点后发生什么 建议 出处
1 Kueue TAS 对节点 DiskPressure 的宽限 0 s 调度 立即驱逐；4x8x8 占满整个 cube，没有节点可换，只能整片重来 先防 core dump 写满盘（见经验教训第 42 条）
2 MegaScale 跨片 hang 检测 5 min 多片同步 终止作业，整体重启 —
3 jax shutdown barrier ／ Orbax restore 300 s ／ 300 s，两者赛跑 恢复 一个 coordinator 断连，其余 peer 白等 300 s 🚧 Google 未给建议值
4 Orbax 里的 jax 初始化（写死，不看 MaxText 设置） 900 s 存档 — 只能改代码
5 Orbax 存档 timeout_secs 1,200 s 存档 存档报超时 —
6 jax_distributed_initialization_timeout 1,800 s 初始化 一次坏的重新准入要约 30 min 才暴露 Google 建议 300–600 s ；经验教训第 44 条
7 megascale_topology_discovery_timeout 4,000 s（约 67 min） 初始化 拓扑对不上（INVALID_ARGUMENT）也每 10 s 重试，直到超时 调小前先和 Google 确认 ；经验教训第 44 条
8 TensorStore 单请求 deadline 无 存档 一个挂住的请求只能等外层超时 —

读法：

  • 最外层（第 7 行）最慢，最内层（第 8 行）没有超时。先例里靠人工 suspend 才没等满 4,000 s。
  • 自己能补的一层是驱动看门狗：全部 pod Running 后 N 秒内没人打出 jax.devices() returned 就删 JobSet、收证据（06c §6.10 第 8 条）。
  • 版本一换，值就可能变。使用方的表按交付 BOM 的版本重新核一遍 [推断]。

7.3故障演练

要证明的：停一台 VM → JobSet 重启 → Kueue 避开那台重切。 步骤：

  1. 起带 MTC 的多片任务，跑过至少一次本地检查点。
  2. 注入故障。实测时用过（§7.4）：手删 Slice 2 次、instances.stop 1 次、instances.delete 3 次、simulateMaintenanceEvent 1 次；没有把杀 pod 当注入（删挂住的 worker-0-0 是救火，见下「杀一个 worker pod」）。
停一台 VM
  • gcloud compute instances stop <节点名> --zone=$ZONE，实测（3 片演练）：
  • 读图：全程不用人动，坏切片被自动换成新切片；instances.delete 与 simulateMaintenanceEvent 同样约 16–20 s 发现。
  • 上一代 TPU 上：所在 Slice → FAILED（"Partition is in failed state"）、Job BackoffLimitExceeded，不重叠的不受影响；节点恢复后仍 FAILED、要删了重建。

模拟计划维护

  • GKE 文档的「手动开始维护」走 GKE 流程（taint、驱逐、再请求 GCE） 源https://docs.cloud.google.com/kubernetes-engine/docs/concepts/handle-disruption-gpu-tpu。

  • 另一轮在 2 × 4x4x4（无 MTC）上复测：+2 s 整个 JobSet 挂起、+24 s 两片在原 cube 同名重建、+60 s 重新准入、+67 s 32 个 pod 全 Running，JobSet restarts 仍是 0 → 见经验教训第 38 条。
杀一个 worker pod

故障 谁先反应 切片会不会重切 从哪层恢复
杀一个 worker pod JobSet：BackoffLimitExceeded → RestartJobSet（39 s） 不重切 原地重启 → 本地层。生产作业上 10+ 片十多次注入（exec 杀训练进程和删 pod）全部原地恢复、都从本地层读回（恢复点都落在本地存档的步数上）；演练中跨 cube 挂住的条件不同，见表下

演练中「杀 pod 跨 cube 挂住」的条件不同（3 × 4x4x4，缩小版 MoE 模型，JIT）：

  • 唯一一次删 pod 是删 worker-0-0 救火：那一代在删 Slice 后已跨 cube 挂住（47 个旧 pod 没删净，84 次 conflicting rank）。
  • 后两代建 pod 时仍有 32 / 17 个旧 pod 活着，replica 跨 3 / 3 / 2 个 cube，照样挂住，最后手删 JobSet 才清掉。
  • 该次演练的条件：core dump 开着（旧 pod 2–6 min 才删净）、Kueue v0.17、没打 device-id 补丁；「RestartJobSet 也会跨 cube」是推断（演练时没开 Kueue 的详细日志，看不到分配过程）。
  • 生产作业上那批注入是 10+ × 4x8x8、AOT、有补丁，注入打在健康的一代上；core dump、落在哪些 cube、旧 pod 删没删净、Kueue 版本未核。所以只能说「健康一代上杀 pod 能原地恢复」，不能说「跨 cube 挂住已解决」。

7.4b 走一遍：10+ 片 × 256 芯里坏一个 cube，备件 cube 顶上

结论先看
  • 上游 MaxText 换 cube（硬件坏、维护）时本地层用不上，恢复点（RPO）＝ checkpoint_period，不是本地层的 20 步。带上 device id 配对补丁后，10+ 片二十多次恢复（其中原地重启十几次，其余为驱逐重建、换片 / 人工重建，见 07a）全读本地层（07a §7a.3）；这是绕过办法，上游未合入；在你使用的代码版本上演练通过前，按持久层周期定 RPO 和演练预期。
  • 现在就能做、不改代码的三件事见 P0：容器里 ulimit -c 0、准入后核 cube、按持久层周期定 RPO。
  • 让换 cube 也能读本地层，要改 MaxText / Orbax 的恢复逻辑，属于上游改动。

把 §7.3、§7.4 的实测串成一个交付场景。规模：10+ 片 × 4x8x8 = 数千芯、数十个 cube、片数 × 64 台 host；一片 = 4 个 cube = 64 台 host。 各段耗时取自 3 片演练，放到 10+ 片是推断，标在表里。

稳态时 MTC 在做什么

  • 本地层：每 20 步，每台 host 把自己那份分片（权重 + 优化器状态 + 步数 + 数据迭代器状态）写进 /local（ramdisk）。
  • 列：多片训练按片做数据并行，10+ 片各存一整份同样切分的状态。片内同一位置的 N 台（N = 片数） host 手上的分片一模一样，这 N 台叫一列。
    • 这要求片内不再做数据并行。生产任务正是如此（ici_fsdp_parallelism: 512、ici_data_parallelism: 1），一列就是片内同位置的 N 台。
      • 3 片演练的配置不一样：片内还有 4 路数据并行（ici_data_parallelism: 4、ici_fsdp_parallelism: 32），一份完整副本只占 4 台。真正同分片的是 runtime index 模 4 相同的 12 台，不是模 16。
  • replicator：每台 host 上的 MTC 组件，把本地存档复制给 peer（/peers/N），并按 MTC_BACKUP_INTERVAL_STEPS 备份到 GCS（非标准格式）源公开 MTC 文档「Replicator」。
  • 持久层：MaxText 自己每 checkpoint_period（演练 40 步）往 GCS 写一份标准 Orbax 检查点。

读图：顺利时打断到新 step 约 6 min；红框那条岔路是 半小时到一个多小时 的来源；黄框那条岔路是「换 cube 时本地层用不上」。

其余各片为什么能落回原地

「落回原地、存档还在」不是哪个组件特意保证的，是四个环节各自确定性、串起来的副作用：

  1. Kueue 挑 cube：每次都挑当时空闲健康 cube 里分区号最小的。坏 host 所在的 cube 只剩 15 台，装不下一组 16，整个跳过。空闲池没变，选出来的还是那批，坏的那个由下一个分区号顶上。空闲池变了（别的 cube 刚空出来）就不一定。
  2. pod 落到哪台节点：按 rank 对号入座。cube 集合和顺序没变，每个 pod 就回到同一台节点。旧 pod 没删净时会 rank 冲突，Kueue 改贪心乱塞，对号全错，还会跨 cube（见经验教训第 42 条）。
  3. 存档为什么还在：/local 挂的是 MTC CSI 驱动管理的节点内存盘，不是 pod 的 emptyDir。pod 删了重建，节点上的存档原样留着。
  4. 缺的谁来补：replicator 按 runtime index 给每台 host 准备「自己那份」，本机有就用本机，没有就从同列 peer 或 GCS 备份灌回。3 片演练换 cube 的 6 次恢复，48/48 台都拿到了 .restore 目录，数据层面每次都是完整的。
  • 但「落回原 cube」≠「每个 pod 回原节点」：备件的分区号插在哪，决定后面多少片换主人。换了主人的 host 由 replicator 从同列补齐，数据仍然完整；真正挡住读本地的是编号校验（下一小节）。
  • 两套编号别混：runtime process index（JAX 运行时发，落回原 cube 不变）和 distributed id（GKE MTC 组件写进 /local/jax-init-info.txt，按节点名排，节点集合一变就重排）。

为什么备件 cube 一进来，本地层就用不上

  1. 坏的那片换进一个备件 cube，其余各片多半落回原 cube，数据也由 replicator 补齐了（上一小节）。
  2. rank server 按节点名发编号；新 cube 的节点名不同，排序一变，不只是那 16 台，排在它后面的 host 编号都会挪（3 片换 1 个 cube 时 10–28 台被拒收）。
  3. MaxText 从最新步往回走，问「所有 host 的本地层都能用吗」；一台说「我手上是另一列写的」就全体放弃本地层，去 GCS 找最近的持久层步数。
  4. 所以换 cube 时的恢复点（RPO）= checkpoint_period，不是本地层的 20 步。演练时把「落回原 cube」和「换 cube」分开量。
  • 演练配置片内还有数据并行，第 3 步的拒收里有一部分是校验把列算严了，数据本身没错。生产配置片内不做数据并行，这道校验的列算法本身是对的；换 cube 时本地层能不能用，要在 10+ 片上演练确认。
  • 换 cube 也能读本地层需要上游改动；在你使用的代码版本上演练通过前，交付按持久层周期估丢步。
  • 「回到原节点」不是能指望的前提：停机、删机、维护时 Kueue 一定会避开坏 cube（§7.3 表）。

这样不行：本地层恰好在最常见的故障里失效

  • 硬件坏 → Kueue 一定换 cube（§7.3 表）→ 本地层用不上。本地层只在「软件崩、原地重启」时生效，而那正是它最不需要的场景。
  • MTC 要换来的两样东西都落空：读回快（3 片 3 s 对 21–33 s），和恢复点密（20 步对 40 步）。

怎么修

数据本来就在同列的其余各片里。让换 cube 也能读本地层，要改 MaxText / Orbax 的恢复配对逻辑（按分片认领，或找一片本地完整的读本地、再广播给其余片），属于上游改动，使用方不用自己改代码。修好前按下面 P0 做，RPO 按持久层周期定。

7.5备件 cube 与维修现实

  • 有备件机制：交付时留出备件 cube，坏了的 cube 由备件顶上（§7.4b）。
  • 维修由 Google 负责：坏主机进入 REPAIRING，从数小时到数天不等，使用方不用处理硬件。一条坏 ICI 链路 = 一台坏 host，整个 cube 不可用。
  • 使用方要做的：
  1. 最大任务 ≤128 cube；Σ 配额 ≤ min(128, 健康 cube − 备件 S) × 64，每天重算（03 §3.5）。
  2. 每天统计：健康 cube 数、15/16 的 cube 数（领先指标）、REPAIRING >12 h 的 VM。
  3. VM 反复坏：02 §2.5 recreate-instances 重建一次；同一宿主机再坏，带证据联系 Google（08 §8.5）。
  4. 替换节点回来后核对标签（gke-tpu-partition-*、gke-tpu-slice、gke-tpu-topology）→ 见经验教训第 50 条。

7.6「exit 0」不等于训练成功

⚠️要数 step，不看状态Completed 只说明退出码是 0；只能数 completed step: 行数（06c §6.5）。

三种「成功退出但没训练」：

  • MTC replicator 初始化失败（下图）。
  • 基准测试 exit 0 但结果只在 GCS，stdout 无数字。
  • SIGTERM 也是 exit 0：送到训练进程时 MaxText 以 0 退出，JobSet 判 Completed 后不再重启；而且抢占时默认不存盘（显式存盘策略替换掉了抢占触发的保存）。修法：致命错误改非零退出码（可以改成 exit 3）＋ podFailurePolicy 配 RestartJobSetAndIgnoreMaxRestarts；补回抢占存盘；terminationGracePeriodSeconds 30 → 90 → 见经验教训第 44 条。

每次任务结束核对 [推断]：

# worker-0-0 = replica 0 的 0 号 pod（选择器同 06-jobset.sh 的 w00）；JobSet 名默认 $JOBSET_NAME

说得出（先自己答，再点开对答案）

  • 为什么坏一台要全部重切？
    多切片全有或全无：workload 被驱逐 = 全部切片重切，TAS 不能只换坏片；JobSet 重启不重切
  • MTC 两层各存在哪？
    本地层在每台 host 内存的 ramdisk /local，持久层在 GCS HNS 桶
  • 恢复最慢的是哪一段？
    不是切片（64–106 s），是 TPU 初始化挂住：旧 pod 没删净就放新 pod，rank 冲突，一片撒到多个 cube，一代挂 12–13 min
  • 为什么同一次演练第一次读回 step 60、第二次只读回 step 40？
    第一次落回原 cube，本地层可用；第二次三个 cube 全换，36/48 台本地副本被列校验拒收，退回持久层
  • JobSet Completed 能当成功吗？
    不能，要数 step 数
