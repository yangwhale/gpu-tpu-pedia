这个专题要回答的一个问题

MLA、GQA、SWA、DSA、NSA、CSA、HCA、DeltaNet、GDN、KDA、Gated MLA……

名词多到像是各搞各的。但它们其实在解同一道题，而且只有三个旋钮可以拧。

讲完这个专题，看到任何一个新变体，应该能立刻说出： 它在拧哪个旋钮、省了什么、赔了什么。

这一节的目标不是记住这些名词，是拿到一把尺子。名词一年换一批，尺子不换。

第 零 节

一切从长上下文说起 —— 两条独立的动机

这两条要分开讲。 它们指向同一批技术，但出发点完全不同， 混在一起讲就变成了名词罗列。

0.1 线索 A · 硬件账算不过来

上下文一长，KV cache 就爆。

它的增长是双重的：随序列长度线性增长，又随层数线性增长。 而且它跟参数不一样 —— 参数是固定的一次性开销，KV cache 是随用户输入长度涨的。

用一个大家已经熟悉的形状来砸体感：就用专题一那个 V3 （61 层、hidden 7168、128 个头、每头 128 维）。 假设它用的是最朴素的 MHA，128K 上下文，bf16 存：

每 token 每层    2 × n_h × d_h  = 2 × 128 × 128 = 32,768 个数
每 token 全模型  × 61 层                        = 1,998,848 个数
                × 2 字节                        = 3,997,696 B = 3.81 MiB
128K token       × 131,072                      = 523,986,010,112 B
                                                 = 488 GiB

一个用户、一段 128K 的输入，KV cache 488 GiB。

摆三个对照，让这个数字站住：

对照物数值于是
一块 TPU v7 device 的 HBM94.74 GB ≈ 88.23 GiB一个用户的 KV 就要 5.5 个 device 装
V3 的全部权重（671 B × 2 B）1.342 TB ≈ 1250 GiB单用户占权重的 39%；三个并发用户就超过权重本身
同样形状换成 GQA-830.50 GiB16 倍，但还是装不进一块卡
同样形状换成 MLA（V3 真实方案）8.58 GiB56.9 倍

⚠️ 这个 488 GiB 是「假如 V3 用 MHA」的反事实数字，不是 V3 的实测值。 而且这里沿用了 V3 论文比较表的口径（K、V 都按 d_h=128 算）； V3 真实的 K 每头是 128+64=192 维，所以严格算 MHA 基线还会更大一点。 讲的时候要说清楚这是自己按公式推的、口径是什么 —— 这门课自己的规矩：推出来的数字必须带推导链。

推理场景更狠：并发用户越多，KV cache 线性叠加。 权重是所有用户共享的一份，KV cache 是每人一份。 所以 KV cache 不是显存里的一项开销，它直接决定了你能同时服务多少人 —— 这一条到专题六会变成 batch size 的硬上限。

这一条是工程账：不解决它，长上下文根本上不了线。

0.2 线索 B · 信息本身不需要那么多

这条更有意思，也更少被讲。

一个 128K 的序列，真的需要 128K 份独立的 KV 吗？

几个可以摆出来的观察：

  • 注意力矩阵实测是极其稀疏的 —— 绝大部分权重集中在很少的位置上， 剩下的近乎为零。那么把那些近零的算出来，算的是什么？
  • Attention sink —— 模型会把大量注意力"停放"在序列最开头的几个 token 上， 跟内容无关。这说明注意力权重里有一部分根本不是在做检索
  • 远近有别 —— 邻近几十个 token 的关注是密集、细粒度的； 几万 token 之外的关注是稀疏、粗粒度的。 凭什么用同一套精度去处理这两种？
  • 于是：压缩（远处的多个 token 合并成一个）、 稀疏（只挑相关的看）、分层（近处精细远处粗糙）都变得合理

这一条是信息账：即使显存无限，把全部算力花在一个高度冗余的矩阵上也是浪费。

0.3 两条线的关系

A 说「必须省」，B 说「可以省而不太亏」。

这两句话缺一不可：

  • 只有 A，你得到的是一堆有损压缩的权宜之计，效果掉了只能认
  • 只有 B，你没有动力去付 kernel 那么难写的代价
  • 两条合起来，才解释了为什么这个方向在过去三年里投入了这么多人 —— 它同时是一件不得不做和做了不太亏的事

所有变体都活在这两条线的交汇处。 一个变体好不好，就看它在 「省了多少（A）」和「亏了多少（B）」之间落在哪。

第 一 节

先解决一个误会：那个矩阵从来没被存下来过 —— FlashAttention

⭐ 2026-09-04 从原来的第七节提到这里，并且展开了一大截。 理由：上一节刚算出 488 GiB 和 32 GiB 两个吓人的数， 不先说清「那个大家伙根本不落地」，后面所有「怎么少算」的讨论都建在恐慌上。 而且顺序反过来讲，逻辑更硬： 「怎么算」这条路已经被走到头了，剩下的省法只能去改「算什么」 —— 三个旋钮正是从这句话长出来的。

1.1 它跟三个旋钮不是一类东西

三个旋钮改的都是算什么。FlashAttention 一个字都不改数学 —— 它改的是怎么算。

三个旋钮FlashAttention
改什么算什么（模型变了）怎么算（模型没变）
要不要重训通常要完全不用
相互关系彼此权衡，开了这个就得放弃那个跟谁都能叠，而且必须叠
效果由什么决定数据、任务、长度纯粹是硬件的访存层级

⭐ 一句话定位：三个旋钮解决的是「这个矩阵太大了，能不能少算点」； FlashAttention 解决的是「这个矩阵根本不用存下来」。两条路都要走。

1.2 它删掉的是哪一项

朴素写法是三步：① 算 S = QKᵀ ② 对 S 做 softmax 得 P ③ 算 O = PV。

三步之间，那个 L×L 的 S 每次都要落一趟 HBM： 写 S、读 S、写 P、读 P —— 三个步骤，四趟。

而这个 S 有多大：128K 上下文、单个头就是 131072² × 2 B = 32 GiB，一层 128 个头。

FlashAttention 把三步融成一个 kernel：S 分块在片上算完， softmax 用在线归约边走边更新最大值和求和项，S 整项消失。

⭐ 所以三笔账的形状是所有算子融合共有的： FLOPs 一分不省，省的全在「中间产物不落地」这一行。

1.2b ⭐ 那张经典图：内循环、外循环 —— 以及 FA2 为什么把它掉了个个儿

FlashAttention 论文那张图，画的是两层循环： HBM 里躺着 Q、K、V、O，SRAM 是旁边一个小方块； 外层循环搬一块进 SRAM，内层循环扫过另一边的所有块。

⚠️ 但那张图画的是第一版的顺序，而第二版把它换了过来 ——  这个「换」本身，比图更值得讲。

第一版：外层是 K／V，内层是 Q。

for j in K/V 的每一块:              # 外层
    把 K_j, V_j 搬进 SRAM
    for i in Q 的每一块:            # 内层
        把 Q_i、O_i、m_i、ℓ_i 从 HBM 读进来
        算这一格，更新 O_i、m_i、ℓ_i
        再把 O_i、m_i、ℓ_i 写回 HBM

⛔ 看内层那三行：O_i 和那两个统计量每一轮外循环都要读进来、写回去一次。 为什么躲不掉？—— 因为下一块 K／V 还会碰到同一个 Q 块， 它的输出没算完，只能先存回去。

第二版：把两层对调。

for i in Q 的每一块:                # 外层 ← 换成了 Q
    把 Q_i 搬进 SRAM，O_i、m_i、ℓ_i 就地清零
    for j in K/V 的每一块:          # 内层
        搬 K_j, V_j 进来，算，就地累加进 O_i
    整个内层跑完，才把 O_i 写出去一次

⭐ 两个后果，都很硬：

  1. O_i 和那两个统计量在整个内层循环里一直待在片上，一次都不落 HBM。
  2. 不同的 Q 块之间彻底独立 ——  可以直接铺到几百个执行单元上，互相不用通信。

⭐ 一句话记住它： 外循环放谁，谁的中间状态就不用来回搬。 而 attention 里「需要被累加到最后」的是 O，所以外循环必须放 Q。

1.2c 同一个原则，在 warp 这一层又用了一遍

这件事在块内部还发生了第二次 —— 而且这一次是官方原话：

  • 第一版：把 K 和 V 切给 4 个 warp，Q 大家共用（叫 sliced-K）。 ⛔ 于是每个 warp 都得把中间结果写进共享内存、同步、再加起来 ——  这些读写拖慢了前向。
  • 第二版：反过来，把 Q 切给 4 个 warp，K 和 V 大家共用。 ⭐ 每个 warp 算出自己那一片 QKᵀ，直接乘共享的那片 V 就得到自己那片输出 —— warp 之间完全不需要通信。

⭐⭐ 两个尺度，同一条判据： 切「要被累加的那一维」就得合；切「各自独立出结果的那一维」就不用合。 attention 里前者是 K／V（它们在求和号里面），后者是 Q（每行输出各管各的）。

⚠️ 这条判据的用处远不止 attention ——  任何融合 kernel 在分工时，先问一句「我切的这一维在不在求和号里」。

1.3 ⚠️ 在线 softmax 不是免费的 —— 它是后面 35% 那个数的根

softmax 要减最大值才数值稳定，而最大值要看完整行才知道。 在线归约的做法是：每来一块就更新一次 running max 和 running sum， 并把已经累好的输出按比例重标定一次。

⛔ 这里有个几乎人人都会踩的误会：压力不在那两个 running 值上

「在线 softmax 只要存一个最大值和一个求和项」—— 这句话是对的， 而且它们确实很小：每行各一个标量。一个 bq = 512 的 Q 块， 两个加起来也就 4 KB 量级。

真正占地方的是 S = Q@Kᵀ 那一整块。 它的形状是 [bq, bkv] —— 512 × 512 的 fp32 就是 1 MB， 2048 × 2048 是 16 MB。比那两个 running 值大两三个数量级。

而且它不是存一次就完了：每来一个 KV 块就重新生成一整块。

所以卡住的是 S 的生命周期，不是那两个数。

一个 KV 块内，S 要连着走完四步才能扔： ① MXU 产出 → ② 沿着行求最大值 → ③ 减掉它再取指数 → ④ 喂给第二个矩阵乘。

这四步里它一直是活的。 ②③ 是向量单元的活，而 ① ④ 是矩阵单元的活 ——  矩阵单元想开始下一块，可它的输出还被 ②③ 占着。

⭐ 再加上流水线：要让下一块的矩阵乘和这一块的向量运算重叠， 就得同时留住不止一块 S。 于是「一块」变成「好几块」。

📌 ② 那一步在 TPU 上还额外贵一点：行方向的最大值是一次跨 lane 归约， 而 lane 正是硬件那 128 的方向。归约越慢，S 活得越久。

这条链在 1.6 会变成一个具体的数字。

1.4 块开多大 —— GPU 那边是一堵墙

块大小不是调着玩的旋钮，它由片上暂存的容量直接顶死。

GPU 侧：一个线程块最多拿 227 KiB 共享内存。 装三块 128×128 的 bf16 tile（Q／K／V）就是 3 × 128 × 128 × 2 B = 96 KiB， 再留双缓冲，基本到顶。

而块开不大，代价是 K／V 被重复读 —— 重读次数 ≈ 序列长度 ÷ Q 块大小。 所以那 227 KiB 不只是「装不下」，它通过块大小间接决定了 HBM 流量。

⚠️ 顺带拆掉一个常见误解：标准 FlashAttention 前向不需要跨块归并。 每个执行单元拿走一个 Q 块，自己走完整条 KV 循环，在线 softmax 在块内就闭合了。 需要合的只有两种：KV 也被切开时（长上下文解码那类做法， 要跨切片重新对齐最大值和求和项），以及反向（对 Q 的梯度要跨块累加）。 所以 GPU 的代价在「分」，不在「合」。

1.5 ⭐ TPU 那边是三堵墙 —— 而且「块越大越好」是错的

TPU 侧对应的是 Splash Attention。它的灶台看着大得多 （Ironwood 每个 TensorCore 64 MB VMEM，一颗 chip 两个核 = 128 MB）， 但块反而不能随便开大。

JAX 里 Splash Attention 的默认块是 128 × 128， 而且源码里挂着一句 TODO：「以后按启发式选更好的参数」。

我们自己在 Hunyuan3-295B 上扫过这个参数（seq = 4096，v7 64 芯片， 完整数据见 tpu/Hunyuan3-295B-Pretraining/TUNING-v7.md）：

块大小KV 方向切出几块结果
2048（甜点）2 块228.4 TFLOP/s/device
40961 块VMEM 直接爆（爆在反向）
4096（compute 压回 2048）1 块−11.5%
512（照抄官方长上下文配置）8 块−1.0%

三堵墙，方向各不相同：

  1. 往上是容量墙 —— 再开大一档就装不下，而且先爆的是反向那一侧
  2. 往上还有第二堵，常常比容量更早撞到：并行度 —— 块一大，KV 方向只切得出一块，那一维的流水直接塌掉。 ⭐ 这一堵最反直觉：装得下，却更慢。
  3. 往下是碎块开销 —— 每块的固定开销（mask 检查、running max/sum 更新、 pipeline stage 切换）摊不动
⚠️ 一条可迁移的教训：块大小要看 block / seq 的比例，不是绝对值

那个 512 不是我们瞎试的，是官方 tpu7x benchmark 里的值 —— 但那份配置是给 max_target_length = 131072 调的： 512 相对 131072 是 1/256；到我们 seq = 4096，512 就成了 1/8。 跨序列长度照抄配置会反向优化。

我们记下的经验规则是「块 ≈ seq/2」，可证伪版本是 「换 seq = 8192 时最优块应当变成 4096」—— ⚠️ 这一条尚未验证。

⭐ 所以两边的墙不是「硬件 vs 调参」，是一面 vs 三面： GPU 那边容量一堵墙顶死，方向反倒清楚 —— 能开多大就开多大； TPU 那边最优往往不在最大处，得在三面之间找那个点。

1.6 ⭐ 融合之后，它还是只跑到 35% —— 三层原因，都不是配置问题

这是这一节最该带走的一段：FlashAttention 不是终点。 我们在 v7 上量到 splash attention 占 23% 的时间、效率只有 35.5%，全场最低。

① 记账口径：报出来的那个百分比，分子是虚高的。 XLA 给 splash 记的 FLOP 是不折 causal 的全量 4·b·s²·h·d。 所以 32.8–39.0% 这个区间是拿虚高的分子算出来的，真实执行效率比它更低。

⚠️ causal 跳过上三角是节省，不是又一道要乘上去的折扣 —— 它只造成记账错位。这两件事最容易混。

② 形状锁死 50%：MXU 是 256×256，而 head_dim = 128 只吃得下一半。

matmul形状浪费在哪
QKᵀ[q_len, 128] @ [128, kv_len]收缩维只有 128 → 废一半
PV[q_len, kv_len] @ [kv_len, 128]输出维只有 128 → 废一半

两个矩阵乘各撞一次，所以整个算子的 MXU 利用率封顶 50%。 Google 侧的结论是明确的：head_dim = 128 时 MXU 利用率无法超过 50%， 没有办法绕过。

③ 为什么连 50% 都到不了 —— 回到 1.3 那条链。 持有 Q@K 输出（也就是整块 S，不是那两个 running 值）的寄存器， 在最大值和减法完成前不能释放，于是不断堆积 → 寄存器压力 → spill 到 VMEM → MXU 停在等数据载回。 一句话：VPU 跟不上 MXU。

⭐ 这也解释了 1.5 那三堵墙里最反直觉的一堵为什么存在： 块开大 → S 那一块跟着变大 → 生命周期更长、更容易 spill。 「装得下」和「跑得快」在这里是两回事。

⭐ 三层叠起来的结论很硬： 形状锁死一半、寄存器压到 35%、记账口径还让它看着比实际好看。 这三层没有一层是配置能救的 —— 要么改 head_dim，要么改 kernel 的数据流。 （我们试过的那条出路是把矩阵乘全转置，见 TUNING-v7 的附录。）

⚠️ 还有一条方法论：同一份 profile，不同工具页的百分比不可混用

「HBM 受限占多少」—— 一个工具页说 35.6%，另一个说 19.5%。 破案的钥匙是两者的 self-time 合计正好差 2.00 倍， 而 v7 恰好是 2 device/chip。分母不是同一个东西，分子上的百分比自然对不上。 ⇒ 判瓶颈用 roofline 那一页，归因到算子用 op stats 那一页； 引用任何百分比都要写清出自哪个工具页。

1.7 这一节留下的那句话

「怎么算」这条路，到这里基本走到头了。

中间产物已经不落地，块大小已经贴着三堵墙，而算子仍然只跑到三成多 —— 剩下的空间不在「怎么算」里，只能去改「算什么」。

⭐ 下一节的三个旋钮，就是「改算什么」的全部可能位置。

第 二 节

分类学：只有三个旋钮

这是这个专题的骨架。把所有名词收进一张表：

旋钮在改什么代表
① 每个 token 存多少减少 KV 的份数或维度MQA → GQA → MLA → Gated MLA
② 每个 query 看多少限制范围或动态挑选SWA · NSA · DSA · CSA / HCA
③ 换一套数学用固定大小的状态代替不断变长的 KV线性注意力：DeltaNet → GDN → KDA
①+②+③ 混着来不同层用不同方案Hybrid：V4 的 CSA+HCA、K3 的 KDA+Gated MLA

⭐ 前两个旋钮省的是同一样东西的两个不同侧面： 旋钮 ① 让每份 KV 更小，旋钮 ② 让读的份数更少。它们可以叠加。

⭐ 旋钮 ③ 是换赛道：它不再有"随长度增长的 KV"这个概念， 代价是把无损的检索换成了有损的状态压缩。

⭐ 为什么恰好是三个

不是凑出来的。回到注意力那个式子，一个 query 要做的事只有三步：

①  从每个位置取出一份 K、一份 V        ← 存什么、存多大
②  跟哪些位置算，然后加权求和           ← 求和的范围有多大
③  用 softmax(qKᵀ/√d) 做这个加权        ← 用哪种运算

三个旋钮就是这三步各自可以动的地方。 除此之外没有第四个位置可以动 —— 除非你不改算什么、只改怎么算，那就是 FlashAttention —— 那是第一节刚讲完的事。

这张表建议做成板书，讲完每个支线回来填一格：

第 三 节

旋钮①：每个 token 存多少

2.1 MHA → MQA → GQA：一个连续旋钮

  • MHA：每个头各存一份 K/V。128 个头就是 128 份
  • MQA：所有头共用同一份 K/V。省 128 倍，但质量掉
  • GQA：分成 g 组，组内共用。g = n_h 退化成 MHA，g = 1 退化成 MQA

⭐ 值得强调的是「GQA 是一个连续旋钮」这件事本身 —— 它不是一个新机制，是把 MHA 和 MQA 之间的空白填上，让你可以按需要选一个点。 这门课后面会反复见到这个套路：把一个二选一变成一个可调的连续量。

代价说清楚：省的是 KV 的份数，赔的是表达能力 —— 本来 128 个头可以各自关注不同的东西，现在被迫共享。

2.2 MLA：不砍头，改成低秩压缩

  • KV 不再按头存，而是压成一个 512 维的隐向量（d_c = 512）， 用的时候再用上投影矩阵升回 128 个头
  • 位置信息单独走 64 维一路 RoPE（d_h^R = 64）
  • 所以每 token 每层只存 512 + 64 = 576 个数 —— 对照 MHA 的 32,768 个，56.9 倍
  • 出处：V3 论文 §4.2 超参一节，n_h=128, d_h=128, d_c=512, d_h^R=64, 61 层

代价：用计算换显存。 多了一对降维/升维的矩阵乘。 这句话在专题四 §1.2 会被再打一个折扣 —— ⚠️ MLA 的压缩在训练前向里其实不生效（K/V 会被解压出来算）， 它省的是推理时的 KV cache，不是训练时的激活。这是一个非常常见的误解。

⚠️ 落到硬件上有个反直觉的后果：MLA 在推理时可以把上投影矩阵"吸收"进 query 那一侧，从而改变整个计算的形状。同一个数学式子有多种算法实现， 选哪种取决于是 prefill 还是 decode。 这一条留到专题六。

2.3 ⚠️ 为什么 RoPE 必须单独走一路

这是理解 MLA 的关键一步，也是最容易讲糊的一步。值得花两分钟。

MLA 想做的事是：把上投影矩阵吸收掉，让推理时只需要读那个 512 维的隐向量。 数学上，qᵀ (W_UK c) 可以重写成 (W_UKᵀ q)ᵀ c —— 上投影跑到 q 那边去了， 于是 K 根本不用真的解压出来。

但 RoPE 一插进来这个重写就不成立了。 RoPE 是一个跟位置有关的旋转， 它作用在解压之后的 K 上；旋转矩阵夹在中间，W_UK 和 c 就分不开了。

所以 MLA 的解法是把这两件事拆开走两条路： 一路 512 维不带位置、可以被吸收；另一路 64 维专门扛 RoPE、老老实实存着。 576 = 512（可吸收）+ 64（不可吸收）。

⭐ 这个「因为要保留某个代数变换，所以把功能拆成两路」的动作， 在后面还会以别的面貌出现（V4 的部分 RoPE、K3 的 NoPE）。 值得当成一个套路记住，而不是当成 MLA 的一个实现细节。

2.4 Gated MLA

  • 在 MLA 的输出端加一个门控：gate = σ(W_g x)，逐元素乘在注意力输出上
  • Kimi K3 用的是全秩门控矩阵（K2 那代是低秩的）
  • 出处：K3 技术报告 §2.1.2

它的作用不是省显存 —— 门控不减少任何 KV —— 而是让模型能学会「这一层这个位置，注意力的输出干脆不要」。 放在旋钮 ① 里是因为它改的是 MLA 这一支的形状，但要讲清楚它省的不是显存。

第 四 节

旋钮②：每个 query 看多少

3.1 SWA（滑动窗口）

  • 每个 token 只看自己前面固定窗口内的（Mistral 7B：4096）
  • 最简单，KV cache 从随长度增长变成常数
  • 代价很硬：长距离信息只能靠层层传递间接到达 —— 第 1 层看 4K，第 2 层能间接摸到 8K，要跨 128K 得堆 32 层
  • 所以一般不单用，跟全注意力混排（见第六节）

3.2 Attention sink —— 一个现象，不是一个方案

这一段是全课少有的"实验发现改变了工程做法"的例子，值得单独讲。

StreamingLLM（arXiv 2309.17453）的观察：如果你朴素地做滑动窗口， 把开头那几个 token 的 KV 也滑掉，模型立刻崩。

而它们发现的解法简单到有点荒谬：留住最开头 4 个 token 的 KV 就够了 （论文原话："with just 4 initial tokens sufficing"）， 再加上滑动窗口，Llama-2 / MPT / Falcon / Pythia 就能稳定处理到 400 万 token， 比"滑窗 + 重算"这个可用基线快 22.2×。

为什么？因为 softmax 强制所有权重加起来等于 1 —— 模型有时候什么都不想看， 但它没有"弃权"这个选项，于是它学会了把多余的注意力倾倒在开头几个位置上。 那几个 token 不是在传递信息，它们是停车位。

⭐ 两个层次的教训，都要讲：

  1. 工程上：任何"扔掉一部分 KV"的方案，都必须先问「有没有扔掉停车位」
  2. 方法上：这个 bug 从公式上完全看不出来，只有把注意力矩阵画出来看才发现。 这是这门课反复要说的那件事 —— 量出来的和算出来的，是两回事

后续：DeepSeek-V4 干脆给每个头加了一个可学习的 sink logit， 直接加进 softmax 分母里，于是这一行的注意力总和可以小于 1，甚至接近 0。 把一个模型被迫发明的 hack，变成了架构里的一等公民。

3.3 NSA —— 「native」是什么意思

  • 三条支路并行：压缩（粗看全部）/ 选择（细看挑出来的）/ 滑窗（细看邻近）， 再用一个小 MLP + sigmoid 出的门控分数融合
  • 效果：64k 长度下，解码快 11.6×、前向快 9.0×、反向快 6.0×（arXiv 2502.11089）

「native」的意思是训练时就这么做，不是训练完再加的推理优化。 这个区别很重要，值得单独说三十秒：

推理期稀疏训练期稀疏（native）
模型知不知道自己会被稀疏不知道知道，权重是在稀疏条件下学出来的
掉点有，且难预测小得多，甚至能反超
能不能省训练成本不能能（上面那个 6.0× 反向）
代价无，随时可开关要重训，没法给已有模型打补丁

⭐ 这张表解释了后面一个反复出现的现象： 为什么这些新注意力方案总是跟新模型一起发布，而不是作为一个推理框架的开关。

3.4 DSA（DeepSeek-V3.2）—— Lightning Indexer

  • Lightning Indexer：一个极轻量的打分网络，为每个 query 挑出 top-k 个 KV
  • 打分式子 I(t,s) = Σ_j w_j · ReLU(q_j · k_s) —— ⭐ 用 ReLU 不用 softmax，纯粹是为了吞吐，论文自己这么说的
  • 头很少，而且跑在 FP8 上
  • k = 2048。128K 上下文下，参与主注意力的从 128K 降到 2K —— 64 倍
  • 复杂度从 O(L²) 变成 O(L·k)
  • 出处：arXiv 2512.02556

⚠️ 两个必须一起讲的细节，不然这个方案听起来像免费午餐：

  1. indexer 自己还是 O(L²)。 每个 query 要给所有 KV 打分才能挑 top-k。 省下来的是「主注意力的 O(L²)」，换来的是「一个便宜得多的 O(L²)」。 省的是常数，不是阶。
  2. 它需要一个专门的训练阶段。 先冻住除 indexer 之外的全部参数， 让 indexer 去拟合主注意力自己的分布（把各头注意力加起来、L1 归一化， 当作 indexer 的学习目标）。稀疏是学出来的，不是规则定出来的。

3.5 ⭐ CSA + HCA（DeepSeek-V4）—— 压缩率按距离分层

这是线索 B「远近有别」最直接的体现，也是这一节的高潮。

CSA（Compressed Sparse Attention）

  • 每 m = 4 个 token 的 KV 压成 1 个 entry，然后在压缩后的 entry 上做 DSA
  • V4-Pro top-k = 1024，V4-Flash top-k = 512
  • 压缩不是简单平均：用了两套交错的压缩序列（互相错开半个块）， 各带一组可学习的位置偏置，在 2m 个元素上做 softmax。 ⭐ 交错是为了不让块边界成为信息断层 —— 一个 token 总在某一套里落在块中间

HCA（Heavily Compressed Attention）

  • 压缩率 m′ = 128，远大于 CSA 的 4
  • 而且不做稀疏：压完之后在全部 entry 上做密集注意力
  • ⭐ 逻辑很干净：都压了 128 倍了，剩下的条目本来就没几个，再挑就没意义了

两者混排：V4-Pro 前两层用 HCA，之后 HCA 与 CSA 交替； V4-Flash 前两层用纯 SWA。

效果（都是 V4 技术报告自己给的）：

口径数字
1M 上下文，vs DeepSeek-V3.2单 token 推理 FLOPs 27%、KV cache 10%（V4-Pro）
同上，V4-FlashFLOPs 10%、KV cache 7%
以 BF16 GQA-8（head dim 128）为基线，1M 上下文KV cache 降到约 2%

⭐ 最后那个 2% 值得停一下算给学生看：同样形状的 GQA-8 在 1M 下是 244 GiB， 2% 就是 不到 5 GiB —— 一百万 token 的上下文，KV 装得进一块卡的零头。 对照本节开头那个 MHA 的 488 GiB（那还只是 128K）。这就是三年的进展。

⚠️ 这里还叠了一层跟注意力机制无关的优化：KV 混合精度存储 —— RoPE 那几维用 BF16，其余用 FP8，光这一项就"近乎减半"。 报告一个总收益的时候，要能拆出哪几分是机制带来的、哪几分是精度带来的。

3.6 ⭐ 这一支的共同结构

讲完四个方案，回头把它们叠在一起，会看到同一个骨架：

                 ┌─ 一条"粗看"的路：压缩 / 全局，保证不漏
一个 query 的注意力 ┼─ 一条"细看"的路：挑出来的 top-k，保证准
                 └─ 一条"近处"的路：滑动窗口，保证局部连贯
  • NSA：三条都有，显式的三支路 + 门控融合
  • DSA：主要是中间那条（top-k），配一点局部
  • CSA/HCA：HCA 是粗看，CSA 是细看，另外还挂了一条 n_win=128 的滑窗支路
  • SWA 单用：只有第三条 —— 所以它单用不行

⭐ 看到一个新的稀疏注意力方案，先问它这三条路各占什么位置。 这比记住它叫什么有用得多。

第 五 节

旋钮③：换一套数学 —— 线性注意力

4.1 基本换法

softmax 注意力必须把所有 K 都留着，是因为 softmax 的分母要对所有位置求和 —— 你没法提前把它们合并。

把 softmax 去掉（换成某个可分解的核函数），求和就可以重排：

softmax 版： out_t = Σ_{s≤t} softmax(q_t·k_s) v_s      ← 必须留下所有 (k_s, v_s)
线性版：     S_t   = S_{t-1} + k_t v_tᵀ                ← 一个固定大小的状态
            out_t = q_t S_t

于是：

  • 复杂度 O(L²·d) → O(L·d²)，对长序列是数量级的差别
  • 没有随长度增长的 KV cache —— 只有一个 d_k × d_v 的状态矩阵
  • 推理时它就是一个 RNN：读一个 token、更新一次状态、吐一个输出

代价说死：状态大小固定 → 信息必然有损。 序列越长，往同一个矩阵里塞的东西越多，长程精确检索（"第 30 万字提到的那个电话号码"） 会力不从心。这不是实现问题，是这个换法的性质。

4.2 谱系：四步，每一步都在修上一步的一个具体毛病

步名字补了什么出处
1朴素线性注意力把 softmax 拆掉，换来固定状态Katharopoulos 等, arXiv 2006.16236
2delta rule状态只加不减 → 写满就糊。改成「先擦掉旧的，再写新的」Schlag 等, arXiv 2102.11174（2021）
3GDN（Gated DeltaNet）delta rule 不会主动遗忘 → 加一个遗忘门，让陈年旧事自然衰减arXiv 2412.06464（2024-12）
4KDA遗忘门是个标量，全部通道同一个速度 → 升级成 per-channel 向量Kimi Linear, arXiv 2510.26692（2025-10）

⚠️ 两处容易记错的出处，讲的时候要说对：

  • delta rule 不是 2024 年的东西，是 Schlag 等 2021 年那篇 Linear Transformers Are Secretly Fast Weight Programmers（可上溯到 1990 年代的 fast weight programmer）。2024 年那篇（arXiv 2406.06484）做的是 把它并行化，这是另一件事、也是很关键的一件事 —— 见 §4.4
  • KDA 是 2025 年 10 月的 Kimi Linear，不是 2026 年

⭐ 第 4 步为什么值得单独说：标量遗忘门意味着「整个状态一起变旧」。 per-channel 意味着不同特征维度可以有各自的遗忘速度 —— 有些通道记语法（该快忘），有些记实体名（该慢忘）。 KDA 还把它做成了一个特殊的 DPLR（对角 + 低秩）形式， 正是因为这个特殊形式，才配得出一个比通用 DPLR 便宜得多的分块并行算法。 表达力和可算性是一起设计的，不是先设计再优化。

4.3 ⚠️ 它不是「更快的 attention」，是另一个模型

这是本节最重要的一句话，也是最容易被听众误解的一句。

三个旋钮里，只有旋钮 ③ 改变了模型能表达什么：

  • 旋钮 ①②：改的是存法和看多少，理论上你还能指着某个历史 token 说 "注意力权重在这儿"。检索是显式的
  • 旋钮 ③：历史被碾进了一个矩阵。你无法指着状态里的某一块说 "这是第 3 万个 token"。检索是隐式的、有损的

所以：

  • 它不能给已有模型打补丁，必须从头训
  • 评测上要特别看 needle-in-a-haystack 这类精确检索任务， 平均分好看不代表这一类不塌
  • 也正因如此，几乎没有人纯用线性注意力 —— 全都是混合（第五节）

4.4 硬件视角：串行的状态怎么榨出并行度

这一段是我们的角度，别人的课不会这么讲。

S_t = S_{t-1} + ... 是逐 token 串行的。而加速器要的是宽而规整的并行。 训练一个 100 万 token 的序列，串行跑一百万步 —— 直接不用想。

解法叫 chunkwise parallel：块内并行、块间串行。 把序列切成长为 C 的块，块内用矩阵乘一次算完，块与块之间才传递状态。 于是并行度从 1 变成 C，串行步数从 L 变成 L/C。

⭐ C 怎么选，是一个纯硬件问题：

  • C 太小 → 串行步数多，而且每步的矩阵乘太瘦，算力吃不满
  • C 太大 → 块内那个中间矩阵放不进片上内存（SRAM / VMEM），要往 HBM 上倒
  • 所以 chunk 大小是被片上内存容量顶死的 —— 跟专题一 splash attention 的块大小是同一类问题

这条路有多难走，看两个信号：

  • K3 为了 KDA 专门写了 CUTLASS 的 FlashKDA kernel， 因为块内并行和块间串行交替进行时 SM 会空转
  • 长序列训练还要 KDA Context Parallelism —— 标准的序列并行做法是把各段 局部结果直接相加，但这对 KDA 不成立，因为 delta rule 的状态更新是 token 相关的矩阵连乘，前一段的影响不是简单的加法

⭐ 一句话收：线性注意力在纸上是 O(L)，在硬件上是一场 kernel 战争。 我们在 TPU 上写过 KDA kernel，这里有一手的坑可以摆。

第 六 节

旋钮④（其实是元旋钮）：混合

5.1 为什么混合几乎是唯一的答案

单用任何一个旋钮都有一个致命短板：

单用短板
SWA跨不了长距离
纯线性精确检索塌
纯全注意力KV 和 FLOPs 都爆

混合的逻辑很朴素：全局层负责精确长程检索，线性/窗口层负责局部与效率，各司其职。 关键在于全局层不需要很多 —— 只要有几层能做无损检索， 信息就能沿着残差流传给其余层用。

5.2 配比：3:1 是怎么来的，以及它不是定律

模型配比出处
Kimi LinearKDA : 全注意力 MLA = 3 : 1（48B 总 / 3B 激活）arXiv 2510.26692
Kimi K3KDA : Gated MLA = 3 : 1（69 KDA + 24 MLA = 93 层）arXiv 2607.24653 表 1
Ling-3.0-tinyKDA : MLA = 3 : 1模型卡
Ling-3.0-flashKDA : MLA = 5 : 1模型卡
一篇系统性消融建议区间 3:1 ～ 6:1arXiv 2507.06457

⭐ 三件事要讲清楚：

  1. 3:1 是消融出来的，不是推出来的。 Kimi Linear 的消融里， 0:1（纯全注意力）反而表现不好 —— 这个结果比"3:1 最好"更有意思： 加线性层不只是省钱，它可能还带来了别的东西
  2. 同一家不同规模就换了配比（Ling 的 tiny 3:1 / flash 5:1）—— 配比是超参，跟规模和数据有关，不要背下来当常识
  3. 区间比点值可信。 记 "3:1 到 6:1 这个量级" 就够了

5.3 ⭐ K3 的 NoPE —— 混合带来的一个意外红利

这是全节最漂亮的一处，值得留三分钟。

K3 的全注意力（Gated MLA）层完全不加位置编码（NoPE）： 没有 RoPE，没有 YaRN，什么都没有。

为什么敢这么做？ 因为它们中间夹着的 KDA 层， 本身就是靠递归的衰减和门控在编码顺序 —— 一个天然带时序的算子。 位置信息由线性层提供，全注意力层只管检索。

三个后果，一个比一个实在：

  1. 不用调 RoPE 外推。 模型直接外推到 1M，不需要任何位置编码的重标定 —— 长上下文扩展里最烦人的一块调参，直接消失了
  2. MLA 层在推理时可以退化成纯 MQA。 位置编码没了， §2.3 里那条"不可吸收的 64 维"也就不存在了 —— 上投影可以完全吸收
  3. KV cache 最多降 75%（Kimi Linear 的数字）， 1M 上下文下 TPOT 从 11.48 ms 降到 1.84 ms，6.3×

⭐ 这才是"混合"真正的意思：不是"两个方案各跑一半凑合用"， 而是让每一层只做自己擅长的事，然后把别人不用做的事一并省掉。 一个架构选择（混合）解开了另一个看起来完全无关的约束（位置编码）。 这门课想教的就是这种"看见约束之间的连接"的能力。

第 七 节

代价：没有免费的午餐

一张表把所有方案摆在一起：

KV 显存计算量长程质量kernel 复杂度能否给已有模型打补丁
MHA基准基准基准简单—

要讲透的四个取舍：

  1. 省显存 ≠ 省计算。 MLA 省了显存但增加了计算；DSA 省了计算但 KV 还在那儿。 这两个是不同的资源，问"省了多少"之前先问"省的是哪一样"
  2. 训练时省和推理时省是两回事。 MLA 的压缩在训练前向里不生效； NSA 的 native 意味着训练时也省。一个方案属于哪一类，直接决定它能不能被采用
  3. 不规则访存的代价常常被低估。 稀疏方案在纸面上是 64 倍， 落到硬件上是 gather、是不连续访问、是 kernel 难写 —— 实际加速比远小于理论值。这一点我们有实测可以摆
  4. ⭐ 收益是有天花板的，因为注意力只是账单的一部分。 把注意力砍到 0，剩下的 MoE、MLP、通信一分钱没省。 专题一那条曲线说得很清楚：短上下文下注意力只占 12%， 这时候你把它优化到极致，端到端也就快 10%。 所有这些技术的价值都随上下文长度而涨 —— 讲的时候必须带上"在多长的上下文下"， 不然那些倍数全是耍流氓
第 八 节

落到硬件（本专题的落点）

回到全课那条主线：每一个变体都是被硬件逼出来的，也都对硬件提出了新要求。

变体它假设了什么硬件条件条件不成立会怎样
MLA算力相对充裕、显存相对紧张算力紧张的机器上，用计算换显存这笔交易不划算
稀疏（DSA/NSA/CSA）gather 不太贵对规整访存友好的加速器反而吃亏 —— 纸面 64 倍拿不到
线性（KDA）片上内存够放下 chunk 的中间量chunk 被迫调小 → 并行度掉 → 优势被吃掉
长上下文 + MoE 同时上HBM 带宽够两边分all-to-all 与 KV cache 抢同一份带宽

一句话收尾：注意力的变体史，就是一部 「在显存、算力、访存规整度三者之间反复搬家」的历史。 早期搬显存（MQA/GQA/MLA），中期搬算力（稀疏）， 现在在搬访存规整度（chunk 化的线性注意力）—— 而访存规整度是最难搬的那一样。
