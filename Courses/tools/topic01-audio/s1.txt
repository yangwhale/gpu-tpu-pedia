[friendly] 上一节我们把尺子立好了，底牌也发了。这一节走第一步：一个字，是怎么变成一串数的。

[curiosity] 先把落点放在前面。这一步什么都还没算，只是查了一次表。可等它走完，显存已经掉了一块。掉了多少，我们一笔一笔算出来。

[focus] 一句话进来，第一件事是被切成 token。token 不等于字，也不等于词。中文里常见的字，大多一个字就是一个 token；英文里一个长单词，可能被拆成两三段。

[casually] 切完之后，每个 token 就是一个整数编号。在 V3 上，编号从零排到十二万九千二百七十九，因为它的词表一共有十二万九千二百八十个词。

[realization] 这个数有什么讲究吗？请看这张图，把同一代几个模型的词表放到同一根轴上。它一点都不特别，跟 Llama 3 的十二万八千几乎是同一个点。两年多里主流词表涨了四到八倍，十二万九千二百八十就落在这一代的主流区间里，不是魔法数字。

[thinking] 词表大小在权衡什么？往大做，同一句话能切成更少的 token。序列短了，后面注意力里那个跟长度平方挂钩的项，立刻跟着往下掉，这一条第二步会兑现。另外，罕见的词不再被拆成碎片，专有名词、代码符号、生僻字，都能整块进模型。

[seriously] 往大做赔的有三样。第一，进门和出门的两张表变大。第二，每个罕见词分到的训练样本变少，学不好，极端情况会变成一碰就让模型出乱码的死词。第三，出口要在整张词表上算 softmax，越大越贵。

[focus] 但第一条在 V3 身上几乎不成立。表有多大，只跟词表乘以宽度有关，跟层数无关。十二万九千二百八十乘以七千一百六十八，再乘以两张表，大约十八亿五千万个参数，只占六千七百一十亿的百分之零点二八。模型越大，这笔占比越小；换成一个小模型，同一张词表能吃掉快一半的参数。所以小模型不敢做这么大的词表，V3 敢。真正拉住 V3 词表的，是后两条。

[friendly] 编号有了，接下来要变成向量。向量有多宽？七千一百六十八。请记住这个 d，它是这个模型的主干道宽度，后面每一步都要用到。

[thinking] 七千一百六十八是怎么定的？这里要把两件事分开。一半是硬约束：它等于一百二十八乘以五十六，也等于二百五十六乘以二十八。TPU 的矩阵单元是一百二十八或者二百五十六见方，GPU 那边也要求维度按八或者六十四对齐。七千一百六十八两边都整除，放到哪里都不会因为补齐而白算。

[seriously] 另一半是取舍：同样的参数，做宽还是做深。这个 DeepSeek 从来没公开说过。对齐只解释了为什么不是七千，也不是七千二；它解释不了为什么不是六千一百四十四，或者八千一百九十二，那两个也一样整除。所以别把约束说成理由。

[realization] 下面是这一步真正的动作。从编号变成向量，默认用的不是乘法，是查表。

[casually] 模型里存着一张大表，十二万九千二百八十行，七千一百六十八列。请看这张图，你的编号是多少，比如八千四百九十二，就把第八千四百九十二行抽出来。没有乘，没有加，按下标取一行，算力是零。

[thinking] 数学上，这等价于拿一个 one-hot 向量去乘这张表。可真这么乘，一个 one-hot 向量长十二万九千二百八十，只有一个位置是一。十三万一千零七十二个 token 摞起来，光这个几乎全是零的中间矩阵，就要三十一点五六个 GiB。同一个式子，换一种算法，代价差出几个数量级。

[amused] 不过要说准一点：真实的训练框架里，这一步经常还是做成矩阵乘，最合理的解释是，它把一次不规则的取行，变成了一个规整的稠密矩阵乘，能沿着词表那一维切开分给多张芯片，反向也跟着变成矩阵乘。这么做，每个 token 大约多花一点八五个 GFLOP，整条序列加起来，也只占整步算力的百分之零点四六，淹没在噪声里。所以准确的说法是：算力是零，只对查表那条路成立。

[focus] 但它一点都不便宜，贵的是显存。那张表本身，十二万九千二百八十乘以七千一百六十八，九亿两千六百六十八万个参数。bf16 每个两个字节，一点七三个 GiB。这是权重，从模型加载到卸载全程常驻。而且出口那张表是另外一份，不是同一块显存，两张合起来三点四五个 GiB，第六步走到出口时再算。

[thinking] 顺便说一句，这一步只有内容，没有位置。这个 token 排在第几位，是到第二步在注意力里用 RoPE 现场加进去的，下一节会看到它有多麻烦。

[seriously] 第二笔账。查完表，十三万一千零七十二个 token，每个都变成一个七千一百六十八维的向量。摞在一起，十三万一千零七十二乘七千一百六十八，bf16 下是一点七五个 GiB。

[thinking] 这个数跟长度是线性的。换成四千个 token，只有五十六个 MiB；到十二万八千，整整三十二倍。线性还算好消息，第二步会遇到一个跟长度平方一起长的东西。

[seriously] 两笔加起来。一张表，一点七三个 GiB；一个张量，一点七五个 GiB。一共三点四八个 GiB。

[realization] 而我们，还没有进第一层。

[focus] 最后交代一件事，它决定了后面六十一层该怎么理解。

[contemplative] 刚才那个一点七五个 GiB 的张量，不是用完就扔的中间结果。它就是残差流，一条从第一层通到第六十一层的主干道。每一层都从它上面读一次，算完再写回去一次。所以七千一百六十八不是某一层的内部尺寸，是全程主干道的宽度。后面算激活显存，公式都是同一个：token 数，乘以七千一百六十八，乘以字节数。

[curiosity] 还有一个特别容易想当然的地方：七千一百六十八，要不要能被注意力的头数整除？

[thinking] 在标准的多头注意力里，宽度必须等于头数乘以每头维度。请看这张图上面一行，头拼起来正好把残差流填满，一个字节不多不少。

[realization] V3 不是这样。请看下面一行：一百二十八个头，每头输出一百二十八维，乘起来一万六千三百八十四，是七千一百六十八的两倍多，没有任何整除关系。注意力内部先撑到一万六千三百八十四，最后由一个输出投影矩阵收回七千一百六十八。

[casually] 这个输出投影是一万六千三百八十四乘以七千一百六十八，一亿一千七百四十四万个参数。一层注意力的权重一共一亿八千七百一十一万，它一个就占了百分之六十三。它本身没什么特殊，纯粹是因为跨着这道口子，输入输出两头都宽。

[seriously] 更要紧的是后果：头数和宽度从此各按各的道理定，不必互相迁就。这正是第二步 V3 能把一百二十八个头全部保留下来的前提。

[warmly] 回头看这一步：切成 token，查表取行，摞成一条七千一百六十八宽的主干道。什么都还没算，三点四八个 GiB 已经没了。下一节进第二步，全课最重的一段：注意力，以及 KV cache 的那场仗。

[friendly] 这一节就到这里，大家有问题吗？
