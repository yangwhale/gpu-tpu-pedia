> 抓自 [stanford-cs336.github.io](https://stanford-cs336.github.io/)，Spring 2026 版，2026-08-21。
> 课名 **Language Modeling from Scratch**，5 学分，19 讲 + 5 个作业。
> 讲师 Percy Liang / Tatsunori Hashimoto。全部讲座有 [YouTube playlist](https://www.youtube.com/watch?v=JuoVZkPBiKk&list=PLoROMvodv4rMqXOcazWaTUHhq-yembLCV)。

带学生走完开发一个语言模型的全过程：预训练数据的收集清洗、Transformer 构建、
训练、评测、部署。

## 五个对我们的编排启示

### ⭐ 1 · 「算账」在第 2 讲，不在最后 —— 这是最重要的一条

第 2 讲就是 **resource accounting：FLOPs、显存、arithmetic intensity**。
第 1 讲讲完 tokenization，第 3 讲才讲架构。也就是说：

> **CS336 把「算账」当成基础工具教，不是当成结论讲。**

学生从第 2 讲起就会算，此后每讲一个架构都能立刻算一遍它的代价。
到第 5 讲讲 GPU / TPU 时，学生已经有了「这个设计要多少 FLOP、多少带宽」的语感。

**我们的大纲 v0.1 把性能工程放在第 5 部分（九个模块里的第五个），这个位置太靠后了。**
按 CS336 的做法应该拆成两半：
- **算账的方法**（怎么数 FLOP、怎么估显存、什么是 arithmetic intensity）→ 挪到很前面，紧跟第一课
- **调优的实践**（profile、XLA flag、通信隐藏）→ 留在后面

### ⭐ 2 · `arithmetic intensity` 就是我们要的那个量化工具

Chris 的理念第 2 条说「Attention 需要什么算力、MLP 需要什么算力」——
**arithmetic intensity（算术强度 = 计算量 / 访存量）正是这个问题的标准答案形式。**

我们大纲里只把「Attention 卡带宽、MLP 卡算力」当成一个要记住的现象，
但 CS336 把它变成一个**可以算的数**。有了这个数：

- 「为什么长序列解码卡带宽」→ 算一下 KV cache 的 intensity 就知道
- 「为什么 batch 越大越划算」→ intensity 随 batch 线性涨
- 「什么时候该上 FlashAttention」→ 因为它改变的正是访存量

**必须补进课程，而且要早。**

### 3 · 2026 版第 5 讲已经是「GPUs, TPUs」

Spring 2025 时这一讲只有 GPU，2026 加上了 TPU。**CS336 自己也在往 TPU 靠。**

但一讲能讲的深度有限。**这恰好界定了我们的空间**：
我们不是补 CS336 的缺，而是把它一讲带过的东西展开成半门课
—— 而且带着真实的 64 卡 v7 实测数据。

### 4 · 我们完全缺的两块：Data 和 Post-training

CS336 19 讲里：**Data 占 2 讲 + 1 个作业，Post-training/Alignment 占 3 讲 + 1 个作业。**
我们的九个模块**一块都没有**。

这需要一个明确决定（见下面「要拍板的问题」）。

### 5 · 每个作业都能判分

`test_*.py` + `adapters.py` 胶水层 + leaderboard。
学生写完能立刻知道对不对，不用等人批。

**我们的练习也应该这样设计** —— 尤其是前半程那些能在笔记本上跑的。
「跑得通测试」比「读完文章」是强得多的完成标志。

## 两边的分配比例对照

| 内容 | CS336（19 讲） | 我们大纲 v0.1（9 模块） |
|---|---|---|
| 模型本体（tokenizer / 架构 / MoE / attention 变体） | 4 讲 · 21% | 第 0 部分，约 1/9 |
| **算账与系统**（资源核算 / GPU-TPU / kernel / 并行 / 推理） | **6 讲 · 32%** | 第 1、2、3、5、7 部分，约 5/9 |
| 规模与评测（scaling laws ×2 / evaluation） | 3 讲 · 16% | **无** |
| 数据 | 2 讲 · 11% | **无** |
| 后训练 / 对齐 | 3 讲 · 16% | **无** |
| 客座 | 2 讲 | — |

**读法**：我们在系统侧的比重更高（那本来就是我们的价值所在），
但**模型侧的绝对量不能低于 CS336** —— 地基不牢的话，后面系统侧的结论只能靠背。

而 scaling laws / evaluation / data / 后训练这四块，我们目前是完全空白的。

## 三个要拍板的问题

### 问题 1 · Data 和 Post-training 要不要讲？

- **A · 完全不讲**，课程边界就是「预训练 + 系统」，明说这是有意的取舍，需要的人去看 CS336
- **B · 各给一讲概览**，讲清楚它们在整个链条里的位置和对系统的要求
  （比如数据管线本身就是个吞吐问题，RL 训练的通信模式跟预训练完全不同）
- **C · 完整覆盖** —— 那这门课就变成 CS336 的中文重制版了，工作量翻倍，
  而且我们在这两块没有独家积累

**我倾向 B。** 理由：不讲会让人以为训完就完事了；讲全了又偏离我们的独特价值。
一讲概览既补上认知地图，又能自然接到我们真正擅长的系统侧
—— 我们仓库里其实有 RL 训练的实战材料（`gpu/rl-training/`、
以及 agentic RL 训练、GRPO 内部机制、RL 下的 MoE 并行等术语页），
从「RL 的并行策略跟预训练有什么不同」这个角度切进去，反而是我们的强项。

### 问题 2 · 「算账」要不要提到第二课？

按 CS336 的编排应该提。这样顺序变成：

```
第一课  大模型是什么          （已建）
第二课  怎么给它算账          ← FLOPs / 显存 / arithmetic intensity
第三课  Attention 与 MLP      （带着算账的能力回看这两个零件）
...
```

好处是第一课末尾那个「1750 亿参数 = 350 GB 权重」的钩子，
第二课立刻就给出了工具去算它。**衔接非常顺。**

代价是模型细节被推后了一课。

### 问题 3 · 练习要不要做判分

CS336 的 `adapters.py` + `test_*.py` 模式很成熟，可以照搬结构。
但要写测试就是真投入了 —— 值不值得，取决于这门课是给人**读**的还是给人**做**的。
