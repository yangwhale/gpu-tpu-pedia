配置 diff 的细账 （18 个 tile 键、为什么原配方的 1024 不是它真用的 tile）
  • tile 键一共 18 个，两份配置里都有；另外 6 个 *_batch_seq 两边都是 512，没变。真正变了值的是上表 12 个，再加 use_tokamax_gmm。
  • 原配方走 tokamax 那条实现时，tile 不读这 12 个键，是启动脚本另外注入的：编译出来的程序里写着 (512, 2048, 1536)。所以「1024 → 2048」不等于 kernel 真用的分块变了。
  • 出处：MaxText 把整份配置写进 TensorBoard 事件文件，两份逐行 diff；注入的 tile 从 profile 目录里的 HLO 读出来。

1.1　第一把尺子：MFU

MFU ＝ 每芯片实际 TFLOP/s ÷ 峰值。v7x 每芯片 BF16 峰值 2,307 TFLOP/s。 算 FP8 时，运算量照样按模型形状数（一次乘加记 2 次运算，和一个数占几个字节无关），分母也照样用 2,307，这样两种精度放在同一把尺子上。

每芯片 TFLOP/sMFU
公开的 MoE（BF16，Qwen3-235B／DeepSeek-V3）629.8／612.727.3%／26.6%
混元3 BF16（64 芯片，tile 调好）662.328.7%
混元3 FP8 原配方677.029.3%
混元3 FP8 改后1,014.844.0%
稠密 llama3.1-405B（BF16）1,261.454.7%

改后那一行一下子从 MoE 那一堆里跳出来，离稠密模型只差一截。怎么看出来的：每芯片 TFLOP/s ＝ MaxText 记的 每 device 每步运算量 3,981.54 TFLOP × 2（一颗芯片 2 个 device）÷ 步时。两份 FP8 的运算量一模一样，所以 MFU 涨多少，完全是步时短了多少。

MFU 的分母：2,307、2,057.5、4,614 各是什么 （同一个数换个分母就变）
  • 2,307：每芯片 BF16 峰值，MaxText 和本课都用它。每 device 是它的一半 1,153.5。
  • 2,057.5：XProf 的 Roofline 页写的是每 TensorCore 1,028.75 TFLOP/s，乘 2 是每芯片 2,057.5，比 2,307 小 10.8%。拿 XProf 的利用率和 MaxText 的 MFU 比，先换成同一个分母。
  • 4,614：每芯片 FP8 峰值。FP8 的 MFU 要是除它，数会凭空减半（1,014.8 ÷ 4,614 ＝ 22.0%）。报 FP8 的 MFU 一定写明分母。
  • 出处：v7x 规格（每芯片 BF16 2,307、FP8 4,614 TFLOP/s，2 个 TensorCore）见 Google Cloud 公开文档 cloud.google.com/tpu/docs/tpu7x；TUNING-v7 §⁠1.1（分母）、§⁠1.2（公开实测表）、§⁠2.7（XProf 常数）；1,014.8 ＝ 2 × 3,981.54 ÷ 7.847，677.0 ＝ 2 × 3,981.54 ÷ 11.761（本课复算）。
自己算一遍 （从 MaxText 写的 TensorBoard 事件文件读两个数，八行 Python）

1.2　第二把尺子：屋顶线

屋顶线回答「一个算子最快能多快」：横轴是算术强度（每从显存搬一个字节，做几次运算）， 左边斜坡受搬运带宽限制，右边平顶受算力峰值限制，两段交在拐点。

FP8 让一个数从 2 字节变 1 字节，两头各翻一倍：落在平顶上的矩阵乘，平顶抬高一倍；落在斜坡上的，要搬的字节减半，点往右挪一倍，沿斜坡也正好快一倍。 所以一个矩阵乘最多快一倍，而且只有矩阵乘吃这一倍：路由、按专家重排 token、逐元素运算、通信，都不在这张图上。

右边那条曲线怎么来的 （1 ÷ (1 − p/2)，以及反推 p）
  • 一步时间 ＝ 矩阵乘 p ＋ 其余 (1 − p)。FP8 最好的情况是矩阵乘砍半、其余不变：新步时 ＝ p/2 ＋ (1 − p)，快 1 ÷ (1 − p/2) 倍。
  • 反过来，实测快了 s 倍，矩阵乘至少占 p ≥ 2 × (1 − 1/s)：DeepSeek-V3 s ＝ 1.214 → p ≥ 35%；稠密 405B s ＝ 1.528 → p ≥ 69%；混元3 改后 s ＝ 1,014.8 ÷ 662.3 ＝ 1.532 → p ≥ 69%。
  • 前提是 FP8 只动矩阵乘。原配方还把专家权重先量化成 FP8 再做 all-gather，通信字节也减半；但这份 profile 里没被计算盖住的通信每步只有约 0.2 s，算进去结论不变。

1.3　拿同类比一比

公开实测报的都是「同一个模型从 BF16 换 FP8，每芯片 TFLOP/s 涨多少」，所以混元3 也拿自己的 BF16（662.3）当起点。 这和第零节的 1.50 倍不是一回事：那个是拿 FP8 原配方当起点。

⭐ DeepSeek-V3（MoE）换 FP8 只多出两成，混元3 原配方只多出 2%。改后这一份比混元3 BF16 多出 53%，和稠密的 405B 一样。 要么改后这份把 MoE 的老毛病全治好了，要么有什么东西不对。

2.1　Overview：先下一句结论

⭐ 两份主核都没闲着（Duty Cycle 99.9%）：少掉的 3.9 秒出在主核干的活上，去 Trace Viewer 看它干了什么。

#是什么页面上读到什么（框按页面文字的位置画）
①Average Step Time平均步时：原配方 11,793.8 ms、改后 7,857.0 ms（XProf 按主机记的 3 步取平均，比 jit_train_step 中位步长 0.2–0.3%）

打开 profile 默认落在 Overview。它回答两件事：一步多长、主核有没有大段空着。Duty Cycle 是主核有活的时间占比，两份都是 99.9%。 停在 done 上等通信（2.5 讲 done）也算「有活」，所以它只说明没有大段空转，等了多少要去 Trace Viewer 里看。左栏其余几格见下面的 2.1B。

Hlo Op Profile 把主核上所有指令按类别归堆，每类给两样：TIME %（占主核时间的比例）和 FLOPS（这一类的利用率，下面细说怎么算）。 custom-call 是 XLA 不自己生成、直接调用的外部 kernel：这里就是用 Pallas 手写的 kernel，注意力（splash）和专家矩阵乘都在这一类（gmm 算前向和对输入的梯度，tgmm 算对专家权重的梯度，0.3 术语框）。 两份对比，custom-call 每步从 6,532.9 ms 掉到 2,969.9 ms（Op Stats 同口径，8 个 TensorCore × 3 步平均），一类就少了 3.6 秒，其他类加起来变化不大。

怪的是第三列：时间少了一半多，利用率从 53.39% 涨到 117.45%。利用率超过 100%，意思是这一类每秒做的运算比这页自己用的峰值还多。先别下结论，展开看是谁。

Op Profile 的 FLOPS 和 WASTED 怎么算 （两个式子，和页面逐位对上）
  • FLOPS 利用率 ＝ 记账的 FLOP ÷（实测时间 × 峰值）。实测时间来自 trace；记账的 FLOP 不是测出来的：XLA 自己生成的算子由编译器按形状算，Pallas kernel 由 kernel 作者在代码里自己报（pl.CostEstimate，编译后存在 HLO 里叫 cost_estimate）。
  • 这页用的峰值是每核 1137.1 TFLOP/s ＝ Roofline 页写的 1,028.75 TFLOP/s × Time Scale Multiplier 1.10537。Time Scale Multiplier 是 Roofline 页顶写的一个换算系数：这份 profile 里每个算子事件上挂着 1.15789 或 1.0 两种值（时长占比约 2:1），按时长加权就是 1.10537 （页顶 Apply Dvfs Scaling Factor 开关的说明：按设备当时的性能档换算；拨开它，Roofline 页的峰值就变成 1,137.15，和这页一样）；停 4 左栏 58.53 PFLOP/s ÷ 5,147.80% 反推出来是同一个数。
  • 按这个式子自己算一遍：三份 FP8 记在 custom-call 上的 FLOP 每步每核都是 3,966.1 TFLOP（下一小节拆开），原配方 custom-call 实测 6,541.8 ms → 53.31%，改后 2,972.8 ms → 117.32%；页面是 53.39% 和 117.45%，差在第二位小数（我们用 TPU:0 的 3 步，页面用 8 个核）。
  • WASTED ＝ 时间占比 ×（1 − max(FLOPS 利用率, HBM 利用率)）：又费时又没吃满硬件才算浪费。利用率过了 100%，括号里成了负数，页面就记成 0.0%——一颗没干活的 kernel，被判成「一点没浪费」。

    operational_intensity = flops_v2 / bytes_accessed       # 横坐标：自报的字节
hbm_bytes = 每条指令 memory_accessed_breakdown 里 HBM 那几项之和   # 没有这份账才退回 bytes_accessed
hbm_bw    = hbm_bytes / time                              # 表里的 HBM BW
flops_utilization  = measured_flop_rate / peak_flops
hbm_bw_utilization = hbm_bw / peak_hbm_bw
Bound by  = 利用率最高的那一项（Compute、HBM；TPU 上有 CMEM、VMEM 的字节时也一起比）

第三节把账对上了：少掉的 3.9 秒，九成是没算的专家矩阵乘。可「没算」到底是程序里哪一段没了？ profile 只记录发生了的事，没发生的不会在上面留下任何痕迹。要知道本来该有什么，得看程序本身：编译器最后交给芯片的那份 HLO。

4.1　HLO：编译器改写之后的程序

⭐ HLO 是 XLA 把你的 JAX 程序切分、融合、排好顺序之后的最终程序，一行一条指令、每个值都带形状。trace 上每个色块的名字，就是 HLO 里一条指令的名字。

HLO（High Level Optimizer 的中间表示）是 XLA 编译器内部的程序形式。你写的是一个 train_step 函数，编译器把它按 64 张卡切开、把一串逐元素运算融成一个 fusion、 在需要的地方插入集合通信、再排好执行顺序，得到的就是最终 HLO。它每行长这样：

名字 ＝ 类型[形状] 操作码(操作数, …), 属性…
gmm.27 = bf16[229376,1536] custom-call(…, get-tuple-element.14549, …), custom_call_target="tpu_custom_call"

第二行就是第二、三节里反复出现的那颗 gmm.27：输出 229,376 行 × 1,536 列的 bf16，操作码 custom-call 表示调用一个外部 kernel（这里是 Pallas 写的专家矩阵乘）。 trace 告诉你每条指令什么时候跑、跑多久；HLO 告诉你它吃什么、吐什么，以及程序里一共有哪些指令——包括 profile 里看不到的、根本没被生成的那些。

量化那一步两份一字不差，乘的 2 就是 448 ÷ 224（配置把权重的量化范围定成 ±224，FP8 最大能表示 448）。原配方确实先量化再收，收的是 FP8，比收 bf16 省一半字节； 改后并没有挪动量化，只是量化之后那条 all-gather 没了。

改后剩下的那几条 all-gather 是什么 （为什么不是 92 → 80）
  • 改后还剩 82 条 all-gather，形状里带 192 的只有两类：路由器那张 [4096,192] 的小权重（沿 4096 这一维收），以及 MTP 层（多 token 预测，主干 80 层之外的那一层）三份专家矩阵的 bf16 版 bf16[3,4096,1536] → [192,4096,1536]。
  • 后者两份程序里都有，op_name 是 convert_element_type 而不是 shard_map/all_gather：不是代码里写的那几行收的，是编译器按权重的切分自己插的（这两条 all-gather 带 is_spmd_generated=true，4.1 折叠块讲这个属性）。所以 MTP 层在两份里都是收齐了 192 个专家再算（4.5 再用到）。
  • 原配方循环外那一层的前向，3 份 FP8 权重是和别的权重（MTP 层、输出层）合在一条 all-gather 里一起收的：[3,1,4096,1536] → [192,1,4096,1536]，所以表里按形状数是 12 条、按指令数是 10 条。

4.6　回头看第三节的两个疑点

⭐ 改后 loop fusion 多出来的 276 ms，就是上面那个「其余行写 0」；循环外没缩水的 9 颗专家矩阵乘，是 MTP 那一层，它的专家权重由编译器收齐了。

第三节的疑点在 HLO 和 trace 里查到的结论
loop fusion 改后多 276 ms改后每层多出两类 loop fusion：前向 broadcast_select_fusion（op_name 末段 jit(gmm)/jit(_where)/select_n，输出 bf16[229376,4096]）每步 79 次、95.1 ms； 反向 select_add_fusion 每步 79 次、225.6 ms，里面是三个 select（同样来自 jit(gmm)/jit(_where)）加一个把两路输入梯度相加的 add_any。原配方那个 add_any 是单独一个逐元素算子（每步 135.5 ms，记在 non-fusion elementwise 里） 就是 backend.py 的补 0（jnp.where）：每层把 229,376 行里 189/192 的行写成 0，前向一次、反向和相加融在一起。loop fusion ＋ 276 ms 里，约 135.5 ms 是原来就有的那次相加换了类别（3.4 表里 non-fusion elementwise 同时 − 133.7 ms），净多出来的约 140 ms 才是补 0 本身
循环外 9 颗 gmm 没缩水，在哪一层中位步里循环外一共 21 颗专家矩阵乘：前向循环前 3 颗、反向循环后 9 颗，op_name 带 while/body，权重和梯度都是 [3,…]，每颗约 0.05–0.07 ms（循环剥出来的那一层，同样缩水）； 其余 9 颗 op_name 不带 while/body，梯度 bf16[192,…]，每颗 4.2–5.2 ms（TPU:0 上 3 步逐颗；3.3 的 Op Stats 是 8 个核的平均，所以写 4.2–5.0），调用栈经过 multi_token_prediction.py，权重参数名是 mtp_block/…/MoeBlock_0/wi_0 是 MTP 层（多 token 预测，主干之外的那一层）。它的专家权重由编译器按 bf16 收齐成 192 个（4.2 折叠块），走的不是那两行收和散，所以没漏，两份里一样慢

4.7　补上之后

⭐ 把收和散从 tokamax 那一支里提出来、两支共用，一步 12.501 秒，比原配方的 11.761 秒还慢 6%：「快了 50%」全部来自漏算。

修法就是把 ① 的 all_gather 和 ④ 的 psum_scatter 挪到 if 外面：只要声明了 weight_gather_axes 就收，前向收了反向就散。 补上之后的数来自混元3 调优记录（TUNING-v7 的 3.4.10 节）：一步 12.501 s，每芯片 637.0 TFLOP/s，原配方 11.761 s、677.0 TFLOP/s。 文档数 这一次没有留 profile，本课复算不了，只能照录。

这类错误为什么会静默 专家维 192 被切成每卡 3 个，而「3 个专家」对分组矩阵乘来说是一个完全合法的输入：kernel 只会认为这次就是 3 组。 如果切的是收缩维（比如 4096 那一维），形状就对不上，当场会报错 [推断]。把一个维度切小之后，下游还能把小的当成合法的输入用，错误就不会报出来——这时候能报警的，只有「快得不像真的」这一条。
第 五 节

对照：真变快长什么样？

📝 本节讲义

5.4　BF16 为什么没踩坑

⭐ BF16 的专家权重不是按「专家」那一维切的，而是按 4096 那一维切；编译器替你插了收齐（HLO 里看得到），不管走哪条分支，kernel 拿到的都是 192 个专家。

调优记录（TUNING-v7 3.4.10 节）把 FP8 那次漏算的触发条件写成三条，要同时成立。拿 BF16 的配置逐条对：

② use_tokamax_gmm=False，走 native 那一支成立成立（同一个改动）

两页的数对不上时：它们读的是同一份文件里的哪类原料

⭐ 这些工具页不是七个数据源，是同一份 xplane 的不同视图。数对不上，先查两边各读了哪一类：时长信运行时实测的那一类；flops、字节、行号这些编译期写好的数，可能是按形状估的。

上排是 fp8old 那一份 xplane 里实际装着的四类东西，计数是用 xplane_pb2 现读的：实线的一类是跑的时候录下来的（每个事件的起点、时长；分配器的每次分配和释放），虚线的一类是编译时就定下的（每条指令的类别、flops、字节、形状、op_name、源码行；整份编译后的程序）。 中排每页右上角的号就是它读哪几类。下排是本课碰到的四次「两页数打架」：⑤ 是 3.2 的 117%，⑥ 是 3.2 录屏停 3 和 Op Profile 左栏，⑦ 是 3.6 的显存，⑧ 是上面 Roofline 第 1 节的点。四次都是两边各读了一类，哪一页都没算错。

6.2　庆祝之前，先查三样

⭐ 数字漂亮的时候先查三样：尺子对不对得上、同样的活还在不在、有没有数超出物理上限。

查什么怎么查真快（BF16）漏算（FP8）
① 尺子换算成 MFU，和同类模型做同样改动的涨幅比+5%，和专家矩阵乘快 13% 折算下来对得上MoE 涨了稠密模型的 +53%
② 同样的活还在不在同一层并排；Op Stats 里关键 kernel 的次数；HLO 里集合通信按形状的条数；显存峰值那一刻的大块每一行都在，只是变窄小核上一类通信整块消失，收专家的 all-gather 12 → 0，循环里 [192,…] 的梯度块不见了
③ 有没有超出物理上限Op Profile 的利用率；单颗 kernel 的 FLOP rate、HBM 带宽和硬件峰值比49.62%117.45%，单颗 25 倍峰值

三样都过了，才轮到下一个问题：损失曲线和改之前对不对得上——那是数值正确性，profile 管不了，要跑足够多步去比。

6.3　自己抓一份、自己打开

⭐ MaxText 里打开 profiler=xplane 抓几步，把产物里的 tensorboard/ 目录交给 xprof --logdir，本课每一屏都能在自己的机器上开出来。

本课这 7 份不用自己抓，直接从 GitHub Release 下载：每个附件解压出来就是 <run>/plugins/profile/<时间戳>/<主机>.xplane.pb，和下面自己抓的产物是同一种目录结构。
