## 这门课给谁

**目标读者**：会写 Python、懂深度学习基本概念、在 GPU 上跑过训练，但**没碰过 TPU**的工程师。

**不是给谁的**：
- 想要 API 手册的 —— 那个看官方文档更快
- 只想跑通一个 demo 的 —— 直接去 `tpu/` 下找对应项目的 README
- 找论文解读的 —— 去 `Learning/`

**学完之后应该能**：
1. 看着一个模型和一批卡，判断出该用什么并行策略、装不装得下
2. 独立把一次预训练从零拉起来，包括数据、checkpoint、故障恢复
3. 拿到一份 profile，说得出瓶颈在哪、下一步该动哪个旋钮
4. 把一个 PyTorch 模型迁到 TPU 上，并解释清楚数值对不上时该怎么查

## 编排原则

写之前先把规矩定死，否则写着写着就变成文档堆砌。

**1. 每一章都从「一个具体的坑」开始，不从定义开始。**
不要「TPU 是一种 ASIC……」。要「你把 batch 调小了，VMEM 还是 OOM —— 为什么？」
定义在解决问题的过程中自然出现。

**2. 所有数字必须是实测的，并且标出在哪一代硬件上测的。**
仓库里已有的实测数据是这门课最值钱的部分。没实测过的推论要明确写「推测」。
——这条跟 `tpu/tpuguru` 里 `evidence` 分三档是同一个原则。

**3. 讲清楚「为什么错的直觉是错的」。**
最贵的知识都是反直觉的：降 batch 治不了 VMEM OOM；编译通过不等于装得下；
块越大不等于越快。每一条这样的知识都值一个小节。

**4. 边走边算，不留到最后总结。**
「算账」不是一门独立的课，是**每讲一个部件就立刻算它的代价**。
学会算 FLOP、算显存、算 arithmetic intensity 之后，每个设计选择都能自己推一遍
—— 这样结论是**算出来的**，不是背下来的。

**4b. 拆真模型，不讲通用架构。**
不讲"Transformer 一般长什么样"，而是拆 DeepSeek V3 这一个具体的模型，
所有数字取自它的官方 `config.json`。通用规律在拆的过程中自然浮现，
但**每个数都能对回一个真实字段**。

**5. 每章末尾有一个能真跑的练习。**
不能真跑的课程只是读物。练习要能在最小规模上完成，不要求读者有 64 卡。
能判分的（跑得通测试）优于只能读的。

**6. 中文先行。**
先把中文写透、迭代稳定，最后再一次性翻译。不要中英并行改。

## 课程序列

**顺序的依据**：先有模型，才有对硬件的需求，才有硬件的样子。
每一课只依赖它前面的课。

### 第一课 · 拆开 DeepSeek V3　🚧 大纲已立

[**→ 第一课**](第一课/)

不泛讲"Transformer 是什么"，而是**拆一个真模型**：
跟着一个 token 从分词一路走到出口，**每走一步就把账算一遍** ——
这一步产生多大矩阵、吃多少显存、要多少算力。

口径固定：**128K 序列、batch=1、bf16、只算前向**。
七站走完，"装不进任何一块卡"是**算出来的结论**，不是一句口号。

> 为什么是 V3 而不是 GPT-3：早就不是 175B 那个时代了。
> V3 是当下事实上的黄金标准，后来的开源模型基本都从它出发再改。
> 而且它一次把三件事做成了 —— MLA 压 KV、细粒度 MoE 压激活、FP8 压成本，
> **每一件都直接对应硬件上的一个瓶颈**，正好是这门课要建立的那条因果链。

### 后续（顺序待定，随第一课定稿再敲）

| 课 | 主题 | 要点 |
|---|---|---|
| 反向与一个完整 step | 把账补全 | 反向的 FLOPs、激活为什么要留、recompute 是个决策、优化器状态 |
| 硬件 | TPU 与 GPU | 芯片解剖、**HBM 与 VMEM 是两层内存**、chip vs device、ICI 与 3D torus、跟 GPU 对照 |
| 编程模型 | JAX 与 XLA | `jit` 到底做了什么、编译期思维、`shard_map` 与 mesh、怎么读 HLO |
| 并行策略 | 把它切开 | 四种切法、FSDP 在 TPU 上、MoE 的 all-to-all、**先选拓扑再调参** |
| 训练实战 | 从零拉起来 | MaxText 配置、数据管线、checkpoint、抢占与恢复、跑起来看什么 |
| 性能工程 | 从能跑到跑得快 | MFU 什么时候骗人、抓 profile、三种瓶颈、通信隐藏、XLA flag、**调参的天花板** |
| 精度 | FP8 与量化 | V3 的 FP8 训练、量化在哪里会毁掉收敛 |
| 推理 | 另一套约束 | prefill / decode 的根本差异、KV cache、静态形状与分桶、吞吐与延迟 |
| 迁移 | PyTorch → TPU | 三条路的代价、算子对不上、**数值验证方法论** |
| 数据 / 后训练 | 概览 | **刻意放最后** —— 跟模型架构不相关，只讲它们对系统提的不同要求 |

## 每一课的目录结构（约定）

**每一课都长成一样**，找东西不用想。新建一课时照抄这个骨架：

```
第N课/
├── README.md          这一课讲什么 + 大纲 + 练习
├── 教学材料/           ← 相关的东西都往这里放
│   ├── README.md          材料清单：哪来的、什么许可、能不能公开
│   ├── <来源>文字版/       抓下来的原文
│   ├── <来源>图/           渲出来 / 下载的图
│   └── ...                我们自己写的、画的
├── RENDER.md          （按需）图怎么生成的
└── *.sh               （按需）能重跑的脚本
```

### 三条规矩

1. **材料先进 `教学材料/`，别散在别处。** 想不清楚放哪就先扔进去，之后再归类。
2. **每样材料都要在 `教学材料/README.md` 里有一行**，
   写清楚三件事：哪来的、什么许可、**能不能进公开仓库**。
3. **产物入不入库，看重建成本。**
   - 小、稳定、但**重建要搭一套环境**的 → 入库（例如渲出的图）
   - 大、易变、或**一条命令就能重来**的 → 不入库（视频、编译产物、缓存）

   无论入不入库，**生成它的东西必须在库里**：脚本、抓取命令、场景引用。
