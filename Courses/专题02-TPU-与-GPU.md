## 这一版为什么重写

上一版的骨架是**顺着机器往下走**：出身 → 芯片 → 内存 → 互联 → 指标 → 范式 →
软件栈 → 擅长什么 → 实测。这是市面上所有硬件对比文章的写法，**逐层参观**。

问题在于，专题一不是这么讲的。专题一是**跟着一个 token 算账**，
每一步问同样四个问题，最后算出一堵墙。这门课的承诺是「算出来的，不是听来的」——
第二课换成参观，方法就断了。

**所以这一版继承同一套方法：不参观机器，接着算同一笔账。**

专题一结尾留下的其实是一张**需求清单**：

| 专题一算出来的 | 谁来回答它 |
|---|---|
| 要放下 **1.23 TiB** 的常驻权重 | **内存**（答案一） |
| 要算 **52.50 PFLOP** 的前向 | **计算单元**（答案二） |
| 要摊到 **14.3 个 device** 上，卡之间得说话 | **互联**（答案三） |
| 而且撞上了一堵 **94.74 GiB / device** 的墙 | 这堵墙本身，开场就还 |

三条回答完，会自然剩下第四个问题：**这些安排到底是谁做的决定** ——
运行时的硬件调度器，还是编译期的编译器。**这就是范式，也是真正的分水岭。**

### 更细一层：专题一那七步，各自撞的是不同的墙

⚠️ **这一课不能只拿 embedding 当例子。** 它是七步里**唯一算术强度为零**的一步 ——
只用它，整课会听起来像「TPU 的问题都是访存布局」，而真实的账不是这样。
**七步各撞各的墙，而且撞的是不同的墙：**

| 专题一的哪一步 | 它压的是硬件的哪一块 | 落在本课 |
|---|---|---|
| **入口** · 从文字到向量 | 纯带宽，**算术强度为零**；布局导致的读放大 | §2 |
| **注意力** · MLA / Flash | **片上内存容量** —— 整个 Flash 家族就是为它而生 | §2 |
| 同上 | **非 matmul 那部分**（softmax / 归一化）算力配比 | §3 |
| **Dense MLP** | **MXU 的主场** —— 形状对不齐就白扔 | §3 |
| **MoE 路由** | **数据相关的控制流** —— 矩阵单元完全做不了 | §3 · §5 |
| **MoE dispatch / combine** | **all-to-all** —— 拓扑说了算 | §4 |
| **层间 / 数据并行** | **all-gather · reduce-scatter · all-reduce** | §4 |
| **出口** · logits | 又一次纯带宽，外加一个**巨大的中间量** | §2 |

> **这张表就是专题二和专题一的接缝。** 不是「继承了方法」，
> 是**字面上接着那七步往下走** —— 每一步在模型侧算过账了，
> 现在看它在硬件侧撞的是什么。

**出身那段留着，但位置变了。** 它不再是第一章的内容，
而是开头抛出的一个**假设** —— GPU 从像素并行长出来所以灵活，
TPU 一开始就为矩阵乘造所以规整。后面四条回答，
**每一条都是对这个假设的一次验证**。

### 两条编排决定

**① 实测拆开，不当压轴。** 上一版把「我们跑过什么」压在最后一节。
这一版**谁的账算到哪，实测就跟到哪** —— 内存那节配布局放大与 Flash 的 tiling，
计算那节配 MXU 形状对齐与「慢 24 倍却被选中」，
互联那节配 NVL72 域内均匀的实测带宽与 all-to-all。

> **⚠️ 2026-08-31 修正：这条只对了一半，写的时候被迫拆成了两类。**
>
> **用来说明机制的实测跟着机制走**（上面那三处），这条站得住。
> 但**用来做跨平台比较的实测不能跟着走** —— 它得先有一把尺子，
> 否则读者拿到 854 对 662 只会当成「谁更快」。
>
> 所以最后不是「只留一节讲怎么比」，是**留了两节**：
> **§6 只立规矩、一个对比数字都不给**，**§7 才把两边的真数摆出来**。
> 中间那道墙是刻意的 —— 规矩先立，数字才有地方落。
>
> **代价是这一课从 60 分钟涨到了约 75 分钟**（见下方时间表）。

**② 重头戏是 TPU，但 GPU 要讲全。**
听众是熟悉 GPU 的人，**GPU 是锚点不是陪衬** ——
warp、SM、CUDA core、Tensor Core、L1/L2、NVLink、RDMA 都得讲到位，
**因为缺一个，TPU 那边对应的东西就说不明白**。
每一节的结构因此是固定的：**先讲 GPU 那一侧 → 再讲 TPU 那一侧 → 对照表 → 落点**。

**GPU 侧以 GB200 / NVL72 为主线，GB300 单开一节讲「下一代变了什么」。**

- **不用单机八卡那套讲** —— **NVL72 把 NVLink 域从 8 张扩到 72 张，
  「域内均匀、跨域断崖」这句话的尺度整个换了**，
  这是跟 TPU 的 ICI 最值得对照的一处（见 §4.2）
- **主线选 GB200 的理由是「我们真跑过」**：DeepEP、NCCL、RDMA 都有自己的实测；
  GB300 那边本仓库里大量条目还写着**待测 / 待确认**。
  拿一份没验证过的规格表当主线讲，**跟第一原则直接冲突**
- **换代不影响要讲的道理**：NVL72 拓扑两代完全一样，
  §4.5 那个「域内均匀 ≠ 集合通信均匀」的结论与代次无关

## 0 · 开场：先把上一课欠的那个数还了

专题一从头到尾用 **94.74 GiB / device** 当判 OOM 的线，
**但从来没解释过它哪来的**。这一课的第一件事就是还这笔账 ——
它正好是整个专题的缩影：**一个看起来简单的数字，藏着三层口径问题。**

### 三层，一层一个坑

| 层 | 数 | 坑在哪 |
|---|---|---|
| 官方口径 | **192 GiB / chip** | 源码里写的是 `206_000_000_000` —— **十进制字节** |
| 除到 device | **96 GiB / device** | v7 是 **2 device / chip**，「一张卡」永远指 device |
| 扣掉保留 | **约 94.7 GiB / device** | runtime 自己留约 1.2 GiB，**物理容量 ≠ 可分配容量** |

**`206 × 10⁹ ÷ 2³⁰ = 191.85 ≈ 192 GiB`** —— 两个数是同一个容量的两种进制写法，
都对。坑在于**同一份源码内部就混着两套单位**：
VMEM 写成 `64 * 1024 * 1024`（二进制），HBM 写成 `206_000_000_000`（十进制）。
照抄字段值再自己换算，就会把「192」这个业界通用口径洗成一个谁也认不出来的「206」。

> ⭐ **这一段真正要教的不是那个数，是那个毛病**：
> **数字没错，单位和口径错了。** 凡是要写进材料的容量、带宽、算力，
> 落笔前多问三句：**二进制还是十进制？per chip、per device 还是 per core？物理量还是可用量？**
> 这一类错误比数值写错更隐蔽 —— 单看每一步都自洽，只有放回读者的常识里才会露馅。

### 然后立假设

> **GPU 从图形渲染长出来 —— 基因是「大量独立的小核 + 运行时灵活调度」。**
> **TPU 一开始就是为神经网络造的 ASIC —— 基因是「少数巨大的矩阵单元 + 编译期把一切排好」。**

| | GPU | TPU |
|---|---|---|
| 出发点 | 像素并行 → 通用并行 → AI | 矩阵乘 |
| 组织形式 | **上百个独立 SM** | **少数巨大的 MXU** |
| 谁做决定 | **运行时**（硬件调度器） | **编译期**（编译器） |
| 优先什么 | 灵活性 | 效率 / 能效 |

**这四行现在只是假设。后面四个答案，每一个都回来验一次。**

## 1 · 一张图：先建坐标

⭐ **这一节的主体是两张全景图**，后面每一节都是在放大其中一块。

### 1.1 TPU v7 芯片全景

> 📐 **图已备好**（内部准备材料里那张画了 100+ 轮的），
> 搬过来时**去掉内部代号**，其余保留。

要在图上一眼看出来的四层归属：

```
一颗 chip
├── 2 × TensorCore   ← 每个 TensorCore = 1 个 JAX device
│   ├── MXU × 2        256 × 256 脉动阵列
│   ├── VPU × 1        8 sublane × 128 lane
│   ├── XLU × 2        跨 lane：转置 / 规约 / 洗牌
│   ├── 标量单元 × 1    发 VLIW bundle、发 DMA 描述符
│   ├── VMEM 64 MiB    私有，编译器管
│   └── SMEM 1 MiB + IMEM
├── 4 × SparseCore   ← 每 device 2 个
│   └── 每个 = 1 个标量序列器 + 16 个向量 tile（每 tile 16 lane + 自带 SRAM）
└── HBM 192 GiB · 7.4 TB/s · 一个 HBM 控制器（全芯片唯一）
```

**图上最该停下来看的三处**：

1. **「device」这一层** —— 一个 JAX device = 1 TensorCore + 2 SparseCore，
   一颗 chip 装两份。**所有框架日志都按 device 报，所有容量除以 2 才是你的额度。**
2. **HBM 控制器只有一个** —— 两颗核在同一个仲裁器下抢它。
   这条后面要用：**「把活卸载给 SparseCore」省的是指令周期，不是 HBM 带宽。**
3. **所有 SRAM 都是私有的** —— 没有共享地址空间、没有缓存一致性，
   跨核只能显式 DMA + 同步标志。**这跟 GPU 完全相反**，见 §2。

### 1.2 GPU 芯片全景（对照图）—— 以 GB200 为准

同样画一张，层级对齐：`GPU → SM → warp scheduler / CUDA core / Tensor Core /
寄存器 / shared memory + L1 → L2 → HBM`。

**⚠️ 芯片内部那一层全部待现查，不许从上一代顺延**：SM 数、
每 SM 的 shared memory / L1、L2 容量、Tensor Core 代次与支持的精度。
—— 这正是 §8 第 1 条要防的病，**在自己的课件上先犯一次就太难看了**。

> **多画一层：GPU 侧要画三层。**
> `GPU → 节点（Grace + 4 × B200）→ NVL72 域`。
> TPU 侧对应的是 `TensorCore → chip → 切片（torus）`。
> **两边的「一台机器」边界完全不在同一个地方**，这是 §4 的伏笔。

### 1.3 一张对照表（本节落点）

| | GPU | TPU v7 |
|---|---|---|
| 计算核心数量级 | **上百个 SM** | **2 个 TensorCore / chip** |
| 每个核心的自主性 | 各有调度器，可以各干各的 | 一条指令流，编译期排好 |
| 片上存储归谁管 | shared memory 程序员管，L1/L2 硬件自动 | **VMEM 编译器管，没有硬件 cache** |
| 稀疏 / 不规则 | 无专用单元 | **SparseCore** |

> **「少数巨大」这四个字在这张图上是字面意思** —— 不是修辞。
> 一颗 v7 chip 上跑通用计算的核心只有 2 个，GPU 是三位数。

## 2 · 答案一：放得下 —— 内存

**这一节是整个专题最长的一节，也是最能讲出 TPU 特色的一节。**
它回答专题一的第一条需求（1.23 TiB 权重放哪），
但真正的收获是**理解「布局」这件事在 TPU 上的分量**。

### 2.1 GPU 那一侧：cache 替你适应

- 层次：**寄存器 → shared memory / L1 → L2 → HBM**
- shared memory 程序员显式管，**L1/L2 是硬件 cache，自动的**
- ⭐ **关键性质**：你的访问模式跟数据布局不合，**cache 会替你兜一部分**
  —— 命中率下降，但不会变成整数倍的浪费
- 要讲到的具体机制：**合并访存**（coalescing）、**bank conflict**、
  `__shared__` 的手工 tiling —— 这些正是 GPU 上「布局意识」的体现，
  **但它是优化项，不是硬约束**

### 2.2 TPU 那一侧：没有 cache

- 层次：**向量寄存器 → VMEM → HBM**。就三层，**中间没有硬件 cache**
- 公开硬件表里 `cmem_capacity_bytes = 0` —— v5p 起连那块也取消了
- **VMEM 64 MiB / core，编译器管，不是程序员管**
- ⭐ **关键性质**：**布局就是一切。** 访问模式跟布局不合，
  付的是**整数倍**的代价，没人替你兜

> **这是 GPU 和 TPU 最锋利的一条对照，值得单独停一分钟。**
> GPU 的 cache 是一层缓冲垫 —— 它让「写得不够好」的代码只是慢一点。
> TPU 把这层垫子拿掉了，换来的是**确定性**（编译期就能算出 OOM）
> 和**能效**（cache 一致性逻辑很贵），代价是**布局错了就是错了**。

### 2.3 ⭐ lane 和 sublane 不是内存概念，是寄存器概念

**这是全节的地基，也是最容易搞混的一点。**

TensorCore 的向量寄存器是**二维**的：**128 个 lane × 8 个 sublane**，每格一个 32 位值。
lane 和 sublane 就是这两个维度的名字，**仅此而已**。

而 VPU、MXU 是**整个寄存器整个寄存器地吃数据**的。于是有一个选择题：

- 要么内存随便存，每次喂计算单元前先做一次搬运；
- 要么**让内存里的排布本身就长得跟寄存器一样**，搬过来直接就能用。

**TPU 选了后者。这个选择就是全部麻烦和全部性能的来源。**

推论（后面反复用）：**数组的最小维配给 lane，第二小维配给 sublane。**
所以「一块内存」的定义不是随便定的 —— 它就是「跟一个向量寄存器同形状的那块内存」。

> 💡 **名字本身在骗你**：`sub` 不是「更小」，是「第二个维度」。
> 一条 sublane（512 B）比一个 lane（4 B）**大 128 倍**。
> 把 `sub` 读成「次要维度」，这一个字改过来就不会再错。

| 怎么分 | lane | sublane |
|---|---|---|
| 寄存器的哪个方向 | 宽的那维，横着 128 格 | 高的那维，竖着 8 层 |
| 对应数组哪一维 | **最后一维**（minor-most） | **倒数第二维**（second-minor） |
| 一个单位多大 | 4 B（一格） | **512 B**（一整排 128 格） |

### 2.4 直接后果：窄矩阵在 TPU 上很亏，不是玄学

**chunk-padding**：lane 方向不足 128 补到 128，sublane 方向不足 8 补到 8，
**补进去的是未定义的垃圾**。

- **一个标量占 4 KiB** —— 整整一个块，其余 1,023 格全是垃圾
- 形状 `[A,B,C,D]` 要几块：**`A·B·⌈C/8⌉·⌈D/128⌉`** —— **后两维决定浪费，前面只是倍数**
- 一个 `[N, 8]` 的数组，最小维只有 8，要补到 128 → **16 倍的空间和带宽白扔**

> **这条是全课最能直接改代码的一条。** 「把窄维凑齐到 128 的倍数」
> 在 TPU 上不是微调，是数量级。

### 2.5 bf16 的打包，以及那个「16」

- bf16 只有 16 位，一个 lane 装得下两个 → **相邻两个逻辑行挤进同一条物理 sublane**
  （低 16 位放前一行，高 16 位放后一行）
- v7 起对 16 位类型默认把第二小维分块**从 8 提到 16**：
  **16 个逻辑行 → 2:1 打包 → 8 个物理 sublane → 一块正好 4,096 B**
- ⚠️ **压的是行，不是列** —— 列数还是 128，不会变成 256

> **必答的追问**：一个 lane 是 32 位，装 bf16 岂不是空一半？
> **lane 一位都没空着**，因为填满高 16 位的是「下一个逻辑行的同一列」，
> 不是「同一行的下一列」。所以每个逻辑行在 lane 方向仍是一列一个元素。
> ⚠️ **这个问题不能靠算术验证** —— 两种猜法的总字节数一模一样，只能靠布局规则定。

### 2.6 ⭐⭐ 本节落点：形状约束是一路传递的

**每一个单元都只认一种形状，而且互不让步：**

| 单元 | 只认 |
|---|---|
| 标量核 | 单个 **4 B** 的值 |
| DMA | **32 B** 的 granule |
| VMEM | 按 **512 B** 对齐 |
| 向量核 / 向量寄存器 | 严格 **8 × 128 × 32 bit**（= 4,096 B） |
| MXU | **256 × 256** |

**于是「我只要块里的一小条」这种访问，必然要按整块付钱。**

> **这句话就是「编译期把一切排好」最具体的化身。**
> 它不是某一个单元的缺陷，是这串约束**串起来之后的必然结果** ——
> 而这正是 §5「谁做决定」那一节的落点：
> **控制权交给编译器，换来的是它能看到整张图；代价是这串形状你绕不开。**

### 2.7 ⭐ 主例：Flash 家族为什么存在 —— 片上内存才是主角

**这是本节最该花时间的例子，比 embedding 重要得多。**

注意力的中间量是一张 `seq × seq` 的矩阵。128K 序列下它大到荒谬 ——
**但真正的问题不是它算得慢，是它根本不该落地到 HBM。**

- **Flash 的全部思想只有一句**：把注意力**分块**，让每一块的中间量
  **只在片上内存里出生和死亡**，从不写回 HBM。
- 于是「片上内存有多大」直接决定了「块能开多大」，
  而块开多大又决定了**HBM 流量降到原来的几分之一**。

| | GPU | TPU |
|---|---|---|
| 片上内存 | shared memory / L1，**每 SM 百 KB 量级** | **VMEM 64 MiB / core** |
| 谁管 | **程序员显式管**（`__shared__`、手工 tiling） | **编译器管** |
| 块大小谁定 | 写 kernel 的人（Triton / CUTLASS 里的 tile 常量） | 编译器选，**但要服从形状约束** |
| 代表实现 | FlashAttention 系列 | Pallas 写的 splash / flash 变体 |

> ⭐ **本节最重要的一个数量级对照**：
> **片上内存比 HBM 快约一个数量级** —— 这句话是**所有 tiling 优化的唯一动机**，
> 无论 GPU 还是 TPU。Flash、算子融合、MoE 的分块 dispatch，
> 全都是同一件事的不同外衣：**把数据留在片上，别让它来回过 HBM。**
>
> 两边的差别不在这个动机，在**谁来决定块怎么切**：
> GPU 上是写 kernel 的人，TPU 上是编译器 —— 而编译器的选择受 §2.6 那串形状约束。

**⚠️ 待补**：两边各取一个真实的 tile 配置做对照；
TPU 侧要说清「块大小不是自由的，得对齐到 8 × 128」。

### 2.8 第二个例子：MoE 的 ragged 撞的是同一堵墙

MoE 的 dispatch 之后，每个专家拿到的 token 数**是不齐的**（ragged）。
而 TPU 的分块尺寸由寄存器形状定死 ——
**「我只要块里的一小条」这种访问，都要按整块付钱。**

- 业界现有的绕法是**在预处理阶段 reshape**，好让编译器选一个更小的分块，
  从而能切得更细。**但这个 reshape 本身开销不小。**
- 这跟 §2.7 的 tile 对齐、跟下面 embedding 的 16×，
  **是同一个机制的三种表现**

> **这一条对听众最有价值** —— 因为 MoE 是他们每天在跑的东西，
> 而「TPU 上 ragged 难做」这句话，到这里才有了物理解释：
> **不是编译器笨，是布局的粒度本来就不是任意的。**

### 2.9 第三个例子：出口的 logits —— 巨大的短命中间量

专题一算过：出口那个 `序列长 × 词表` 的 logits 矩阵，
在长上下文下**能吃掉几十 GiB**，而它只活一瞬间。

- **两边的解法是同一个**：分块算，算完立刻取 argmax / 采样，不整块落地
- **但两边的难度不同** —— 分块要不要重编译、块大小能不能运行时变，
  是 §5「谁做决定」的直接后果

### 2.10 第四个例子：embedding 的 16 倍读放大

**⚠️ 它是七步里最不典型的一步**（算术强度为零），
所以放在最后当**几何关系的干净演示**，不当主例。

一张 `词表 × hidden` 的 bf16 嵌入表，「取一行」这个动作在 v7 上的真实形状是：

- 一行 **不连续** —— 它横跨 56 个块，**每块里只占 1/16**
- 每块 4,096 B 里，属于这一行的只有 **256 B** → **`4096 ÷ 256 = 16`**
- 同一个 16 倍会在三个层面各出现一次：**字节**（HBM 流量）、
  **容量**（VMEM staging）、**指令条数**（load 次数）

> ⚠️ **为什么这个浪费在 profile 上看不见**：
> 总线**确实**跑满了 —— 「HBM 忙不忙」这个指标会告诉你一切正常。
> 只有把**有效字节**和**总字节**分开看，才看得见那 15/16 是白搬的。
> **带宽被打满 ≠ 有效带宽被打满。**

**⚠️ 待补**：这一节的具体数字要从内部准备材料里搬，
**只搬公开源能支撑的那部分**（分块规则、几何关系、放大倍数）。

## 3 · 答案二：算得动 —— 计算单元

回答专题一的第二条需求：**52.50 PFLOP 的前向，靠什么算出来。**

### 3.1 GPU 那一侧：SM / warp / CUDA core / Tensor Core

**这一节要讲透，因为它是后面所有对照的锚点。**

- **SM**：GPU 的调度与执行单元，一颗芯片上百个，**每个都有自己的调度器**
- **warp**：32 个线程一组，**SIMT** —— 同一条指令，各线程各自的数据；
  分支发散时两条路径**串行执行**
- **CUDA core**：标量 ALU，通用浮点/整数
- **Tensor Core**：矩阵单元，**warp 级指令**，吃固定形状的小 tile
- ⭐ **关键遗产**：**灵活是刻在骨子里的** —— 每个 SM 可以做完全不同的事，
  硬件调度器在运行时决定谁上

### 3.2 TPU 那一侧：TensorCore / VPU / MXU / XLU / 标量单元

- **MXU × 2**，**256 × 256 脉动阵列** —— 数据流过一个固定的阵列
- **VPU × 1**，8 sublane × 128 lane —— 唯一能「从块里抠出一条」的单元
- **XLU × 2** —— 跨 lane 的转置 / 规约 / 洗牌
- **标量单元 × 1** —— 发 VLIW bundle，**DMA 描述符也由它发**
- ⭐ **一个 bundle = 一个 PC 值 = 若干个槽，同一周期全部发射**；
  **槽位不对称、编译期钉死**；**全片没有乱序、没有分支预测**
  —— 用「照发射但不生效」的谓词代替分支

> **这一条对照最能说明问题**：
> GPU 用**硬件**在运行时解决分支发散（warp 内串行两条路径）；
> TPU 把分支这件事**整个推到编译期**，硬件里根本没有分支预测器。
> 省下来的晶体管全给了 MXU —— **这就是「效率优先」的物理含义。**

### 3.3 MXU 是 256 × 256，不是 128 × 128

⚠️ **一个非常容易套错的旧数**：128 × 128 是老世代的 MXU 尺寸，
**第 6 代起就变成 256 × 256，而且每核 2 个**。

> ⭐ **这条错法很典型，值得当案例讲**：它是一个「**听起来像常识**」的架构常数，
> 在科普材料里被引用了太多年，以至于**不会有人想到去核**。
> **凡是跨代沿用的数字（MXU 尺寸、寄存器数、tile 形状），都要按目标代号单独查一遍。**
> —— 跟专题一那条「hidden = 头数 × 每头维度 在 MLA 上不成立」是同一类病。

**峰值怎么来的**（推导链，不背结论）：
`MXU 数 × 每个 MXU 的 cell 数 × 每 cell 每周期的 FLOP × 频率`。
⚠️ **待补**：公开表报的是最高频档，默认档要低一些 —— 这个差别要讲清，别让人拿峰值当实得。

### 3.4 三个负载，压的是计算单元的三个不同部位

**⭐ 这一小节是本节的骨架** —— 不同的算子吃的是完全不同的东西。

**① Dense MLP —— MXU 的主场，也是「形状对齐」最直接的地方**

- 大矩阵乘正是脉动阵列天生要算的东西，MFU 最高的一段
- ⚠️ **但形状要对齐**：MXU 只认 `256 × 256`，
  一个宽度不是 256 倍数的矩阵，**尾巴那一截是白填的**
- GPU 侧有对应物：Tensor Core 也有它自己的 tile 形状要求，
  只是**粒度更小、更容易凑**
- **⚠️ 待补**：拿专题一那个 MLP 的真实形状算一遍两边各浪费多少

**② 注意力 —— 瓶颈在「非 matmul 的那部分」**

注意力不是一个 matmul，是**两个 matmul 夹一个 softmax**。

- 两个 matmul 归 MXU / Tensor Core，这部分很快
- **softmax、归一化、mask 归向量单元** ——
  而 TPU 上 VPU 只贡献全核算力的**约 3%**
- ⭐ **所以「注意力慢」在两边都常常不是 matmul 慢，是那一小撮逐元素运算慢**
  —— 这也是算子融合最有价值的地方：**别让中间结果为了做 softmax 而过一趟 HBM**

**③ MoE 路由 —— 矩阵单元完全做不了的那一类**

- top-k 选择、排序、计数、前缀和 —— **全是数据相关的不规则计算**
- MXU 做不了，Tensor Core 也做不了
- GPU 侧靠 CUDA core + 手写 kernel（DeepEP 那一族）
- TPU 侧：**这恰好是 SparseCore 的原语清单** —— 见下

### 3.5 第四层：SparseCore

**GPU 上没有对应物**，所以这一节纯粹是「TPU 多出来的东西」。

- **每 device 2 个**（每 chip 4 个），
  每个 = **1 个标量序列器 + 16 个向量 tile**，每 tile 16 lane + 自带 SRAM
- **它是可编程向量处理器，不是 DMA 引擎** —— 公开 API 里列着
  `cumsum` / `cummax` / `sort_key_val` / `scan_count` /
  `fetch_and_add` / `addupdate_scatter`
- ⭐ **把这份清单和上面 §3.4 的第 ③ 条并排看**：
  前缀和、排序、计数 —— **这正是 MoE 路由要的那几样原语**。
  不是巧合：它们都属于「矩阵单元完全做不了」的那一类不规则计算
- **但它没有 MXU**，做不了矩阵乘；整芯片合计算力只有 MXU 的约 **1.2%**
- ⭐ **它存在的理由，一句话说得清**：
  整个 TensorCore 只有**一个**标量单元在产地址，
  它每花一拍算地址，MXU 就空转一拍 ——
  而一个 device 的 2 个 SparseCore 有 **32 个 tile 各跑各的**

> ⚠️ **最容易误解的一条**：卸载给 SparseCore **省的是指令周期，不是 HBM 带宽**。
> 因为全芯片只有一个 HBM 控制器，两颗核在同一个仲裁器下抢同一批 DMA。
> **SparseCore 大量查表时，会真实地挤占 TensorCore 的 HBM 份额。**

**那 LLM 用得上它吗 —— 用不上，而且理由很干脆。**

判据是「**同一批行被反复查多少次**」：

| 场景 | 索引数 | 可选行数 | 比值 | 适不适合 |
|---|---|---|---|---|
| 推荐系统的稀疏特征表 | 数万～数十万 | 几百～几千 | **几十～几百** | ✅ 正是为它设计的 |
| LLM 的词嵌入 | ≈ 序列长度 | ≈ 词表大小 | **≈ 1** | ❌ 判据最低端 |

> **LLM 的词嵌入一点都不稀疏** —— 每个 token 查一次、几乎不重复，
> 拿不到「去重」这份红利。**「TPU 有专门做 embedding 的硬件」这句话是真的，
> 但对我们这类负载不成立。**

### 3.6 实测：生产环境根本没在做 gather

**⭐ 这是本节的实测，也是全课最好的一个「工程判断」样本。**

翻实跑的编译产物发现：**我们所有生产配置都没走查表这条路** ——
它们把 embedding 写成了 **one-hot × 表的矩阵乘法**，交给 MXU 算。

而这个矩阵乘**比查表慢大约 24 倍**。

> ⭐ **大家主动选了慢的那个。为什么？**
> 因为它只占一步总算力的 **0.62%**。
> **这不是一个「优化」，是一个「便宜到可以不讲道理」的选择。**
>
> 这一条值得让听众自己先猜一遍 —— 几乎所有人的第一反应都是
> 「肯定是为了省显存带宽」，**而算完发现完全相反：它不省，它花。**
> 成立的唯一理由是**分母够大**。

**⚠️ 待补**：具体形状与 FLOP 数从内部准备材料搬，
框架里那个开关的名字与那六行分支代码是**开源**的，可以直接引。

## 4 · 答案三：卡间说话 —— 互联

回答专题一的第三条需求：**摊到 14 个 device 上之后，它们怎么通信。**

> **本节只讲拓扑的形状和物理性质。**
> 「怎么拿这个形状去切模型」是[专题五](专题05-并行策略.md)的事，不提前借。

### 4.1 GPU 那一侧 —— ⭐ NVL72 把「一台机器」这个词废掉了

**这一小节值得多花时间，因为它推翻了大多数人脑子里那张图。**

上一代的常识是「**机内 NVLink 8 卡、出了机器就掉到网络**」。
**NVL72 不是这样** —— 一个 NVLink 域是 **18 个节点 × 4 GPU = 72 张卡**，
它们之间**全部走 NVSwitch 第五代全互联**，不是网络。

```
GPU (B200)
  └─ 节点：Grace ARM64 + 4 × B200   ← 「一台机器」原来的边界，现在不重要了
       └─ NVL72 域：18 节点 = 72 GPU，NVSwitch 5 全互联   ← 新的边界在这
            └─ 跨域：RoCE / RDMA
```

#### ⚠️ 但是 72 这个数不能直接拿来算 —— 能跑训练的是 64

**这是本节第一个必须讲清的口径问题。**

- **72 张是域的物理规模**，不是能进一个训练任务的规模
- 实际编排是 **16 个节点 = 64 张卡进训练任务**，
  **剩下 2 个节点 / 8 张卡做热备**
- 64 也恰好是 2 的幂，**并行切分本来就想要这个数**

| | 按 72 卡（物理域） | **按 64 卡（可训练）** |
|---|---|---|
| GB200 显存合计 | 13.4 TB | **11.9 TB** |

> ⭐ **这是 §8 那条方法论的现成活教材**：
> 同一个「一个域有多少显存」，**答案取决于你问的是物理规模还是可用规模** ——
> 跟 §0 里 192 GiB / 96 GiB / 94.74 GiB 那三层是**一模一样的病**。
> **落笔前先问：物理量还是可用量？**

#### 节点的网络：两套网，别混着报

**这是本节第二个口径问题，而且极容易看错。**

GB200 每个节点上有两类网卡，**带宽必须分开报**：

| | 网卡 | 数量 × 单卡 | 合计 |
|---|---|---|---|
| **RDMA（GPU 之间跨域通信）** | CX-7 | 4 × 400 Gbps | **1,600 Gbps** |
| **管理网** | GVNIC | — | **400 Gbps** |
| | | **节点合计** | **2,000 Gbps** |

> ⚠️ **看到「2,000 Gbps」不要当成 RDMA 带宽** —— 它含了 400 的管理网。
> 真正拿去算 all-to-all 的只有 **1,600**。
> 这类「合计里混进了不该算的东西」，跟 §0 那个 HBM 十进制/二进制混用是同一类错。

#### ⭐ 拿这个数回头看专题一

专题一算过：那个模型常驻权重 **1.23 TiB**。
**一个 NVL72 域按可训练的 64 卡算有 11.9 TB 显存** ——
整个模型连同 KV cache **可以完全装进一个 NVLink 域里**。

也就是说，对这一档模型，**「跨域断崖」这件事在推理时根本不必发生**。
**「域」才是新的「一台机器」。**

#### RDMA 的两条语义（后面 TPU 那边要对照）

**内存区域必须先注册**；**发送方不能凭空写进对方任意地址**。

- 拓扑性质：**域内均匀，跨域断崖** —— 但「域」现在是 **72 张**（可训练 64），不是 8 张
- 通信库：**NCCL**（以及 MoE 专用的 DeepEP 那一族）

#### 4.1b 下一代变了什么：GB300 (A4X MAX)

**不当主线讲，但要给听众一个「接下来会怎样」的落点。**
（来源：本仓库 `gpu/a4x-max/README.md`；标 ⚠️ 的是规格不是实测）

| | GB200 (A4X) | **GB300 (A4X MAX)** |
|---|---|---|
| GPU | 4 × B200 | 4 × B300 Ultra |
| 每 GPU 显存 | 186 GB | **~279 GB HBM3e（+50%）** |
| **64 卡可训练显存** | 11.9 TB | **17.9 TB** |
| RDMA 网卡 | CX-7 VF，**挂在 CPU 上** | **CX-8 SuperNIC PF，直连 GPU（GPUDirect）** |
| RDMA 带宽 / 节点 | 4 × 400 = **1,600 Gbps** | **4 × 800（双端口）= 3,200 Gbps** |
| ＋管理网 | 400 Gbps | 400 Gbps |
| **节点合计** | **2,000 Gbps** | **3,600 Gbps** |
| 实例形态 | VM | **裸金属** |
| 网络栈 | IPv4 | **IPv6-only** |
| NVL72 拓扑 | 18 节点 / 域 | **18 节点 / 域（不变）** |

**三句话总结这一代的变化：**

1. **显存 +50%** —— 能装的模型档次上一级
2. **RDMA 翻倍且直连 GPU** —— 跨域那条路不再绕 CPU 内存，
   **「跨域断崖」这个断崖变浅了**
3. **拓扑没变** —— 所以 §4.5 那个结论（域内均匀 ≠ 集合通信均匀）**照样成立**

> ⚠️ **本仓库那张表里「网络带宽 2,000 / 3,200」两个数口径不一致** ——
> 2,000 含管理网，3,200 只是 RDMA。上面这张表已经拆开报了。
> **这正是 §8 第 2 条说的「口径不一致的表不能拿来推口径」，而且它就出在我们自己的文档里。**

### 4.2 TPU 那一侧

- **机内 / 机间是同一套**：ICI，构成 2D / 3D **torus**
- 拓扑性质：**规则的网格，有明确的「距离」概念** —— 相邻极快，对角要绕
- ⭐ **跨芯片寻址是「片间版的 RDMA memory region」**：
  发送方给的不是物理地址，是**「哪颗芯片 + 哪个段 + 偏移」**，
  **段的物理基址由接收方决定**。两个直接后果 ——
  **远端只能落进指定的几类存储**；**落点由接收方掌握**。
  跟 RDMA 要先注册缓冲区是同一个设计动机
- 通信由**编译器生成**，没有独立的通信库

### 4.3 对照与落点

| | GPU | TPU |
|---|---|---|
| 机内 | NVLink 域，近似全连接 | ICI，torus |
| 机间 | IB / RoCE + RDMA | **同一套 ICI 延伸** + DCN |
| 拓扑性质 | 域内均匀，**跨域断崖** | **规则网格，有距离** |
| 谁生成通信 | 人写 + NCCL | **编译器** |

**很实在的两个差别：**

- **all-to-all 在全连接域里很自然，在 torus 上要绕** ——
  这就是为什么 **MoE 的分组限制路由在 TPU 上尤其重要**（接回专题一 §4）
- **torus 上相邻通信极快** → ring 类算法天然合适

### 4.4 ⭐ 四个集合通信原语：分别是谁产生的

**⚠️ 不要把这节讲成通信库教程。** 每一个原语都要能指回专题一的某一步 ——
听众关心的是「**我这个模型为什么会产生这种通信**」。

| 原语 | 谁产生它（回指专题一） | 通信形状 | 对拓扑敏感吗 |
|---|---|---|---|
| **all-gather** | FSDP / ZeRO-3 用之前把权重收齐；张量并行拼输出 | 一对多广播式 | 一般 —— **ring 就能做好** |
| **reduce-scatter** | 梯度：算完各自持有一片 | 多对一归约 + 切分 | 一般 |
| **all-reduce** | 数据并行的梯度同步 | = reduce-scatter + all-gather | 一般 |
| **all-to-all** | ⭐ **MoE 的 dispatch / combine** | **每一对都要通信** | **极其敏感** |

> ⭐ **一句话记住区别**：前三个都能拆成「沿着某个环走一圈」，
> 所以**在 torus 上也很舒服**；
> **只有 all-to-all 天生要求「任意两点直接说话」** ——
> 它是唯一一个会因为拓扑不同而**表现出数量级差异**的原语。
>
> 这就把两件事接上了：**为什么 MoE 是 TPU 上最难的那类负载**，
> 以及**为什么分组限制路由不是省算力的技巧，是省拓扑的技巧**。

### 4.5 ⭐⭐ 实测：域内均匀 ≠ 集合通信也均匀

**这是本节最反直觉的一条，也是本节的落点。**

我们自己在 NVL72 域内跑过 DeepEP，8 / 16 / 32 GPU 三档
（来源：本仓库 `gpu/a4x/06-deepep-test/README.md`，GB200 A4X，同域）：

| 操作 | 8 GPU | 16 GPU | 32 GPU | 变化 |
|---|---|---|---|---|
| **Copy（纯 NVLink 点对点）** | 5600 | 5500 | **5700 GB/s** | **基本不变** |
| Dispatch（all-to-all） | 700 | 660 | **636 GB/s** | 每翻倍 −5~6% |
| Combine（all-to-all + reduce） | 724 | 683 | **590 GB/s** | **−19%** |

**怎么读这张表**（这才是讲课的重点，数字本身不重要）：

1. **Copy 纹丝不动 → 域内均匀这句话是真的**，NVSwitch 带宽确实不是瓶颈
2. **但 all-to-all 还是掉了。** 原因不在带宽，在**形状**：
   8 卡时每张卡把 token 分发给 7 个目标，平均每目标 ~100 GB/s；
   32 卡时分给 31 个目标，平均每目标只剩 ~22 GB/s ——
   **总带宽没变，但每一笔都变小了，小块分散写的链路利用率远低于大块连续传输**
3. **Combine 掉得更快（−19% vs −9%）**，因为它多做一次 reduce ——
   **归约的同步深度随参与者数量增长**，32 路比 8 路要多等

> ⭐⭐ **本节落点**：**「链路均匀」是硬件性质，「集合通信均匀」不是。**
> 中间隔着一层**消息大小与同步深度** —— 而这一层由**你的模型怎么切**决定。
> 换句话说：**拓扑给你一个上限，能不能吃到它取决于负载的形状。**
> —— 这跟 §2 的结论是同一个道理换了个层面：**形状决定一切。**

**⚠️ 待补**：TPU 侧同一批原语在 torus 上的实测对照；
Hy3-295B 在两边的通信占比。

## 5 · 答案四：谁做决定 —— 范式

**⭐ 这一节是软件栈所有差别的根，也是开头那个假设的最终验证。**

前面三个答案都是「硬件长什么样」。这一节问的是**「谁在安排」** ——
而它才是那四行对照表里真正起作用的一行。

### 5.1 两种心智模型

| | GPU / CUDA | TPU / XLA |
|---|---|---|
| 心智模型 | **写一个 kernel，描述一个线程干什么**（SIMT） | **写整张计算图，描述数据怎么变换**（SPMD） |
| 形状 | 运行时可变 | **编译期必须确定** |
| 控制流 | 随便写 | 数据相关的控制流很贵 |
| 优化在哪发生 | 人写 kernel + 库 | **编译器做全局优化** |
| 调试 | 打印、单步 | 读编译产物、读 profile |

**静态的代价**：形状一变就**重编译**（可能十几分钟）；
变长序列要靠**分桶 + padding** 绕；数据相关的操作（MoE 路由）实现起来别扭。

**静态的红利**：编译器看得到整张图 → **跨算子融合、通信与计算重叠、内存复用**都能自动做；
显存规划是确定的 → **能提前算出会不会 OOM**。

> **一句话**：**CUDA 把控制权交给你，XLA 把控制权交给编译器。**
> 各自的痛苦也就完全不同 —— 一边是「写不出足够快的 kernel」，
> 一边是「编译器不听话，而我插不上手」。

### 5.2 后果一：训练框架

| | Megatron-LM（GPU） | MaxText（TPU） |
|---|---|---|
| 并行怎么表达 | **手工切**：显式写通信 | **声明式**：给张量标 sharding，编译器生成通信 |
| 心智负担 | 每一处 all-reduce 在哪都要知道 | 要理解 mesh 与 partition spec |
| 出问题时 | 看得见每一步 | **要会读编译产物** |
| 配置复杂度 | 参数极多 | 参数少，但**一个 sharding 标错全盘皆输** |

> ⭐ **这就是「谁做决定」在框架层的复现** —— 不是两个团队风格不同，是同一条基因。

### 5.3 后果二：手写 kernel

- **Triton**（GPU）与 **Pallas**（TPU）定位相似：用 Python 写高性能 kernel
- 差别在底下：编译目标不同 → **能表达的东西不同**
- 什么时候不得不自己写：编译器生成的不够好，或者算子根本不存在
- ⭐ **我们写过 TPU 侧的 kernel**，有第一手经验

> ⭐⭐ **Flash Attention 是这一节最诚实的一个例子** ——
> 它在**两边都得手写**：GPU 上是 CUTLASS / Triton，TPU 上是 Pallas。
> **没有任何一侧的编译器自己长出了它。**
>
> 这就给「XLA 把控制权交给编译器」这个说法**钉了一个边界**：
> 编译器擅长的是**把已有算子编排好**（融合、重叠、复用），
> 不擅长的是**发明一个新的算法**。
> Flash 改的是数学上的计算顺序，不是编排 —— **那永远是人的活。**

### 5.4 后果三：推理引擎的移植难点

- vLLM / SGLang **都起于 GPU，都在往 TPU 上移植**
- 难点集中在一处：**动态性** ——
  连续批处理、变长序列、KV cache 的动态分配，**全是编译器最不喜欢的东西**
- 解法：**静态形状 + 分桶 + 预编译**
- ⭐ 我们部署过其中好几个，坑可以直接摆出来

### 5.5 后果四：AOT —— 静态的最大红利

**能在不占卡的情况下，提前算出「装不装得下」。**
这一条 GPU 侧没有对应物，**而它直接回答专题一那堵墙**：
判 OOM 不用真跑，编译一遍就知道。

## 6 · 怎么比才有意义

> **⭐ 这一节最重要的编排规则：一个跨平台对比数字都不给。**
> 规矩和数据分两节，是为了让台下先拿到尺子，再看到东西。
> 混在一起讲，读者只会记住那个倍数。

### 6.1 先说怎么比不对

- ❌ 直接比峰值 —— **精度口径常常不一致**，而且峰值只是分母
- ❌ 只看 HBM 容量 —— 得同时看带宽，**还得看每 chip 还是每 device**
- ⚠️ **单位陷阱**：v7 是 **2 device / chip**，而框架日志一律按 device 报。
  同样的 `per_device_batch_size`，**v7 的 global batch 是上一代的两倍** ——
  **跨平台比 loss 曲线之前先对齐 global batch**，否则轨迹必然不同
- ⚠️ **MFU 的分母是个选择，不是常数**（课件 P-12 / P-13）：
  per chip 还是 per device、dense 还是含稀疏、FLOP 公式加没加模型白名单。
  **漏白名单能让 MFU 虚高约 5 倍，而且不会报错。**

### 6.2 该怎么比 —— 四档阶梯（课件 P-14）

| 档 | 怎么比 | 代价 |
|---|---|---|
| ① | 比峰值 | 免费。**网上的文章绝大多数停在这里** |
| ② | 比 MFU | 要有一边的实测，但**分母的口径得说清** |
| ③ | **同模型同规模，两边各自调到最好** | 要两边的卡、两边的人，和好几周 |
| ④ | 每美元 / 每瓦 | **采购真正要的，也是最答不了的** |

> **③ 档真正贵在哪**：不是卡，是「两边都得有人会调」——
> 而「会调」里有一部分是**继承来的**（抄来的官方 recipe 背后是别人几个月的工作），
> 那部分不出现在任何工时统计里。这一条在 §7 的 P-16 里有具体形态。

## 7 · 两边的实测

> **⚠️ 2026-08-31 换掉了这一节。** 原来这里是「各自擅长什么（克制，不吹不黑）」，
> §6 底下挂一个小小的「实测」子节。写下来之后发现顺序反了：
> **在给出真数之前先下「谁擅长什么」的结论，等于把结论建在还没摆出来的证据上。**
> 现在 §7 就是那组真数，「各自擅长什么」的去向见本节末尾。

**这一节只做一件事：把 §6 的规矩用在一组真数上，然后看还剩下什么能说。**
—— 剩下的比开口之前想说的少得多，**而这正是它的价值**。

同一个 **Hunyuan3-295B-A21B**（80 层、192 专家）、同样 **seq 4096**、
两边各 **64 个计算单元**、两边都是我们自己跑的。

### 7.1 先把两个数摆出来（P-15 / P-16）

| | GB300 NVL72 · 64 GPU | TPU v7 · 64 chips |
|---|---|---|
| BF16 实测 | **854.0** TFLOP/s | **662.3** TFLOP/s/chip |
| MFU | 34.2% | 28.71% |
| tok/s / 计算单元 | **6,242** | **4,770** |

> ⛔ **这一节最重要的一句，是一句自我否定。**
>
> 854.0 ÷ 662.3 = 1.084（峰值比）× 1.190。第一版把后面那段叫
> **「软件效率之比」**，再由此推出「差的不是硅片，是软件」。
> **这是用命名冒充证明** —— 因为 MFU ≡ 实测 ÷ 峰值，
> 这个式子对**任意两个数**都成立，那 1.190 是**余项**不是测量值。
> HBM 带宽、片上 SRAM、MXU 收缩维形状、互联拓扑，**全都落在余项里**。
>
> 最直接的反例就在这门课自己手上：**§3.4 论证过 `head_dim = 128`
> 在 v7 的 256 收缩维上只喂满一半** —— 纯硅片效应，表现形式恰恰是 MFU 偏低。
> 而 §4.5 立过规矩：「**一个走错路的对照项比没有对照项更危险。**」
>
> 所以现在只说「**这 1.19 不来自峰值差**」。
> 「有多少来自软件」交给 **P-16 那条纯软件爬升曲线**回答 ——
> **v7 硬件一颗没换、只改软件，457 → 662.3，+44.9%**
> （按 §6 口径剥掉频率档那一步仍有 +33.4%）。
> **那是真实验，不是恒等式的余项。**

> ⚠️ **两边不是同一种「调到最好」。** v7 侧确实撞墙（四个方向 8 组实验无一正收益）；
> **GB300 侧没有** —— 它自己的扫点表里 EP 32→16 是 +3.3%（882.3）没跟进复测。
> **所以这一节所有倍数都是下限。**

### 7.2 然后是最难的一步：不说过头（P-17 / P-18）

**同一组数换三种问法，得到三个不同答案：**

| 问法 | 答案 |
|---|---|
| ① 都跑 BF16 | **1.31×**（6,242 ÷ 4,770）—— 口径最接近的一问 |
| ② 各自用最擅长的精度 | **2.06×**（9,945 ÷ 4,830）—— 但两个不是同一种 FP8 |
| ③ 每美元 / 每瓦 | **答不了** —— 而「答不了」在图上也占一根条 |

**外加六条边界（P-18），每条都标出它把倍数往哪边推**：
global batch（利于 GB300）· **64 这个规模是 GPU 主场**（利于 GB300）·
重算策略不同（利于 GB300）· 软件成熟度（利于 GB300，且会变）·
v7 那 662.3 含一个频率档（利于 v7）· 「每芯片对每 GPU」已是最优待（利于 v7）。

> **⭐ 这一节唯一要背下来的一句**（课件底带，抄走就能用）：
>
> 「在 Hunyuan3-295B-A21B、seq 4096、各 64 个计算单元、**以 2026 年 8 月两边的软件栈**，
> GB300 的每卡吞吐是 v7 每芯片的 **1.31 倍**（6,242 对 4,770 tok/s）；
> 换成 TFLOP/s 口径是 1.29 倍，其中 **1.084 倍**来自峰值差（2,500 对 2,307），
> **其余不来自峰值**。」
>
> 比「GPU 快 30%」长了五倍，但半年后它还能被查。

### 那「各自擅长什么」去哪了

**原计划它是本节内容，现在挪到全课收尾。** 理由是这一节整节都在证明
**「不带边界的结论会被误引」**—— 紧接着甩一份
「GPU 更适合 X / TPU 更适合 Y」的清单，恰好是它刚拆掉的那种东西。

挪过去之后要求也变了：**每一条都得指回本课某一节，指不回去的不写。**
灵活性 → §5 谁做决定；规整训练 → §2 形状约束 + §3 MXU 对齐；
扩展性 → §4 拓扑（**以及 P-18 那条「64 是 GPU 主场」**）；
生态 → §5.5 推理引擎移植。

> **两边的差别不是「谁更强」，而是「把控制权交给谁」。**
> 交给人，就得有人有能力写；交给编译器，就得接受它的脾气。

### 8.1　同一个漏法，两次　→ P-19

八笔撤回里有两笔属于同一种故障：**上游撤了，从它算出来的那个数还挂着**。
两次代价差 15 倍（15 天 vs 不到 1 天），**而原因不是「第二次更小心」**——
是第二次的撤回和复查发生在同一天。**能安排的是间隔，不是仔细。**

> **⛔ 这一格的第一版把机制写错了，而且错法正是这一节自己在批的那一种。**
>
> 第一版写的是「那次清理**按字符串走**，`7,308` 里没有『1,014.8』这几个字，所以搜不到」。
> 听起来极其合理 —— **然后审计去查了 diff**：
>
> - `8c46582`（标题「清掉**全部**失效的 1,014.8」）改的是 `README.md` 的**第 26 行和第 137 行**；
>   而那句「已反超 +17%」就在**同一个文件的第 51 行**，第 52 行还挂着一条含 `7,308` 的口径提醒。
> - `483128b`（撤 GB300 峰值）动了十个文件，**正好包含含 `31.60%` 的那三个**，三处一个没改到。
>
> **两次都不是搜不到。文件就在手上，改了别处，跳过了它。**
> 「按字符串走」是从结果倒推的机制，全仓没有证据 ——
> 一节在教「推出来的要标成估」的附录，第一版自己把推的当成了测的。

**所以规矩也跟着换了**：原来的落点「撤回后记得搜一遍下游」是废话，
**搜索从来不是瓶颈，注意力才是**。负担挪到落笔时 ——
**一个数如果是算出来的，就把算式写在它旁边**（`7,308 = 1,014.8e12 ÷ 138.9e9`），
这样改上游的人在同一屏上就能看见它。**这正好是 8.3 甲格 ④ 要求的事，两张图因此接得上。**

### 8.3　落笔之前　→ P-21

8.1 讲错了之后为什么没跟着改，8.2 讲八笔各活了多久，这一张讲写下之前怎么防。
**三张必须连着出**，否则前两张只是自我批评，没有可带走的东西。

**甲格 · 来源分级**——最后一列不是「否则不严谨」，是八笔账对号入座：

| 等级 | 台账里的类型 | 这一课的实例 | 该怎么写 | 它是怎么坏的 | 犯过 |
|---|---|---|---|---|---|
| ① 官方规格 | 编的 / 套错 | 2,500 / 2,307 dense BF16 | 给出口径：dense 还是含稀疏、每 chip 还是每 device | **两种坏法方向相反**：2,700 没出处（猜高）；2,250 规格是真的、套错机型（猜低） | **2 笔** |
| ② 自己实测 | 测的 | 854.0 / 662.3 | 连 step time + 配置 + 规模一起给 | **测量本身错了** —— 1,014.8 漏 all-gather | 1 笔 |
| ③ 他人实测 | —— | 707.2 厂商官方 recipe | 注明谁跑的、什么配置、能不能对齐 | **配置对不齐却并排放** —— 本课没犯过 | **0 笔** |
| ④ 算出来的 | 派生 / 口径 / 归类 | MFU、tok/s/chip | **把算式写在它旁边**：tok/s/chip = pdbs × 8192 ÷ step | 上游撤了没跟着撤、分母没交代、加数里混进不该加的项 | **4 笔** |
| ⑤ 推出来的 | 推的 | 没有直接测量的一切 | 写清推导链，明确标「估」 | **换个名字就当成发现** —— 「软件效率之比」 | 1 笔 |

> **⛔ 这一列的第一版写的是「五种失败模式一一对应五个来源等级，这不是巧合」——数一下就知道不对。**
> 八笔散在四级上：**④ 独占四笔（一半）**，③ **零笔**。
> 「一一对应」是先有了「工整」这个愿望再回头凑数字。
> **这一节因此在同一处栽了三次**：编机制、编结构、选择性记账 ——
> **三次都是「先有形状，再找证据」。**

如实报数之后反而说出两件真的事：
**① ④ 最危险恰恰因为它有出处**（出处是①或②），所以看上去已经处理过了；
**② 那个零笔什么都证明不了** —— 这一课总共只引用过**一个**他人实测的数，
**样本 1 里出 0 个错**。所以那格写的是「本课没犯过」，不是「本课不会犯」。

**乙格 · 落笔前的三句自问**——三句都是**单位问题不是态度问题**，所以可执行：

1. **二进制还是十进制？** 官方 HBM 那栏是十进制，206 GB 就是 192 GiB，差 7.4% ——
   足够把「刚好装下」变成 OOM。判 OOM 一律用 **94.74 GiB/device**。
2. **per chip / per device / per core？** v7 是 2 device/chip，而框架日志按 device 报。
   **per-chip = 日志读数 × 2。这一步错，结论差一倍。**
3. **物理量还是可用量？** 94.74 GiB 是可用的不是标称的；2,500 是 dense 的不是含稀疏的。

**第四句由 P-19 给**：这个数的上游，最近有东西动过吗？**四句合起来才完整。**
（⚠️ 别跟 §6 那三处自曝错误搞混 —— 那三处是**案例**，这三句是**动作**。）

**红色 band · 这一课查完仍然没有答案的六处**——不是免责声明，
那六条**跟前面所有内容一样都被核过**，区别只在于核完之后仍然没答案。
**而且有两种「查不到」，必须分开念**：

| 查不到的 | 哪一种 | 所以课件里怎么写 |
|---|---|---|
| B200 到底几个 SM（第三方拆解一致给 148，官方文档从未写） | 外部 | 148 / 592 及派生**一律注「第三方拆解」** |
| 138.9 与 137.2 差 1.2%，未定位 | 外部 | P-15 图上**索性不提这个数** |
| B300 是不是双 die 封装（只考据过 B200） | 外部 | P-18 ⑥ **只按 device 抽象说** |
| GB300 的 EP16（882.3）没复测 | 自己没做 | §7 所有倍数**都写成下限** |
| 软件成熟度差多少无法量化 | 自己没做 | P-18 ④ **只定性写「会变」** |
| GB300 那条 FP8 路的收敛没审过 | 自己没做 | P-17 甲② 的 2.06 倍**要加第三条限制** |

> **「自己没做」那三条才是真正该道歉的那种** —— 尤其最后一条：
> 2.06 倍是全课最大的数，而**我们只审了自己一侧的收敛**
> （v7 侧因伤收敛剔掉了 `fixed` 校准版，同一把尺子没量过对面）。
>
> **一份从头到尾没有「不知道」的材料，不是查得更全，是没在查。**

### 课件里没画的四条（原大纲内容，留给读者）

课上不讲，但写材料时用得上 —— 它们讲的是**怎么把一个数查对**，
跟上面两张图讲的**「查对之后怎么别让它坏掉」**互补：

1. **跨代沿用的常数必须按代号重查。** MXU 从 128 变 256 就是例子 ——
   「听起来像常识」的架构关系最危险，因为不会有人想到去核。
2. **口径不一致的表，不能拿来推口径。** 曾经有一条推理链是
   「这张表里 A 那行若按 X 填就矛盾，所以它按 Y 填」——
   看起来很严密，但前提是**这张表内部口径一致**，而它并不一致。
   **推得越漂亮，错得越彻底。**
3. **「交叉验证」本身可能没有分辨力。** 用「容量和带宽都对得上」去验证 HBM 配置 ——
   而两种完全不同的配置都能凑出同样的容量和带宽，**这个验证从一开始就分辨不出对错**。
   有效的做法是找一张**不同来源**的表，再拿一次**实测**对一下。
4. **想知道「有几个 X」，直接去找那个枚举。**
   在这类代码里，「数量常数」经常就住在「清单枚举」的最后一项 ——
   顺手就把「是哪几个」也拿到了。

### 讲法

**六十分钟的版本里这一节第一个该砍**——它不含任何硬件知识。
**但如果目的是让台下以后能自己判断一份对比报告，它是全课迁移性最强的一节。**
真要压缩：**保留乙格三句自问，其余全砍**；
**唯一不能砍的是红色那条「查不到的六处」**，念的时候把「外部」和「自己没做」分开。
