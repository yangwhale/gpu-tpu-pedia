# 读 profile 的陷阱（每一条都栽过）

## 陷阱 1：按算子名统计会漏掉大头

实测：按名字 grep MoE 的矩阵乘，只得到一步的 **1.3%**（100 ms / 7,850 ms）——
而理论计算量要求它至少占 1.80 s，**比物理下限还低 18 倍**。

**不是时间消失，是名字消失** —— 编译器把大量计算融进了别的算子，融合后不再叫原来的名字。

**修法**：给源码打 `jax.named_scope`，归属信息会留在 profile 的 `Framework op name` 字段里。

| 统计口径 | MoE 每步耗时 | 占比 |
|---|---|---|
| 按算子名 grep | 100 ms | 1.3% ❌ |
| **按 named_scope 聚合** | **2,565 ms** | **33%** ✅ |

再拆一层才看得见钱花在哪：量化辅助算子 1,464 ms、激活 offload 等待 603 ms、
排序 161 ms，**真正的矩阵乘只有 100 ms**。→ 优化方向完全变了。

## 陷阱 2：`Total self time` 不是「每步」

它是**跨所有 core、跨所有被抓的 step 的总和**。
除以 `core 数 × step 数` 才是「每 device 每步」。

**验算法**：用注意力算子对一下 —— 换算后应该占一步的 30–40%，
数量级不对就是除数错了。

## 陷阱 3：`Model GFLOP/s` 不是实测

它读的是代码里手写的 `cost_estimate`（`flops = 2*m*k*n`），
按输出张量的完整形状算，**不看 group_sizes 实际激活了多少行**。

**超过硬件峰值就是假的。** 见过报到峰值 54 倍的。
按实际激活行数重算才是真值 —— 重算后与端到端报的吞吐吻合到 0.3%。

## 陷阱 4：profile 只落在一个进程上

多机切片里，**profile / debug 输出只在 JAX 的 0 号进程那台机器上**。
查错了机器会得出「什么都没生成」的错误结论。**一晚上栽了三次**：
张量指纹、logits 落盘、xplane 文件，全是这个。

**先全机器扫一遍再下结论。**

## 陷阱 5：在分片区域内部做归约，拿到的是本卡局部值

分组矩阵乘通常跑在手动分片区域里。在其内部算的任何归约都是**本卡那一片**的值，
不是全局值。用它做跨 run 对比会得到**假的差异**。

（曾据此得出「换个分块就 0/30 位相同」，而同一配置在 logits 上其实完全一致。）

## 能看 / 不能看

- ✅ Pallas kernel 的**执行时长**（custom-call 的 self time）是准的
- ❌ kernel **内部**（分块循环轮数、VMEM 命中、MXU 利用率）看不到，要 LLO 层
