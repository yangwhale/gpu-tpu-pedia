## 2026-08-21 · 起手点应该是「大模型是什么」，不是「加速器是什么」

### 原始想法

1. 首先要讲大模型是什么，**从 Transformer 讲起**
2. 让大家理解了大模型之后，才会知道**为什么大模型需要 GPU、需要 TPU** ——
   Attention 需要什么样的算力、MLP 需要什么样的算力、训练和推理有什么区别，
   这些**全都需要模型的知识**才能讲清楚
3. 人们也要知道**模型的智商是从哪来的** ——
   Attention 决定「自己关注自己」，MLP 里存的是**事实**

### 这推翻了什么

v0.1 大纲的第 0 部分是「为什么需要另一种加速器」，从矩阵乘和脉动阵列讲起。
**这个起手点错了。**

错在哪：它默认读者已经接受「大模型就是要算很多矩阵乘」这个前提，
然后去讲怎么算得快。但读者并不知道**为什么**要算这些矩阵乘、
为什么是这个形状、为什么这一部分卡带宽而另一部分卡算力。
于是硬件部分只能靠背 —— 而背下来的东西没法迁移到新硬件上。

正确的顺序是：**先有模型，才有对硬件的需求，才有硬件的样子。**

### 为什么这条特别重要（我的理解）

这不只是「顺序好看一点」的问题，它决定了后面性能工程那部分能不能讲透。

Transformer 里两大块的计算特征是**根本不同**的：

| | Attention | MLP / FFN |
|---|---|---|
| 干什么 | token 之间**路由信息** —— 决定"这个词该看哪些词" | 存放并检索**事实** |
| 计算形状 | 序列长度的平方项，矩阵瘦长 | 稠密 GEMM，矩阵方正 |
| 推理时的瓶颈 | **带宽受限** —— KV cache 要反复读 | **算力受限** |
| 长序列时 | 占比迅速上升 | 相对稳定 |
| MoE 改的是谁 | 不是它 | **是它** —— 稀疏化的是 MLP |

一旦读者理解了这张表，后面很多结论就不用死记：

- 为什么长序列推理要盯着显存带宽而不是 TFLOPS
- 为什么 MoE 省的是算力不是显存
- 为什么训练和推理的硬件取舍不一样（训练全是稠密大矩阵，推理是一个 token 一个 token 挤）
- 为什么会有 KV cache、为什么它那么占地方
- 为什么 attention 有那么多变体（MQA/GQA/MLA/线性注意力），而它们**都在省同一样东西**

**反过来，如果先讲硬件再讲模型，上面每一条都变成孤立的结论，只能背。**

### 「智商从哪来」这条要单独展开

这是一个大多数系统课程**完全不讲**的角度，但它恰恰是让人真正理解模型的入口。

- **Attention 负责关联** —— 它决定在当前上下文里该关注什么。
  「自己关注自己」（self-attention）这个名字里就写着答案：
  一句话里的每个词都去看这句话里的其它词，从而知道自己在这里是什么意思。
  能力体现在：指代消解、上下文一致、把远处的信息拉过来。
- **MLP 负责记忆** —— 事实性知识主要存在这里。
  可以理解成一组 key-value：前一层矩阵在做"这是在问什么"的匹配，
  后一层矩阵吐出"那答案是什么"。
  （这个观点有论文支撑，写的时候要把出处找出来补上 —— Geva 等人关于
  FFN 作为 key-value memory 的工作。**待核实原文，不要凭记忆写。**）
- 于是能顺理成章地解释很多现象：
  为什么模型「知道」很多事却「推不动」几步逻辑；
  为什么扩参数量主要是在扩 MLP；
  为什么 MoE 是在扩"记得多少"而不是"想得多深"。

### 对大纲的影响（草记，不定稿）

新的第 0 / 1 部分大概应该是：

```
第 0 部分 · 大模型是什么
  0.1 从一句话预测下一个词说起
  0.2 Transformer 的两个零件：Attention 与 MLP
  0.3 智商从哪来 —— 关联在 Attention，事实在 MLP
  0.4 训练与推理是两件不同的事
  0.5 规模是怎么长起来的：参数量、上下文、MoE

第 1 部分 · 于是它需要什么样的机器
  1.1 把 0.2 的两个零件翻译成算力和带宽的需求
  1.2 Attention 卡带宽，MLP 卡算力 —— 两种瓶颈
  1.3 训练卡吞吐，推理卡延迟
  1.4 单卡装不下：于是需要互联
  1.5 到这里才引出 GPU 和 TPU 各自的答案
```

原来的「脉动阵列 / 为什么 CPU 不够」下沉到 1.5 里，
从"历史叙事"变成"对一个已经提出来的需求的回答"。

这同时解释了两件事：模型为什么难解释，以及**为什么放大收益这么大**。

## 2026-08-21 · 扒了 CS336 的完整课程安排 → 三处编排要改

详见 [`参考-CS336课程安排.md`](参考-CS336课程安排.md)（19 讲课表 + 5 个作业 + 对照分析）。

最要紧的三条，都会动到大纲：

1. **「算账」应该在很前面，不是第 5 部分。**
   CS336 第 2 讲就是 resource accounting（FLOPs / 显存 / arithmetic intensity），
   把算账当**基础工具**教而不是当结论讲。学生从第 2 讲起就能对每个架构算一遍代价。
   我们 v0.1 把性能工程排在九个模块的第五个，太靠后。
   应该拆成「算账的方法」（前置）+「调优的实践」（后置）。

2. **`arithmetic intensity` 是 Chris 理念第 2 条的量化形式。**
   我们只把「Attention 卡带宽、MLP 卡算力」当现象记，CS336 把它变成能算的数。
   有了它，长序列为什么卡带宽、batch 为什么越大越划算、FlashAttention 到底改了什么，
   都能算出来而不是背下来。**必须补，而且要早。**

## 2026-08-21 夜 · Chris 的一条纠偏：深度收一收

补完实测数据之后，Chris 立刻指出**讲得太细了**：

> 「64 啊 128 呀、remat 增加了多少减少了多少、开了什么具体扩大多少倍 ——
> 这是一门**通用课程**，不是针对某一项参数的 deep dive。
> **听众是普通技术人员，不是大模型调优工程师。**」

### 他给的正确示范

> 「就讲明白方向性问题。举个例子：**remat 会省多少显存？会浪费多少算力？**」

一句话点透了标准：**要的是"这件事大概怎么回事、代价多大"，
不是"某个开关在某个规模上是 +1.22 还是 −0.74"。**

### 立成第 5 条编排原则

| ✅ 该讲 | ❌ 不该讲 |
|---|---|
| 数量级（"省掉大部分激活"） | 精确到小数点的实测值 |
| 比例关系（"算力从 3× 变 4×"） | 具体参数名和取值 |
| 方向（"用算力换显存"） | 只在某个模型上成立的细节 |
| 反直觉的结论（"换规模可能反向"） | 支撑结论的整张消融表 |
| 硬件常数（一张卡 94.74 GB） | 整除约束、分片形状这类调参细节 |

### 已按这条改掉的

| 原来 | 改成 |
|---|---|
| `temp_size` 报 142.30 GB、78.42→80.48、86.30→72.28 | 「远超单卡上限」「换个实现显存就会变，方向不固定」 |

| 锁频 +8.0% | 「有些 flag 是**纯赚**的，白拿百分之几还不涨显存」 |

### ⭐ 提炼出的一条一般规则

> **我们的实测数据，价值在于佐证一个方向性结论，不在于数字本身。**
> **留结论，砍表格。**

### 旧结构与推翻理由

旧：主线 6 个（V3 → 硬件 → 反向 → 并行 → 推理 → 调优），
注意力演进挂在「深入（按需）」的第一个。

推翻它的是**第一课自己算出来的一条曲线**。同一个模型、一个字没改，
只是把输入拉长，注意力占总算力的比例是：

| 序列长度 | 4K | 8K | 16K | 32K | 64K | 128K | 256K | 1M |
|---|---|---|---|---|---|---|---|---|
| 注意力占比 | 12.3% | 21.9% | 35.9% | 52.9% | 69.2% | **81.8%** | 90.0% | **97.3%** |

**瓶颈换了地方，而模型没变。** 一门以「边走边算」为方法的课，
把这条曲线算出来了却把「大家怎么应对」放进选修，是自相矛盾的。

第二条理由是**下游依赖**：并行策略里的序列维、推理里 prefill/decode
为什么瓶颈相反、模型对比里那一列「注意力方案」，全都要用到同一组概念。
按需选修意味着**主线课要么重复讲一遍，要么建立在听众没学过的东西上**。
