# 量化

## 精度链是两步

```
fp32 主权重（优化器里的真身）
   ↓ astype(dtype)        通用路径，所有精度都走
bf16 计算副本
   ↓ quantize(...)
fp8（权重 e4m3 / 激活 e5m2）
   ↓ 矩阵乘
fp32 累加 → bf16 输出
```

两步转换在数值上等价于一步（fp32→bf16 只丢尾数，指数位不变）。
**fp32 从来没有进过矩阵乘**，它只活在优化器里。

**激活用 e5m2**（多一位指数、少一位尾数）—— 动态范围大。

## 主权重必须 fp32

每步更新是 `主权重 += lr × 梯度`，梯度相对权重量级极小。
bf16 只有 8 位尾数，加上去直接被舍掉 = **更新丢失**。

外部佐证：Google 给 TPU 的官方建议是「权重和梯度保持 fp32，只把激活转 bf16」；
NVIDIA NeMo 的推荐模式是「fp32 主权重 + fp32 优化器状态 + bf16 计算」。

我们已经比标准激进了（梯度、一阶动量都降到 bf16），**主权重这条不能再动**。

## 校准方式

| | scale 怎么来 | 显存 | 质量 |
|---|---|---|---|
| `absmax` | 按通道动态求最大值 | 要归约缓冲 + scale 张量 | ✅ |
| `fixed,-a,a` | 钉死在预设范围 | **零**（编译期常量） | ❌ 伤收敛 |

**channel-wise 粒度本来就是开的**（权重按输出通道、激活按行），
所以粗糙的不是粒度，是校准方式。

**`fixed` 唯一的正当理由是跨卡量化收集。** 不用它就必须换 `absmax`。

**实测代价**：`absmax` 吃掉两档 batch（13 → 11），727.0 → 670.8（−7.7%）。
**这 7.7% 主要不是算得慢，是 batch 少了。**

## 量化只作用于分组矩阵乘

规则按算子名注册，**注意力全程 bf16**，不受影响。
