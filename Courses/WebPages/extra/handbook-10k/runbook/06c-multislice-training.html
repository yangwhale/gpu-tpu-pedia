06c 起一个数千芯片多切片训练（复现一份参考训练配置）

目标：第一次跑真实规模训练，并认得「跑对了」的样子。 难点：切片、DCN、共享存储、libtpu flag 任一环错都可能「看起来在跑」；JIT 下从 pod 起来到首步 32–45 分钟（从 apply 起算 40–50），出错也可能 exit 0。

💡状态 / 一句话结论

  • 本章是判读样板：私有代码路线照抄跑不起来；要跑的配方见 06b。
  • §6.1–6.8 已实测：10+ 片跑通，步时和原任务差 < 1%。
  • 这是 JIT 对照；大规模建议提前编译（AOT），Google 可协助。
  • 更大规模有已知限制（见 §6.9「规模边界」）。
  • 数千芯 10+ × 4x8x8，device 数 = 芯片 × 2
  • 约 +40% 10+ 片 JIT 稳态步时 p50（比 1 片）
  • 72% 弱扩展效率（以单片为 100%）
  • 40–50 min apply 到第一步，两段编译各约 20 min
  • 84 GiB 每 device HBM，上限 94.74 GiB

目标：所有 worker 在 /models 看到同一个桶。实测集群用静态 PV/PVC（scripts/06-data-pv-pvc.yaml）：

⚠️本书的 Kueue 配置会把 smoke pod（和 §6.2 构建 pod）永远挂在 SchedulingGated（未实测）

  • 原因：03 开了 manageJobsWithoutQueueName: true 和 pod 集成，$NS 没排除；带队列名也不行，ClusterQueue 只覆盖 google.com/tpu。实测集群注释掉了（03 §3.2）。

JAX 编译缓存

读图：缓存只省编译那一段，trace + lower 省不掉；权限不够时不报错。

  • 实测：1 cube 冷启动三十多 min → 命中缓存约 28 min（两次编译各 133 s → 7 s），trace + lower（~15 min）照做。
  • 权限：装了 TensorFlow 时 etils 走 gfile，makedirs 要整桶 storage.objects.list；gcsfs（EPATH_USE_TF=false）读也要 list（可用 objectListPrefix 限前缀）。
  • 键含 LIBTPU_INIT_ARGS 和 XLA_FLAGS（jax 0.11.0 cache_key.py _hash_xla_flags），改 flag 不误命中。放 gs://<你的桶>/jax-cache/<tag>/，即同区域的 gs://$DATA_BUCKET/jax-cache/<tag>/ [推断：路径布局照搬，未实测]，pod 身份要有上面那条整桶 list 权限。

overlay 管不到模型 yml 里已有的键（实测）

6.4JobSet（JIT 基线作业原样，删掉无关字段）

可直接跑的同构 JobSet 见 06b 公开配方。节选运维要对上的字段：

yaml
metadata:
  name: ${JOBSET_NAME}
  labels: {kueue.x-k8s.io/queue-name: ${LOCAL_QUEUE}}
spec:
  failurePolicy: {maxRestarts: 0, rules: [{action: RestartJobSet, onJobFailureReasons: [BackoffLimitExceeded]}]}
  replicatedJobs:
  - name: worker
    replicas: N
    template:
      spec:
        completions: 64
        parallelism: 64
        template:
          metadata:
            annotations: {cloud.google.com/gke-tpu-slice-topology: 4x8x8, gke-gcsfuse/volumes: "true"}
          spec:
            hostNetwork: true
            dnsPolicy: ClusterFirstWithHostNet
            nodeSelector: {cloud.google.com/gke-networking-dra-driver: "true", cloud.google.com/gke-tpu-accelerator: tpu7x}
            containers:
            - name: jax-tpu
              image: <公开 Python 基础镜像@sha256:…>
              securityContext: {privileged: true}
              command: [bash, -c, "<多行脚本>"]         # 解压 /models/${ENV_TAR} → 激活 venv → 合并 overlay → 启动训练脚本
              env:                                   # 只列运维要对上的
              - {name: ICI_FSDP_PARALLELISM, value: "512"}
              - {name: ENABLE_CHECKPOINTING, value: "false"}
              - {name: LIBTPU_INIT_ARGS, value: "--megascale_grpc_interface_prefixes=eth1,eth2,lo ..."}
              resources: {requests: {google.com/tpu: "4"}, limits: {google.com/tpu: "4"}}
              volumeMounts: [/models ← PVC, /tmp/ramdisk ← 200Gi 内存盘, /dev/shm ← 内存盘]
字段为什么这样写
  • completions: 64：一 pod 一台 host。hostNetwork: true：01 §1.7。queue-name 标签填 $LOCAL_QUEUE，即 03 §3.5 建的 LocalQueue（实测集群叫 multislice-queue）。
  • gke-networking-dra-driver：只有双网卡池有 eth2（02 §2.7 第 5 条）；megascale 是 libtpu 里管 DCN 通信的层。
  • command 另有打印版本、worker 0 日志同步（scripts/job_log_sync.sh → /models/pretrain/moe-large/<RUN_NAME>/）、tee，exit code 由 ${PIPESTATUS[0]} 透传；提交后多出 Kueue 注解、4x4x4-state 亲和、gke-tpu-topology: 4x8x8 nodeSelector 和 scheduling gate，正常。

flag 怎么生效

读图：越右越优先，能改中间两格，生效值认日志那行。

  • 默认 flag 另有 SparseCore collective offload 一组和 async allgather。XLA_FLAGS 不走这条链：默认 --xla_disable_hlo_passes=all_gather_decomposer,collective-pipeliner-forward，一设就整个替换 源实测作业启动脚本。

6.4.1 每个要紧参数是干什么的

取值出自 Config param 行和生效 LIBTPU_INIT_ARGS。

并行与 batch

参数 JIT 基线作业 干什么 约束 / 证据
num_slices N（片数） JAX 认为有几片 §6.3 规则
dcn_data_parallelism N（片数） 片间数据并行，每步 all-reduce 梯度 求和在 host CPU
ici_fsdp_parallelism 512 片内 FSDP 切 512 份 不开专家并行（EP=1）
per_device_batch_size × max_target_length 按生产配置 决定每 device 每步 token 数 超 HBM 可能静默挂住（一次韧性演练梯度累积 2 → 101.0 GiB，挂约 6 min 被杀，经验教训第 44 条）
weight_dtype / grad_dtype / dtype float32 / float32 / bfloat16 参数 / 梯度 / 计算的精度 梯度精度决定 DCN 流量

显存与编译

参数 JIT 基线作业 干什么 约束 / 证据
remat_policy custom：按张量选存 HBM 还是重算 重算换显存 多存常变慢
scan_layers true 按一层编译再循环 不 scan 编译更久、稳态略快
XLA_FLAGS 关 all_gather_decomposer、collective-pipeliner-forward 前者防止 all-gather 被改写成 all-reduce；后者关掉数据并行的通信重叠，省显存的是它（注 1） 有片间数据并行就必须带：不带时大号模型两片数据并行要 103.7 GiB；单片约 +3%
HLO 通信重排 关 一组私有的 XLA HLO pass（未开源），改集合通信的切法、落点和调度顺序；本书只讲理念和判据，实现需读者自行开发 只在 AOT 编译时生效，本章 JIT 基线不开
compiled_trainstep_file 空（= JIT） 加载 AOT 程序 JIT 10+ 片到 step 0 四十多分钟；AOT 编 512 device 约一小时

参数 JIT 基线作业 干什么 约束 / 证据
quantization: fp8_full + use_qwix_quantization + fp8_format: hybrid + use_tokamax_gmm 开 matmul 用 FP8（hybrid 以 Qwix 源码为准） 部分层保留 BF16

  • 注 1：数千芯 DEVICE_CHECK 一次过；≤4 片 DCN 基准看不出双网卡差别（按双网卡建网仍是经验教训第 20 条的要求）。

  • 怎么认出来：pod 全部 Running，日志停在 jax.devices()，超过看门狗时限没有下一行。
  • 有办法：Google 侧可协助对齐软件栈与初始化方式；大规模建议提前编译（AOT），Google 可协助。
  • 你要配合：上更大规模之前，先用要交付的训练栈重跑一次多片初始化；驱动带 INIT_TO 看门狗（§6.10 第 8 条），挂住时自动删 JobSet 并收证据。

说得出（先自己答，再点开对答案）

  • 为什么是 10+ × 4x8x8 而不是一个数千芯片的单片？
    整 pod 本来就得走 multislice；少而大的同形状切片 + DCN 数据并行已验证
  • ici_fsdp_parallelism: 512 和 dcn_data_parallelism: N 各管什么？
    前者切片内、走 ICI，= 每片 512 device；后者切片间、走 DCN，= 10+ 片
  • 一片 4x8x8 为什么是 completions: 64？
    256 chip ÷ 每 pod 4 chip = 64 pod
  • 日志停在 jax.devices() 或 Total memory size 之后 20 分钟没新行，要杀吗？
    不要：两段都是训练步编译，§6.6 ①；超过 60 min 再查经验教训第 44 条
  • 外部给的 TFLOP/s 和 MaxText 自报的怎么比？
    先确认是每 chip 还是每 device，每 chip = 2 device
  • 为什么不能单独加 --xla_tpu_use_megascale_host_reduction=false？
    运行 B 步时变成约 1.9 倍；要和 shard size 一起开，以训练步时为准
  • 10+ 片均值比 p50 高约 20%，扩展效率报多少？
    都报：对 1 片是 71%（p50）/ 59%（均值），差在慢步；本书实测无慢步，72%；§6.6 ③
  • 本章步时能当生产基线吗？
    不能：本章全是 JIT 对照；大规模建议提前编译（AOT），Google 可协助
  • 为什么 1 cube 冒烟不用大号模型？
    按 FSDP 切的状态变 4 倍；实测编了约 18 min 后报 OOM，光 HLO 临时内存就 97.12 GB > 94.74 GB
  • 阶梯跑到一半 JobSet ReachedMaxRestarts，第一件事查什么？
    Workload 有没有 NodeFailures、节点有没有 Shutdown / NodeNotReady——掉了 host 就直接重提，Kueue 会避开 UNHEALTHY 的 cube
