# playbook：跑通了但比预期慢

## 0. 先反向确认：是不是「其实是别的配置快得不真实」

如果对照组快得离谱，**先查对照组有没有漏算**（`knowledge/02-silent-failures.md`）。
慢的那个可能才是对的。

## 1. 算理论下限

```
每 device 每步 FLOPs ÷ 单 device 峰值 = 理论最快时间
```

拿它跟实测比，得到 MFU。**MFU 低于 30% 才值得往下查**；已经 50%+ 的话，
优化空间可能不在计算上。

## 2. 分清是计算还是通信

看通信算子的**暴露耗时**（async 的 self time 只算没藏住的部分）。
暴露占比高 → 通信没藏住，查 `knowledge/07-xla-flags.md`：
- SparseCore 卸载族有没有整套开
- 有没有手写的集合通信钉在依赖链中间

## 3. 用 named_scope 重新归因

**不要按算子名统计** —— 会漏掉被融合的部分（实测差 25 倍）。
打上作用域标签后重新聚合，看时间真正花在哪。

见 `knowledge/08-profiling.md` 的五个陷阱。

## 4. 常见的「慢」及其原因

| 现象 | 查什么 |
|---|---|
| MoE 矩阵乘占比很低但整体慢 | 量化辅助算子、激活 offload 等待 |
| 某个 kernel 的效率只有峰值百分之几 | Mosaic 参数（如流水缓冲深度）没配 |
| 换了 kernel 之后变慢 | `knowledge/11-tokamax-vs-native.md` |
| batch 小得反常 | 分片宽度被某个整除约束锁住了 |

## 5. 汇报

给出：理论下限、实测、MFU、时间构成的前三名、以及**下一步最值得试的一件事**。
不要罗列所有可能性。
