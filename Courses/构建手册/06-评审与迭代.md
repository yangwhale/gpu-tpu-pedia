# 06 · 评审与迭代

> 核心假设：**作者看不见自己的坑，因为作者已经知道答案了。**
> 所以要请一批不知道答案的人来读，每个人只戴一副眼镜；
> 然后真的站上去讲一遍，讲不下去的地方就是材料缺的地方。
>
> 这一篇讲：有哪几副眼镜、报回来的意见怎么核实、「十轮评审 ＋ 二十轮边讲边改」的完整协议、
> 修复的先后顺序、怎么记录、什么时候算审完。任务书原文在 [模板/评审任务书.md](模板/评审任务书.md)。

---

## 一、多副眼镜，一个 agent 只戴一副

| 眼镜 | 查什么 | 最值钱的产出 |
|---|---|---|
| **外行（麻瓜）** | 一个聪明但完全不懂这个主题的成年人，读到哪里会停下、皱眉、放弃。按四类报：看不懂、一目了然不了、字太多、卡壳。不查事实 | 最值钱的一副。专题三第一次跑就抓到别的眼镜都没报的三件事：一个符号三个意思、承重术语没定义、读图钥匙放在图底 |
| **逐图** | 每张图判 ✅ 原理 ／ ⚠️ 半图半表 ／ ⛔ 写字板，给最小改法；要求沿用已有比喻体系 | 顺手抓到静默渲染 bug：「两条曲线一根都没画出来，读者看到的是空坐标系，旁边还有个文字框在解释一张不存在的图」—— 所有自动检查都是绿的 |
| **文字** | 加粗滥用、该删的句子（至少 20 句）、该合该拆的小节 | 病灶的形状：「十段里九段是第一个分句被加粗」—— 一条能机械执行的规则胜过一百条逐段建议 |
| **讲师** | 拿着讲义真讲一遍：哪段讲不下去、时间对不对、哪些舞台指示漏到读者页面、台下必问而材料答不上的 5 个问题 | 教材和讲义之间的缝 |
| **分领域专家** | 按领域分：分布式训练、MoE／长上下文、推理系统、TPU、GPU、数字口径、kernel…… | 硬伤。专题五 R1 抓出 TPU v7 硬件门槛算错一倍 |
| **对抗式** | 专门找错、找自相矛盾 | 专题五 R8 抓到 13 条，例如一张图说 FSDP 通信不变、另一处说多一半 |
| **台账抽查** | 从出处台账里抽 N 行，回原文核对 | 专题五 R7 抽 18 行：一处并发数写错、一处数据混了两组实验，补了 7 行出处 |
| **自学者** | 不看讲义，只靠课件自学一遍 | 专题五 L18：softmax、rank 没定义；两处结论之间缺适用条件 |

⛔ **别写一份「全面审一遍」的任务书。** 它会退化成四平八稳的摘要 —— 每条都对，每条都不能动手。

**所有任务书末尾都加一句**：「凡是拿不准的，标一句『这条我不确定，判据是 X』。」
没有这句，agent 会把「我猜」写成「实测」；加了之后它会自己分层，而那一层正好就是你该去核的那批。

**派之前先跑脚本**：`脚本/course-metrics.py` 量静默渲染失败、投屏字号、加粗占比。
能算出确切数字的，不要写进 agent 的任务里 —— agent 擅长判断，不擅长数数，而且数错了还很自信。

**交集优先**：专题四一次派了 5 个外行加 5 个专家，互不通气，按「几人都报了」分级。
被 3 人列为第一优先的「loss 怎么算整条链缺失」，经 grep 核实后排在最前面修。

## 二、核实之后才动手

**agent 报的不都是真的，而假的那部分长得跟真的一模一样。**

### 认现象，不认根因

实测：事实性发现基本都成立，**因果解释常常是错的**。
例：报「落点带被盖住，因为面板高度声明不足」—— 现象是真的（内容确实没了），
根因是错的（是被下一块面板的**白底**擦掉的）。两种根因的修法完全不同。

### 反例：认了它的算式，结果修错了

专题三有一轮认了专家给的「batch=32 就是 8.0×」—— 那是稠密模型的直觉，而 V3 是 MoE，实际只有 1.66×。
被下一个专家当场逮住。记录原话：「算术对，模型错。」「我认了它的算式。」

### 怎么核

| 声明类型 | 怎么核 |
|---|---|
| 「这个词没定义过」 | `grep -c` 数一下，再看上下文 |
| 「说三条只列了两条」 | 去看那个列表 |
| 「曲线没画出来」 | `grep -l 'd="\[(' figs/*.svg`，一秒确认 |
| **几何类（被盖住、溢出、重叠）** | **必须真的渲染一张出来看**，别信描述 |
| 数字、口径 | 回原始记录（论文、config、运行手册）核 |

⚠️ **关键词扫描会扫出假缺口。** 专题四连续几轮误判「讲义缺口」，其实只是措辞不同。真缺口是按顺序读出来的。

## 三、两阶段迭代协议

以专题五为标准版（2026-09-25 凌晨，初稿完成后约三小时跑完三十轮）。

### 第一阶段：十轮评审（R1–R10）

每一轮：

1. **并发派两个只读 agent**：一个外行视角、一个专家视角，每轮换眼镜和范围。
2. 回报后**逐条核实**（现象认、根因自己查），决定改或不改；不改的写理由。
3. 改 → `bash build-all.sh` → commit／push → 追踪文件记一行 → 发下一轮。
4. 每轮结束发一条通知（不触发任何人接着干活，只是让人看一眼）。

专题五的轮次安排和实际抓到的东西：

| 轮 | 外行那副 | 专家那副 | 抓到的（节选） |
|---|---|---|---|
| R1 | 产品经理读零–三节 | 分布式训练 | **v7 硬件门槛 1,922 → 3,845**（把收发合计带宽当成了单向），TP 上限 17 路 → 约 8.4 路；两节互相矛盾；ZeRO-2 切 micro-batch 时不白送 |
| R2 | 爱好者读四–五节 | MoE／长上下文 | **DCP 每层 3 次通信不是 1 次**（动画重渲）；补 Q／K／V、MLA、节点等词 |
| R3 | 外行读六–八节 | 推理系统 | **KV 传输「约 100 ms」是按带宽估算不是实测**（动画重渲）；AFD 要 3–4 个小批；GB300 同并发 2.09× |
| R4 | 逐图审（全部图 ＋ 动画） | 讲义↔课件一致性 | **流水线动画的气泡没有真的缩一半**（重画）；频率图改线性刻度；讲义跟上 GB300 口径等 14 处 |
| R5 | 文字眼镜 | TPU | 重画两张写字板图；去补丁味；TP8 在 V3 上实际落在线下 |
| R6 | 讲师试讲 | GPU／NVIDIA | GB300 头条从 2.47× 改为同并发 2.09×（2.47× 是首字延迟 95 秒的点）；补术语、比方、过渡、5 处互动 |
| R7 | 外行全篇重读 | 台账抽查 18 行 | 一处并发数错、一处数据混杂；新增全景图 |
| R8 | 只听讲义 | 对抗式找错 | 13 条矛盾；所有「看图」句补口述 |
| R9 | 外行全篇 | 专家全篇 ＋ 复查前八轮改动 | 新增 Ulysses 动画；专家总评「可以放进内部培训」 |
| R10 | 收敛轮：只报剩余严重问题 | 同左 | 外行「能直接上课」（易懂 8／图 9／主线 9）；专家「无硬错」 |

### 第二阶段：边讲边改（L1–L20）

原始指令：「按照最新文档，迭代式：先讲一节，发现有什么要修改的地方，之后二十轮就光优化这个文档。」

每一轮派一个「讲师」agent，按最新课件和讲义把指定小节**完整口播一遍**（写出逐字稿，含现场会补的话），同时报告：
哪里讲不顺、哪里必须临场补话（说明材料缺了）、哪张图讲的时候不够用、有没有说错。
核实 → 改课件和讲义 → 构建 → 提交 → 记一行。

| 轮 | 做什么 | 抓到的（节选） |
|---|---|---|
| L1–L8 | 一节一轮，从开场讲到收尾 | 看图钥匙前置；动画与新图不同步（重渲）；DEP8 当场定义原说法不准；AFD 图改成三条道三个小批；删掉一段误导的归因 |
| L9 | 全篇串讲，只看衔接与节奏 | 删 6 处重复接力；PCP 挪到第六节；砍掉一段拖节奏的图；互动重新分布 |
| L10–L17 | 第二遍，换**自学视角** | 讲义里好用的比方和推导补回课件；DCP 动画加对照帧；**共用基元 `anchorize` 把「技术报告 §2.1」链到了本讲 §2.1**（静默错链） |
| L18 | 整本自学通读 | 自学 7／图 8／主线 8；8 个卡点；去补丁味 6 处 |
| L19 | 讲义↔课件终稿对账 | 一条备答写错；讲义指错列；「可压到」五节全低于地板（删掉并加断言） |
| L20 | 逐张截图目检 ＋ 全量构建 | 三处文字重叠，其中一处根因在共用基元（图例估宽漏乘等宽系数），改基元全课受益 |

### 两阶段抓到的东西不一样

- **评审阶段**抓的是**事实和口径**：算错的门槛、说错的通信次数、估算当实测、同条件比较。
- **试讲阶段**抓的是**讲法、衔接和共用基元**：讲不下去的顺序、缺的过渡、指错的列、藏在共用库里的静默错误。
- 抓到了但没处理对的：L19 发现上游运行手册把 DeepSeek-V4 写成 MLA、跟专题三矛盾，
  当时只在讲义备答里注了一句「手册笔误」，没去改源头。改源头，以及写对它到底是什么（CSA 与 HCA 交错堆叠），
  都是人看了之后指出来的。由此立了两条规矩：**发现错误当场改源头；更正要写出正确的是什么。**
  也说明 **AI 扮演的审稿人再多，也替代不了真人看一次。**

## 四、修复的先后顺序

1. **静默 bug** —— 内容压根没渲染出来（空图、被擦掉的字、SVG 被截断），比任何文字问题都严重
2. **一个符号／术语在同一份材料里有两个意思** —— 会让读者整节都理解错（例：「累加器」在两节里指两样东西）
3. **承重但没定义的词** —— 一句话就能补
4. **正文复述图注、逐字重复** —— 删了零损失
5. **加粗瘦身**
6. **重画写字板图** —— 最贵，放最后

两条元规则：

- **修基元，不修实例。** 同一个毛病出现在八张图上，病根在共用库里。
  实测：面板外框从白色实心改成透明，一行代码救回 14 张图被擦掉的内容。
- **判据做成断言或 lint，别只写进注释。** 写在注释里的判据只在那个文件生效。
  例：「三条限制只列了两条」→ `lint_list_counts`（标题说几条，列表就必须正好几条）。

## 五、记录和汇报纪律

- **追踪文件**：每个多轮任务一份，格式见 [模板/追踪文件模板.md](模板/追踪文件模板.md)。
  开头记现场原话和轮次安排；每轮一行「轮次 commit：抓到什么／改了什么／没做什么」。
- **口头约定的配额当场写进文件**（「来十轮」「二十轮」）—— 隔一夜，「还剩几轮」谁都答不出。
- **评审原文落盘**。评审只活在对话里等于没做。
- **每轮 commit／push**，只 add 自己改的文件。共享仓库里 `git add -A` 曾经误带了另一个人正在改的另一讲。
- **中途播报用通知，不用会触发别人干活的消息**。一个每分钟播报一次的任务，不该每次都让接收方停下手头的事。
- **跨夜的任务要挂定时唤醒或监控**。「我继续做，做完告诉你」说出口不等于有人在做 —— 有一次提交后空转了 9 小时。

## 六、什么时候算审完

- **最后一轮只报剩余严重问题并打分**。专题五 R10：外行评「能直接上课」，专家「无硬错」。
- **机器指标全绿**：循环接缝全绿、没有静默渲染失败、加粗占比达标、对账 0 条对不上。
- **出率衰减**：同样的审法，削出来的东西越来越少，就是快到底了（专题四：没审过的节削 20%，审过一轮的 9–10%）。
- **目标没达到就如实报**，不硬凑。专题四炼钢目标削 21%，实际 7.1%，如实写进记录。
