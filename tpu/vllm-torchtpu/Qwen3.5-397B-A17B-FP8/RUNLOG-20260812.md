## R0 · 拿到 4 芯片测试环境　✅

**先试的路（失败）**：在自有项目 `tpu-launchpad-playground` 的 `chrisya-tpu` 集群上用 DWS
flex-start（node pool `hy3-v7-4-dws`，2x2x1）。

- ProvisioningRequest `Accepted=True / SuccessfullyQueued`，但 **排队 4 小时未拿到节点**。
- 结论：自有项目上的 v7 flex-start 容量不可预期，不适合有时限的验证。

**踩坑 1 — DWS node pool 有两个 taint，少容忍一个就永远 Pending**

```
taints:
  google.com/tpu=present:NoSchedule
  cloud.google.com/gke-queued=true:NoSchedule   ← 容易漏
```

只加前者时 autoscaler 一直回 `Pod didn't trigger scale-up: 1 node(s) didn't match Pod's
node affinity/selector`。两个都容忍后仍不触发 —— 因为 `gke-queued` taint 表示这是
**排队式 DWS**，必须先提 `ProvisioningRequest`，Pod 再用注解去消费它：

```yaml
annotations:
  cloud.google.com/consume-provisioning-request: <pr-name>
  cloud.google.com/provisioning-class-name: queued-provisioning.gke.io
```

**踩坑 2 — TPU Pod 的 nodeSelector 不能精简**

想只留 `gke-nodepool` 一条时被准入控制器拒绝：

```
Workload included the 'cloud.google.com/generate-allowlist: "true"' annotation,
but the constraint(s) {tpu-accelerator-topology-constraints} cannot be bypassed
```

`gke-tpu-accelerator` 与 `gke-tpu-topology` 两条**必须都写**。顺带确认 v7x 的值是
`tpu7x`（不是 `tpu-v7x-slice` 那种 v5p/v6e 风格），topology `2x2x1`。

**成功的路**：共享集群 `bodaborg-tpu7x-nap` 提 JobSet，**22 秒** Kueue admit + Pod Running。

```yaml
metadata:
  namespace: priority-dev
  labels:
    kueue.x-k8s.io/queue-name: multislice-queue
spec: ... 
        priorityClassName: medium
        nodeSelector:
          cloud.google.com/gke-tpu-accelerator: tpu7x
          cloud.google.com/gke-tpu-topology: "2x2x1"
          cloud.google.com/reservation-name: cloudtpu-20260710003900-159478293
        resources:
          limits: {google.com/tpu: 4}
```

提交前实测的容量（19:07 HKT，**off-peak**）：

| 指标 | 值 |
|---|---|
| `priority-dev` 队列 nominal | 119（off-peak；peak 为 375） |
| 队列 used | 64 → **剩 55** |
| 物理 tpu7x 节点 | 29 台 / 116 芯片 |
| 物理 Running 占用 | 116 芯片 → **物理 0 空闲** |

> **判断**：物理 0 空闲**不代表拿不到**。这是 NAP 集群，pending 的 workload 会触发自动扩节点，
> 上限 375 芯片。判据是 `min(队列余额, 375 − 已开)`，不是 `min(队列余额, 当前已开 − Running)`。

**拿到的环境**：

```
node        : gke-tpu-bdaf394b-4s86
/dev/vfio   : 0..7          → 8 device = 4 chip（chip:device = 1:2）
TPU_TOPOLOGY: 2x2x1         TPU_CHIPS_PER_HOST_BOUNDS: 2,2,1
host        : 224 vCPU / 944 GB RAM / 95 GB 根盘（可用 76 GB）
```

8 个 device 正好对上 Qwen3.5-397B 三种布局的 `TP × DP = 8`。

**踩坑 3 — 后台 watch-task 会抢 kubeconfig 的 current-context**

盯 DWS 的那个 watch 任务每 3 分钟跑一次 `gcloud container clusters get-credentials chrisya-tpu`，
把默认 context 改走，导致这边 `kubectl exec` 报 `namespaces "priority-dev" not found`。

修法：本次会话所有命令走独立文件，不碰默认 kubeconfig。

```bash
export KUBECONFIG=/tmp/kc-bodaborg.yaml
gcloud container clusters get-credentials bodaborg-tpu7x-nap \
  --region=us-central1 --project=cloud-tpu-shared-capacity
kubectl config set-context --current --namespace=priority-dev
# 验证 server 必须是 https://35.253.203.133
```

## R2 · torch_tpu 本体验证　✅

镜像自带的关键包：

| 包 | 版本 | 说明 |
|---|---|---|
| `torch` | **2.11.0+cpu** | 注意是 **CPU 版** torch |
| `torch_tpu` | 0.1.1 | |
| `torchax` | 0.0.11 | torch ↔ JAX 桥接 |
| `jax` / `jaxlib` | 0.9.2 | |
| `libtpu` | 0.0.41 | |
| `numpy` | 2.0.0 | |

`import torch, torch_tpu` 的输出暴露了接入机制，值得记：

```
PyTorch PrivateUse1ProfilerRegistry not found. Native TPU profiling will be disabled
    (this is expected on PyTorch < 2.12).
PjRt runtime initialization deferred for tpu
Successfully renamed PrivateUse1 backend to 'tpu'. Device: device(type='tpu')
Registered Python module for 'tpu'.
Initializing TPU distributed runtime
```

**结论**：torch_tpu 走 PyTorch 官方的 **PrivateUse1 第三方设备接入点**，把它改名成 `tpu`，
底下接 PJRT。所以 torch 本体是 CPU 版并不矛盾——TPU 能力整个由 PrivateUse1 后端提供。
import 耗时 **8.5 秒**（每次进程启动都要付）。

### 最小计算验证

```python
import torch, torch_tpu
print(torch.tpu.device_count())          # 8
d = torch.device("tpu")
a = torch.randn(4096,4096, device=d); b = torch.randn(4096,4096, device=d)
c = a @ b; float(c.sum().cpu())
```

| 项 | 实测 |
|---|---|
| `device_count()` | **8**（= 4 chip × 2，与 `/dev/vfio` 的 0..7 一致） |
| 首次 matmul（含编译） | **3.10 s** |
| 稳态 4096³ matmul | **0.289 ms/次** |
| 编译缓存命中 | `num_cache_hits=23 {85.1%}` |

> ⚠️ **不要**把 0.289 ms 直接换算成 MFU 去跟峰值比。输入是 `torch.randn` 的 **float32**，
> XLA 在 TPU 上对 fp32 matmul 有自己的降精度策略（bf16 多趟等），这个数字的精度口径未确认，
> 且只用了 device 0。作为「环境活着、算得动」的冒烟足够，作为性能数据不合格。
> 真实性能以后面 vLLM benchmark 为准。

## R3 · 安装 vllm_torchtpu

**踩坑 5 — `vllm_torchtpu` 不是预编译包，registry 里没有**

```
$ pip3 index versions vllm_torchtpu
ERROR: No matching distribution found for vllm_torchtpu
```

私有 registry `torch-tpu-virtual-registry` 提供的是 **torch-tpu 及其依赖**，
`vllm_torchtpu` 本身必须**从源码 editable 安装**（`pyproject.toml` 里 `name = "vllm_torchtpu"`，
但不发布 wheel）。README 的 Installation 第 2 步写的就是 `uv pip install --pre -e .`。

**踩坑 6 — `TOKEN_FAIL` 的真因是镜像里没有 curl**

一开始想在 pod 内用 metadata server 拿 token，脚本报 `TOKEN_FAIL`，第一反应是
Workload Identity 没配。实际是 **`curl` 命令不存在**。改用 `python3 urllib` 后 metadata 正常：

```
node SA: cloud-tpu-shared-capacity.svc.id.goog
```

> 教训：在精简镜像里，「命令不存在」和「权限不足」的报错长得很像。诊断顺序应该是
> 先 `command -v`，再谈权限。

**镜像内工具链实测**：

```
git:N   uv:Y   pip3:Y   python3:Y   gcc:N   g++:N   make:N
网络   pypi 200   github 200   us-python.pkg.dev 200
磁盘   74 GB 可用
```

`uv` 有（官方推荐路径可用），但 **`git` 和编译器都没有**。所以：

- 不能 `git clone vllm` → 改用 `urllib` 直接下 GitHub 的 tag tarball
- 若 vLLM 安装过程需要编译 C 扩展，会失败（`VLLM_TARGET_DEVICE=tpu` 理论上跳过 CUDA kernel，待验证）

**采用的安装流程**（无 git 版）：

```bash
export UV_TORCH_BACKEND=cpu
export UV_INDEX_TORCH_TPU_REGISTRY_USERNAME=oauth2accesstoken
export UV_INDEX_TORCH_TPU_REGISTRY_PASSWORD="$(gcloud auth print-access-token)"

# 1. 下 vLLM v0.26.1rc0（无 git，用 urllib 拉 tarball）
python3 -c "import urllib.request,shutil;u='https://github.com/vllm-project/vllm/archive/refs/tags/v0.26.1rc0.tar.gz';open('/work/vllm.tgz','wb').write(urllib.request.urlopen(u,timeout=120).read())"
tar xzf vllm.tgz && mv vllm-0.26.1rc0 vllm

# 2. 关键一步：删掉 tpu-inference 依赖，否则会跟 vllm-torchtpu 装到一起冲突
sed -i '/tpu-inference/d' vllm/requirements/tpu.txt

# 3. 装 vLLM（editable，TPU target，锁版本防 .dev 预发布错配）
SETUPTOOLS_SCM_PRETEND_VERSION=0.26.1rc0 VLLM_TARGET_DEVICE=tpu \
  uv pip install --system -e /work/vllm

# 4. 装 vllm_torchtpu
uv pip install --system --pre -e /work/vllm-torchtpu
```

> 用 `--system` 而不是建 venv：镜像里的 `torch_tpu` / `libtpu` 装在系统 python 下，
> 新建 venv 会把它们隔离掉。

```
Because torch-tpu was not found in the package registry and

```

| | 版本 |
|---|---|
| 主干 `pyproject.toml:35` 钉死 | `torch-tpu==0.1.1.dev20260804130134`（**08-04** 的 nightly） |
| 可访问的最新 base 镜像 | `torch-tpu:nightly-20260726`（**07-26**），自带 `torch_tpu 0.1.1` |

### plugin 激活确认（本轮最关键的一步）

```
INFO [__init__.py:54] - torchtpu -> vllm_torchtpu.platforms:register_tpu_platform
INFO [__init__.py:18] TPU info: node_name=None | tpu_type=tpu7x-8 | worker_id=0
                      | num_chips=8 | num_cores_per_chip=2
INFO [__init__.py:237] Platform plugin torchtpu is activated
current_platform: TpuPlatform tpu
```

注册到的两个 entry point：

| group | name | target |
|---|---|---|
| `vllm.platform_plugins` | `torchtpu` | `vllm_torchtpu.platforms:register_tpu_platform` |
| `vllm.general_plugins` | `torchtpu_layers` | `vllm_torchtpu.layers:register_layers` |

**这证实了架构分析：vllm-torchtpu 是纯 plugin，vLLM 上游代码零改动。**

> ⚠️ **口径注意**：vLLM 报的是 `num_chips=8 | num_cores_per_chip=2`，但我们申请的是
> **4 chips**（2x2x1）。真实硬件是 4 chip × 2 core = 8 device，`/dev/vfio` 里也是 8 个，
> `torch.tpu.device_count()` 也是 8。**vLLM 这里的 `num_chips` 实际是 device 数**，
> 按字面理解会把规格记成两倍。配置 `TP × DP = 8` 指的是 8 个 **device**，对应一台四芯片机器。

> `ERROR [tpu_info.py:26] Unable to poll TPU GCE Metadata. Got status code: 404` —— GKE pod
> 里拿不到 TPU GCE metadata，会 fallback 到环境变量推断，**不影响运行**，别被 ERROR 级别吓到。

### ❌ 阻塞 C（本轮终点）：jax 版本与主干 kernel 不兼容

依赖补齐后，`LLM(model="Qwen/Qwen3-0.6B")` 报：

```
AttributeError: module 'jax.experimental.pallas.tpu' has no attribute 'BufferType'.
Did you mean: 'BufferedRef'?
```

**这条推翻了我在 R3 里的推测。**当时看到 `--no-deps` 能装能 import，我写的是
「钉死的 dev 版本号更像 CI 复现性要求，不一定是硬性 ABI 约束」——**错了，那是硬约束**：

| | |
|---|---|

## R6 · 修正 R5 的结论：不需要 CI 镜像，缺的是版本矩阵

R5 我把结论下成「必须拿 `torchtpu-vllm-*` CI 镜像的权限」。**这个结论过头了。**
真正缺的只是一组明确的版本，而这些包在我们**有权限**的 python registry 里都拿得到。

先验证那个被钉死的 torch-tpu 确实能下：

```bash
# → torch_tpu-0.1.1.dev20260804130134-cp312-cp312-manylinux_2_31_x86_64.whl (146.3 MB)  ✅
```

**踩坑 12 — `uv` 不读 `PIP_INDEX_URL`**

R3/R5 里 `Because torch-tpu was not found in the package registry` 的真因在这里：
我只设了 `PIP_INDEX_URL`，而那几步用的是 `uv pip install`。**uv 不认 pip 的环境变量**，
它要 `UV_INDEX_URL` / `--index-url`，或者 `pyproject.toml` 里命名 index 配套的
`UV_INDEX_<NAME>_USERNAME/PASSWORD`。改用 `python3 -m pip` 后一次就过。

> 这是本轮最有代表性的一个误判链：`uv` 拿不到包 → 报「registry 里没有」→ 我据此推断
> 「必须用 CI 镜像」。**工具的报错在描述它自己看到的世界，不是客观事实。**

**踩坑 13 — 装配套 torch-tpu 并不会自动带来配套 jax**

装上 `torch-tpu==0.1.1.dev20260804130134` 后：

```
JAX 0.9.2
BufferType 有没有: False
```

jax 仍是镜像自带的 0.9.2。torch-tpu 对 jax 的依赖是宽松的，**版本约束在 vllm_torchtpu
的 pyproject 里，不在 torch-tpu 里**。

### 完整版本矩阵（`pyproject.toml` 的 `dependencies`，这是唯一权威）

### pyproject 注释里藏着的两条运维信息（值得单独拎出来）

原文注释：

> `jax==0.10.2` — See the JAX fori-loop lowering monkey-patch in
> `src/vllm_torchtpu/env_override.py`; it works around a **Pallas remainder-loop bloat**
> this JAX pin regresses on (**validated on Qwen3.5-397B DP=8 EP**).

> `libtpu==0.0.44.1` — This libtpu pin needs the workarounds in `env_override.py`

**踩坑 14 — 让 pip 按 pyproject 解依赖会触发它重建 vLLM，而且用错 target**

不加 `--no-deps` 装 `vllm_torchtpu` 时，pip 看到 `vllm @ git+...@v0.26.1rc0`，

## R8 · 真实推理：Qwen3-0.6B 冒烟

模型加载后进入 TPU 编译阶段，日志清楚展示了**静态形状税**的实景：

```
[tpu_runner.py:4029] Compiling gather_logprobs with different input shapes.
[tpu_runner.py:4029] Compiling substitute_placeholder_token with different input shapes.
[tpu_runner.py:4029] Compiling model backbone with different input shapes.
[tpu_compiler.py:287] [TpuCompilerAdaptor] Compiling FX graph for range (16, 16)
[backends.py:393]     Compiling a graph for compile range (16, 16) takes 6.55 s
[tpu_compiler.py:342] Saved compiled executable to
    /root/.cache/vllm/torch_compile_cache/798870e724/rank_0_0/backbone/artifact_compile_range_16_16_subgraph_0
[backends.py:378]     Cache the graph of compile range (16, 16) for later use
[tpu_compiler.py:287] Compiling FX graph for range (32, 32)
```

要点：

- **每个 token 数桶单独编译一次**，单个 backbone 图约 **6.5 秒**。桶越多冷启动越久，
  这正是 `_get_exponential_token_paddings` 存在的原因——用指数分桶压桶的数量。
- 除 backbone 外，`gather_logprobs`、`substitute_placeholder_token` 等**采样侧算子也各自编译**。
- 编译产物落盘 `/root/.cache/vllm/torch_compile_cache/<hash>/rank_0_0/...`，**可复用**。
  → **在 60 分钟窗口里跑大模型，第一件事应该是把这个 cache 目录挂到持久卷或同步到 GCS**，
  否则每轮 pod 都要重新付一遍编译时间。397B 的桶数远多于 0.6B，这笔钱很贵。

### ✅ 推理成功

```
MODEL_READY_SEC 201.2
GEN_SEC 0.2
OUTPUT: ' Paris. The capital of Italy is Rome. The capital of Spain is Madrid.'
SMOKE_OK
```

| 项 | 实测 |
|---|---|
| 从 `LLM(...)` 到就绪 | **201.2 s**（含 HF 下载 + 权重加载 + 全部 shape 桶编译） |
| 16 token 贪心生成 | **0.2 s** |
| 输出正确性 | ✅ `The capital of France is` → ` Paris. ...` |

**`vllm-torchtpu` 在 TPU v7 上的端到端推理链路，本轮全部打通。**

201 秒里绝大部分是编译，不是加载——0.6B 的权重只有 1.2 GB。这更凸显了上面那条：
**编译缓存必须持久化**，否则 397B 的每一轮都要重付一次，而它的桶数和图规模都远大于 0.6B。
