## 这个专题要回答的一个问题

专题一里我们跟着一个 token 走完了前向，算出「装不进任何一块卡」。

**但那只是账单的一小半。**

真正训练一步，你要同时在显存里放着：权重、梯度、优化器状态、
还有一大堆**不能扔掉的中间激活**。

这个专题把这张账单补全。补完之后会发现一件事：

> **最大的那一块，既不是权重也不是激活 —— 是优化器状态。**
>
> 而这，正是所有并行策略要解决的第一个问题。

## 一 · 反向传播要付什么

### 1.1 算力：大约是前向的两倍

- 每一个矩阵乘，反向要算**两个**梯度：对输入的、对权重的
- 所以反向 FLOPs ≈ 2× 前向 → **一个完整 step ≈ 3× 前向**
- 这个 3 倍是后面所有 MFU 计算的基准，要讲清楚它从哪来

**算**：拿专题一第 7 步的前向 FLOPs，乘出一个完整 step 的算力

### 1.2 显存：激活为什么必须留着

**这就是专题一第 5 步立而未答的那个问题。**

- 链式法则要用到前向的中间结果 —— 算权重梯度时需要那一层的输入
- 所以前向过程中产生的激活，**不能算完就扔，得留到反向用到它为止**
- 于是显存占用不是"某一层的峰值"，而是**一路累加**

#### 专题一那个 106.75 GiB，其实已经是打过折的

专题一第 5 步算过：残差流每层一份 1.75 GiB，61 层 **106.75 GiB**。

**但那个数字有个隐含前提 —— 它假设每层只留入口那一份。**
而「每层只留入口那一份」恰恰就是**开了重算之后**的样子：层里面的东西全扔掉，
反向用到时拿入口那份重新算一遍。

所以 106.75 GiB 不是「激活的账」，是**已经做过一次交易之后的账**。
原始账单在下面 —— 而这个顺序很重要，**先看到原始账单，第二节那个决策才有分量**。

#### 不开重算，一层还要留什么

以 V3 为例，序列 131,072、batch 1、bf16。
基准单位：一份 hidden 宽的张量 = 131,072 × 7,168 × 2 B = **1.75 GiB**。

| MLA 子层留什么 | 宽度 | 大小 |
|---|---|---|
| norm 的输入（= 残差入口，重算模式下唯一留的那份） | 7,168 | 1.75 GiB |
| norm 的输出 | 7,168 | 1.75 GiB |
| Q 降维结果（layernorm 前后各一份） | 1,536 | 0.75 GiB |
| KV 降维结果（含 rope 那 64 维） | 576 / 512 | 0.27 GiB |
| **Q 展开后** | 128 头 × 192 = **24,576** | **6.00 GiB** |
| **K、V 解压后** | 128 头 × 256 = **32,768** | **8.00 GiB** |
| attention 输出 | 128 头 × 128 = 16,384 | 4.00 GiB |
| logsumexp（fp32） | 128 | 0.06 GiB |
| **小计** | | **约 22.6 GiB** |

| MoE 子层留什么 | 份数 × 宽度 | 大小 |
|---|---|---|
| norm 的输入 / 输出 | 2 × 7,168 | 3.50 GiB |
| 路由分数 | 256 | 0.06 GiB |
| **派发出去的激活** | **9 份** × 7,168 | **15.75 GiB** |
| gate / up / SwiGLU 乘积 | 3 × 9 份 × 2,048 | 13.50 GiB |
| **专家输出（合并前）** | **9 份** × 7,168 | **15.75 GiB** |
| **小计** | | **约 48.6 GiB** |

> 「9 份」= 被激活的 8 个路由专家 + 1 个共享专家。
> **每个 token 的那份激活被复制了九遍**，进去一次、出来一次，就是 31.5 GiB。
> 这是 MoE 在显存上最贵的地方 —— 而它在专题一那张参数量的表上**完全看不出来**。

**一层 MoE 块 ≈ 71 GiB，一层 dense 块 ≈ 40 GiB。**
58 层 MoE + 3 层 dense ≈ **4,245 GiB ≈ 4.15 TiB**。

> ⭐ **对照：开了重算 106.75 GiB，不开 4.15 TiB —— 约 40 倍。**
>
> 这不是「优化一下」级别的差距。**在这个规模上，重算不是选项，是前提。**

⚠️ **这张表的三条边界，讲的时候必须说清楚：**

- 这是**按算子逐项推出来的估算**，不是从哪份报告抄的。不同框架的算子融合程度、
  是否顺手重算便宜算子、MoE 派发是否真的物化九份副本，差别都很大 —— **当量级看，别当准数**
- **注意力分数矩阵没算在里面。** 专题一算过它在 128K 上是 4 TiB／层。
  FlashAttention 压根不把它写进显存，所以它不出现在这张表上。
  **换成不带 flash 的朴素实现，这张表整个作废**
- batch 和序列长度是**直接乘进去**的。上面全部是 batch=1、128K 的数字 ——
  长上下文在这一项上最痛，这也是[专题五](专题05-并行策略.md)里上下文并行存在的理由

#### ⭐ 一个反直觉的发现：MLA 的压缩，在训练前向里不生效

回头看 MLA 那张表里最大的两项：Q 展开的 6 GiB、K/V 解压的 8 GiB。

MLA 的卖点是把 KV 压到 512 维 —— 专题一第 2 步算过，128K 上省了 **56.9 倍**。
但那省的是**推理时的 KV cache**。训练的前向里，attention 依然要拿
完整的 128 头 × 256 维去算，**压缩表示必须先解压回来**。

这一条是从官方参考实现确认的，不是推断：`kv_b_proj` 作用在每个位置的
`compressed_kv` 上，输出宽度就是 `num_heads × (qk_nope_head_dim + v_head_dim)` = 32,768。

> ⭐ **同一个设计，在推理的账本上是省，在训练激活的账本上不省。**
>
> 这是全课反复出现的那个主题的又一个实例：**参数量、算力、显存是三本账，
> 不能拿一本的结论去推另一本。**

#### ⚠️ 一个非常常见的误解：FSDP 不分摊这笔账

很自然会想：都上 FSDP 了，这些激活应该被摊到几百张卡上了吧。**不会。**

**FSDP 的契约是模型状态 —— 参数、梯度、优化器状态这三样。**
ZeRO 论文把显存分成两类：model states（就是这三样）和 residual states
（激活、临时缓冲、内存碎片）。**FSDP / ZeRO-3 处理的是前者；激活属于后者，不归它管。**

容易混淆的地方在于：FSDP 下每张卡确实只持有自己那几条样本的激活，看起来像是「分掉了」。
但那是**批次被分了**，不是激活被切了 —— **每条样本的激活，在它所在的那张卡上是完整的。**

上面那 4.15 TiB（或者开了重算的 106.75 GiB）算的是**一条 128K 序列**的账。
这条序列整个待在一张卡上，**加多少张卡都不会让它变小**。

> ⭐ **要把这笔账切开，得动另外一条轴：**
>
> | 沿什么切 | 叫什么 | 切掉的是 |
> |---|---|---|
> | token | 序列并行 / 上下文并行 | 那 1.75 GiB 里的序列维 |
> | hidden | 张量并行 | 子层内部的中间张量 |
> | 专家 | 专家并行 | MoE 那九份副本 |
>
> 这几条跟 FSDP 是**正交的**，可以同时开 —— 这正是[专题五](专题05-并行策略.md)的主题。

补一句精确性：DeepSpeed 的 ZeRO-R 里**确实**有一项 activation partitioning，
但它沿的是**张量并行那条轴**，不是数据并行。所以结论不变 ——
**FSDP 那条轴不切激活。**

### 1.3 通信：梯度要汇总

- 数据并行下每张卡算出的是**部分梯度**，要 all-reduce
- 通信量正比于**参数量**，与 batch 无关
- 这一条留给[专题五](专题05-并行策略.md)展开，这里只把它列进账单

## 二 · Recompute：第一个真正的「决策」

专题一刻意只讲事实。到这里，**第一个需要做选择的地方出现了**。

- **想法**：激活占太多显存，那就**不留了** —— 反向要用的时候现算一遍
- **代价**：多一次前向，算力 3× → **4×**（约 +33%）
- 这是一笔明确的交易：**用算力换显存**

**粒度有三档**，从粗到细：

| 档 | 怎么切 | 特点 |
|---|---|---|
| **全量** | 每层只留入口，层内全扔 | 一个开关，省得最多，也最贵 |
| **按层** | 只 checkpoint 一部分层 | 粒度受层数限制，模型一大就不够细 |
| **按算子（选择性）** | 逐个张量决定留还是扔 | 粒度最细，**但需要一个判据** |

下面 2.2 就是那个判据。它比想象中简单 —— **只有一个数**。

### 2.1 全量重算：这笔交易到底划不划算

先把量级说清楚 —— **这才是要记住的东西**：

| | | V3 在 128K 上具体是多少 |
|---|---|---|
| **省下什么** | 激活那一大块 —— 显存里**随 batch × 序列长度增长**的部分 | **4.15 TiB → 106.75 GiB**，约 **40 倍** |
| **付出什么** | 多跑一次前向：总算力 **3× → 4×** | 大约 **多三分之一** |

> ⭐ 一句话：**用三分之一的算力，换掉四十分之三十九的激活显存。**
>
> 这个兑换比例夸张到不像是个「权衡」。所以在大模型训练里，
> **默认就是开着的** —— 值得讨论的从来不是开不开，而是开到哪一档。
>
> 反过来说：显存本来就宽裕的时候（小模型、短序列），它就是纯亏。

### 2.2 ⭐ 选择性重算只需要一个指标：每省一字节要付多少 FLOPs

对每一个中间张量问同一个问题：**把它扔掉，反向时重算回来，每省一个字节要付多少次浮点运算？**

比值越小越该扔。就这一个数，整张排序表自己就出来了。

**对线性层，这个数有闭式解，而且漂亮得出乎意料：**

```
一个 [S,k] × [k,n] 的矩阵乘
  重算代价 = 2·S·k·n  FLOPs
  产出张量 = S·n·2    bytes（bf16）
  ────────────────────────────
  每字节代价 = 2·S·k·n ÷ (S·n·2) = k
```

> ⭐ **重算一个线性层的输出，每字节要付的 FLOPs 恰好等于它的输入宽度。**
>
> `S` 和 `n` 全约掉了 —— **跟序列长度无关，跟输出多宽也无关。**
> 所以「哪个线性层最该重算」这个问题，答案就是**看谁的输入最窄**，
> 不用算，扫一眼 config 就知道。

**但 attention 不服从这条规则** —— 它不是线性层，代价随 S² 涨而产出只随 S 涨：

```
代价 = S²·nh·(qk_dim + v_dim)   ← causal 已折半
产出 = S·nh·v_dim·2  bytes
────────────────────────────
每字节代价 = S·(192+128) / (128·2) = 1.25 · S      ← 随序列长度线性增长
```

> ⭐ **两条线，一条是常数（输入宽度），一条随序列长度线性上升。所以它们必然相交。**
>
> 对 V3：`1.25·S = 7168` → **S ≈ 5,734**。
>
> - **短于 ~5.7K**：attention 比大多数线性层还便宜，是个好的重算对象
> - **长于 ~5.7K**：它一路变成最贵的那个，而且是线性地越来越贵

⚠️ **5,734 是个粗略交叉点，跟专题一那个 98,688 是同一种东西 —— 不是工程阈值。**
它依赖 causal 折半的口径、依赖 V3 的头维度（192/128）、依赖你拿哪个线性层做对照。
**要记的是那句「两条线斜率不同所以必然相交」，不是这个数。**

### 2.3 V3 在 128K 上排出来的名次

一层 MoE 块、序列 131,072、batch 1、bf16。按每 GiB 的重算代价升序：

| 张量 | 省显存 | 重算代价 | **每 GiB 付** | 结论 |
|---|---|---|---|---|
| MoE 派发（复制成 9 份） | 15.75 GiB | ~0 | **0** | 白捡 |
| RMSNorm 输出（每层 2 个） | 3.50 GiB | 0.01 TFLOP | **~0** | 白捡 |
| SwiGLU 乘积 9 份（逐元素） | 4.50 GiB | 0.01 TFLOP | **~0** | 白捡 |
| K/V 解压（输入宽 512） | 8.00 GiB | 4.40 TFLOP | **0.55** | 划算 |
| Q 展开（输入宽 1,536） | 6.00 GiB | 9.90 TFLOP | **1.65** | 划算 |
| 专家输出 9 份（输入宽 2,048） | 15.75 GiB | 34.63 TFLOP | **2.20** | 划算 |
| gate / up / 路由 / 降维（输入宽 7,168） | 9.14 GiB | 39.08 TFLOP | **7.70** | 边际 |
| **attention 输出** | **4.00 GiB** | **703.69 TFLOP** | **175.92** | **绝不** |

> ⭐ **回答那个直觉问题：「有没有占显存很小、算力却很大的东西？」**
>
> **有，就是 attention，而且极端。** 它只占 4 GiB，重算一次要 703.69 TFLOP ——
> 比排在它前面那一档贵 **23 倍**，比最便宜的那三项贵到没法比（除数是 0）。
>
> **但结论是反过来的：正因为如此，它是最该「留着」的那一个，不是最该重算的。**
> 判据只有一条比值，比值高的留、比值低的扔。

**把比值小于 3 的全收下来**：一层省 **53.5 GiB**，付 **48.9 TFLOP**。
而一层前向总共 **857.1 TFLOP**。

> ⭐ **约 6% 的算力，换掉约 77% 的激活显存。**
>
> 对比全量重算：**33% 的算力，换掉 97%**。
> **选择性重算的性价比高一个数量级** —— 这就是为什么它值得单独配。

**为什么 attention 会这么极端**：一层前向 857.1 TFLOP 里，
attention 一项就占 **82.1%**。

> 📌 **这个 82.1% 是个交叉验证，不是新数字。** 专题一第 2 步那条曲线在 128K 处报的是
> **81.8%** —— 两边算法完全独立，对上了。
> **这是全课反复用的那招：找一个外部锚点，一次性验证整套公式。**

### 2.4 ⭐ 同一条判据，2022 年给出的是相反的答案

「选择性重算」这个概念出自 NVIDIA 的
*Reducing Activation Recomputation in Large Transformer Models*
（Korthikanti 等，arXiv **2205.05198**，2022-05）。

**它的判据跟 2.1 一模一样** —— 论文原话是：挑那些
「占显存不少、但重算起来不贵」（*take up a considerable amount of memory
but are not computationally expensive to recompute*）的部分。

**但它选出来要重算的，恰恰就是 attention** —— QKᵀ、softmax、softmax dropout、
以及 attention over V。理由写得很清楚：这些算子
「输入很大因而激活很大，然而每个输入元素上的浮点运算次数非常低」。

论文的收益：GPT-3 省 **70%** 激活显存，只付 **2.7%** 算力；MT-NLG 省 **65%**，付 **1.6%**。

**为什么结论会反过来？因为它的序列长度是 2,048。**

| | 序列长度 | attention 每字节代价 | 占一层算力 |
|---|---|---|---|
| GPT-3（论文） | 2,048 | 2,560 FLOP/byte | 约 2.7% |
| **V3（我们）** | **131,072** | **163,840 FLOP/byte** | **82.1%** |

代入 2.2 那条公式：`1.25 × 2048 = 2,560`，比 V3 任何一个线性层的输入宽度都小 ——
**在 2K 上，attention 真的是最划算的重算对象。** 论文没错，是前提变了。

> ⭐ **同一条判据、同一个模型族、判据一个字没改，结论翻转。变的只有序列长度。**

⚠️ **一处口径要说明白，不然数字对不上**：论文那个 2.7% 用的是
`(s/6h) / (1 + s/6h)` 这个 Megatron 传统公式，**没有为 causal 折半**。
换成本课统一的 causal 口径，GPT-3 的 attention 占比是 **1.37%**。
两个都对，只是约定不同 —— **跨文献比这类比例前，先确认对方折没折半。**

**顺带一句：这件事今天已经不用你操心了。** FlashAttention 天生就不把分数矩阵
写进显存、反向时现算，等于把论文那条建议**内建成了默认行为**。
所以现代框架的选择性重算候选名单里，attention 根本不出现。

### 2.5 ⚠️ 但收益不能照抄别人的

**我们在混元 3 上做过完整消融，最值得记住的一条不是某个数字，
而是这个现象：**

> **同一个模型、同一个开关，换一个规模，收益可能从正的变成负的。**

原因不神秘：重算改变的是**计算与访存的配比**，
而这个配比在不同的并行配置、不同的芯片数下本来就不同。

**由此推出一条通用规则**（这条要记住，它不只对 remat 成立）：

> ⭐ **凡是会改变数据分片形状的参数，都不能跨规模照抄。**
> 小规模上验过的结论，到目标规模上必须重验。

**2.4 那个例子说明这条规则比听起来更狠**：序列长度也在这个名单里，
而且它翻转的不是收益的大小，**是收益的正负号** ——
在 2K 上最该重算的那一项，到 128K 上变成最不该动的那一项。

**另一个值得知道的量级**：在真实的训练 profile 里，
**重算掉的那部分 FLOP 可以占到已执行算力的三分之一左右**。

> 这顺带解释了一个常见困惑：**为什么 MFU 看起来那么低** ——
> 分母里有一大块被重算吃了，它做了功但不算进"有效算力"。

**顺带**：host offload —— 把激活挪到 CPU 内存，

## 三 · 优化器状态：真正的大头 ⭐

**这一节是整课的重心。**

### 3.1 一个参数到底要占多少字节

标准的 bf16 混合精度 + AdamW，**每个参数**在显存里的分身：

| 存的什么 | 精度 | 字节 | 为什么必须有 |
|---|---|---|---|
| 权重 | bf16 | 2 | 前向/反向实际用的那份 |
| 梯度 | bf16 | 2 | 反向算出来的 |
| **主权重（master weight）** | **fp32** | **4** | bf16 精度不够做累加更新，小的更新量会被直接吃掉 |
| **一阶动量 m** | **fp32** | **4** | AdamW 的动量项 |
| **二阶动量 v** | **fp32** | **4** | AdamW 的自适应缩放项 |
| **合计** | | **16 字节 / 参数** | |

> ⭐ **注意这三行 fp32**：主权重 + m + v = **12 字节**，
> 是那 2 字节 bf16 权重的**六倍**。
> **模型本身反而是这张账单上最小的一项。**

### 3.2 落到 V3 上

- 671B 参数 × 16 字节 = **约 10.7 TB**
- 其中纯优化器相关（master + m + v）= 671B × 12 = **约 8 TB**
- 对照一个 TPU v7 device 的 **94.74 GB**

> **光是把权重、梯度和优化器状态放下，就需要一百多个 device。
> 激活还一个字节都没算。**

这个数字就是**为什么必须并行**的最直接答案 ——
比专题一那个前向的账更硬。

### 3.2b ⭐ 但那 16 字节是「每张卡都有全套」的账 —— 切一刀就完全变了

上面那 16 字节，说的是**不分片**的情况：每张卡都自带完整的一套。
一旦开始切，账就完全不一样了 —— 而且**切到哪一级差别是数量级的**。

**671B、每参数 16 字节，看 N 张卡分摊之后每卡还剩多少：**

| 每卡常驻 | 公式 | 128 卡时 |
|---|---|---|
| **纯 DP** | 16 B × 全量 | 约 **10.7 TB** —— 荒谬 |
| **ZeRO-1**（只切优化器状态） | 4 B 全量 + 12 B ÷ N | 约 **2.7 TB** |
| **ZeRO-2**（再切梯度） | 2 B 全量 + 14 B ÷ N | 约 **1.4 TB** |
| **ZeRO-3 / FSDP**（全切） | 16 B ÷ N | **不到 100 GB** |

> ⭐ **看公式那一列，不用记数字。**
>
> ZeRO-1 和 ZeRO-2 的公式里都有一项**不带 ÷N** —— 那是全量常驻的部分。
> **加再多卡也压不下去，它是个地板。**
> 只有 ZeRO-3 把所有项都除掉了，才真正随卡数线性下降。
>
> **这就是为什么光有 ZeRO-1 不够，必须一路切到 ZeRO-3。**

**再往下一步**：ZeRO-3 下模型状态摊薄之后，对着单卡的 **94.74 GB** 一减，
看看还剩多少给激活：

| 卡数 | 模型状态 / 卡 | 单卡剩余余量 |
|---|---|---|
| 128 | 83.9 GB | **10.1 GiB** |
| 256 | 41.9 GB | 49.2 GiB |
| 512 | 21.0 GB | 68.7 GiB |
| 1024 | 10.5 GB | **78.5 GiB** |

> **所以「至少一百多张卡」是个假答案。**
> 真正的下限由**激活**决定，而激活随 batch × 序列长度涨。
> 这就把[专题一](专题01-一个-Token-的一生.md)那笔前向的账和这里接上了。

#### ⭐ 而且把这两个数放在一起看，会得到一个更硬的结论

- 1.2 节算过：**一条 128K 序列，即使开了重算，激活也要 106.75 GiB**
- 上表最后一行：卡加到 1024 张，**每卡余量最多也就 78.5 GiB**

余量的上限是单卡 HBM 本身，**88.23 GiB —— 永远小于 106.75。**

> ⭐ **也就是说：卡加到无穷多，这条 128K 序列也装不进任何一张卡。**
>
> 这不是估算，是个上界比较：106.75 > 88.23，中间没有可以调的旋钮。
> **FSDP 这条轴到此为止 —— 想跑 128K，就必须把序列本身切开。**
>
> 上下文并行不是「一种可选的优化」，它是长上下文训练的**准入条件**。
> 这条结论直接把[专题五](专题05-并行策略.md)从「还有哪些花样」变成「非做不可」。

### 3.2c ZeRO-3 下 bf16 权重根本不常驻 —— 它是流动的

上表 ZeRO-3 那一行写「16 ÷ N」其实还偏保守。
**bf16 那 2 字节在 FSDP 下连分片都不常驻，是用一层转一层的。**

这一条我们查过 PyTorch 源码，机制很干净：

- **常驻的是 `_local_shard`** —— 分片，且是**原始精度（fp32）**
- **`_mp_shard`**（低精度分片）在初始化时**立刻被 `_free_storage` 释放**，
  只有轮到这一层才 `_alloc_storage` + 一次 `copy_()` 隐式转成 bf16
- all-gather 的落点 `_full_param_padded` 是 bf16 的**完整一层**
- **all-gather 一完成，`post_unshard()` 立刻把 `_mp_shard` 释放掉**

官方对 `FULL_SHARD` 的描述逐字印证了这个生命周期：

> unshards (via all-gather) **before the forward**, reshards **after the forward**,
> unshards **before the backward** computation, and reshards **after the backward**.

也就是说 —— **前向走到某层：fp32 分片 → 转 bf16 → all-gather 成完整一层 → 用 → 全扔。
反向回到这一层：再转一次、再 all-gather 一次。**

任意时刻显存里的 bf16，只有**当前那一两层**的量，不是 61 层的量。

**代价是什么**（天下没有免费的）：
- 每层每方向多一次 fp32→bf16 的转换，纯访存
- 反向要**再 all-gather 一遍**（`SHARD_GRAD_OP` 可以不 reshard，
  用显存换掉这次通信 —— 又一个决策点）

> 📌 **讲课时要点破的一句**：
> 「每参数 16 字节」是个**教学用的朴素账**，用来砸出量级。
> 真实峰值要看**时间线**，不是把各项简单相加 ——
> 有些项是常驻的，有些项是流动的。**这个区分本身就是[专题五](专题05-并行策略.md)的入口。**

### 3.3 为什么主权重必须是 fp32

这一条值得单独讲，因为它反直觉：

- 训练后期，单步更新量相对权重本身**非常小**
- bf16 只有 8 位尾数 —— 小的更新量加上去会被**直接舍掉**，等于没更新
- 所以要留一份 fp32 的"真身"来累加，bf16 那份只是它的投影
- 这也解释了为什么 **FP8 训练难**：精度往下压的时候，
  哪些量可以压、哪些必须保留高精度，是有讲究的（那是另一课）

### 3.4 换个优化器，账单就变了

| | 状态大小 | 每参数字节（含权重与梯度） |
|---|---|---|
| **AdamW** | 2× 参数量（m + v） | 16 |
| **Muon** | **1× 参数量**（只有动量） | **约 12** |
| SGD + momentum | 1× 参数量 | 约 12 |

- **Muon** 用 Newton-Schulz 迭代对整个梯度矩阵做正交化，
  代替 AdamW 逐元素的二阶矩缩放 → **省掉了 v 这一整份**
- 671B 上这一份就是 **2.7 TB** 的差别
- ⚠️ 但它多了正交化的计算开销，而且不是所有参数都适用
  （embedding / head 通常还是走 AdamW）
- 待核实：Muon 实现里主权重是否仍需 fp32

> **优化器的选择是一个显存决策，不只是收敛速度的决策。** 这一点常被忽略。

## 四 · 这张账单直接决定了并行策略长什么样

**这一节是通向专题五的桥。**

把上面的账按大小排一下：

```
优化器状态（12 B/参数）  ████████████  最大
激活（随 batch × 序列长度涨）  ████████?   长上下文下可以超过它
权重（2 B/参数）        ██
梯度（2 B/参数）        ██
```

**ZeRO 的三级设计，正是照着这个顺序来的：**

| 级别 | 切什么 | 为什么是这个顺序 |
|---|---|---|
| ZeRO-1 | **优化器状态** | 它最大，而且**只在更新时用一次**，切了几乎不增加通信 |
| ZeRO-2 | 再切梯度 | 次大，反向结束时才需要完整的 |
| ZeRO-3（≈ FSDP） | 再切参数 | 最后才动它，因为**每一层前向都要用**，切了就得每层 all-gather |

> ⭐ **顺序不是随意的，是「谁最大、谁最少被用到，就先切谁」。**
> 理解了这张账单，ZeRO 的分级就不用背了。

同理：
- **重算**针对的是激活那一项
- **offload** 针对的是"暂时用不到"的那些项
- **CP** 针对的是激活里随序列长度涨的那部分

## 五 · 一个完整 step 的总账

把前向（专题一）+ 反向 + 更新合成一张表：

| 阶段 | FLOPs | 峰值显存贡献 | 通信 |
|---|---|---|---|
| 前向 | 1× | 激活一路累加 | （并行策略带来的） |
| 反向 | 2× | 激活逐步释放 + 梯度产生 | 梯度 all-reduce |
| 更新 | 极小 | 优化器状态常驻 | （ZeRO 下有额外通信） |
| **合计** | **3×**（重算则 4×） | | |

要回答：

1. 一个 step 总共多少 FLOPs
2. **峰值出现在哪个时刻** —— 这个问题比"总共多少"更有用
3. 全部加起来要多少 device

**顺带讲**：梯度累积 —— 用多个 micro-batch 攒一次更新，
在不增加显存的前提下放大有效 batch。它改变的是**时间线**不是总量
