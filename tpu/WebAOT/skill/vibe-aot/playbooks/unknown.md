# playbook：遇到没见过的失败

## 步骤

1. **读原始日志**，不要凭错误串的前缀猜。定位真正的异常类型与栈顶
2. 判断属于哪一类：配置非法 / 资源不足 / 编译器限制 / 依赖缺失 / 代码路径问题
3. **区分「实测过的」与「推断的」**，结论里明确标注置信度
4. 给出最小复现建议（通常是：减层数 + 保留同样的开关）

## 必须产出一条候选规则

按 `prompts/propose_rule.json` 的格式写一条草稿，包含：

- `when`：什么条件下会触发（尽量用确定性表达式）
- `detail`：会发生什么，**特别注明是不是静默的**
- `fix`：怎么绕开
- `evidence`：这次的实测现场（报错原文 + 配置）

人工确认后进规则库。**每踩一个新坑就沉淀一条，下次自动拦住** —— 这是这套东西唯一能复利的地方。

## 反面

- ❌ 不要因为「编译通过了」就说没问题 —— 最贵的那类 bug 恰恰是编译通过的
- ❌ 不要用短程 loss 判断分片改动对不对
