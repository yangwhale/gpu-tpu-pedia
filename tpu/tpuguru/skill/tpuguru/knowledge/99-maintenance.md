# 知识的维护：怎么让它不腐坏

这套东西的价值在于**准**。一条过期的数字比没有更糟 —— 它会被当成事实引用出去。

## 每条知识必须有的三样

1. **出处** —— 哪次实测、什么规模、什么日期
2. **置信度** —— 🟢机制 / 🟡规律 / 🔴数字（见 `00-scope.md`）
3. **可证伪的形式** —— 「X 比 Y 快 N%」可证伪；「X 更好」不可证伪，不要写

## 什么时候必须回来改

| 事件 | 要复查什么 |
|---|---|
| 换编译器 / 镜像 tag | **全部 🔴 数字**，以及「能不能提升出循环」这类编译器行为 |
| 上游改了 kernel 代码 | 🟢 机制类的结论（分支逻辑、参数消费位置） |
| 换模型 | 所有 per-chip 数字、batch 上限、tile 甜点 |
| 换硬件代次 | 硬件常数、峰值、device/chip 比 |

## 推翻旧结论的规矩

**不要偷偷改数字。** 被推翻的结论要：

1. 保留原文，加撤回标记，写清**为什么错**
2. 在汇总表/最高水位那类**容易被单独引用的位置**同步更新 ——
   实测教训：正文改了、汇总行没改，读者只看汇总就走了
3. 如果错误结论已经沉淀成规则，标 `supersedes`

> 已作废的例子见 `10-baselines.md`：某个 per-chip 数字曾被报为最高水位，
> 实为漏算换来的。**凡是看到它，一律当无效。**

## 复利路径

```
遇到新坑 → playbooks/unknown.md → 产出候选规则（prompts/propose_rule.json）
        → 人工确认 → 进规则库 → 下次自动拦住
        → 若这条坑有普遍性，再补一篇 knowledge/
```

**判断值不值得沉淀的标准**：它是不是**静默的**。
报错的坑看一眼就知道；静默的坑要花几天 —— 那种才值得写进来。
