# LiveAvatar on B200 · 优化实录

从 **0.232× 实时** 到 **1.357× 实时**（单卡，5.8×）的完整过程：每一步做了什么、
量到什么、哪些假设被证伪、哪些坑是自己挖的。

**按时间顺序记，包括走错的路** —— 那些否定结果和成功的一样有用，
因为它们标出了「这个方向别再试了」。

> 所有性能数字都是**纯视频生成时间**，不含启动/加载/编译。
> 口径见末尾「测量方法」一节。

## 第一阶段 · 定位瓶颈（不是 attention）

### 出发假设：Blackwell 上的 FlashAttention 代际问题

合理的怀疑：B200 是 sm_100，FA2 没有原生 kernel。**微基准证实了这一点**
（B200，40 头 ×128，bf16）：

| seq len | FA2 | **cuDNN** | flash-SDPA | mem-efficient |
|---|---|---|---|---|
| 1560 | 0.155 ms | **0.056 ms** | 0.165 ms | 0.343 ms |
| 3000 | 0.486 ms | **0.172 ms** | 0.525 ms | 1.149 ms |
| 3640 | 0.666 ms | **0.251 ms** | 0.716 ms | 1.698 ms |

**cuDNN 比 FA2 快 2.8×。假设成立。**

### ❌ 但这条路拿不到收益

扒代码发现 `causal_model_s2v.py:40` 导的是 `wan_2_2.modules.attention`，
里面 `cudnn_require()` 的条件是「无滑窗 且 head_dim ≤ 256」——
**默认恒为真，主干 attention 一直走 cuDNN**。

profile 坐实：热路径是 `cudnn_generated_fort_native_sdpa_sm100_flash_fprop`
（32.9 ms / 40 次），`flash_attn` 只有 4.04 ms / 52 次。

> **教训：换库之前先确认现在用的是哪个库。** 装了 FA2 不等于在用 FA2。
> 官方 v1.1 changelog 里「cuDNN attention」那句就是这个意思，我先动手后读的。

### 官方代码自带瓶颈探测器

```python
vae_wait_start = time.time()
dist.recv(block_latents, self.src_gpu)
if time.time() - vae_wait_start < 0.01:
    print(f"WARNING: VAE serves as a bottleneck!")
```

VAE 那级如果 `recv` 秒回，说明数据早就在等 → VAE 是瓶颈。三次跑命中 **15% 的块**。

### 插桩量出真实分布

| 每块（12 帧 = 0.48 s 视频） | 耗时 | 占周期 |
|---|---|---|
| VAE decode | 0.1930 s | 61% |
| VAE → CPU 拷贝 | 0.0198 s | 6% |
| 其余（4 级 DiT 摊薄） | 0.105 s | 33% |
| **周期** | **0.318 s** | |

### ❌ 一个中途被推翻的猜测：流水线退化成串行

各 rank 的 `recv` 等待呈 1:2:3（0.449 / 0.895 / 1.335 s），
看着像「rank N 在等前面 N 级依次跑完」——完美拟合串行模型，`c ≈ 0.447 s`。

**打时间戳一测就否了**：同一块穿过四级的**延迟** 1.55 s，
但**吞吐周期**只有 0.318 s。**流水线是真的在重叠。**

> **教训：能完美拟合一个模型，不等于那个模型是对的。** 那组 1:2:3 同样
> 可以由「流水线填充 + 各级速度不同」解释。判据要用**独立的量**（绝对时间戳），
> 不能用同一组数去验证从它推出来的假设。

## 第二阶段 · VAE 优化（三条假设，一条成立）

### 消融表

| 方案 | VAE 独立基准 | 判定 |
|---|---|---|
| 基线 | 189.50 ms | — |
| **`channels_last_3d`（只转 5D 权重）** | **75.43 ms** | ✅ **2.51×** |
| 去掉 Upsample 的 `.float()` | 189.55 ms | ❌ 零变化 |
| CUDA Graph | 187.47 ms | ❌ 1%，噪声级 |
| `channels_last` ＋ 去 fp32 | 75.24 ms | 与单独 `channels_last` 一致 |

### ✅ 为什么 `channels_last_3d` 有效

cuDNN 的 3D 卷积内部就是 NDHWC。喂 NCDHW 进去，它**每层前后各转一次** ——
profile 里 `nchwToNhwc` + `nhwcToNchw` **一次解码调 312 次**（占 8.6%）。
转过去之后这些全消失，而且卷积能直接吃原生布局，**所以收益远大于那 8.6%**。

```python
# ⚠️ 只能转 5D 权重。对 1D/4D 调 channels_last_3d 会抛
#    "required rank 5 tensor"，整个 .to(memory_format=) 挂掉
for mod in self.vae.model.modules():
    for _, p in list(mod.named_parameters(recurse=False)):
        if p.dim() == 5:
            p.data = p.data.to(memory_format=torch.channels_last_3d)
```

### ❌ 为什么另外两条不成立

- **fp32 cast**：`vae_streaming.py` 里 `super().forward(x.float()).type_as(x)`
  看着像浪费带宽，实测那个 Upsample **不在热路径上**，去掉零变化。
- **CUDA Graph**：VAE 是**大 kernel、GPU 受限**（7,120 个 kernel，平均 26.6 µs），
  启动开销本来就被完全掩盖。1% 属噪声。

### ⛔ 差点报出完全相反结论的一次

为了数 Upsample 调用次数，我写了个子类当探针：

```python
class UpProbe(nn.Upsample):        # ⛔ 这个子类打断了 torch.compile
    def forward(self, x): ...
```

**基线从 189 ms 变成 1035 ms**（编译回退到 eager）。在那个瘸腿基线上，
`channels_last` 测出来是 **1015 ms vs 1035 ms ≈ 慢 5.4 倍**（对比真基线 189 ms）——
**跟真相完全相反**。

发现它纯粹是因为多看了一眼 baseline 数字对不上。

> **教训：探针本身会改变被测对象。加探针后第一件事是核对 baseline 有没有变。**
> 正确做法是改源码而不是包子类 —— 后来用源码级替换重测，才拿到真数。

### 端到端效果

| | 优化前 | 优化后 |
|---|---|---|
| VAE decode | 0.1930 s | **0.0912 s** |
| 每块周期 | 0.318 s | **0.290 s** |
| VAE 占周期 | 61% | **31%** |
| 实时倍数 | 1.51× | **1.66×** |

**VAE 快了 2.1×，整体只快 8.8%** —— 瓶颈换人了，现在卡在 DiT 每级 0.206 s。
理论下限 0.48 / 0.206 = **2.33× 实时**。**VAE 这条路到头了。**

## 第三阶段 · DiT（全军覆没）

### profile：碎

一次前向 206 ms，**26,617 个 kernel**，平均 **7.7 µs**（VAE 是 26.6 µs，碎 3.5 倍）：

| 项 | 耗时 | 性质 |
|---|---|---|
| cuDNN sm_100 flash attention（40 次） | 32.9 ms | 算 |
| fp8 GEMM · nvjet Blackwell kernel（344 次） | 27.2 ms | 算 |
| **copy / mul / add / cat / elementwise（1,900+ 次）** | **~58 ms** | **搬** |
| fp8 absmax 量化（40 次） | 2.9 ms | 量化开销 |

真正算数的约 29%，纯搬数据约 28%。**看着正是 CUDA Graph 的主场。**

### ❌ 但 inductor 拒绝捕获

`inference_utils.py` 里写的是 `torch.compile(mode=None)` —— **不开 cudagraphs**。
改成 `"reduce-overhead"` 之后，日志里两个原因各出现 14 次：

```
skipping cudagraphs due to mutated inputs (2 instances)
skipping cudagraphs due to cpu device (arg0_1 / view_6)
```

`mutated inputs` 就是 **KV cache** —— 因果流式模型每块都要原地改它，
而 CUDA Graph 要求输入不可变。**架构冲突，不是开关问题。**

代价还是负的：**前向从 0.206 s 变成 39 s**（反复重编译）。已还原。

> 同一个工具（CUDA Graph）在 VAE 上无效（GPU 受限），在 DiT 上被架构堵死。
> **「这个优化有没有用」永远是「对这段代码有没有用」。**

## 第四阶段 · 转向单卡（决定性突破）

### 为什么转向

5 卡配置追求单流速度，但产品需求是**多人共用的 avatar 服务** ——
**N 张卡跑 N 路，比 N 张卡跑 1 路快 N 倍更有价值**。
而且官方基线就是 5×H800，用 8 卡去比 5 卡本身不公平。

### ❌ 先撞一堵墙：关不掉 offload

官方单卡脚本默认 `--offload_model True`（为 80 GB 卡设计）。
B200 有 183 GB，理应关掉 offload 全放显存 —— **直接崩**：

```
RuntimeError: Input type (CUDABFloat16Type) and weight type (CPUBFloat16Type) should be the same
```

单卡路径**写死了假设 offload 开着**，有些模块永远留在 CPU。
**B200 的显存优势在这条路上没有出口**，不是不用，是代码不让用。

### 起点：比 5 卡还差

| | 生成 1 s 视频 | 实时倍数 | 每卡效率 |
|---|---|---|---|
| 5×B200（TPP） | 0.604 s | 1.66× | 0.33 |
| **1×B200（官方单卡）** | **4.303 s** | **0.232×** | **0.23** |

单卡路径是**另一套实现**，且没人调过。

### ✅ 刀一：分辨率（收益最大）

产品场景是手机上 LiveKit 的一个小方块，根本不需要 704×384。
`--size` 档位里最小的是 `384*256`，**面积只有 36%**：

| 分辨率 | 生成 1 s 视频 | 实时倍数 |
|---|---|---|
| 704×384 | 4.303 s | 0.232× |
| **384×256** | **1.694 s** | **0.590×** |

**2.54×。一个参数。**

> **教训：先问「产品实际需要多少」，再优化实现。**
> 我在 704×384 上折腾了好几轮 kernel 级优化，
> 而这个分辨率从一开始就不是需求决定的，是我照抄官方脚本抄来的。

### ❌ 刀二的第一版：改增量解码 —— 更慢 3.7×

单卡路径每轮 `decode(cat[motion_latents, clip_output])` 出 **413 帧**，
然后 `image[:, :, -48:]` **只保留 48 帧** —— 看着是 88% 的浪费。

于是照 TPP 路径改成 `stream_decode` 增量解码。**结果反了：**

| 方案 | 每次解码 | 帧数 | 生成 1 s 视频 | 实时倍数 |
|---|---|---|---|---|
| 原版 `decode` | 1.786 s | 413 | 1.694 s | 0.590× |
| 「修复」`stream_decode` | **6.606 s** | 45 | 4.767 s | 0.210× |

**解 45 帧比解 413 帧慢 3.7 倍。**
`stream_decode` 是带 cache 的逐块因果解码，**延迟受限**；
`decode` 一整批过去，**GPU 利用率高得多** —— 多算 9 倍反而更快。

（顺带：单卡 pipeline 原本 `from .wan_2_2.modules.vae2_1 import Wan2_1_VAE`，
导的是**非流式** VAE，压根没有 `stream_decode`，得先换成 TPP 用的流式版。）

> **教训：「算了没用的东西」不等于「慢」。** 批量效率经常能盖过冗余计算。
> 收回我此前「88% 是浪费、是 bug」的说法 —— **那是有意的取舍。**

### ✅ 刀二的正确版：保持批量解码，只少喂历史

方向对了但手法错了。正确做法是**仍然一次性 `decode`，只是把 `motion_latents` 裁短**：

```python
_k = int(os.environ.get('LA_TRIM_K', '0'))
_hist = motion_latents[:, :, -_k:] if _k > 0 else motion_latents
decode_latents = torch.cat([_hist, clip_output.unsqueeze(0)], dim=2)
```

| `TRIM_K` | 每次解码帧数 | decode 耗时 | 生成 1 s 视频 | 实时倍数 |
|---|---|---|---|---|
| 0（全量） | 413 | 1.786 s | 1.694 s | 0.590× |
| 16 | 109 | 0.476 s | 0.868 s | 1.152× |
| **8** | **77** | **0.337 s** | **0.781 s** | **1.28×** ✅ |

解码 **5.3× 加速**，端到端 **2.17×**。

### 画质验收（必须做）

裁历史帧会不会掉画质？抽 5 个时间点与全量版逐帧比：

```
trim16 vs 全量  PSNR: 2s=36.4dB  6s=22.1dB  10s=30.0dB  14s=24.1dB  17s=29.8dB
trim8  vs 全量  PSNR: 2s=36.2dB  6s=23.1dB  10s=28.3dB  14s=24.1dB  17s=26.6dB
```

PSNR 22–36 dB 看着不高，**但这不是画质损失**：
解码结果会 feed 回下一段的 motion 条件，**微小差异沿时间轴累积成运动相位的分叉**。
肉眼比对（3×3 对比图，行=全量/trim16/trim8，列=2s/10s/17s）：
**人物、光照、背景机柜完全一致，无伪影、无退化、无漂移。**
两边都是合格输出，只是不是同一段。

> **教训：生成模型之间不能用 PSNR 判优劣**，只能判「是不是同一段」。
> 判质量要看图。

## 第五阶段 · 九组消融全矩阵

所有组在**同一套补丁状态**下重跑（两条 pipeline 都带 `channels_last_3d`），
同一段音频（17.48 s）、同一张参考图、同一个 seed。

| 配置 | 卡 | 分辨率 | `TRIM_K` | 生成 1 s 视频 | 实时倍数 | **每卡实时倍数** | decode 均 |
|---|---|---|---|---|---|---|---|
| `5c-704` | 5 | 704×384 | n/a | 0.621 s | 1.610× ✅ | 0.322 | 0.109 s |
| `5c-384` | 5 | 384×256 | n/a | 0.593 s | 1.687× ✅ | 0.337 | 0.058 s |
| `1c-704-t0` | 1 | 704×384 | 0 | 4.303 s | 0.232× | 0.232 | 4.562 s |
| `1c-704-t16` | 1 | 704×384 | 16 | 2.192 s | 0.456× | 0.456 | 1.207 s |
| `1c-704-t8` | 1 | 704×384 | 8 | 1.972 s | 0.507× | 0.507 | 0.855 s |
| `1c-384-t0` | 1 | 384×256 | 0 | 1.692 s | 0.591× | 0.591 | 1.786 s |
| `1c-384-t16` | 1 | 384×256 | 16 | 0.868 s | 1.152× ✅ | 1.152 | 0.475 s |
| `1c-384-t8` | 1 | 384×256 | 8 | 0.781 s | 1.281× ✅ | 1.281 | 0.337 s |
| **`1c-384-t4`** | **1** | **384×256** | **4** | **0.737 s** | **1.357× ✅** | **1.357** | **0.268 s** |

> ⚠️ `TRIM_K` 对 5 卡**不适用**：TPP 路径本来就是增量 `stream_decode`，
> 每次只解新块，**没有历史可裁**。「少喂历史」是单卡路径独有的优化，
> 因为只有它在做整段重解。

### 读表要点

**① 5 卡几乎不吃分辨率红利：像素砍到 36%，只快 4.8%（1.610 → 1.687）。**

VAE 解码确实快了 1.9×（0.109 → 0.058 s），但周期几乎没动 ——
说明 5 卡路径是**延迟/启动受限**，不是算力受限。
DiT 一次前向 **26,617 个 kernel**，这个数**不随分辨率变**，只是每个变小了。
分辨率降下去，它只会更加 launch-bound。

**② 5 卡在两种分辨率下都追不上官方宣称的 H800 1.80×。**

| | 分辨率 | 实时倍数 |
|---|---|---|
| 官方 5×H800（宣称） | 未注明 | 1.80× |
| 我们 5×B200 | 704×384 | 1.610× |
| 我们 5×B200 | 384×256 | 1.687× |

**即使给 B200 一个 2.75× 的像素优势，5 卡配置仍然追不平。**

**③ 但单卡每卡效率是 5 卡的 4.0 倍。**

`1.357 ÷ 0.337 = 4.03`。同样 5 张卡：
跑 1 路 1.687×，还是跑 5 路各 1.357× —— **后者总吞吐是前者的 4 倍**。

**④ 单卡上，分辨率是实时的必要条件。**
704×384 即使裁到 `TRIM_K=8`，也只有 0.507×，**差一半**。
必须降到 384×256 才跨得过 1.0× 线。

**⑤ `TRIM_K` 收益递减但还在涨：** 16 → 8 → 4 给出 1.152 → 1.281 → 1.357。
更小的值（2 / 1）未测。

### `TRIM_K=4` 的画质验收

与全量版（`t0`）逐帧对比：

```
2s=39.0dB   7s=32.4dB   12s=27.7dB   17s=31.8dB
```

比 `t8` 那组还高。肉眼比对（4 个时间点两行并排）：
**人物、光照、背景机柜完全一致，无伪影、无退化。**

PSNR 不到 40 dB 是因为解码差异沿 motion 反馈累积成运动相位分叉 ——
**不是画质损失，是「不是同一段」。**

### 服务形态结论

| 方案 | 并发 | 每路速度 | 总吞吐 |
|---|---|---|---|
| 8 卡跑 1 路（5 卡 TPP ＋ 3 闲置） | 1 | 1.687× | 1.687× |
| **8 卡跑 8 路（单卡 `1c-384-t4`）** | **8** | **1.357×** | **10.9×** |

**推荐后者**：8 路并发 live avatar，每路都在实时线以上。

## 测量方法

1. **只量视频生成，启动一概不算。** 常驻服务的加载成本只在部署时付一次。
2. **周期取稳态**：在解码处打绝对时间戳，取连续两次之差，**丢掉前 2 次**（预热/编译），
   对剩下的取均值。
3. **换算**：`每秒视频耗时 = 周期 ÷ 每块视频秒数`，`实时倍数` 取倒数。
4. **分项计时必须夹 `torch.cuda.synchronize()`**，否则量到的是入队时间。

### ⛔ 已经踩过的测量坑

**① 别拿子阶段的进度条下吞吐结论。**
采样进度条稳态 22 it/s 看着飞快，但它**只量 DiT 去噪那一段**，
不含 VAE、音频特征、motion frame。据此得出的「比实时快」是错的。

**② 别用整跑时间反推生成速度。**
最初用 9 条视频（10.6–21.4 s）拿「整跑耗时 vs 视频长度」做线性回归想摊掉启动，
得到 1.39 s/s = 0.72× 实时。**错了一倍以上**（R²=0.64，残差 ±5 s）——
跨度太窄、点太少，175 s 的启动把斜率带偏了。**一开始就别把启动放进来。**

**③ 探针会改变被测对象。**（见第二阶段）加探针后先核对 baseline。

**④ 能拟合一个模型 ≠ 那个模型对。**（见第一阶段）用独立的量去验。

**⑤ 生成模型之间 PSNR 不判优劣。**（见第四阶段）判质量要看图。
