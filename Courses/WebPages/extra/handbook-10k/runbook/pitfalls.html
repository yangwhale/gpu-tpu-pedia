经验教训与注意事项

这一页按交付阶段列出万卡级 TPU7x 集群交付过程中踩过的坑。动手前通读一遍，做到哪一阶段再回来对照那一组。

一、拿资源：预留、配额与验收

  1. 报 GCE_STOCKOUT / No available resources，但其实不缺货。 注意：专属 pod 上的「缺货」多半是配置错、坏主机、泄漏对象或平台事故，先按报错对模式分诊，别先删池重建。最常见的配置错是 reservation: 没填预留真名、资源路径用了 project number 而不是 project ID；真缺货只有一种：自己把预留用满了。

  2. 预留标的 cube 数 ≠ 能用的 cube 数，坏机器原地修复时还占着 cube 好几天。 注意： 坏机器原地修复期间仍占着 cube，任何时刻都有若干 cube 降级，交付几天后可用数还会往下掉。按保底可用数而不是标称数排任务。「健康 cube 数」先约定按哪个口径数：按「有一台机器不可用整个 cube 就不算」、按 GCE sub-block 健康、按「降级也算可用」，同一时刻会给出不同的数，书面约定里写明口径。备件深度要自己定、自己数，并写进运维规程。

  3. 预留到期被删，GKE 跟着删掉全部 TPU 节点。 注意：这是设计行为，只能提前读到期日、提前续；要拆预留时先删 Slice 再删预留，否则会留下悬挂的 Slice。

  4. 默认配额不够，查配额的命令本身会骗人，还有一项配额使用方根本看不见。 注意：TPU、Hyperdisk 容量与 IOPS、IP 地址、实例数都读 limit 而不是 usage，申请后和上线当天各读一遍，Hyperdisk 通常最慢到位。多 cube 切片还依赖一项与 MIG 数量相关的区域配额（控制台里看不到），默认值对整 pod 太低，交付前请 Google 按 project + region 调高。存储侧的 GCS 读 QPS、Anywhere Cache 带宽与容量也有上限，几千芯同时读数据和检查点前一并申请。

  5. 想用整个 pod 跑一个 ICI 切片，发现做不到。 注意：公开文档写明单个 ICI 切片最多 32 个 cube（2,048 芯），整 pod 只能多片走 DCN；作业布局一开始就按多片设计，并给坏 cube 留出备用。

二、建集群与节点池

  1. 一台坏主机或一条坏 ICI 链路，让整个 cube 的池卡在 15/16；放在多 cube 原子大池里则整池回滚并报假缺货。 注意：一个 cube 一个节点池（16 个节点），不用跨 cube 的原子大池。验收时先重建一次，同一台再坏就带证据请 Google 下线。

  2. 开了节点自动配置（NAP）/ Cluster Autoscaler，出现池叠在同一 sub-block、缩容活锁、读配额被打满等一串问题。 注意：TPU 池建议全部预先手工建好、不开自动伸缩。

  3. 版本低于下限，建集群或跑任务时才报错；节点 Ready 但 TPU 数是 8 或 0。 注意：交付前出一份版本清单（GKE、COS、device plugin、slice controller、Kueue、JobSet），逐项对照下限并确认在目标 zone 可用，动态切片只支持 COS。验收时逐台核对 google.com/tpu 数量和 chip-ids 注解，老版本常不认新机型。

  4. CPU 系统池建不出来或静默封顶。 注意：配额够不代表 zone 有货；一些建集群工具默认关掉 SMT 让 vCPU 减半，Kueue 控制器会调度不上；换机型后要重算配额。

  5. 集群名或作业名太长，报看不懂的正则错误或静默卡住。 注意：GCP 资源名和 K8s 标签值上限 63 个字符，控制器还会在后面拼接后缀，集群名、Slice 名、JobSet 名的实际预算要从这个上限倒推，建集群前就定好。

  6. 改活集群 / 活节点池的配置，导致整池重建或在满预留上卡死。 注意：很多设置建时就固化，事后改要么重建集群、要么整池 16 台 VM 重建、要么 surge 时没有余量卡住；不少修复也只对新 VM 生效。网络、DNS、身份等设置在建首个池前定稿。

  7. 用 Cluster Toolkit / Terraform 建集群，一串「不报错」的坑。 注意：老版本静默跳过 TPU 设置、部分参数被静默忽略、状态桶没开版本控制、默认并发下建一百多个池要几个小时；选这条路要钉工具版本并逐项核对产出。

三、网络、DNS 与 DCN

  1. 节点上百台后大部分节点静默断网，几天后才从下载超时暴露。 注意：Cloud NAT 用自动分配 IP + 动态端口；某些工具默认只给 2 个手动 IP，建完核对 NAT 配置，并检查 mapping 数是否接近节点数。

  2. 网络设计错了只能重建全部池：Pod IP 耗尽、网段重叠、多网卡配置不可改。 注意：建集群前定死 maxPodsPerNode 和 Pod 网段，将来可能互联的集群网段错开。附加网卡、Network / GKENetworkParamSet、VPC、MTU 在建首池前定稿，附加的 DCN 网卡默认没有公网出口。

  3. 两千节点以上 DNS 扛不住。 注意：换成多副本（例如 15 副本）的自管 CoreDNS 加 NodeLocal DNSCache，或改用 Cloud DNS；之后再换提供方要滚动全部节点，所以一开始就定。

  4. DCN 默认 flag 下跨切片 all-reduce 只有线速四成多，片数一多效率掉到 36%。 注意： DCN 相关 flag 要成组配：用参考配方里的整套设置，不要单独改其中一项 —— 只关 host reduction 反而让训练变慢。按双网卡建网；作业规模按 1/2/4/8 片的梯子逐级跑通，同 pod 的其它任务也会抢 DCN 带宽。

  1. 两千节点以上的集群，作业提交大面积 webhook 超时，DNS 也间歇失败。 注意：konnectivity-agent 的副本数按全集群节点数扩（带 taint 的 TPU 节点也算），却只能落在少数系统 CPU 节点上，把这几台的邻居表（ARP，默认上限 1024）打满。建集群时就用节点池 sysctl 调大 gc_thresh，给 agent 加反亲和，系统 CPU 池按规模配、别只有 3 台。
  2. 某一台主机的检查点上传一直慢，全体每个周期都在等它。 注意：训练依赖的外部服务（TensorBoard、镜像仓库、日志、数据源）跨 region 时不报错只变慢。交付清单逐项核对依赖和集群同区，region 从节点 label 读、不写死。

四、存储与检查点

  1. pd-ssd 永远挂不上；gcsfuse CSI 挂载失败。 注意：tpu7x 只支持 Hyperdisk（Balanced 和 ML），启动盘和持久卷吃同一份 Hyperdisk 配额，Retain 策略的 PV 不清理会持续占配额。gcsfuse 要求 Workload Identity 在集群和每个节点池（含系统池）两级都开，集群开了不代表每个池都是 GKE_METADATA。

  2. 没有 Local SSD，/dev/shm 和临时存储不够用。 注意：tpu7x 本地只有主机内存和一块小启动盘，数据缓存、检查点本地层、编译缓存都从内存里划，要事先算账。

  3. 检查点写得慢、训练被 checkpoint 卡成 hang，或备份格式下游不认。 注意：桶类型实测写入速度再选；Orbax 在 GCS 上的 barrier 会让非主进程阻塞到触发 hang 检测；MTC 的 GCS 备份不是标准 Orbax 格式。持久层存数 TiB 级检查点要几分钟、本地层只阻塞几秒，但持久层不能全关。

  4. 多片任务重切到别的 cube 后，MTC 本地层被拒收，退回持久层丢掉若干步。 注意： 数据其实还在，是恢复时的校验整体放弃了它，最坏重算步数＝持久层周期。已知问题，有绕过办法（按 device id 恢复的补丁），上游未合入；你需要做的是：在所用版本上演练通过前按持久层周期定 RPO，并用删片演练验证恢复走的是本地层。

  5. 从检查点恢复后 step 慢 3–6 倍。 注意：MegaScale 给 DCN 预分配的内存不能扩容，--megascale_grpc_premap_memory_bytes 设到每台主机检查点大小的 2 倍以上；TPU_PREMAPPED_BUFFER_SIZE 是另一个旋钮，分开配。

五、镜像与软件栈

  1. 版本不钉死，或 flag 写了没生效：flag 不认、API 不兼容、数值静默出错。 注意：jax、libtpu、镜像当一套组合按 digest 和确切版本钉死，升级先过回归门。跑数值 canary，并 dump 生效的 flag 与 HLO 核对，确认各 worker 编译出的程序一致。

  2. 大量 pod 启动时各自从外网装环境，既慢又不可复现。 注意：环境构建一次打成 tar（或镜像），worker 只解压；从浮动分支现装是版本漂移的入口。

  3. Kueue slice controller 是全集群单点，用了 :latest 镜像缺 flag 直接 CrashLoop，所有提交被 webhook 拒绝。 注意：上游 manifest 只有 1 副本、没有 PDB，要自己加高可用；所有控制器按 digest 钉版本，线上临时改动回写 Helm values。

  4. sub-slice 建不起来，GKE 侧看不出原因。 注意：sub-slice 要求主机侧几件软件都达下限且全 pod 一致；super-slice 建成也不能证明这一点，启用前要逐台核对主机版本。

  5. AOT 编译通过，上卡却差几 MB HBM 报 OOM。 注意：实测申请 1.39 G 只剩 1.38 G，连续 3 次 RESOURCE_EXHAUSTED。AOT 产物报的 temp_size 离 HBM 上限不到约 1 GiB 的，先在真机小规模跑通；这是显式报错，不同于超 HBM 时首步挂住。

六、调度、Kueue 与切片

  1. 作业被拒、一直 Pending，或只调度了一部分 pod，报错不提「配置错」。 注意：TPU 作业必须写 gke-tpu-accelerator: tpu7x，走 Kueue 时写 gke-tpu-slice-topology 注解，requests == limits，不带 exclusive-topology / placement-policy-name；把正确清单做成模板照抄。

  2. sub-cube 形状（2x2x1 到 2x4x4）永远不被准入，或在大片的一部分上跑小拓扑出错。 注意：TAS 的 Topology 必须包含 sub-cube 分区层级，删掉重建同名 Topology 会污染调度缓存（重启调度器即可恢复）。只用动态切片，不和静态切片混用；要小形状就建对应的 Slice，别在大片上改环境变量凑。

  3. Kueue 准入了，作业却永远放不下。 注意：Kueue 只做芯片数加减，不知道 cube 坏了或被碎片占着，配额按「健康整 cube 数减去留空」来设并随健康状况调整。同一集群不要混用手工 Slice 和 Kueue，手工 Slice 占着的 cube 在 Kueue 账本里仍是空闲，巡检用的小切片用完即删。

  4. cube 坏了以后作业不会被驱逐重排。 注意：Kueue 的 waitForPodsReady 必须开着，它是 TAS 下唯一能把作业从坏 cube 上挪走的机制；加池工具或手工改配置常会悄悄关掉它。

  5. 整 pod 规模下准入和切片激活都慢，成批 EvictedDueToAdmissionCheck，看起来像硬件坏。 注意：突发建大量切片会被串行处理，slice controller 的 --activation-timeout 显式设到 10–15 分钟以上，并请 Google 确认已开批量建片。Kueue 并发配置里要显式包含 Pod（否则 pod reconciler 只有 1 个 worker），并发和 API qps 一起调高，使用带 TAS 缓存的 Kueue 版本。

  6. 验收任务被生产任务抢占、大作业饿死、队头卡住。 注意：Kueue 优先级同时决定「谁先准入」和「谁能抢谁」，优先级梯子、谁能抢谁、验收任务的优先级与时间窗、要不要运行时上限，都在交接前定好。

  7. Slice 进入 ACTIVE_DEGRADED 后再没回到 ACTIVE，任务跑在上面随后失败。 注意：它不是 OCS 引起的 cube DEGRADED。实测一天二十多次，没有一次回到 ACTIVE，却照样能被准入。出现即删 JobSet 换片。

七、运行期故障与恢复

  1. 一个 Slice 出事，多片任务常常全部 Slice 重建；一台主机在 step 0 后宕机，几十分钟的编译和初始化全部白做。 注意：手删 Slice 一定全部重切；自动只换部分的实测只有 2 次，判据未确认，恢复时间按全部重切估。maxRestarts 不要设 0（不开检查点的验收跑法除外，见 06b），编译缓存放共享持久路径或用 AOT。

  2. Slice 卡在 ACTIVATING / DEACTIVATING / INCOMPLETE，两个 Slice 抢同一分区，或 FAILED 后不自愈。 注意：过渡态正常几十秒，超过 10–15 分钟就是故障；FAILED 是终态，要由 Kueue 删了重建。删 JobSet 后等旧 Slice 真正消失再建新的，抖动时不要批量删了重提。

  3. 拆除卡住：手摘 finalizer 或删池顺序错，cube 既建不了片也删不了池。 注意：要保留的集群上，finalizer 默认不要手摘；唯一例外是 Slice 的 finalizer：MMIG 成员已为 0、且已开 Google case 时，按 05 的步骤摘；Kueue 对象的不摘（摘了，已准入的 workload 会挂在不存在的配额上）；整集群销毁时由清理流程统一摘除。回收按「配额置 0 → 删 JobSet → 删 Slice → 等底层多 MIG 关联清空 → 删池」的顺序；卸载 Kueue 也要先删它的 CR。删除卡住时先查底下的 GCE 操作，「失败」的删池可能已经清空了 cube。

  4. 看不见的对象静默吃容量：孤儿 Slice、ProvisioningRequest、VM、MIG，以及「GCE 有、K8s 没有」的节点。 注意：它们不报错，最后表现成「缺货」；每次拆除后核对，并把预留 / GCE / GKE 三方对账做成定时巡检。

  5. 一次 abort 写出几十 GB core dump，节点 DiskPressure，Kueue 把整个任务驱逐。 注意：限制 core dump 大小或不写到启动盘；否则会触发「驱逐 → 旧 pod 没删净 → rank 冲突 → 一片的 pod 撒到多个 cube → TPU 初始化挂住 → 再 abort」的死循环。

  6. START_SESSION failed，第一反应是主机坏了。 注意：它只是「ICI 会话没建起来」的总称，背后有形状不匹配、主机代理崩溃、pod 撒到多个 cube、OCS 维护、坏主机等十几个分支；先收证据再分型，别直接送修。

  7. 训练挂住不报错，或 JobSet 显示 Completed 而训练其实失败了。 注意：单片卡在 ICI 上没有看门狗，超 HBM 也表现成首步挂住，自己加 step 进度告警；megascale_graph_hang_threshold 要盖住恢复加编译（生产有设 20m 的）。分布式初始化超时默认常配成 1800 秒，一次坏的重新准入要半小时才暴露，改成 300–600 秒。MaxText 会把致命错误包成 exit 0，SIGTERM 也是 exit 0，JobSet 判 Completed 后不再重启；抢占时默认不存盘。致命错误改非零退出码并配 podFailurePolicy，以 step 数和检查点落盘为准。

  8. 某一片或几台主机突然变慢，整个多片任务跟着慢。 注意：最慢的一片决定全局步时，按片看集合通信延迟和 duty cycle 找出那一片；取证后重建 JobSet，降频主机用 soak 基准找出送修。

  9. 故障演练杀掉训练进程，同片别的主机报 SLICE_FAILURE_CHIP_DRIVER_ERROR，看起来像芯片坏了。 注意：这是 libtpu 的连坐终止，实测多次杀进程，绝大多数都出现。演练期间按 exec / 删 pod 审计时间去重，别送修。

  10. 多片恢复时间随片数上涨，更大规模的一次恢复约是 10+ 片的 2 倍。 注意： 片数一多，MTC 协调组件出故障、全员等满超时的机会也更多（见第 62 条），不全是规模效应。按你们交付的片数实测恢复时间，不拿小规模外推。

  1. 多层检查点（MTC）自己的控制组件出故障，影响面比训练任务还大。 注意：协调组件注册时碰上一次 apiserver 瞬断就放弃、不通知其余节点，上千个节点白等满 300 秒；排名服务旧版本在几百个 pod 的规模就活锁，还会拖住全集群的作业提交；MTC 目前只支持 rapid 发布通道，和钉版本冲突。交付前核对组件版本带了修复、排名服务放专用节点，演练里专门测这几种失败。

八、健康、维修、维护与运维

  1. 健康信号各说各话：Node Ready、分区标签、预留 API、super-slice ACTIVE 都可能报健康而 cube 已坏；GCE 侧标了降级，GKE label 也不跟着变。 注意：一台主机功率传感器读错被限频到约 3% 算力，健康信号照样报正常。健康判断多信号取 AND 再加自己的探针（准入和每日巡检跑 gemm / HBM 基准）；要有自动化把降级同步成 label + taint，待检原因分型打标签。

  2. 主机维护或 GKE 升级把正在跑的切片打成 FAILED，修好的机器版本和其它主机不一致。 注意：主机维护自己按整 cube 分批触发，保持健康 cube 不低于 SLO 线，做完逐台核对主机版本。GKE 钉版本和发布通道、给 TPU 池加维护排除，先在一个 cube 上 canary 再按 cube 分批手动升级。

  3. GCE 读配额被打满，健康切片被标成 Ready=Unknown。 注意：这时不要批量删切片，删片可能把底层 MIG 解绑卡死；把 slice controller 升到修复版，开了 Autoscaler 要知道它和切片控制器共用读配额。

  4. 控制面成为瓶颈：etcd 写满、控制器 OOM、几千个 pod 同时重启打爆 apiserver。 注意：定期清理已完成的 pod，盯控制器内存，大规模重启错峰；Cloud Logging 配额默认按小项目给，要提前调高。

  5. 告警会漏、错误信息笼统、Kueue 驱逐 Event 被 RBAC 拒、日志拉取静默截断。 注意：Slice FAILED 的 message 可能全空（实测一天多次），分型要同时拉 GCE 操作、节点事件和 worker 首条日志。第一天建好告警，给 Kueue 补写 Events 的 RBAC，日志分时间窗拉并核对首末时间戳。

  6. 权限、准入策略和组织策略的失败都是无声的。 注意：RBAC 在请求时才解析主体，apply 后要实际验证；Kyverno 类策略在 helm upgrade 时整份重渲染，例外清单放进 values。控制面授权网段别写成会轮换的单个出口 IP，可信镜像、VPC Service Controls 等组织策略在交付前逐条核对。

  7. 性能对比结论站不住：差异来自维护、降级 cube、profile 开销或步时统计口径。 注意：用绝对步时和大样本说话，先排除维护、降级、profile 等外因再怀疑配置；MaxText 自报的步时滞后 2 步，对齐外部事件时要校正。

  8. 往运行中的生产 pod 里 exec 调试，随后训练报协调服务错误退出。 注意：因果未证实，但一次失败就是二十多分钟。生产命名空间收掉 pods/exec。

  9. 作业变慢时，找不到是哪台主机的 DCN 出了问题。 注意：常驻监控没有主机粒度的 DCN 网卡计数。备一个按需 DaemonSet：只调度到该作业的主机，每秒读网卡计数，采完即删。

  1. 检查脚本报 PASS，实际没过：少读一层字段、中途静默退出，都会被读成 PASS。 注意：PASS 也要抽查原始字段。检查脚本只在明确读到通过条件时才报 PASS；读不到字段、退出码非 0、输出不完整，一律按失败处理。实测里，预检在有维护正在进行时照样报过 PASS。
  2. 规模一大，监控自己先失灵：托管的 kube-state-metrics OOM，所有基于 kube_* 指标的告警一起失效。 注意：按集群规模向 Google 申请评估 kube-state-metrics 的资源限额；交付前在满规模下确认这些指标还在上报，并给告警链路本身配「数据缺失」告警。
