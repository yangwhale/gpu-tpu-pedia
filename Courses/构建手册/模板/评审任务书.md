# 评审任务书（可以直接粘给 agent）

> 每个 agent 只戴**一副眼镜**。⛔ 别写一份「全面审一遍」的任务书 ——
> 它会退化成一份四平八稳的摘要，每条都对、每条都不能动手。
>
> 用法：把某一节整段作为 agent 的任务，把 `{{课件}}` `{{讲义}}` `{{图目录}}` `{{比喻表}}` `{{范围}}`
> 换成真实路径与内容。**每份末尾都加上最后那段「通用尾巴」。**
>
> 派之前先跑 `构建手册/脚本/course-metrics.py`，把量出来的数字填进任务书 ——
> 能算出确切数字的，不要让 agent 去数。

## A · 外行（麻瓜）

> 最值钱的一副。它报的不是「哪里写错了」，是**哪里把人劝退了** —— 作者永远看不见这个。

```
你要扮演一个完全不懂这个主题的聪明成年人（比如一个做产品的、或者一个别的方向的工程师），
从头到尾读一遍这份课件的 {{范围}}，然后诚实地告诉我你在哪儿卡住了。

文件：{{课件}}（分段读完，别只抽样。）

⛔ 你不是来审查事实正确性的，也不是来夸的。你唯一的任务是回答：
   「一个第一次接触这个主题的人，读到哪一段会停下来、皱眉、或者放弃？」

请按这四类分别列出，每条必须给出具体位置（小节号或图的名字）和具体理由：
1. 看不懂：这句话／这张图需要我已经知道某个东西，但前面没讲过。写清「它假设我已经知道 X」。
2. 一目了然不了：这张图我盯了十几秒还没抓到它想说什么。写清「我先看到的是 A，但它大概想让我先看 B」。
3. 字太多：这一段／这张图，信息量配不上它的长度。指出哪几句删掉不影响理解。
4. 卡壳：读到这儿我想问一个问题，而接下来没回答（或者隔了很远才回答）。

⭐ 最有价值的是具体到句子的反馈，不要写「整体不错，建议精简」这种。
⭐ 如果有地方写得特别好、一下就懂了，也单独列一节说明为什么懂了 —— 那是可复制的做法。

最后给一个排序：如果只能改 5 个地方，按「改了之后对新读者帮助最大」排。
再给三个 1–10 分：易懂度、图的帮助、主线清晰度。
```

## B · 逐图

```
审查这份课件里的 {{N}} 张图（含动画），判据只有一条：这张图有没有把原理画出来，让人一眼看懂。

图的源：{{图目录}}（绘图脚本头部注释写着每张图的意图）
图在课件里的上下文：{{课件}}

这门课的标准（原话）：
  「图是图，字是字。图的目的是把原理画出来，让人一目了然，
    而不是把本来该写在正文里的东西放进表格里 —— 那些表格不是图。」
  「要跟现实生活中的世界结合起来，不要那么抽象。我们是大众课程。」
  「图里的字不要太小，也不要太多，打到屏幕上去分享那样的图。」

请对每一张图给出：
- 一句话：这张图当前实际传达出来的是什么（不是它想传达什么）
- 判定：✅ 画出了原理 ／ ⚠️ 半图半表 ／ ⛔ 本质是一块写字的板子
- 如果不是 ✅：具体怎么改 —— 该画什么画面、用什么生活化的比喻。
  这门课已经立起来的比喻（要沿用，别另起炉灶）：{{比喻表}}
- 有没有渲染问题：字被盖住、压线、曲线没画出来、图例挤在一起

最后给优先级清单：最该动的 8 张，每张一句话说清最小改动。
```

⚠️ 它报的几何问题（被盖住、溢出）必须自己截图核实，别信描述。

## C · 文字

```
审查这份课件正文（不是图）的可读性。文件：{{课件}}　源码：{{正文源码}}
已知的硬指标：{{course-metrics.py 量出来的加粗占比等}}

请回答三个问题，每条都要具体到段落（小节号 ＋ 原文前 20 字）：
1. 加粗滥用：哪些段落已经「全都加粗等于都没加粗」？对最严重的 10 段，给出该保留哪几个词的加粗。
   判据：一段里加粗的部分单独拎出来读，应该正好是这段的骨架。
2. 该删的话：铺垫句、重复上一句、解释一个刚解释过的东西、凑气势的排比、元评论。至少 20 句。
3. 该合并／该拆的：相邻小节在讲同一件事（该合），一个小节塞了两件不相干的事（该拆）。
另外标出「补丁味」：嵌套括号、括号里的更正说明、同一个解释重复出现三次以上的地方。

⛔ 不要建议「整体精简」「注意节奏」这类不可执行的意见。⛔ 不要动事实、数字、出处。
⭐ 这是给普通人和爱好者的大众课程，标准是「读起来顺」，不是「信息密度高」。

最后给可执行清单：按「改动小、收益大」排，前 12 条。
```

## D · 讲师（讲义与课件的缝）

```
你要按这份讲义真的把这节课讲一遍（在脑子里走一遍，掐时间）。
讲义：{{讲义}}　课件：{{课件}}

回答四个问题：
1. 哪一段讲不下去：讲义让我「滚到 X」「指第二格」，而课件里那个东西已经改了名字、挪了位置或根本不存在。逐条列出。
2. 时间对不对：按讲义标的时长走，哪一节必然超时、哪一节会空出来？给出估时依据（多少字、多少张图、要不要现场算数）。
3. 哪些话是写给作者自己的：舞台指示（「这句要主动说」「留三分钟」）如果出现在读者页面上，读者会觉得在偷看备课笔记。列出位置。
4. 台下一定会问什么，而讲义没准备：列出 5 个最可能被问、材料里答不上来的问题。

⛔ 不要复述讲义内容。只报缝。
```

## E · 分领域专家

```
你是 {{领域：分布式训练 ／ MoE 与长上下文 ／ 推理系统 ／ TPU ／ GPU 与 NVIDIA ／ 数值精度 ……}} 方向的专家。
审查这份课件 {{范围}} 里所有跟你的领域有关的技术说法。文件：{{课件}}；出处台账在最后一节。

请逐条检查：
1. 硬错：事实、数字、公式、架构关系说错了。给出正确的说法和你的依据（论文节号、config 字段、官方文档）。
2. 口径问题：数字本身对，但口径不对或没说清 —— 收发合计还是单向、总量还是每卡、同条件还是挑了最好的点、实测还是估算。
3. 说宽了：结论在课件的例子上成立，但写得像普遍规律。给出反例或适用条件。
4. 过时：有更新的做法或数据，课件还停在旧的上面。

⭐ 每条标严重程度：会误导人 ／ 不精确但无害 ／ 措辞。
⛔ 这是给普通技术人员的课，不要求补充调参细节；只关心说对没有。
```

## F · 对抗式找错

```
你的任务是找出这份课件里最可能错的地方。假设作者至少犯了 10 个错，把它们找出来。文件：{{课件}}

重点找：
- 自相矛盾：同一个量在两处给了不同的数；一处说 A、另一处说非 A。
- 数字对不上：图里的数和正文的数、正文的数和台账的数、加起来不等于合计的表。
- 方向反了：比较类断言（谁比谁大、何时更快）。
- 因果倒置或因果链断了。
- 图和它的图注说的不是一回事。

每条给出两处原文位置和原文，说明矛盾在哪。
```

## G · 出处台账抽查

```
课件最后一节是出处台账。随机抽 {{N}} 行（覆盖论文、源码、实测三类），逐行回原文核对。文件：{{课件}}

每行回答：
1. 出处能不能找到（arXiv 号、节号、源码路径、实测记录是否存在）
2. 出处里真的这么说吗？原文怎么说？
3. 课件引用时有没有说宽、说窄、换了口径
4. 标「本课推导」的，推导链对不对

另外列出：正文里有、但台账里没有出处的关键说法（至少 5 条）。
```

## H · 试讲（边讲边改用）

```
你是这门课的讲师。按最新的课件和讲义，把 {{第几节}} 从头到尾完整讲一遍。
课件：{{课件}}　讲义：{{讲义}}

请写出完整的口播逐字稿 —— 包括你在台上会临场补的话、指屏幕的动作、跟台下的互动。然后报告：
1. 讲不顺的地方：哪句话念出来别扭、哪里的过渡接不上。
2. 必须临场补话的地方：讲义没写、但你不补一句台下就听不懂 —— 这说明材料缺了。把你补的那句话写出来。
3. 图不够用的地方：讲到这里想指一个东西，但图上没有；或者图上有但太小、太挤。
4. 说错或说不准的地方。
5. 这一节实际讲了多久（按每分钟 200 字估）。

⭐ 最有价值的是第 2 类：你临场补的那句话，往往就是课件和讲义该补进去的那句话。
```

第二遍（换自学视角）用这个变体：

```
这一次你不是讲师，是一个自学的人：没有讲义、没有人讲，只有这份课件的 {{第几节}}。
读完后回答：讲义里那些比方、推导、过渡，哪些你在课件里找不到、但没有它就读不懂？逐条列出，并写出应该补进课件的那句话。
```

## I · 自学通读

```
你是一个想自学这个主题的人，手里只有这份课件，没有讲义也没有老师。从头到尾读完。文件：{{课件}}

1. 卡住的地方：读到哪里读不下去了，为什么。

4. 读起来像「打过补丁」的地方：嵌套括号、括号里的更正、同一个解释重复多次。
```

## J · 讲义↔课件终稿对账

```
逐条核对讲义和课件是否一致。讲义：{{讲义}}　课件：{{课件}}（含 SVG 里的文字、aria-label、图注）

1. 数字与口径：讲义台词里的每一个数，在课件里能不能找到？口径一样吗（并发、卡数、单位）？
2. 说法：讲义里的每一个结论，跟课件的说法一致吗？
3. 屏幕提示：讲义指的每张图、每段动画、每个小节、每一列每一格，在课件里存在吗？指的位置对吗？
4. 时长表：计划时长、照稿念完的时长，加上动画和互动，各节会不会超？「可压到」的承诺能不能兑现？
5. 「别讲什么」和备答：跟课件一致吗？

⛔ 只读，不改文件。只报需要改的，对得上的不用列。
```

## L · 手册对账（双向）

```
背景：{{手册目录}} 是课程构建手册，{{课件}} ／ {{讲义}} 是按它做出来的一讲。
任务：双向对账。拿手册里的判据逐条检查这一讲，每发现一处对不上，判断属于哪一种：
  (A) 这一讲没做到 —— 手册是对的，这一讲该改（给出位置和改法）
  (B) 手册说过头或说错 —— 这一讲的做法其实更好，或者规矩在这里不适用（手册该怎么改）
  (C) 手册没覆盖 —— 这一讲有好做法，手册没写（该补进哪一篇）
重点逐条过：03 四个保证、04 绘图、05 讲义、10 动画、01 的课件与讲义分工。别抽样。
输出按 A／B／C 三组，每条：手册出处 → 实际情况（文件:行号）→ 理由 → 建议改法；组内按严重程度排。
最后给总判断：哪边问题更多，各自最该改的三条。
```

## M · 外部蒸馏（借讲法）

> 用法见 [11 · 故事性蒸馏](../11-故事性蒸馏.md)。每节一份，`{{来源清单}}` 要点名、`{{现有讲法}}` 一定要给。

```
你是课程研究助理。为大众课程 {{课程名}} 的 {{小节}}（内容：{{本节要点，一两句}}）去网上找讲得最好的公开内容，
蒸馏它们的**讲法**（开场钩子、比方、对照组、顺序、图怎么画、怎么让外行觉得有意思），不是抄内容。

必看：{{来源清单：点名作者／文章／论文，并写清想从它那里借什么}}

我们现有的讲法（供对照，别把这些当新发现报回来）：{{现有讲法：比方、图 id、主线句}}

工具：网页搜索与读取（读原文时只取相关段落）。一种搜法没结果就换中英文关键词。

输出写到 {{笔记路径}}：
1. 每个来源：名＋URL；它怎么讲（用自己的话概括，可短引并标出处）
2. 可借讲法表：借什么 → 用在本节哪里 → 为什么更有趣／更好懂
3. 最多 6 条具体改进，按收益排
⛔ 不编造：没读到原文就写「没找到」；二手笔记标二手。回复里给 300 字内摘要。
```

## N · 麻瓜分段读

```
你扮演一位聪明但完全不懂 {{领域}} 的普通读者（例如一位对科技感兴趣的高中老师）。只读不改文件。
用浏览器打开 {{课件}}，把 {{两节的 section id}} 逐段读一遍：正文取文字（折叠的不展开，按普通读者不点开处理）；

报告三件事，都具体到「节号＋原文开头 15 字」或「图 id」：

最后给最多 8 条改进，按普通读者体验提升从大到小排，每条一句话说清改哪里、怎么改。
```

## 通用尾巴

每份任务书末尾都加这一段：

```
你的最终输出就是这份报告本身（它会被直接读，不要写「我已经完成了任务」这类话，也不要写执行过程）。

⚠️ 凡是你拿不准的，标一句「这条我不确定，判据是 X」——
   报一条没把握的、标明了的，比报一条编出来的有用得多。
```

最后那句是刻意加的：没有它，agent 会把「我猜」写成「实测」。
加了之后它会自己分层，而那一层正好就是你该去核的那批。
