## 这个专题要回答的一个问题

前四个专题讲的都是训练：一个目标（吞吐最大化）、一种负载、跑几个星期。

**推理不一样，而且不一样在两个层面：**

1. **目标从一个变成三个**：延迟、吞吐、成本，**三者互相打架**
2. **负载内部是分裂的**：一次请求里有两个阶段，**它们的瓶颈完全相反**

第二点是这个专题的主线。理解了它，后面所有的技术
（连续批处理、PD 分离、投机解码……）都是它的自然推论。

## 一 · 两个阶段，两种性质 ⭐

一次请求分成两段：

| | **Prefill** | **Decode** |
|---|---|---|
| 在干什么 | 把整段 prompt 一次吞进去，算出 KV cache | 一个 token 一个 token 往外吐 |
| 一次算多少 token | **几千甚至十几万** | **1 个** |
| 矩阵形状 | 大而方正 | **瘦长**（一行乘一个大矩阵） |
| 每算一次要读多少权重 | 同样多 | 同样多 |
| **瓶颈** | **算力受限** | ⭐ **带宽受限** |
| 决定哪个指标 | **TTFT**（首 token 延迟） | **TPOT**（每 token 时间） |

> ⭐ **同样的模型、同样的权重，两个阶段落在屋顶线的两侧。**
> （回到[专题六](专题06-性能调优与工具链.md)那张图：prefill 在平顶下，decode 在斜坡上。）

**decode 为什么那么亏**：为了算 1 个 token，要把**全部权重**从 HBM 读一遍。
671B 的模型、bf16 存，读一遍就是 1.3 TB。**算术强度低到离谱。**

**这一条推出了后面几乎所有的技术**：
- 想办法让 decode 一次多算几个 token → **批处理**、**投机解码**
- 想办法让每次读的字节少一点 → **量化**、**MoE**（只读激活的那部分）
- 既然两阶段性质不同 → **干脆分开部署**

## 二 · KV cache：整个推理系统都在围着它转 ⭐

**这一章篇幅要给足** —— 推理系统里一半以上的工程复杂度都在这儿。

### 2.0 一个统一的视角：这是个存储层次问题

先把心智模型立住，后面所有技术都能挂上去：

> **KV cache 管理，本质上就是操作系统那套内存管理，
> 只不过换了一层硬件。**

| 操作系统里的 | KV cache 里的 |
|---|---|
| 虚拟内存 / 分页 | **PagedAttention** |
| 缓存（cache） | **Prefix cache** |
| 命中率 | **前缀命中率** |
| swap 到磁盘 | **offloading 到 host DRAM / SSD** |
| 存储层次（L1/L2/内存/盘） | **HBM / Host DRAM / 远端** |
| 淘汰策略 LRU | **前缀树 + LRU** |
| DMA / 预取 | **异步 transfer / 预加载** |

⭐ **这张表本身就值一页 slide。** 立住之后，
后面 Mooncake、NIXL、offloading 这些名词就不用死记 —— 它们各自在填哪一格是清楚的。

### 2.1 为什么它是头号约束

- 训练时 KV cache 不存在（一次算完整句）；**推理时它是主角**
- 它随 **序列长度 × 层数 × 并发数** 三重增长
- ⭐ **它直接决定你能同时服务多少人**

**要算的**：拿[专题一](专题01-拆开-DeepSeek-V3.md)的 MLA 数字，
算出一个 128K 请求占多少、一张卡能放几个并发。

### 2.2 HBM 内部：PagedAttention

- 传统做法给每个请求预留一整段连续显存 → **碎片 + 过度预留**，浪费一大半
- **PagedAttention**：切成固定大小的 block，按需分配，逻辑连续物理不连续
- ⭐ 这就是 vLLM 的立身之本
- 顺带带来的能力：**共享**（多个请求共用同一段前缀的 block）

### 2.3 Prefix cache 与命中率

**想法很朴素**：相同的前缀，KV 只算一次。

**什么场景命中率高**（这一节要讲透，因为它决定值不值得做）：
- **系统提示词** —— 所有请求都带，命中率接近 100%
- **多轮对话** —— 每一轮都包含前面所有轮
- **RAG** —— 同一份文档被反复检索到
- **Agent** —— 长长的工具定义每次都要带

**要讲的工程点**：
- 用**前缀树（radix tree）**组织，而不是简单的 hash
- **淘汰策略**：LRU？按前缀长度加权？
- ⭐ **命中率是这一块的核心指标** —— 但要小心：
  命中率高不等于省得多，**要看命中的是多长的前缀**
- 命中率怎么监控、怎么提高（请求路由到同一个实例上 → 亲和性调度）

### 2.4 Offloading：HBM 装不下就往下挪

**分级存储的第一步**：HBM → Host DRAM →（再往下）SSD / 远端。

**核心判据只有一条**（要在课上算给学员看）：

> **把 KV 从 host 挪回来的时间，跟直接重算一遍的时间，哪个更短？**

- 挪回来的成本 = 字节数 ÷ PCIe 带宽
- 重算的成本 = 那段 prefill 的 FLOPs ÷ 算力
- ⭐ **长序列偏向挪（重算太贵），短序列偏向重算**
- 还要考虑：能不能**异步预取**，把搬运藏进计算里

⭐ **我们做过一份完整调研**：vLLM tpu-inference 的 KV cache offloading
（HBM→Host DRAM），把组件架构和 25 个 PR 的时间线都梳理了一遍。

⚠️ **一个容易混的区分**：**offloading ≠ PD 分离**。
前者是"同一台机器上往下挪一层"，后者是"换一批机器"。
两者可以叠加，但解决的问题不同。

### 2.5 Transfer：KV 要在节点之间跑起来

一旦做了 PD 分离（见第四节），KV cache 就得**跨节点搬**。

- 传输量有多大？—— 拿 MLA 的数字算：128K × 61 层 × 576 个数
- 走什么通路？**NVLink 域内 > RDMA > 普通网络**，差好几个数量级
- 能不能**边算边传**（prefill 一层就传一层，而不是全算完再传）

**这一块的代表方案**：
- ⭐ **Mooncake Transfer Engine** —— RDMA 直达（绕过 CPU）、**拓扑感知路由**
  （集群里十张网卡，谁走哪条）。我们拆解过它的这两部分
- **NIXL** —— NVIDIA 的传输抽象层
  > ❓ Chris 提到 GPU 侧还有一个「MIX」，我理解是 **NIXL**，请确认

### 2.6 生态：各家在做什么

| 平台 | 方案 | 干什么 |
|---|---|---|
| **TPU** | vLLM `tpu-inference` 的 offloading | HBM → Host DRAM，我们调研过 |
| **TPU** | JetStream | Google 的 TPU 推理编排层 |
| **GPU** | **Mooncake** | 传输引擎：RDMA + 拓扑路由 |
| **GPU** | **NIXL** | 传输抽象层 |
| **GPU** | LMCache 等 | 缓存层 |

## 三 · 批处理：把 decode 的浪费摊掉

既然 decode 读一次权重只算一个 token，那就**让它一次算很多个请求的 token**。

- batch 越大 → 同一次权重读取服务的 token 越多 → **算术强度线性上升**
- 但 batch 越大 → 单个请求的延迟越差，KV cache 也吃得越多

**静态批处理的问题**：一批里有的请求早早生成完了，
却要等最长的那个 —— **卡空转**。

**连续批处理（continuous batching）**：
谁生成完了谁就走，空出的位置立刻放新请求进来。
⭐ **这是现代推理引擎吞吐提升最大的单项来源。**

## 四 · 分离：一个谱系，不是一项技术 ⭐

**推理系统这几年最重要的一条主线：把混在一起的东西拆开，各自用最适合的配置。**

拆的依据只有一条：**性质不同的负载就该分开放。**
按拆的维度，有三层：

### 4.1 按阶段拆：PD 分离

prefill 算力受限、decode 带宽受限 —— 放同一批卡上意味着：
配置对两边都不最优，而且一个长 prompt 的 prefill 会**卡住所有人的 decode**。

- **拆成两个池**，各自配置、各自扩缩容
- 代价：**KV cache 要从 prefill 池传到 decode 池**。传输量多大？走什么通路？
  ⭐ 我们实测过让它走**域内 NVLink**（而不是网络）

### 4.2 按模块拆：AFD（Attention-FFN 分离）

**比 PD 更细一层，也更反直觉。**

同一个 decode 步里，attention 和 FFN/MoE 的性质也不一样：

| | Attention | FFN / MoE |
|---|---|---|
| 绑着什么 | **KV cache**（跟着序列走） | **专家权重**（跟着模型走） |
| 瓶颈 | 访存 | 算力（MoE 还有 all-to-all） |
| 想要的并行 | 按序列/头切 | 按专家切 |
| 扩缩容的理由 | 并发数、序列长度 | 模型大小 |

既然如此 —— **为什么要把它们塞在同一组卡上？**

- **AFD**：attention 和 FFN 分开部署，中间传激活
- 现状：**SGLang 有原生支持，vLLM 没有**（RFC #22799 仍未落地）——
  ⭐ 这是 vLLM 的一个结构性短板，值得单独讲
- ⚠️ **不是所有模型都适合**：对混合线性注意力的模型（比如 K3），
  AFD 的意义就不如对全注意力 / MLA 模型大 —— 因为 attention 那侧本来就轻了

### 4.3 拆完之后：每一块各自选并行 ⭐

**这是最容易被忽略、也最能体现功力的一层。**

拆开之后，每一块**不再需要用同一套并行策略**：

| 块 | 常用并行 | 为什么 |
|---|---|---|
| **Prefill** | PP、**PCP**（prefill 阶段的 context parallel） | 序列很长，切序列最自然 |
| **Decode** | **DCP**（decode 阶段的 context parallel，**按 token 位置切 KV**） | KV 是主要负担，按位置切能摊开 |
| **Decode 的 MoE 部分** | **DEP / EDP**（decode 阶段的专家并行） | 专家权重是主要负担 |

> ⚠️ **注意 CP 在两个阶段的含义不一样**：
> prefill 的 CP 切的是**正在算的那段序列**，
> decode 的 CP（DCP）切的是**已经存下来的 KV**。
> 名字像，解决的问题不同。

⭐ **一条实测坑**：DCP 下 **不能开 `--enable-symm-mem`** ——
为了 decode graph 的正确性被强制禁用。开了会报错或者结果不对。
这种"某个并行模式下某个优化开关就是不能用"的组合约束，
**只有真跑过才知道**。

## 四点五 · 我们的实测：把单卡 decode 吞吐推到极限 ⭐

**这一节是这个专题的分量所在。** 我们在 GB200 / GB300 上做过一轮很硬的压测，
标的是 DeepSeek V4-Pro 和 Kimi K3。

**几个可以摆出来的数**（tok/s/GPU，decode）：

| | 数值 | 说明 |
|---|---|---|
| 我们实测最好 | **8,540** | |
| dep8 在 GB300 上的**硬天花板** | **12,070** | batch 超过约 890 之后就不再是瓶颈 |
| 官方宣称 | **11,200** | ⚠️ 但要看清口径：**"at roughly 50 tok/s/user"** |
| DCP 配置（FP4） | **2,808** | 不同拓扑差异巨大 |

> ⚠️ **口径陷阱**：官方那个 11,200 是**带着 per-user 速度约束**的。
> 脱离「每个用户多快」谈聚合吞吐没有意义 ——
> 你总可以把并发堆到很高、让每个人都很慢，换一个好看的总数。
> **这一条要在课上专门讲，它是推理测评里最常见的误导。**

⭐ **最值钱的一条结论**（跟[专题四](专题04-并行策略.md)呼应）：

> **换拓扑的收益远大于调参数。**
> 同一个 workload：在 vLLM 里疯狂调参顶多 **+45%**，
> 换成 dep8 拓扑是 **+347%**。

其它可讲的实战点：
- DEP8 Wide-EP 端到端跑通：8 个 DP rank 跨节点，KV cache 走域内 NVLink
- 两个 PP8 prefill worker 喂两个 DCP8 decode 节点的组合拓扑
- 并发能力：GB300 DEP8 理论可扛约 288 并发

> ❓ **待确认**：Chris 记得有一轮把单机 generation 推到过 **9000+**。
> 我在记录里查到的是 **8,540**（实测最好）、**12,070**（dep8 天花板）、
> **11,200**（官方，带 per-user 约束）。
> 9000+ 可能是另一个口径或另一轮 —— 讲之前要对上。

## 五 · 投机解码：用富余的算力换步数

**逻辑链条很漂亮，值得完整讲一遍：**

1. decode 是带宽受限 → **算力是有富余的**
2. 那能不能用算力换点什么？
3. 能 —— **一次猜好几个 token，然后一次性验证**
4. 猜对了就赚了几步；猜错了就退回，损失的只是那些富余的算力

**几种猜法**：
- 小模型当草稿（draft model）
- **MTP** —— ⭐ [专题一](专题01-拆开-DeepSeek-V3.md)站 6 埋的伏笔在这里回收：
  V3 训练时用的多 token 预测头，推理时正好拿来做投机
- n-gram / 前缀匹配

⚠️ **压测陷阱**：验证投机解码效果时**必须固定采样随机性**（temperature=0），
否则接受率会崩到个位数，你会得到一个完全错误的结论。**我们踩过。**

## 六 · 量化：直接砍访存

decode 是带宽受限 → **读的字节少一半，就快一倍**（近似）。
所以量化在推理侧的收益比训练侧直接得多。

- 权重量化：FP8 / FP4 / INT4/8
- KV cache 量化
- 激活量化（更难）
- ⚠️ 哪些层不能量化、精度掉在哪里

## 七 · TPU 上的推理：静态形状这道坎 ⭐

**这一节是我们最有话说的部分。**

推理天生是动态的：prompt 长度不同、生成长度不同、并发数在变。
而 XLA 要求**编译期形状确定**（[专题二](专题02-TPU-与-GPU.md)）。

**这个矛盾怎么解：**

- **分桶（bucketing）** —— 把长度归到有限几档，padding 到桶边界
- **预编译** —— 每个桶编译一份，缓存起来
- **编译缓存** —— 否则冷启动要等十几分钟
- 桶怎么分：太粗浪费算力（padding 多），太细编译爆炸
- ⚠️ 连续批处理 + 静态形状 = **两个方向相反的需求**，这是移植的核心难点

**引擎现状**：vLLM 和 SGLang 都起于 GPU，往 TPU 移植时**卡的全是这一条**。
⭐ 我们部署过六个模型，踩过的坑可以直接摆出来。

## 八 · 服务化：指标与调度

- **指标**：TTFT / TPOT / 端到端延迟 / 吞吐 / **P99**（平均值会骗人）
- **调度**：优先级、抢占、长请求怎么不饿死短请求
- **容量规划**：给定 SLA，一张卡能服务多少 QPS —— **这是所有账的落点**
- 多租户与隔离
