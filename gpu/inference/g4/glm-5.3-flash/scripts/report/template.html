结论先行

  • 能跑，不用打补丁。 vLLM nightly（0.33.0rc1.dev484）原生支持 GLM-5.3-Flash 在 RTX PRO 6000（SM120）上运行。单路生成约 100 tok/s，输入从 1K 到 32K 几乎不变。
  • 最大的性价比杠杆是「NVFP4 + TP4」。 标准对话门槛（TTFT P90 ≤ 3 s、每路 ≥ 25 tok/s）下，每卡输出：FP8 单机 TP8 约 45 tok/s → NVFP4 单机 TP8 约 63 → NVFP4 单机 2×TP4 约 112，合计约 2.5 倍。
  • NVFP4 不掉能力。 GSM8K 全量 1,319 题，FP8 93.33%、NVFP4 92.95%，逐题配对检验 p = %%PVAL%%，无显著差别。
  • 不分离还是 PD 分离，取决于延迟门槛。 同样 16 张卡、128 并发，2P2D 与不分离 4×TP4 吞吐接近（%%P2_128_OUT%% 对 %%C4_128_OUT%% tok/s），P99 ITL %%P2_128_ITL%% ms 对 %%C4_128_ITL%% ms，生成明显更平稳；首字则是不分离快 0.3–0.6 s。门槛严（要求不卡顿）时 2P2D 每卡吞吐最高，门槛宽松时不分离最高。
  • 做 PD 必须注意三件事： P 和 D 用相同的 TP（否则 NIXL 握手失败）；P:D 按容量配（8K 输入 / 1K 输出时 1:1）；UCX 的 TCP 分段调到 1m（默认值下 KV 传输慢 3 倍）。

  • 并发扫描：固定同时在飞的请求数（1 → 256），每档请求数 = 并发 × 4。用来看吞吐和 TPOT 的上限。每档开头一次性涌入，TTFT 会被排队放大。

单独测一个实例的两种能力：prefill（8K 输入、只生成 1 token）和 decode（8K 上下文命中前缀缓存、生成 1,024 token）。

图 2　prefill 吞吐：一个 TP4 实例和一个 TP8 实例几乎一样，一台机器拆成两个 TP4 能力翻倍
  • prefill 能力不随 TP 增长：TP8 实例约 %%PRE8%% tok/s，TP4 实例约 %%PRE4%% tok/s；一台机器两个 TP4 约 %%PRE4X2%% tok/s。
  • decode 在 TPOT 约 45 ms 时两者整机相当（TP8 并发 128：2,658 tok/s；2×TP4 各并发 64：合计 2,620 tok/s），更高负载 TP4 略好。
  • 配比：8K 输入 / 1K 输出每生成 1 token 要 prefill 8 token。一台 P 机器（2×TP4）≈ 18.4K ÷ 8.2K ≈ 每秒 2.2 个请求；一台 D 机器在 TPOT 约 45 ms 时 ≈ 2,620 ÷ 1,024 ≈ 每秒 2.5 个请求 → 按机器 P:D ≈ 1:1。
P 和 D 必须同 TP。 GLM-5.3-Flash 的 KV 块大小要与每卡的 KDA 状态页对齐，TP4 时 2,304 token、TP8 时 1,280 token。P=TP4、D=TP8 时块对不上，NIXL 握手失败（日志 Not pairing remote 2304-token blocks with local 1280-token blocks），所有请求返回 500。

配比随输入输出长度变化：输入越长、输出越短，越需要更多 P。用业务的真实长度代入上面的算法即可。

七、PD 的网络调优：把一块网卡跑满

vLLM 的 decode 日志带 KV 传输统计。UCX 默认参数下，每个 rank 每次传约 80 MB 要 300 多毫秒（约 220 MB/s），远低于网卡能力。用独立的 NIXL 读取基准（scripts/pd/nixl_bench.py，80 MB 拆 300 块，与 vLLM 一致）定位：

%%NET_NIXL%%
  • CPU 内存本来就快（约 24–31 Gbps），GPU 显存在默认参数下只有约 5 Gbps；拆 1 块或 3,000 块差别不大。
  • 根因是 UCX 的 TCP 分段：UCX_TCP_TX_SEG_SIZE=1m + UCX_TCP_RX_SEG_SIZE=1m 后单对连接 27 Gbps（5 倍）；4m 相同；UCX_RNDV_FRAG_SIZE 无效。

九、硬件视角：为什么是这样

1. FP4 的长处在 decode：省显存、省带宽

  • decode 是读权重的活。 高并发时一步 decode 几乎会用到全部 288 个专家，每卡要把自己那份权重读一遍。按实测每卡权重估算：FP8 39.38 GiB ÷ 1,597 GB/s ≈ 26 ms，NVFP4 23.69 GiB ÷ 1,597 GB/s ≈ 16 ms（推导值，未计 KV 与注意力读取）。
  • 省下的显存全部变成 KV：每卡可用 KV 从 38 GiB 涨到 55 GiB。G4 显存大（96 GB）而带宽只有 1.6 TB/s，FP4 补的正是带宽这块短板。
  • prefill 几乎没收益：prefill 每实例约 9K tok/s，折合每卡约 2 × 18B × 9.3K ÷ 8 ≈ 42 TFLOPS（TP8，未计注意力），只占标称峰值的个位数百分比——瓶颈在 SM120 上还不成熟的 sparse MLA 索引器、KDA 等非 GEMM kernel 和调度开销，不在矩阵乘。
软件在快速演进：SM120 的注意力 kernel 成熟后 prefill 会变快，最优 P:D 会向「更少 P」移动。升级引擎后建议用第四节的方法重测两个容量。

2. PCIe 拓扑决定了 TP4 比 TP8 划算

8 张卡两两挂在同一个 PCIe 交换芯片下，每 4 张一个 NUMA 节点，没有 NVLink。TP8 的每次 all-reduce 都要跨 NUMA；TP4 可以留在一个 NUMA 内。实测 prefill 每实例 TP4 ≈ TP8，等于 TP4 每卡效率高一倍。

3. 网络：带宽够，参数要调

G4 跨机没有 RDMA，KV 走 TCP。单网卡 173 Gbps 足够，但 UCX 默认分段让 GPU 显存传输每连接只有约 5 Gbps，调大分段后可以打满（第七节）。

十一、限制与复现

  • SM120 支持目前在 vLLM nightly 中，尚未进入正式版。生产请固定镜像 digest。
  • 未开启 MTP 投机解码（社区报告 nightly 原生 SM120 后端上 MTP 接受率为 0）。
  • 所有数字为 2026-11-03 在 Google Cloud G4（us-central1）实测，每个点一次运行，未做多次重复取平均。
  • NVFP4 权重为第三方量化（RedHatAI），NVIDIA 官方另有 nvidia/GLM-5.3-Flash-NVFP4，本次未测。
