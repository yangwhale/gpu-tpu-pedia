第 零 节

一次请求走一遍

同一个模型，吞 prompt 那一段吃算力，往外吐字那一段吃带宽。 一次请求里，前后两段要的硬件正好相反。

0.1　一个请求的一生

用户只感觉得到两个数：等第一个字等了多久（TTFT），之后每个字隔多久（TPOT）。 这两个数分别由 prefill 和 decode 决定，第二节再把它们的口径校准。

0.2　全课一句话

一句话 decode 每一步都要把权重和 KV 搬一趟。推理的每一招，要么让这一趟分给更多 token，要么干脆少搬。
还有一类招数不碰这一趟本身：把吞 prompt 和吐字拆开，各放到合适的机器上。

第一节先把这一趟的账算清楚：搬多少字节、花多少时间、算力闲了多少。

遇到不认识的词，回这儿查：prefill、decode、KV cache、TTFT、TPOT、吞吐、屋脊点、chip 与 device、PD 分离、投机解码……（每条一句话）

prefill：把整段 prompt 一次喂进模型算完，顺手产出第一个输出 token。
decode：之后每一步只往外出一个 token，出完接着喂回去算下一个。
KV cache：每个处理过的 token 在每一层留下的 K 和 V，后面的 token 算注意力时要回头读它们，所以一直存在显存里（专题三）。
TTFT：从请求发出到收到第一个输出 token 的时间；含不含排队要写清。
TPOT 与 ITL：TPOT 是一个请求除第一个 token 外平均每个 token 花的时间；ITL 是相邻两个 token 之间的每一次间隔，看 p99 时用它。
batch 与并发：并发是同时在服务的请求数；batch 是引擎这一步实际拼在一起算的请求（或 token）数，通常不超过并发。
吞吐：每秒出多少 token。要写清是总量还是每卡（每卡 ＝ 总量 ÷ 卡数，分母含不含 prefill 的卡），以及只数输出还是输入输出合计。
MoE 激活参数：MoE 模型每个 token 只经过挑中的几个专家，真正参与计算的那部分参数；DeepSeek-V3 总共 6,710 亿，每个 token 激活约 370 亿。
HBM 带宽：芯片每秒能从自带显存读写多少字节；TPU v7 每芯片 7.37 TB/s。
屋脊点：峰值算力 ÷ 显存带宽，即每读 1 字节至少要做多少次运算才不被带宽拖住；v7 按 bf16 算约 313（专题二）。
chip 与 device：一颗 TPU v7 芯片对软件显示成 2 个 device；本课的规格按每芯片写，并行度按 device 数。
PD 分离：prefill 和 decode 放到两批不同的机器上跑，中间把 KV cache 传过去（专题五第六节）。
投机解码：先用便宜的办法猜出后面几个 token，再让大模型一步把它们一起验掉，猜对几个就一次出几个。

第 一 节

两个阶段：prefill 吃算力，decode 吃带宽

prefill 一次喂几千行，decode 一次每人只喂一行。 行数差了三个数量级，瓶颈就从算力换到了显存带宽。

1.1　一次喂几行，决定卡在哪

屋脊点是专题二那把尺：v7 每读 1 字节要做 313 次运算，算力才不闲着。 矩阵乘一次喂进 M 行，强度大致跟着 M 涨。

decode 拼 256 个人也只有 239，要到 M ≈ 343 才过线。 prefill 一段 4K prompt 就是 1,911，稳稳卡在算力上。

1.2　一个人解码一步：5 毫秒在读，0.016 毫秒在算

DeepSeek-V3 每个字激活约 370 亿参数，FP8 存，一步要读 37 GB。 按一颗 v7 的规格算，账是这样的：

读完要 5.02 ms，算完只要 0.016 ms，算力利用率 0.32%。 这就是 decode 的字节下限：步时离它越近，说明带宽用得越满。

1.3　上下文一长，KV 接过主角

权重一次读完能分给一整批人，KV 却是每人自己的历史。 拼的人越多、上下文越长，KV 在这一趟里的份量越大。

128K 时每个字要读这个人自己的 9.21 GB KV（MLA 已经压过一轮，专题三）。 256 人一起跑，KV 占到 78%，光靠拼 batch 已经摊不动。

1.4　MoE 把拼好的 batch 又拆散

拼 batch 是为了让一块权重多分几行。 可 MoE 每人只挑 8 个专家，256 人进来，到每个专家手里平均只剩 8 行。

v7 的 MXU 一边是 256，8 行只喂满 1/32。 专家怎么切、怎么把各卡的人收到一起，接着专题一的 MoE 往下讲（第五、六节）。

这一节只要带走一件事 prefill 卡算力，decode 卡带宽；decode 每一步都要把权重和 KV 搬一趟。
后面每一节，要么把这一趟分给更多 token，要么让它少搬几个字节，要么把两段拆开各放各的机器。
第 二 节

先校准尺子：指标与口径

同一次测量，按一种算法是每卡 5,270，按另一种是 11,880。 先把尺子对齐，后面每一节的数才能放在一起比。

2.1　四个时间指标，各量哪一段

TTFT 是进门到第一个字。压测时它往往大半是排队：同一个 Gemma4-31B，并发 1 时 86 ms，并发 256 时 7,756 ms。

TPOT 是首字之后平均每个字的间隔，每个请求一个数；每用户 tok/s 约等于 1000 ÷ TPOT(ms)。 ITL 是逐次间隔，开了投机解码时一次可能吐两三个字，看 p99 要看它。

同一个词，两家定义 NVIDIA NIM 把 ITL 定义成 (e2e − TTFT) ÷ (字数 − 1)，并注明「也叫 TPOT」；vLLM 的 ITL 是逐 chunk 的间隔列表。 拿两家工具的数对比之前，先查定义。

2.2　吞吐和交互性是一条曲线

同一条 vLLM 曲线上，每用户 68 tok/s 时每卡 9,759，提到 173 时只剩 895。 让每个人等久一点，同一趟就能分给更多人，每卡吞吐自然上去。

所以比较的顺序是：先定交互档，再在这一档上比吞吐。PyTorch 博客报的 11,200 就钉在每用户约 50 tok/s 这一档上。

DistServe（arXiv 2401.09670）把这件事做成一个指标：goodput，只数同时满足 TTFT 和 TPOT 目标的请求。 按这个尺子，它报告能多服务 7.4 倍的请求，或者扛住紧 12.6 倍的延迟目标。

2.3　同一次测量，四把尺子

分子只数输出还是输入输出合计，分母只数 decode 卡还是全部卡，排列组合就是四个数。 InferenceX 的两个字段各占一个：output ÷ decode GPU 是 5,270，(输入＋输出) ÷ 全部 GPU 是 11,880。

看到一个百分比或每卡吞吐，先问两句 一，分母是谁？只数 decode 卡，就把 prefill 的成本藏起来了。
二，每卡还是总量，卡按什么数？一颗 TPU v7 芯片对软件显示成 2 个 device，按 device 报的每卡数只有按芯片报的一半。

2.4　尺子以外的四个坑

  • 假天花板：并发扫描在 9,200–9,400 一带涨不动，当时以为到顶了。只改 KV 池的划分比例，同为 4K 输入的端到端从 6,887 涨到 10,614，再调显存比例到 10,704。扫出来的上界只属于那组参数。
  • 峰值和稳态：引擎自报的峰值是某一刻的最高值。同一轮里峰值 12,070、端到端 10,704。
  • 温度：草稿模型按 greedy 猜，服务端却按默认温度 1.0 采样，接受率只有 1.16%；改成温度 0 是 34%，输出 2,911 对 944。草稿按概率采样时没有这个坑。
  • 预热和闭环：第一轮要编译、要热缓存，报第二轮。限并发的闭环压测比开环低 13%，对标要开环。

2.5　落到钱上

DeepSeek 公布过一天的账：平均 226.75 个 H800 节点，按每卡每小时 2 美元算，一天成本 87,072 美元。 如果全部按 R1 定价收费，理论日收入 562,027 美元，成本利润率 545%。

它自己也写明实际收入低得多：V3 更便宜，网页和 App 免费，夜间打折。 同一份文档里，每个节点 decode 时每秒约出 14,800 个字，平均每用户 20–22 tok/s，这又是一个交互档的选择。

这一节只要带走一件事 报一个吞吐，要连同五样一起报：分子分母、交互档、峰值还是稳态、温度和采样、有没有预热和是不是开环。 缺一样，两个数的差距可能全是口径。
考考自己：一份材料写「每卡 12,000 tok/s，超过官方」。你要先问哪三件事？

分母只算 decode 卡还是全部卡、分子含不含输入；在每用户多少 tok/s 的档位上测的；是峰值还是端到端稳态。 放在 TPU 上还要再问一句：卡按芯片数还是 device 数。

第 三 节

KV cache：账、池、复用

每条在跑的序列，都要在显存里单独占一块 KV，这块地方不能和别人共用。 KV 池装得下几条序列，decode 每一趟搬运最多就分给几个人。

3.1　一个 token 留下多少字节：四种记法

KV cache 是每个处理过的 token 在每一层留下的 K 和 V，后面的 token 算注意力时要回头读。 一个 token 留多少字节，由注意力怎么存 K、V 决定（专题三逐项算过）。

全部按 bf16（2 字节）、所有层加起来算；实际部署常把 KV 存成 fp8，字节再减半。字节数取自各模型 config.json，本课推导。
记法每层存什么每 token 字节例子
MHA每个头各存一份 K、V3,997,696V3 的形状假如用 MHA
GQA几个头共用一组 K、V327,680Llama-3.1-70B：8 组 × 128 维 × 80 层
MLA一条压缩向量，所有头从它解出 K、V70,272DeepSeek-V3：(512＋64) 维 × 61 层
线性注意力不按 token 存，每条序列一个大小固定的状态0（另交固定状态）Qwen3.5：45 层线性层每条序列 180 MiB，另 15 层全注意力 30,720 B/token

DeepSeek-V4 不在这张表的任何一行：它每层只存一条所有头共用的 KV，再按层压缩 4 倍或 128 倍（CSA／HCA），3.4 节讲它的两个池。

3.2　batch 上限 ＝ KV 池 ÷ 每条序列的 KV

一颗 v7 芯片 192 GB，放下 V3 的八分之一 FP8 权重，再留一成余量，剩 88.9 GB 给 KV。 V3 的每个 token 占 70,272 字节，4K 上下文能装 308 条，32K 只剩 38 条。

  • 上下文翻几倍，人数就除几倍。KV 和上下文长度成正比，池子是固定的。
  • 记法决定起点。同样 4K，GQA 每 token 327,680 字节，只装得下 66 条，不到 MLA 的四分之一。
  • 线性注意力是一笔固定成本。短上下文时吃亏，长上下文时占便宜。

人数少了，同一趟权重搬运分给的 token 也少了。这就是长上下文贵的第一个原因。

3.3　PagedAttention：像操作系统那样分页

早先的做法按最大长度给每条序列预留一整段连续显存，没写到的部分全浪费。 PagedAttention 把 KV 切成固定大小的块，每条序列用一张页表记下「第几块住在哪个物理块」。

  • 按需领块。序列长一点就多领一块，浪费只剩最后一块没写满的尾巴。vLLM 论文测过，旧系统 KV 显存里真正存着 token 的只有 20.4%–38.2%，分页后到 96.3%。
  • 共享与写时复制。并行采样的几条序列共用 prompt 的块，各记一个引用数；谁要往共享块里写，先给自己复制一份。
  • 块大小跟 kernel 一起定。attention kernel 每读一块查一次页表。TPU 上 Qwen3.5 把块从 16 个 token 调到 256，512 并发时 decode 一步从 428 µs 降到 283 µs。

3.4　混合模型有两个池，预算要分

DeepSeek-V4 每层有两种 KV：滑窗那份只留最近 128 个 token，另一份存压缩后的整段。 SGLang 给它们开两个池，共用一份预算，用 --swa-full-tokens-ratio 定两边怎么分。

4K 输入时，比例 0.20 让全长池先满，每张 decode GPU 只跑出 6,887 tok/s；调到 0.15 两边一起满，到 10,614，高 54%。 再多给显存、多装 13% 的人，只到 10,704：每张卡近 900 条之后，瓶颈已经从装不下换成了算不动。

⚠️ 池子算错不一定报错 tpu-inference 跑 Qwen3.5 时，vLLM 的混合分配器默认 4 层共用一块 KV 张量，而 TPU 上每层必须各存一份。 结果块编号的池子大了约 3.5 倍，编号越界后被 JAX 的 dynamic_update_slice_in_dim 静默截断到边界上，多个请求写进同一块。 表面症状是胡言乱语、OOM 或引擎崩溃，看不出是 KV 池的账错了（tpu/tpu-inference/Qwen3.5-397B-A17B-FP8/README.md:77）。

3.5　前缀复用：算过的不再算

很多请求开头一样：同一段 system prompt、同一份文档、多轮对话的前几轮。 把算好的 KV 留着，下一个请求命中前缀就直接接着算，prefill 省掉一大段。

  • RadixAttention。SGLang 把所有缓存的前缀存成一棵基数树，新请求沿树往下匹配最长前缀，满了按最近最少使用淘汰。
  • 命中率可以很高。DeepSeek 公开过 24 小时的线上统计：6,080 亿输入 token 里 56.3% 命中了存在磁盘上的 KV。
  • 线性注意力和滑窗难复用。线性层的状态是整段压出来的，截不回任意位置；滑窗层早先位置的 KV 已经丢了。想复用，就得在块边界另存一份状态快照。

tpu-inference 跑 Qwen3.5 目前要显式关掉前缀缓存（--no-enable-prefix-caching），否则触发一个断言错误（同一 README:95）。

3.6　分层卸载：搬回来，还是重算

HBM 放不下的 KV 可以往下放：主机内存、本机磁盘、远端存储，一层比一层大、一层比一层慢。 命中之后要搬回来，搬回来比重算慢就白存了。

盈亏带宽 搬回 ＝ 每 token KV 字节 × L ÷ 带宽；重算 ≈ 每 token FLOP × L ÷ 有效算力。
两者相等时：带宽 ＝ 每 token KV 字节 × 有效算力 ÷ 每 token FLOP。链路比它慢，就不如重算。

V3 按 v7 FP8 峰值的一半算，盈亏带宽约 2.19 GB/s；GQA 的 Llama-3.1-70B 每个 FLOP 对应的 KV 多，要 5.35 GB/s。 前缀越长，注意力的平方项让重算越贵，1 GB/s 的慢链路过了约 35K token 也能赢。

  • llm-d（开源的 Kubernetes 推理调度）在 TPU7x 上测过 Qwen3-32B 把 KV 卸到主机内存：平均 TTFT 0.98 s → 0.56 s，P90 2.1 s → 0.5 s，吞吐 +8.9%。它的排障说明里也写着另一面：TTFT 比不卸载还差，就是搬回来比重算慢。
  • Mooncake Store：开源的分布式 KV 存储，把集群各机的内存和 SSD 拼成一个池，机器之间用 RDMA 互取。
  • LMCache：开源的 KV 缓存层，接在 vLLM、SGLang 下面，往主机内存、本地盘、远端存储里放 KV。
  • TPU Sync：Google 开源的 TPU 侧 KV 编排，做多层存储和主机内存卸载，README 写明还在开发中、不建议通用。
这一节只要带走两件事 ① KV 一人一份，它定了 batch 上限，也就定了一趟搬运最多分给几个人。记法、分页、两池分账，都是在同样的显存里多装几条序列。
② 复用和卸载是少算、少搬。命中的前缀不再 prefill；放到下层的 KV 要算清搬回来是不是比重算快。
考考自己：一颗 v7 芯片的 KV 池是 88.9 GB，V3 跑 64K 上下文能装几条？要是把 KV 存成 fp8 呢？

每条 70,272 × 65,536 ≈ 4.6 GB，装 19 条。fp8 字节减半，装 38 条。

第 四 节

批处理与调度：一趟分给更多人

decode 每一步都要把权重搬一趟。同一步里拼进来的人越多，每人分摊到的那一份越小。 批处理就是这条主线里最直接的一招，调度决定这一趟能坐满几个人。

4.1　每一步都重新排一次

静态 batch 凑满一批一起跑，最慢的那个跑完才整批返回。先跑完的槽位只能空着，每一步照样搬一趟权重。

Orca（OSDI'22）改成每一步结束都看一次：谁跑完谁让位，排队的人下一步就补进来。 论文在 GPT-3 175B 上报告，同等延迟下吞吐是 FasterTransformer 的 36.9 倍。今天的 vLLM、SGLang 都是这么调度的。

4.2　新人进门那一步：chunked prefill

逐步调度要在某一步里给新请求做 prefill。一段长 prompt 一口吞下，那一步就特别长，正在出字的每个人都卡一下。

Sarathi（arXiv 2308.16369）和 Sarathi-Serve（arXiv 2403.02310）把 prompt 切成小块，每步只带一块，和 decode 拼在一起。 vLLM V1 默认打开它，并让 decode 先上车；每步塞多少 token 由 max_num_batched_tokens 控制，调小字间隔稳，调大首字快。

在 TPU v7x 上跑 Gemma4-31B 的公开记录里，这个预算设成 16,384，256K 的 prompt 就切成 16 块。

4.3　槽位满了以后

Little 定律把三个数绑在一起：批里的人数 ≈ 吞吐 × TPOT。反过来就是吞吐 ≈ 槽位数 × 1000 ÷ TPOT(ms)。 dep8 那组实测 9,032 × 8 × 0.060 s，反推批里约 4,335 个请求。

槽位满了以后再加并发，两个因子都不动。总负载拉高 4.5 倍，每卡吞吐只从 8,777 到 9,745，首字等待却从 45 秒涨到 253 秒。

槽位也不白给。每卡 batch 从 886 加到 999，峰值只多 0.06%，TPOT 从 77.7 拖到 85.3 ms：每一步要算的人多了，这一步就长了。

TPU 上多一层：batch 大小要落在档位上 XLA 按静态形状编译，batch 大小也是形状的一部分。SGLang-JAX 的做法是为几种 batch 大小提前编译好计算图； 实际人数不在档位上时，通常补到最近的一档，补出来的行照样参与计算。来由见 专题二「运行时，还是编译期」。

4.4　CPU 那几毫秒也要藏起来

每一步之前，CPU 要挑人、拼 batch、准备输入。串着走的话，加速器每一步都要等它一下。

SGLang-JAX 把两件事叠起来：加速器算这一批，CPU 同时排下一批。在 Qwen3-32B 上，prefill 到 decode 之间的空档从约 12 ms 压到 38 µs。

4.5　显存不够时踢谁

批开大了，KV cache 可能在中途装不下，只能先请出去几个请求。被请出去的请求有两种回法： 把它的 KV 换到主机内存再搬回来（swap），或者丢掉 KV、回来时重算一遍 prefill（recompute）。

vLLM 文档的原话是：In vLLM V1, the default preemption mode is RECOMPUTE rather than SWAP, as recomputation has lower overhead in the V1 architecture。

谁先被踢、谁先上车，还牵涉公平：VTC（arXiv 2401.00588）按每个用户已经用掉的 token 数排队，Llumnix（arXiv 2406.03243）把请求在实例之间在线迁移。

这一节只要带走一件事 逐步调度是「一趟分给更多人」的地基。槽位满了，吞吐就钉在槽位数 × 1000 ÷ TPOT 上，再加并发只加排队。 chunked prefill 只摊平了 prefill 对 decode 的打扰，两种活还挤在同一批卡上；把它们拆到不同机器是第八节的事。
考考自己：TPOT 稳定在 50 ms，想让每张卡出 10,000 tok/s，每张卡的批里至少要同时坐多少人？显存只装得下 300 人时会怎样？

10,000 × 0.05 ＝ 500 人。只装得下 300 人，吞吐就钉在约 300 × 1000 ÷ 50 ＝ 6,000，再加并发只会让首字等待变长； 要么少搬（第十二节的量化让 KV 变小），要么换个交互档。

第 五 节

单卡里的两块硬骨头：decode 注意力与 MoE

一张卡上的 decode 有两块最难啃：注意力读的是每个人自己的 KV，MoE 的每个专家只分到几行。两块都是搬运问题，而且多出来的字节常常藏在布局里。

5.1　注意力：攒 batch 救不了它

decode 注意力每读 1 字节只做 G 次运算（G ＝ 每个 KV 头带几个查询头），推导见专题三 §3.1。GQA-8 就是 8 次，离 v7 的屋脊 313 差了近 40 倍。

攒 batch 分摊的是权重：读一遍，所有人共用。KV 是每条序列自己的历史，batch 翻倍它也翻倍。

Llama-3.1-70B 的权重 141 GB，上下文 8K 时每条序列的 KV 是 2.68 GB，batch 53 左右两块一样重。再往上，一步的字节大半是 KV，注意力就成了主角。

5.2　一个 kernel 装下 prefill 和 decode

同一步里常常混着 prefill 和 decode 的请求。RPA 把两者放进同一个 kernel，按这一批的成分分派到三份预先编译的版本，每份各配一组块大小（arXiv 2604.15464 §3.4、§3.5）。

它在 TPU7x 上跑 Llama 3 8B，decode 用到峰值带宽的 86%，prefill 用到峰值算力的 73%，三招拆解见专题三 §9.2。

块大小是最便宜的一档旋钮。Google 开发者博客的 Ironwood 调优实录里，KV 页从 16 个 token 调到 256 个，并发 512 时 decode 一步从 428 µs 降到 283 µs。块太小，向量单元反复停下来算地址。

5.3　布局：窄维被补成整块

TPU 的显存按 tile 存：最内层按 128 格对齐，次内层按 8 行 32 位对齐。bf16 一块是 16 行，fp8 是 32 行，每块都是 4 KiB。

KV 头只有 1–2 个时，把头数放进这两维，就被向上取整成整块。占用 ＝ ⌈次内层 ÷ 每块行数⌉ × 每块行数 × ⌈最内层 ÷ 128⌉ × 128 × 每元素字节。

B 那一列最伤：bf16 和 fp8 都占 8 KiB，换成 FP8 只是让空位变多。RPA 的解法是加一个打包维、把 K 和 V 沿头维并起来，逼编译器选最小的 tile（§3.1）。

5.4　MLA：一个阶段一套算法

专题三 §5.2 推过「吸收」：把投影并进查询，128 个头直接对着同一条 576 维的潜向量算，K/V 不展开。那里留了一句「两套怎么装进一个引擎，留到专题六」。

答案看每个阶段缺什么。decode 缺带宽，吸收让每字节做 242 次运算；prefill 缺算力，展开后每对查询和历史 token 的运算少 3.4 倍。所以引擎里两套 kernel 都留着，按阶段选。

5.5　decode 的 MoE：全算比排序便宜

decode 一批 256 个 token、每个选 8 个专家，DeepSeek-V3 的 256 个专家平均每个只分到 8 行。按专家排序、搬行、再搬回来，比这点矩阵乘还贵。

换个算法：让所有 token 都过这个专家，没选中的乘 0。只要「全算」比「读一遍权重」快，它就藏在搬运的时间里。

v7 单 device 上，一个专家读一遍权重 BF16 要 23.9 µs、FP8 要 11.95 µs，全算分别是 19.5 µs 和 9.77 µs。比值都是 256 ÷ 313，batch 涨到 313 左右两边才打平。

⚠️ 0 × NaN 还是 NaN没选中的 token 要是在这个专家里算出了 NaN 或 inf，乘以权重 0 盖不住。合并时要用选择（where）把它们清掉，不能只靠乘 0。

同一个思路也能用在搬行本身。tpu-inference#2674 在 batch 小时把排序和还原都换成「one-hot 矩阵 × 隐状态」，一次规整的矩阵乘代替按下标取行。

PR 里的实测：输入 1K、输出 8K、并发 64，总吞吐 2,211 → 2,531 token/s（+14.5%）；输入 8K、输出 1K、并发 64，+7.3%。合入的代码里这个开关默认关着，要用环境变量设阈值。

5.6　小 AllReduce 是延迟问题

batch 1 时，每层 TP 的 AllReduce 只有 hidden × 2 字节，V3 是 14 KB。按带宽算，4 张 GB200 之间只要约 24 ns。

实测平均 11.0 µs，是带宽项的约 460 倍；论文的低延迟实现做到 2.37 µs，硬件下限是 1.404 µs（arXiv 2607.16100）。小 decode 的同步要省次数，加带宽没用，第六节比 TEP 和 DEP 时会用到这条。

⭐ 这一节的四处账都指向同一件事：「少搬」要从布局开始。补齐的空位、展开的 K/V、搬来搬去的行，都是没人要的字节；先把它们去掉，再谈量化和加卡。

第 六 节

切专家与注意力：TEP 和 DEP

专家那一半大家都用 EP，分歧全在注意力：几张卡合算同一批请求，还是各算各的。 选哪个，看模型有几个 KV 头、你要多大的 batch。

6.1　一句回顾

专题五 §4.4 讲过：同一批卡，进注意力和进专家时可以用两套切法。 TEP 是注意力用 TP、专家用 EP；DEP 是注意力用数据并行、专家用 EP。

6.2　判据：KV 头数和 batch

TP 按头切注意力。KV 头只有 1 个时切不开，TP 开几路，每个请求的 KV 就存几份。DEP 各存各的，省下的地方用来多收请求。

DeepSeek-V4-Pro 不是 MLA，它的注意力是 CSA 与 HCA 交错，但每层同样只存一条所有头共享的 KV（num_key_value_heads: 1）。 所以 TP4 decode 对它是零节省，换成 dep8（TP1 ＋ 注意力 DP8 ＋ EP8）后，同样并发 512，每卡吞吐从 1,319 涨到 2,758，是 2.09 倍。

  • 口径：吞吐是 prompt 加输出的总 token（21,100 和 55,153），分母含 prefill 的卡（16 张和 20 张）。
  • 反过来：8 个 KV 头的 GQA 模型开 TEP8，每卡正好一个头，没有副本，DEP 在 KV 上就不占便宜。

6.3　DEP 的代价：每个 rank 都得自己备一份

DEP 让每个 rank 像一台小推理机：注意力权重、调度器、请求状态各有一份。状态按请求开、又不随 DP 切的东西，DEP 一宽就成倍涨。

  • K3 上 DEP8 起不来：Kimi K3 的 93 层里有 69 层 KDA（一种线性注意力），每个请求一块固定大小的状态。runbook 记录 DEP8 在 mem-frac 0.85 和 0.70 两次加载都 OOM，它的解释是每个 rank 复制了一份完整的状态池，并认为这正是官方在 K3 上改推 TP 和 DCP 的原因。
  • TP 反而切得开：同一份 runbook 引官方的话，DP、EP、DCP 都不切 KDA 状态池，能改每卡账单的只有注意力的 TP 宽度。
  • 每 rank 的 batch 会撞上实现上限：SGLang 跑 V4-Pro dep8 时，一个注意力 kernel 写死每 rank 最多 1,024 个请求。实测 batch 到 999 时吞吐已不再涨，算力先到顶，上限没真正卡住。
  • 忙闲不均：各 rank 的请求长短不一，专家那一步要等最慢的 rank；没请求的 rank 也得陪跑一遍空前向（专题五 §4.4）。

6.4　DEP 放得下了，就得有人喂

decode 卡每卡放得下的请求一多，瓶颈就挪到 prefill。dep8 不动，prefill 从 1 台加到 14 台，每块 decode 卡每秒出的字从 307 涨到 3,321，几乎一条直线。

出字间隔一直只有 5 到 15 ms，说明 decode 一直在等料。同一套机器换成 TP4 decode，瓶颈就在 decode 那边：加第 4 台 prefill，总吞吐 21,100 → 20,479，纹丝不动。

拓扑一换，瓶颈换边 「prefill 加到 3 台就够」是 TP4 decode 的结论，搬到 DEP8 上就错了。每换一次拓扑，都要重新扫一遍 P:D 配比（第九节）。

6.5　TPU 上也一样，而且要先读懂参数名

tpu-inference 的一个公开 PR，把带线性注意力的混合模型也接上了正确的 DP 注意力。 Qwen3.5-397B 在 v7x-8 上，1K 进 8K 出、并发 512 时，DP=8 比 TP=8 的输出吞吐多 62%；8K 进 1K 出时多 40%。

原因的一种解读：Qwen3.5 的全注意力层是 2 个 KV 头，8 路 TP 下同一份 KV 要在 4 个 device 上各放一份（本课推导，PR 没有单独归因）。并发 64 时两者打平：KV 放得下，复制就不要紧。

TPU 上读启动参数要多一步。tpu-inference 跑 DeepSeek-R1 的命令里写着 --tensor-parallel-size 8， 那其实是总 device 数（v7x-8 是 4 颗芯片、8 个 device）；真正的切法在 additional-config 里：TP=1、开 DP 注意力、EP=8，也就是 DEP8。

6.6　两件顺手的事

  • 名字别照字面套：TEP／DEP 是 TRT-LLM 的叫法，不等于 Megatron 的 ETP／EDP。连「prefill 用哪个、decode 用哪个」，vLLM 部署 K3 和 TRT-LLM 的例子都正好相反（专题五 §8.6）。
  • EPLB：DEP 下专家那一步要等最忙的那张卡，热门专家多复制几份就是 EPLB（专题五 §4.3）。

回到全课那句话：DEP 没让每一趟搬得更少，它让同样的显存放下更多请求，这一趟分给了更多 token。

考考自己：一个模型有 4 个 KV 头，8 张卡开 TEP8，换 DEP8 后 KV 容量最多涨几倍？什么情况下涨了也没用？

8 ÷ 4 ＝ 2 倍。prefill 喂不上、或 batch 已经大到算力先到顶时，放得下更多请求也换不来吞吐。

第 七 节

切序列：DCP 和 PCP

上下文一长，一个请求的 KV 就能占满一张卡，prompt 一长，第一个字就要等很久。 DCP 管前一件，PCP 管后一件，两者都是沿序列切。

7.1　一句回顾

专题五 §5.4 讲过：KV 头比 TP 路数少，每张卡就得存一整份； DCP 把 KV 按 token 轮流存到这几张卡上，各卡算完把自己的分母一并交出来，合并时再统一归一。

代价也在那一节：每层多付三次通信，度数最多开到 TP ÷ KV 头数。

7.2　DCP 只在长上下文赚

Kimi K3 在 GB300 上，128K 输入、8 并发，DCP8 的输出吞吐 365 对 TP8 的 108，多 237%。输入 4K 时各档并发都亏，最多亏 26%。

  • 为什么长了才赚：DCP8 把逻辑 KV 容量从 1.5M token 撑到 12.2M。KV 放不下时，TP8 只能少收请求，128K、8 并发下首字延迟中位数 32.1 s，DCP8 是 2.3 s（这两个数含排队）。
  • 为什么短了亏：短输入时 KV 本来放得下，DCP 只剩代价。runbook 发现那 −26% 正好等于关掉 symm-mem 的损失，而开 DCP 时 symm-mem 用不了。
  • 看的是总量：同是 8K，并发 8 还亏 11%，并发 32 已赚 24%。盈亏点由「输入长度 × 并发」压出的 KV 总量决定。

论文那边，Helix 把同一个想法做到 decode 的极端：注意力用 KV 并行，FFN 复用同一批卡做 TP／EP。 它报告在 Blackwell 上跑 DeepSeek-R1，同样的延迟预算下 batch 最多大 32 倍。

7.3　开 DCP 之前要知道的坑

  • 别的优化会被关掉：SGLang 里开 DCP 就不能开 symm-mem，短输入的亏损主要在这。
  • 缓存层没跟上：HiCache 的 host 层还不完全认识 DCP，L3 一律、L1＋L2 开投机时，都得退回纯 TP。
  • 状态池它不管：K3 的 69 层 KDA 状态池，DCP 一点都不切（6.3）。
配置名要回原文看 K3 官方报过两个数：1 个 PP8 prefill 喂 1 个 TP8 decode 节点，每卡 2,808 tok/s；2 个 PP8 prefill 喂 2 个 DCP8 decode 节点，每卡 2,633。 转述时很容易把高的那个记成「DCP 的成绩」，其实 DCP 组合是 2,633，分母都是 decode 卡。

7.4　PCP：超长 prompt 的首字延迟

prefill 一次要吞整段 prompt，算量随长度往上涨。PCP 在 prefill 阶段沿序列切，让几台机器合算同一个 prompt（专题五 §5.5）。

Meta 的论文用 128 张 H100（16 个节点）给 Llama3 405B 做 prefill：1M token 用 77 s，128K 用 3.8 s，并行效率 93%。 它用的是 ring attention 的两种无损做法，pass-KV 和 pass-Q：传 K、V 还是传 Q，看哪个更小。

  • Ring：各卡拿一段，K、V 沿环一站站传，边传边算。
  • Ulysses：用 AllToAll 把「按序列切」换成「按头切」，算完再换回来；度数受头数限制。
  • USP：两者叠起来用，节点内 Ulysses、节点间 Ring。

7.5　PCP 的两个正确性陷阱

PCP 出错时往往不报错，形状全对、数不对，所以先查对不对，再看快不快。

  • 少算会「更快」：某个 rank 没拿到别段的 K、V，或者干脆跳过了一截，算量少了，速度自然好看。切完之后速度好得反常，先核输出。
  • 线性注意力的状态要接力：softmax 注意力没有跨段状态，靠 pass-KV／pass-Q 拿齐就能算对。GDN、KDA 这类层带着一份随 token 更新的状态，切开后每个 rank 若从空状态起步，算出来的就全是错的。

玩具例子里最后一段差 58%，程序照常跑完。修法是把前一段的末状态传过来；这种「乘上一步再加新东西」的映射能结合，也可以各段先算好再做一次前缀合并。

7.6　落点：都在少复制 KV

DEP 把注意力的副本换成别的请求，DCP 把副本换成同一个请求更长的上下文。 两条路都是让同样的显存多放 token，这一趟就分给了更多 token。PCP 是另一件事：它买的是首字延迟。

考考自己：4K 输入、并发 8 的线上服务，要不要开 DCP8？换成 128K 的 agent 长对话呢？

4K 不开：KV 放得下，DCP 只带来多出的通信和被关掉的 symm-mem，实测亏 9%。128K 开：TP8 会因为放不下而少收请求、排长队。

第 八 节

拆工作：PD 分离与那一趟 KV

prefill 和 decode 放在同一批卡上会互相拖。PD 分离把它们拆到两批机器上，代价是每个请求多搬一趟 KV。 这一节讲那一趟怎么搬、谁来搬、搬错了是什么样子。

8.1　回顾：为什么要拆

专题五 §6.1 讲过：decode 每步只出一个字，读一遍权重只够这一批用一次，所以它拼命凑大 batch。

这时插进来一个长 prompt，它的 prefill 要整块占住算力好几步，那几步里所有人都不出字。拆开以后，decode 机器上只剩出字这一件事。

  • 拆开换来的：出字不被打断，TPOT 稳；两边还能各挑各的切法（第六节、第七节）。
  • 拆开要付的：一趟 KV 传输、两套机器、一份要调的配比（第九节）。

8.2　回顾：那一趟要多久

专题五 §6.2 算过一个 8K prompt：KV 约 1.04 GB，走 100 Gbps 的数据中心网络约 83 ms，前后两段 PCIe 各 10 ms 左右。

和 1–2 s 的 prefill 比，这一趟只占一成以内。这个结论有两个前提：网络真跑在设计带宽上；KV 本身没有大到离谱。8.4 讲第一个前提怎么被打破，8.8 讲第二个。

8.3　三层软件：谁搬、谁派、谁存

一说「KV 传输」，人们常常把三件事混在一起。先分清层，出了问题才知道去哪一层找。

  • 搬运：只管把字节从这块显存挪到那块。GPU 上是 NIXL、Mooncake Transfer Engine；TPU 上是 TPU Sync 和 JAX 自带的 transfer server。
  • 调度：决定哪个请求先去哪台 prefill、算完交给哪台 decode。tpu-inference 的代理先把请求截成只出一个字发给 prefill，再让 decode 端去拉 KV。
  • 存储：KV 不一定只在显存里。Mooncake Store、LMCache、Dynamo KVBM 把它放到主机内存、SSD 乃至远端，让下一个同前缀的请求直接取。

TPU 这边组件少得多。TPU Sync 刚开源，自己写明还不建议通用场景使用；tpu-inference 的 TPUConnector 是目前能直接用的那条路。

8.4　GPU 实战：配错一个开关，慢两个数量级

vLLM 在 GB300 上跑 DeepSeek-V4-Pro 的 PD，起初 KV 传输只有 200 MB/s。按 1.04 GB 这把尺子算，一趟要 5,201 ms，比 prefill 本身还长。

原因是 NIXL 没走 NVLink 的 cuda_ipc，退回了 cuda_copy。补上三样配置后实测 7–167 GB/s，同一份 KV 一趟 149 ms 到 6.2 ms。

那三样配置：vLLM ＋ NIXL 在 GB300 上走 NVLink
  • UCX_TLS=cuda_copy,cuda_ipc,tcp：只留 NVLink 相关通道。
  • UCX_CUDA_IPC_ENABLE_MNNVL=y：允许跨节点的 cuda_ipc。
  • --enable-cumem-allocator：显存用 cuMem 分配，cuda_ipc 才认得出来。

另外 prefill 和 decode 必须在同一个 NVLink 域（GKE 上用 subblock 标签做 podAffinity）。出处：gpu/inference/a4x-max/deepseek-v4/VLLM-V4PRO-RUNBOOK.md:106、180–194。

更麻烦的是，同一个库在两个引擎上的结论正好相反。runbook 里试过的几条路：

引擎 · 场景试了什么结果
vLLM · V4-Pro · GB300NIXL 走 NVLink cuda_ipc能用，这是唯一活路
vLLM · V4-Pro · GB300Mooncake 走 NVLink ＋ 简易代理KV 快了，整体反而慢：并发 64 输出 1,333 对 NIXL 的 1,693 tok/s
vLLM · V4-Pro · GB300Dynamo ＋ vLLM ＋ MooncakeConnector接不上：Dynamo 的 vLLM 集成没有传 Mooncake 握手地址的通路
SGLang · R1 · GB300NIXL 走 RoCEGKE 上调不通，请求 60 s 超时
SGLang · R1 ／ K3 · GB300Mooncake 走 NVLink能用，K3 的部署沿用了这条

所以别问「NIXL 和 Mooncake 哪个好」，要问「在这个引擎、这张网上，哪条路真的通」。两边的共同点只有一个：同一个 NVLink 域里，KV 就别出域。

8.5　混合模型：尾巴不能让 decode 端重算

纯注意力模型的 KV 按 token 一格一格存。老的 connector 只传填满的整块，最后那截不满一块的尾巴让 decode 端自己补算，省一点传输。

GDN、Mamba 这类层存的是一份递归状态，它已经把整段 prompt 吃进去了。decode 端再补算尾巴，等于把这几个 token 喂了两遍，输出就偏了，而且不报错。

  • 修法：全部 block 都传，状态也跟着传，decode 端一个 token 都不重算。tpu-inference 为此单独写了 HMA 版的 connector。
  • 代价：Qwen3.5-397B 在 TPU v7x 上 1K 进 1K 出，每个请求搬约 349 MB；单并发每请求吞吐是单机的 0.95 倍，4 并发是 0.92 倍。
Qwen3.5 PD 的启动要点：tpu-inference

connector 选 TPUConnectorHMA，并显式加 --no-disable-hybrid-kv-cache-manager。出处：tpu/tpu-inference/Qwen3.5-397B-A17B-FP8/README.md:375–389；吞吐表见同目录 README-TPU-VM.md:859–867（XLA 缓存已热的第二轮）。

8.6　PD 坑清单

下面每一条都来自真实部署，后面括号是出处。

  • 两边上下文长度要一致：只改 decode 的 --context-length，KV 布局对不上，握手失败；单条请求能过，压测才暴露（SGLang V4-Pro runbook:941）。
  • 失败策略两头都疼：vLLM 的 kv_load_failure_policy 设 fail，一次瞬时拒收就让引擎死掉；设 recompute 稳，但 12 个 prefill 时每卡 3,187 掉到 2,645，约交 17% 的税（vLLM V4-Pro runbook:760）。
  • 出了 NVLink 域就慢：SGLang 用 Mooncake 走 NVLink，跨域就退到 RDMA（SGLang V4-Pro runbook:63）；vLLM 的 cuda_ipc 则干脆只在域内成立（vLLM V4-Pro runbook:106）。
  • PD 碰上投机解码：刚交接过来的请求只算 1 个 token，别人是 1＋N，批次形状不齐就掉出 CUDA Graph；decode 端补齐到 1＋N 后，TPOT 约 40 ms 降到 22 ms（vLLM GLM-5.2 PD 博客）。
  • 表面报错可能是假的：14 个 prefill 时 pod 接连被驱逐，真因是 core dump 撑爆了临时盘（vLLM V4-Pro runbook §12.4）。
  • 编排层和 connector 要配套：Dynamo 的 SGLang 集成能传 Mooncake 握手地址，vLLM 集成不能（vLLM V4-Pro runbook:703）。

8.7　正确性：拆了以后先比字

PD 出错最常见的样子是「能跑、输出看着通顺、但和不拆时不一样」。所以上线前先比字，再比速度。

  • 怎么比：temperature 设 0，同一批 prompt 拆与不拆各跑一遍，逐个 token 对。
  • 前几个 token 就分叉：多半是 bug，比如尾巴被重算、递归状态没传、两边上下文长度不同。
  • 几百个 token 后才分叉：可能只是批大小不同带来的浮点差异。Thinking Machines 的文章《Defeating Nondeterminism in LLM Inference》讲过，kernel 不做批不变时，同一个 prompt 换个批就会出不同的字。

后一种要靠批不变的 kernel 才能完全消掉；前一种必须修。分辨不清时，把并发降到 1 再比一次。

8.8　跨数据中心：KV 够薄才敢走远路

专题五那个「网络不是瓶颈」只在同一个机房成立。Moonshot AI 和清华的 PrFaaS 论文把 prefill 放到另一个数据中心，前提是混合模型的 KV 薄了很多。

  • 全注意力太胖：32K 输入时，一台 8×H200 做 prefill，Qwen3-235B 每秒要外送 33.35 Gbps，MiniMax-M2.5 接近 60。
  • 混合模型能走：Qwen3.5-397B 只要 8.25，MiMo-V2-Flash 只要 4.66，几台 prefill 合起来一条专线放得下。
  • 还要挑请求：论文只把超过长度阈值的 prompt 送去远端，短的就地算；光靠 KV 薄还不够。

8.9　落点

回到主线 decode 每一步都要把权重和 KV 搬一趟。PD 分离不改变这一趟搬多少，它保证的是这一趟不被 prefill 打断，decode 才敢把 batch 攒满。 代价是每个请求多一趟 KV 传输，所以要先确认它真跑在设计带宽上、输出和不拆时一字不差。
考考自己：PD 上线后 TTFT 比不拆时还高，TPOT 倒是稳了。先查哪一层？

先查搬运层：量一次 KV 传输带宽。如果只有几百 MB/s，多半是退回了 cuda_copy 或跨出了 NVLink 域；带宽正常再看调度层有没有排队。

第 九 节

配几台、拆不拆：P:D 配比、AFD、EPD

决定拆以后，马上要回答两件事：prefill 配几台、decode 配几台；以及这个负载到底该不该拆。 两件事都要拿自己的负载去量，别照搬别人的配比。

9.1　回顾：配比从哪来

专题五 §6.3 用 DistServe 的例子讲过：两边各有一张卡能接的上限，按上限把两边配到差不多同时忙满。

那里的 2:1 来自两个上限之比。换到真实部署，要把「一张接几个」换成能量出来的吞吐。

9.2　配比公式：先算一个起点

prefill 个数 ≈ decode 每秒完成的请求数 × 输入长度 ÷ 一个 prefill 每秒能吞的 token。 左边是 decode 那头每秒要的料，右边是一台 prefill 每秒能备的料。

DeepSeek-V4-Pro，SGLang，GB300，8K 进 1K 出，每张 decode 卡 11,200 output tok/s 那个官方点；推导见 gpu/inference/a4x-max/deepseek-v4/SGLANG-V4PRO-RUNBOOK.md:1082–1091。
步骤算式结果
decode 每秒完成8 卡 × 11,200 ÷ 1,024 个输出 token约 87.5 个请求
prefill 要供的料87.5 × 8,192 个输入 token约 71.7 万 tok/s
一个 prefill（4 卡）4 × 18,200约 7.28 万 tok/s
要几个71.7 ÷ 7.28约 9.8，取 8–10 个

官方的高并发配置正好用 8 个 prefill。实测也印证了公式给的是起点：SGLang 上 prefill 从 14 加到 16，输出只从 8,809 涨到 8,993，约 2%，已经喂饱了。

9.3　多一台 prefill，换来的是首字

一份 B200 上的 DeepSeek-V3 报告，在 1P1D 上再加一台 prefill：总输出只从 1,118.8 到 1,159.0 tok/s，每张卡反倒从 69.9 掉到 48.3。

可是用户那头变化很大：平均 TTFT 少了 28%，P99 TTFT 从 12.07 s 降到 6.23 s。同一组数，按每卡吞吐看是亏，按 TTFT 的 SLO 看是赚。

  • 口径：TTFT 是客户端测的，含排队；两边都关了 CUDA Graph，所以 TPOT 偏高，没拿来比。
  • 为什么吞吐不涨：瓶颈在 decode，并发 128 时排队的请求只是开始得早了。

9.4　换个分母，结论差五倍

vLLM 跑 V4-Pro，decode 固定 8 张卡，prefill 从 1 个加到 14 个。按 decode 卡算，每卡输出从 307 涨到 3,321；把 prefill 的卡也算进分母，最多只到 455。

  • 只除 decode 卡：prefill 的成本被藏了起来，配得越多越好看。这是不少 PD 报告的默认口径。
  • 除全部卡：12 个 prefill 时到顶，第 14 个开始稀释。要算整机成本，看这条。
  • 看到每卡吞吐先问：分母里有没有 prefill 的卡（第二节）。

这条曲线是 2026-07-24 的历史实测，runbook 注明之后没有重测，只当趋势看。输入换成 4K 后，每个 prefill 能喂的 decode 约翻倍，曲线形状随输入长度变。

9.5　不拆反而更好的时候

拆开多一趟传输、多一套机器。prefill 和 decode 本来就没怎么打架时，这些代价换不回东西。

负载不拆拆怎么读
MiMo-V2-Flash，TPU v7x，16K 进 4K 出，batch 64两个 pod 各跑一份：11.70K total tok/s1P1D 10.55K；2P1D 用三个 pod 也只有 10.83K并发不高，打架不明显，拆了亏
同上，batch 12812.78K1P1D 13.64K；2P1D 15.31K并发上来，拆开开始赚

出处与口径：两组 TPU 例子

MiMo：tpu/sglang-jax/mimo/README.md:8–12、81–88，每 pod 4 颗芯片，request_rate=inf，total tok/s 含输入。README 写 1P1D 比不拆高「约 6.8%」，按表算是 6.7%。 Qwen3-Coder：tpu/tpu-inference/Qwen3-Coder-480B/README.md:1005–1021，TTFT 与 TPOT 都是中位数。两组都是单点测量，不是扫描。

9.6　决策树：三个问题

把上面几节压成三问，从上往下问；第一问答「否」，后面就不用问了。

  • 先问打不打架：看不拆时 TPOT 有没有被长 prompt 撑出尖峰。没有尖峰，先试分块 prefill（第四节）。
  • 再问 KV 走哪条线：同一个 NVLink 域或同一个 TPU 切片最省心；出了域，就要算清 KV 有多大（8.8）。
  • 最后问缺什么：TTFT 先破就加 prefill，TPOT 或吞吐先破就加 decode，或者换 decode 的切法（第六节）。

9.7　AFD：再拆一层

专题五 §6.5 讲过：decode 里的注意力和专家也能拆到两批机器上，每一层来回一趟，靠几个小批轮流跑把通信藏住。

论文里的收益很可观。字节的 MegaScale-Infer 报告每卡吞吐最多高 1.90 倍；阶跃星辰的 Step-3 在 Hopper 上、50 ms TPOT 的约束下做到每卡 4,039 tok/s，同条件的 DeepSeek-V3 是 2,324。

开源实现就没这么顺。vLLM 的 AFD 是外部插件，主仓库的 RFC 已因长期不活跃被关闭；插件博客在 Ascend 910C 上给的数，配比一错就比不拆还慢。

  • 配比是关键：16K 输入时 48 个注意力配 16 个专家，每 die 220.3，比不拆少 5.3%；注意力加到 64 个，涨到 258.9。
  • 只能看趋势：这组实验把专家路由换成强制均衡，还用小部署模拟大规模。
  • TPU 侧：我们没找到公开的 AFD 实现或实测。
出处：AFD 的几个数

MegaScale-Infer：arXiv 2504.02263。Step-3：arXiv 2507.19427（4K 上下文、FP8、不开 MTP）。vLLM AFD 插件：vllm.ai/blog/2026-07-23-vllm-afd-plugin、github.com/vllm-project/afd-plugin；RFC #22799 于 2026-05-31 被机器人关闭。

9.8　EPD：多模态把编码也拆出去

多模态模型在 prefill 之前还有一步：把图片、视频编码成 token。图一多，这一步就和 prefill 抢显存、抢算力。

  • 做法：编码器单独一批机器，算完把视觉 token 交给 prefill，prefill 再把 KV 交给 decode。
  • 论文的数：arXiv 2501.05460 报告峰值显存最多降 15 倍，batch 最多大 22 倍，TTFT 最多降 71%。
  • 什么时候值得：每个请求带很多图、或者图很大时。纯文本服务用不上（专题五 §6.6）。

9.9　落点

回到主线 decode 每一步都要把权重和 KV 搬一趟。拆开是为了让这一趟不再等 prefill，两边的切法也能各选各的；AFD 让专家那头一趟分给更多机器的 token。 拆不拆、怎么配，看负载，不看潮流。
考考自己：一份报告说「加到 12 个 prefill，每卡吞吐涨了 10 倍」。你先问什么？

先问分母：每卡是除 decode 卡还是全部卡。V4-Pro 那组数，同样的 12 个 prefill，按 decode 卡算涨 10 倍多，按全部卡算只涨 2.2 倍。

第 十 节

先选拓扑，再调参数

换一次拓扑，抵得上把参数调遍。decode 每一步搬一趟权重和 KV，拓扑定了这一趟走哪条线、能分给多少个请求；参数只在这个上限底下挪动。

10.1　回顾：线有快慢，切法先定

专题五 §7.1 讲过：通信勤的切法要放在快线里，懒的才能跨慢线。 §7.3 又用 V4-Pro 的一组实测说明，按每卡比，换切法比调参数赢得多。

同一组数还能再拆一层：总量里有多少是加卡换来的，多少是调参换来的。

10.2　「+45% 对 +347%」：先看分母

原始记录的结论是：参数调遍只从 14,563 挪到 21,100（+45%），换 dep8 一步到 65,132（+347%）。两个都是总吞吐（prompt 加输出 token），但三档用的卡数是 8、16、20。

拆开看，+45% 里大半是加卡：prefill 从 1 台加到 3 台，卡数翻倍，每卡反而从 1,820 掉到 1,319。同样是 3p1d，只把并发从 256 调到 512，总吞吐 +28%，这才是纯调参的那一份。

换拓扑在两种口径下都赢：每卡 3,257，是 3p1d 最好成绩的 2.47 倍、1p1d 起点的 1.79 倍。原因第六节讲过：V4-Pro 只有一个 KV 头，TP4 把每份 KV 复制 4 份，DEP 把副本的位置让给了别的请求。

口径报一个「提升百分比」时，同时写清分母：总量还是每卡、卡数变没变、并发是多少。缺一样，读的人就可能把加卡的收益当成调参的收益。

10.3　拓扑约束是硬的

同一个模型、同样 16 个 device 跑 TP16，线换了，结果差出一截。Qwen3-Coder-480B 两台 v7x-8 走数据中心网络（DCN），比单机 TP8 慢 17–63%；两台编进同一个 ICI 切片，只慢 15–21%。

张量并行在每层都要把各卡的部分和加起来，这一步放到慢线上，每生成一步就多等一次。原记录的建议是开两份单机做 DP，让 TP 留在快线里。

GPU 上是同一条规矩。V4-Pro 的 SGLang 部署要求 16 个节点都在同一个 NVL72 域：PD 之间传 KV 走 NVLink，跨域就退化成 RDMA，原文只说「显著变慢」，没给倍数。

10.4　TPU 上，device 编号就是拓扑

JAX 的 mesh 是一张 device 列表排成的网格。列表里谁挨着谁，集合通信就把谁当邻居。

顺序排错，环形 all-reduce 的「下一个」可能在物理上隔着两三跳，数据绕远路，还和别人抢同一条线。更糟的是各进程算出的顺序不一致：每个进程都在等一个不会先发的对端，第一次集合通信就卡住，不报错。

所以 mesh 交给 mesh_utils.create_device_mesh 按物理位置生成，跨切片用 create_hybrid_device_mesh 把 ICI 和 DCN 分成两层。还有一处常数错：TPU v7 一颗芯片是 2 个 device，切片名按 device 数，v7x-8 是 4 颗芯片。

10.5　最小切片怎么定

一个引擎最少要几颗芯片，先算纸面账：权重 ＋ KV ＋ 激活余量。拿 DeepSeek-V3 在 TPU v7 上算（本课推导）：FP8 权重 671 GB，每 token 的 KV 70,272 字节，每颗芯片可用约 189.5 GB，留一成给激活后按 170.55 GB 算。

上下文 × 并发权重 ＋ KV纸面芯片数取切片
4K × 64689 GB4.048 颗（v7x-16）
32K × 2561,260 GB7.398 颗
128K × 2563,029 GB17.7632 颗（v7x-64）

上下文短时，权重就是下限，表里前五格都是 8 颗。到 128K、256 并发，KV 涨到权重的 3.5 倍，需要 32 颗。这时与其加芯片，不如考虑第七节的 DCP，把一个长请求的 KV 摊到多个 device 上。

4 颗芯片放完权重只剩约 11 GB 给 KV，纸面上能放 38 个 4K 请求。实际更紧：公开记录里 FP8 的 MoE 每个 device 要 101.8 GB，比可用的 94.75 GB 还多，所以 v7x-8 上实际用的是 FP4。

本课推导的边界纸面账只给下限。激活预留 10% 是假设；KV 按不重复算（DP 注意力或 EP），没算 DP 注意力在每个 device 上各放一份非专家权重的开销。定下限之后，用一次真实启动看实测的 HBM 峰值。

10.6　容量别拿小并发估

R1 在 GB300 上的部署记录里有一句估算：这套 DEP8 decode 理论上能扛约 288 个并发。拿 conc=8 的数去汇报，只用到它的约 3%。

conc=8 时，decode 每搬一趟只分给 8 个请求，测到的是「机器闲着时多快」。往上扫，总吞吐从 854 涨到峰值 10,715，是 12.5 倍；过了 256 只再涨 3%，首字延迟却多等了一倍半。

该停在哪一档，由延迟目标决定。容量规划时先扫出这条曲线，再按 SLA 在曲线上取点。

10.7　对照实验的纪律

  • 先固定拓扑，再扫参数。拓扑一变瓶颈就换边：TP4 decode 时加 prefill 不涨，换成 dep8 后又成了 prefill 受限（第六节）。在错的拓扑上调出的最优参数，搬不到对的拓扑上。
  • 一次只动一个变量。同时改并发和 prefill 台数，涨了也说不清是谁的功劳。
  • 记全口径。卡数、并发、输入输出长度、吞吐算不算 prompt，每一行都写上（第二节）。
  • 压测固定 temperature=0。压测工具没发这个参数时，投机解码的接受率塌掉，V4-Pro 那套服务因此差了 3.1 倍（第十一节）。

10.8　五步选法落到两个例子

专题五 §7.4 的五关（装得下、快线多大、序列、PP、DP），推理时照样走一遍。

② 快线多大一个 ICI 切片；TP 跨 DCN 会慢 17–63%一个 NVL72 域 72 卡；dep8 跨两个节点走 NVLink，SGLang 部署要求全部节点同域

⭐ 拓扑定了那一趟搬运走哪条线、能分给多少人，参数只在这个上限底下挪动。先选拓扑，再调参数；比较时先看分母。

第 十一 节

投机解码：搬一趟，出好几个字

decode 一步把权重搬一趟，只换来一个字。 投机解码先便宜地猜几个字，再让大模型搬一趟、一次验完，猜对几个就出几个。

11.1　先猜后验

草稿可以来自小模型、挂在大模型上的预测头，或者干脆从 prompt 里抄。 大模型把草稿当成一段输入，一步算出每个位置自己想出的字，和草稿逐个对。

收下第 i 个草稿的概率是 min(1, p/q)，p 是大模型给的概率、q 是草稿给的。 被拒时从 p 减 q 剩下的那部分里重抽一个，整体输出分布和大模型自己一个个生成完全一样（Leviathan 等 2022；Chen 等 2023）。

所以投机解码是无损的：它改的是速度，不改答案的分布。 温度为 0 时这条规则退化成「草稿和大模型的贪心选择一致才收下」。

11.2　收益账：接受长度 ÷ 一步变慢了多少

每步平均出几个字叫接受长度。加速比约等于接受长度除以一步变慢的倍数。 小 batch 时一步的时间主要花在读权重上，多验证几个 token 本该几乎不加时间。

稠密部分确实如此：注意力和共享权重验证几个都只读一遍。 MoE 不白送，每个 token 挑自己的专家，按 V3 的结构粗算，验证 8 个要读的字节是验证 1 个的 4.4 倍（本课推导，均匀路由，偏高）。

Kimi K3 在 GB300 上实测，开投机后每字间隔从 11.1 ms 降到 2.31 ms。 每步接受 6.96 个，一步其实慢了 1.45 倍，净赚 4.81 倍（本课推导：2.31 × 6.96 ≈ 16.1 ms）。

11.3　收益会缩：并发、上下文、EP

并发一高，计算单元先忙满，草稿里的每个 token 都得真算一遍。 K3 输出吞吐的加速比从并发 1 的 4.22× 降到并发 64 的 1.74×。

上下文变长也会缩。同样并发 1，K3 的 prompt 从 4K 拉到 32K，加速比从 4.22× 掉到 1.32×；注意力读 KV 的时间变长了，草稿省下的那部分占比就小了。

EP+DP 本来就是给大 batch 配的。B200 上 DeepSeek-V4-Flash 用 vLLM、EP+DP8 开 MTP，十档并发全部变慢，从 −3% 到 −37%。

峰值和端到端也可能方向相反。GB300 上 V4-Pro 把 MTP 从 1 步加到 2 步，decode 峰值掉 13%，端到端反而涨 28%：真实负载下 batch 多数时间不在顶点，那里还是读权重的便车在起作用。

11.4　温度：压测怎么发，结果就怎么变

草稿怎么抽样，要和请求的温度对上。贪心草稿遇上温度 1.0 的随机采样，几乎每个都会被拒。

GB300 上 V4-Pro 的 DSpark 草稿是贪心的，服务端默认温度 1.0。 压测工具不发温度，接受率只有 1.16%、输出 944 tok/s；发温度 0 是 34%、2,911 tok/s，差 3.1 倍。

K3 的草稿按概率抽，官方就用温度 1.0 压测，接受长度在代码类任务约 4.73、创作类约 2.61。

接受率掉了不会报错 它只让 TPOT 慢慢变差。线上要把接受率和接受长度当一级指标告警；跨框架比投机解码，先对齐两边发不发 temperature。

11.5　草稿从哪来

谱系一条主线是草稿越来越贴近大模型：独立小模型、草稿树（SpecInfer）、预测头（Medusa）、读隐状态（EAGLE）、训进模型的 MTP（DeepSeek-V3），到 2026 年的 DSpark。

另一支不要模型。Prompt Lookup 从 prompt 里抄，SuffixDecoding 查历史输出，在重复率高的场景命中最多，比如改代码、长文摘要、agent 循环调用工具。 扩散草稿（DiffuSpec、DFlash）一次并行出一整块，是最新的一支。

11.6　接进系统的代价

草稿要占显存。K3 开 DSpark 后 KV 池从 787,504 个 token 缩到 637,504 个，少了 19%。

引擎的默认值也会跟着变。K3 的 SGLang 配方里，开投机又没写 max-running-requests 时，它会被重设成 48；batch 上限被悄悄压低，吞吐测出来就不对。

线性注意力要能回滚。KDA 这类层把历史压成一个状态，草稿被拒就得退回去；K3 的做法是只存草稿窗口的原始输入、拒了就重放，窗口占用从 512 KB 降到约 16 KB。

EP 的通信缓冲按 token 数开。SGLang 跑 V4-Pro 时要满足 max-running-requests × 草稿数 ≤ DeepEP 每个 rank 的派发上限，否则开不起来。

还有 kernel 和编译。验证一步是「一个请求带好几个 token」的新形状，prefill、decode、验证三套注意力后端要一起选对；PD 分离下混合 batch 还会掉出整图 CUDA Graph。

回到主线 投机解码让搬一趟权重换来好几个字。batch 小、读权重占大头时赚得最多；batch 一大、算力吃满，它就从白送变成纯开销。
第 十二 节

少搬字节：量化与 kernel 融合

上一节让搬一趟出更多字，这一节让每一趟少搬一点。 量化让每个权重占更少的字节，kernel 融合让读权重的流水线不在 kernel 边界上停。

12.1　位数减半，下限减半

batch 小时，一步的时间几乎全花在读权重上。 DeepSeek-V3 每个 token 激活 37B 参数，放在 8 颗 TPU v7 上，BF16 一步至少 1.26 ms，FP8 0.63 ms，FP4 约 0.33 ms（本课推导，只算权重）。

省下的显存可以多放 KV、多接请求，等于顺带走了第四节分摊的那条路。

训练后再量化的三种常见做法：GPTQ 逐层用二阶信息补偿舍入误差；AWQ 按激活大小找出要紧的权重通道，先放大再量化；SmoothQuant 把激活里的离群值挪一部分到权重上，让两边都好量化。

12.2　同叫 4 bit，差在缩放

4 bit 只有 16 个值，必须几个数共用一个缩放。MXFP4 每 32 个数共用一个 8 bit 指数，平均 4.25 bit；NVFP4 每 16 个数共用一个 FP8 缩放，平均 4.5 bit。

块越小越贴合局部数值，精度越好，字节也越多。格式的细节见专题八 §2。

12.3　低精度直接训出来

发布时就是低精度，正在变成默认做法。 Kimi K2 Thinking 在后训练阶段做量化感知训练（QAT），MoE 部分原生 INT4 权重，模型卡称生成速度约提升 2 倍。

DeepSeek-V4 的模型卡写明，MoE 专家参数用 FP4，其余大部分用 FP8。 专家占了参数的绝大部分，也是 decode 时读得最多的那部分。

QAT 让模型在训练时就适应舍入误差，比训完再压精度更稳；部署方拿到的就是最终格式，不用自己再量化一遍。

12.4　FP4 先是被容量逼的

DeepSeek-R1 放到 TPU v7x-8 上，专家权重用 FP8 时每个 device 要约 101.8，超过约 94.75 的上限。 转成 FP4 后专家约 60.9，连同注意力约 70，才放得下。

读法也得对上。对称 INT4 的值是 −8 到 7，文件里整体加 8 存成 0 到 15；加载时忘了减 8，每个权重都偏大 8，模型输出崩成重复的乱词。

格式还要和硬件对上。要是矩阵单元没有 FP4 通路，权重得先在片上解成高精度才能乘；字节省下了，转换的功夫却加上了，净收益只能实测。

KV 也能存 FP8，但要先看布局：窄维被补成整块时，FP8 只是让空位变多（§5.3）。

12.5　kernel 融合：边界上不再干等

一次前向要发上百个 kernel。每个 kernel 收尾、下一个开场时，没人在读权重。

Hazy Research 算过：Llama-3.2-1B 在 H100 上光读权重的上限是每秒约 1,350 次前向；每层 7 个 kernel、16 层、每个边界空等约 5 µs，就只剩约 770 次。

CUDA Graph 只省掉 CPU 发射那一侧的开销，GPU 上 kernel 交接时的空当还在。 megakernel 把整次前向写成一个 kernel，下一段的权重在上一段计算时就开始读。

Hazy 的实测里，vLLM、SGLang 最多用到 H100 带宽的 50%，megakernel 到 78%，比 vLLM 快约 2.5 倍。 Mirage MPK 让编译器自动把模型变成一个 megakernel，论文报的端到端延迟最多降 1.7 倍。

TPU 这边，Inferact 用 Pallas 写了 megakernel。16 颗 TPU v7 跑 Kimi K3，单用户超过每秒 700 token；对照的 16 张 GB200 是 452。 它一步约 8.5 ms、每步接受约 6 个，下一层的权重提前搬进片上内存；整套从零编译用时不到 90 秒（Inferact 博客）。

回到主线 量化和融合都是少搬：一个让每个权重更小，一个让读权重的流水线不断。它们和投机解码叠在一起用，Inferact 那个数就是三招同时起作用的结果。
第 十三 节

落地：TPU 服务化与编排

kernel 调好了，服务还可能第一分钟就卡住。TPU 上推理服务的大部分活，在形状、编译和冷启动里。

13.1　静态形状：服务侧怎么选桶

专题二「谁做决定：运行时，还是编译期」讲过：XLA 按形状编译，变长的请求只能分桶加补零。服务侧要定的是桶怎么切、哪些桶在开服前编好。

桶分得越细，补零越少，编译次数越多。示意分布下，只有一个 8K 桶时算的 token 里 87.3% 是补的零；每 256 一档用 32 个桶，降到 10.8%。

切法比桶数要紧。请求长度大致是对数形状，按 √2 倍一档的 13 个桶，比每 512 一档的 16 个桶还省。

没编过的桶，第一个撞上它的请求就得等编译。Qwen3.5-397B 在 TPU 上，新形状的首个请求要等 60–90 s，之后同形状不到 1 s。

所以桶要写进启动参数预编译。SGLang-JAX 的写法是 --precompile-bs-paddings 1 4 8 16 32 64 128 256 加 --precompile-token-paddings 4096：batch 档和 token 档两维相乘，就是开服前要编的份数。

13.2　编译缓存为什么会失效

编好的程序可以落盘，下次启动直接读：设 JAX_COMPILATION_CACHE_DIR 就行。但缓存命中的条件很苛刻。

  • 键太多。缓存键里有程序本身、库版本、编译参数，还有切片的形状。升一次镜像、改一个参数、换个切片形状，全部重编。
  • 放错了地方。公开记录里把缓存目录设在 /dev/shm，那是内存盘，机器一重启就没了。多机时只有 0 号进程写缓存，目录得放在共享存储上。
  • 有些缓存根本不落盘。R1 的记录里，权重搬上 device 用的传输程序只缓存在进程内存里。同一进程重载 1:48，换个新进程就退回 3:17–3:51。

拆开冷启动的账，编译常常是最大的一块，有时还藏在别的名字底下。

GLM-5.1 未优化时，「加载非 MoE 权重」用了 6 分 29 秒，其实是每加载一个 tensor 就清一次编译缓存，下一个 tensor 又从头编。R1 上同一个问题：1,367 个 tensor 只有 25 种形状，去掉清缓存那一行，这段从 215.7 s 降到 21.4 s。

Qwen3-Coder 两机首次启动约 40 分钟，29 分钟在编译；MiMo-V2.5-Pro 约 50 分钟，编译和预编译占了 22 分钟。拆账的判据很简单：这段时间在搬字节，还是在等编译器。

13.3　权重加载：别让几十个引擎抢一根管子

几百 GB 的权重，从哪读决定了要等多久。Kimi K2.6 把 MoE 权重缓存放在本机内存盘，冷启动 6 分 8 秒；没有缓存时要 57 分钟。放在共享文件系统上，每层读取比内存盘慢 38 倍。

扩容时几十个引擎一起起，共享存储的总带宽被它们平分，每个引擎都变慢（本课推导）。GPU 这边 V4-Pro 的做法一样：806 GB 权重放本地 SSD RAID，读 14 GB/s，加载不到 1 分钟。

一条经验冷启动先拆账：搬字节那段用本地缓存省，编译那段用持久化缓存省。两样都省不掉时，就提前起好备用副本。

13.4　运维的三个坑

  • 「起来了」不等于「活着」。Qwen3.5 的记录里有 EngineCore 静默崩溃；V4-Pro 的 SGLang 部署里 14 台 prefill 全崩了，服务注册表还显示 14 台在线，要等租约过期才消失。判活要看显存、真发一个请求，别只看进程和注册表。
  • SLICE_FAILURE 不要反复重试。这是切片的硬件故障，每次重启都在同一处崩；公开的训练记录里，重试次数一用完，作业判失败，节点池被自动缩到 0，卡直接没了。记录里把重试上限设成 3。
  • 别一卡一个 pkill -9。GB300 上强杀一个满载的 decode，经 MNNVL 每卡漏掉约 97 GB 显存：284 GB 只剩 187 GB，而参数要 241 GB，下次启动必然 OOM。报错还劝你「调大 mem-fraction」，方向正好相反。删 pod 重建，56 秒显存归零。

13.6　编排：把「少算」落到集群层

前缀缓存只在一个副本里有效。路由不知道哪个副本存着哪段前缀，命中率就随副本数摊薄。

KV 感知路由把同前缀的请求送到已经存着它的副本。Red Hat 用 llm-d 实测：命中缓存时首字延迟 340 ms，对照的最坏情况 2,850 ms，命中率 87.4%。

llm-d、NVIDIA Dynamo、Kubernetes 的 Gateway API Inference Extension、GKE Inference Gateway 都在做这件事。它们还有一项共同的活：把坏副本摘掉。

路由层必须做健康检查。8 个副本坏 1 个而路由照常轮询，1/8 的请求就送进一个不会回话的引擎白等（本课推导示意）。

  • SLA 与 goodput。吞吐只数 token；goodput 只数同时满足首字延迟和出字间隔目标的请求（DistServe 提出）。容量按 goodput 规划，第十节那条并发曲线上取的点才有意义。
  • 容量规划。decode 卡数 ＝ 目标用户数 ÷ 每卡用户数。按 V4-Pro 官方 recipe 那一点，每卡每秒出 11,200 个字、每个用户要 50 字/秒，一张卡约服务 224 人。这个分母只算 decode 卡，把 prefill 的成本藏起来了。
  • 成本趋势。Epoch AI 统计：要达到同一能力，每 token 的价格每年降 9 到 900 倍，中位数约 50 倍。今天的成本账，一年后要重算。
  • 多租户 LoRA。S-LoRA 和 Punica 让一份底座权重同时服务成百上千个 LoRA 适配器，那一趟底座搬运分给了所有租户的请求。

⭐ TPU 上推理服务的大部分活不在 kernel 里，在形状、编译和冷启动。路由是把「少算」搬到集群层：前缀只算一次，后面的请求都来复用。

第 十四 节

第一天的八问

接手一个推理服务，第一天先问八件事。前四问是纸上的账，后四问才是开关。

14.1　前四问：算账

  • 负载和尺子先定：同一组机器，换个交互档位或换个分母，结论能反过来（第二节）。
  • 字节下限告诉你离天花板还有多远：实测步时如果是下限的好几倍，先查布局和调度，别急着加卡（第一、五节）。
  • batch 上限由 KV 决定：它定了那一趟搬运最多能分给多少人（第三节）。

14.2　后四问：挑招数

  • 先切法后参数：TEP 换 DEP、加不加 DCP、拆不拆 PD，都是拓扑级的选择，比调并发、调块大小影响大一个量级（第十节）。
  • 投机和量化是「少搬」：投机在并发小时最赚，量化不管并发都减字节（第十一、十二节）。
  • 最后一问最容易被跳过：编译和冷启动没准备好，第一个用户就会等上一分钟（第十三节）。
