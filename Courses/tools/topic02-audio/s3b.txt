[focus] 上一段我们拆了整颗芯片、一个核，还有核里那块地。这一段往上走一层，看编程模型，也就是你写代码时面对的那几层。在这之前，先插一对词，因为后面说一个线程其实是什么，还有那个八乘一百二十八，都得用 TPU 那边的坐标词，而这两个词的字面会骗人。

[casually] 请看这张寄存器形状图，两步就能把画面立起来。第一步，只看一条：一个 sublane 就是横着的一整条，一百二十八格那么长，五百一十二个字节。第二步，把八条叠起来，就是一个向量寄存器，八乘一百二十八，一共一千零二十四格，四个 KiB。所以 lane 量的是长度，第几格，零到一百二十七；sublane 量的是第几条，零到七。对齐八乘一百二十八，用大白话说，就是竖着凑够八条，横着凑够一百二十八格。

[amused] 名字骗人的地方在这里：sublane 不是 lane 的一小段，它是横跨全部一百二十八条 lane 的一整条。sub 说的是第二维，不是更小。几乎所有人第一次都会理解反，包括我。记法只有一句：最内维是 lane，次内维是 sublane。

[thinking] 这张图真正要留下的是：XLA 故意把数组在内存里的布局，做成跟寄存器一样的形状。搬进来就能直接算，一次重排都不用。一段一百二十八个元素正好铺满一百二十八条 lane，这是要的效果。真正的代价是另一样：这个形状被钉死了。换最内维要真的搬数据，转置和一些 reshape 不是改一下步长，是物理搬运；形状不整除就补零，补出来的零占 VMEM、过 MXU，还算进 FLOP；跟外部交接，还要重排一次。

[seriously] 跟 GPU 对照一下。GPU 的合并访存也想要连续，但那是软约束，没对齐照样跑，只是慢。TPU 的分块是硬约束，形状不对，要么补零，要么插一次重排。一边是罚款，一边是直接不让过。

[focus] 好，刚才少掉的是硅片上的部件。往上一层，编程模型里也会少掉东西。同一个原因，第二次露面。这一节，我先把所有东西归到一个问题上。

[seriously] 你写 GPU 代码的时候，不知道这堆活会落在哪个 SM 上，也不知道什么时候落。那是硬件在运行的时候才决定的。四个字：运行时才定。

[curiosity] 既然不知道，你就没法点名，写不出让三号 SM 干这个。那你还能对硬件说什么？你能做的只剩一件事：描述关系。哪些活必须待在一块儿，哪些落哪儿都行。

[casually] 必须待在一块儿的那一批，就是一个 block。为什么是必须？因为这批活之间要互相传中间结果，而中间结果放在 SM 自己身上那块小内存里。所以一批活一旦落到某个 SM 上，就不许再搬走，搬走了，中间结果就找不着了。反过来，互相不用说话的活，落哪儿都行，全部加起来，叫 grid。这两层是你说了算的。你写代码，其实就是在说两句话：这些必须在一起，总共这么多。

[casually] 硬件那边还有它自己的分组，理由完全不一样，是为了省电路。取一条指令很贵，那就让三十二份数据共用同一条指令，一起算。这三十二个绑成一捆，就是 warp。这个数你改不了，是硬件焊死的。到这儿四层齐了。

[thinking] 剩下两层是后来补的，各被一个很具体的麻烦逼出来。warp group，是因为新一代的矩阵指令太大，一个 warp 的寄存器喂不饱，要四捆一起发才凑得出形状。cluster，是因为相邻几个 SM 想直接够到对方那块小内存，不想绕远路。绕远路是绕哪儿？就是绕那个只比显存快两点六倍的 L2。上一段那个反直觉的数，在这儿变成了一整层编程模型。

[realization] 请看这张表，每一层被什么逼出来。这六层，全是从刚才那句不知道长出来的。正因为运行时才决定，你才需要一整套语言，来描述谁跟谁必须在一起，谁能看见谁。

[contemplative] 而 TPU 那边，编译的时候就已经把一切定死了，不存在不知道。所以这一整套语言，它一层都不需要。注意，两边的层根本不在回答同一个问题，所以这张对照表是按问题排的，不按名词排。

[curiosity] 请看这张按问题对齐的表，要看的是空格。空的第一格：没有一组线程。GPU 有 thread block，有几个、落在哪个 SM，启动时才知道；TPU 没有这个中间概念，VMEM 属于整个核，谁能看见什么，编译期就定死了。空的第二格：没有换一个跑。GPU 一个 SM 有四个 warp 调度器、六十四个 warp 槽；TPU 一个都没有。空的这两行，正好是上一段少掉的那五样，在编程模型上的投影。硅片上少了部件，代码里就少了概念。

[suggestion] 顺带说一句：一个 SM 上同时住着好几个 block，它们挨着，但互相看不见对方那块小内存。第五节讲的占用率，量的就是这个 SM 还能塞下几批。

[focus] 再往里拆一层，一个 SM 到这儿为止一直是个黑盒。请看这张四格图：它不是一整块，是四个格子，每个格子自己一套调度器和寄存器。三十二，是一个格子的宽度；一百二十八，是四个格子各出一捆。

[thinking] 这里有个问题值得单独说：一个线程到底独占什么？算的部件，它一样都不占。CUDA core 也好，Tensor Core 也好，都不是分给谁的，它们是流水线上的一个位置，哪一捆这一拍发了指令，就用这一拍，下一拍换别人。它真正独占的只有寄存器。一批活落到 SM 上就把寄存器划走，跑完才还，中途从不搬动。

[realization] 这一条同时解释了两件事。正因为寄存器不搬动，换一捆上来才是零成本的，上一捆的东西原地放着就行。也正因为独占，先卡住你的，一定是寄存器不够，不是算的部件不够。这就是那两百五十六 KiB 寄存器堆的来历，它是运行时适应这张账单上最贵的一项。

[thinking] 能住多少人，由三道闸门里最紧的那道说了算，这就是占用率量的东西。最常先卡住的是寄存器：一个 SM 六万五千五百三十六个寄存器，要住满两千零四十八个线程，每个线程只能用三十二个；用到六十四个，就只住得下一半。所以循环展开、把中间结果留在寄存器里，都在削减能待命的人数。第二道是共享内存，你的 block 要一百 KiB，这个 SM 就只住得下两个 block，寄存器剩多少都没用。第三道是槽位本身，最多六十四个 warp、三十二个 block。

[casually] 最后回到最底下那一格。一捆是三十二个线程，每个线程在这一捆里有个编号，零到三十一，那个位置，就是一条 lane。所以 GPU 上也有 lane，硬件上就是一条 SIMD 通道，跟 TPU 那边的 lane 是同一样东西。

[warmly] 差别只在一件事：GPU 的 lane 有名字，TPU 的没有。GPU 那条，你能对它单独写 if、写循环；TPU 那条，你写不出第三十七号 lane 单独干点别的，哪个元素落在哪条 lane 上，是编译器的事。所以 CUDA 说的线程，是一条有名字的 SIMD lane。

[curiosity] 这句话还太抽象，拿一次矩阵乘落地。先得打掉一个画面，很多人脑子里都是它：一个线程负责输出矩阵里的一格。这个画面在没有 Tensor Core 的年代是对的。那时候一个线程就是一格的主人，它自己跑那个 K 循环，从共享内存读 A 的一段、B 的一段进自己的寄存器，乘加，累加在自己手上，最后写回。搬运和计算，它都干。

[seriously] 用上 Tensor Core 之后，这个画面作废了。矩阵乘指令是整个 warp 一起发的一条指令，它的操作数散在三十二个线程的寄存器里，每人拿一小撮。拿一条典型的指令说，每个线程交出 A 的八个数、B 的四个数、累加器的四个数，就这些。单个线程，自己算不出任何一个完整的输出元素。

[realization] 所以一个线程负责哪一格，这个问题到 Tensor Core 上就失去意义了。线程退化成两样东西：一份寄存器的持有者，和发那条指令的三十二分之一。

[thinking] 那它到底是不是 SIMD？两个层面，答案相反。硬件上是：一个 warp 的三十二条 lane 共享取指、译码、发射，同一拍执行同一条指令。编程模型上不是：你写的是标量代码，而且从 Volta 起，每个线程真有自己的程序计数器，可以各走各的分支。所以 SIMT 这个词的意思就是：用标量的写法，跑在 SIMD 的硬件上。代价写在分支上，真发散了，各条分支只能轮流走，看着能各走各的，实际是排队。

[contemplative] 而这一整套，让你写标量、硬件替你凑成 SIMD、发散了替你排队、再替你在几十批活之间来回换，就是靠运行时适应要付的钱。TPU 不做这个决定，所以它那边连线程这个词都没有。

[focus] 那这笔钱，落到硬件上是哪几样？三套电路，各回答一个很窄的问题。第一，谁现在能发指令。第二，谁跟谁怎么对齐。第三，数据怎么在不占用线程的前提下就位。

[casually] 第一样是记分板。一句话：记分板就是一张表，记着每条指令要的操作数到齐了没有，调度器每一拍扫一遍，谁齐了让谁发射。具体到 NVIDIA，它先按一条线把指令劈成两半：编译器知不知道它要跑多久。知道的那一半，编译器直接在指令里写停几拍，硬件照做。不知道的那一半，访存、特殊函数、矩阵指令，才交给记分板：每个 warp 六个小计数器，发出去加一，写回来减一。所以它只回答一个问题：这个 warp 现在能不能发指令。TPU 那边，这张表整个不存在。

[casually] 第二样是 SM 里的一小组硬件 barrier：warp 陆续到达，硬件数人头，数满全放行。最实用的一条是，等在 barrier 上的 warp 不腾位子，所以同步密集的 kernel，占用率不会因为大家都在等而变好看。

[thinking] 第三样值一张图，请看这张四行的数据通路图，只看中间那一列。两头都一样，左边是全局内存，右边是共享内存加计算单元。最早，数据得在寄存器里过一道，地址和循环全靠线程自己算，搬的时候线程被占住。Ampere 起，cp async 把寄存器那一道砍掉了，地址还是自己算。到 Hopper 的 TMA，一个线程填一张描述符发出去就走，地址生成整个交给硬件，另外三十一个线程完全不参与。三代下来，线程从搬运工加计算工，被剥成了一个寄存器的容器。顺带一句，生产者一换人，对齐的办法也得跟着换：那台引擎不是线程，它不会到达，只会报告往里放了多少字节，所以 Hopper 的 barrier 多了一项本事，连字节数一起数，人到齐并且字节够了，才放行。

[realization] 走到这一步，它和 TPU 那条编译器发的 DMA，已经是同一类东西了。剩下的分歧只有一个：这条 DMA 是运行时某个线程发的，还是编译期就排好的一步。收敛的是怎么搬，谁决定，一步没动。

[warmly] 所以，记分板管谁能发指令，barrier 管谁跟谁对齐，TMA 管数据怎么不占用线程就位。三套加起来，就是跑起来才决定这笔账的明细。TPU 一样都不需要，不是它简陋，是这三个问题，它在编译期就全答完了。

[friendly] 这一节就到这里，大家有问题吗？
