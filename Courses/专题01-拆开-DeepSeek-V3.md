# 专题一 · 拆开 DeepSeek V3

> **一个 token 走完全程，每走一步就把账算一遍。**

> 🚧 **只有大纲，未展开。** 2026-08-21 重写。

---

## 为什么是 DeepSeek V3

早就不是 GPT-3 175B 那个时代了。**V3 是当下事实上的黄金标准** ——
后来的开源模型基本都从它出发再改。要讲清楚"现在的大模型长什么样"，
拆它一个，比泛泛讲十个有用。

而且它一次把三件互相牵制的事做成了：**MLA 把 KV cache 压下去、
细粒度 MoE 把激活参数压下去、FP8 把训练成本压下去**。
每一件都直接对应硬件上的一个瓶颈 —— 这正是这门课要建立的那条因果链。

**这个专题的目的**：让一个 token 走完全程，
**每走一步就把账算一遍** —— 这一步产生多大的矩阵、吃多少显存、要多少算力。

走完之后，"为什么这个模型需要一个机房"就不是一句口号，而是一串算出来的数。

## 统一的算账口径

后面每一站都按这一套口径算，**中途不换**：

| | |
|---|---|
| 序列长度 | **128K = 131,072 token** |
| batch | **1**（先把单条算清楚，要乘再乘） |
| 精度 | 权重与激活都按 **bf16（2 字节）** |
| 方向 | **只算前向**。反向与优化器状态留到后面的课 |
| 参照物 | **TPU v7 单 device 可用 HBM ≈ 94.74 GB** |

> 为什么先只算前向：前向的账是**事实**，一步一步能推出来。
> 反向要牵进 recompute 怎么选、优化器状态放哪、梯度要不要累积 ——
> 那些是**决策**不是事实，混进来会把主线搅浑。

## 路线：跟着一个 token 走完全程

```
文字 → token → embedding → ┌ MLA ┐→┌ MLP(前3层) / MoE(后58层) ┐→ …×61 → norm → lm_head → 概率
                            └──── 残差流一路贯穿 ──────────────┘
```

**每一站问同样的四个问题：**

1. 这一站的**权重**有多大？
2. 它产生的**激活**有多大？
3. 它要做多少 **FLOPs**？
4. **有没有什么东西在这里爆炸？** ← 往往第 4 个才是重点

## 站 1 · 从文字到向量

**讲**
- 分词：词表 129,280 怎么定下来的，大小的两头权衡
- 嵌入：一次查表，仅此而已

**算**
- 嵌入矩阵参数量：129,280 × 7168 = ?
- **128K token 查完表，那个张量多大？**
  → 第一个让人坐直的数字：还没进第一层，显存已经掉一块
- 这个张量此后每一层都要被读写一次（残差流）

## 站 2 · MLA：注意力，以及 KV cache 的战争

**整课的重头，也是 V3 最值得讲的地方。**

**讲**
- 标准 MHA 在长上下文下的死穴：KV cache **随序列线性增长、又随层数线性增长**
- 演化路线 MHA → MQA → GQA → **MLA**，每一步在省什么、代价是什么
- MLA 的做法：
  - KV 压成一个 **512 维**隐向量（`kv_lora_rank`），要用时再升回 128 头
  - 位置信息单独走一路 **64 维** RoPE（`qk_rope_head_dim`）—— 为什么必须分开走
  - Q 也走低秩（1536），但那是为了省参数，不是省 cache
- RoPE 与 YaRN：4K 训练怎么外推到 163,840

**算**
- 五个投影矩阵（`q_a` `q_b` `kv_a` `kv_b` `o`）各多大，一层合计多少
- **每 token 每层的 KV cache = 512 + 64 = 576 个数**
  → 128K × 61 层是多少 GB？
- 对照：**同样 128K，标准 MHA 要多少？** ← 这个差值就是 MLA 存在的理由
- ⚠️ **注意力分数矩阵**：128 头 × 128K × 128K 如果真物化出来是多少？
  → 大到荒谬（PB 量级）
  → **这就是 FlashAttention 必须存在的原因 —— 不是为了快，是为了根本放得下**
- FLOPs：$QK^\top$ 与 $AV$ 两处都是序列长度的**平方项**
  → 上下文越长，attention 在总算力里的占比怎么爬升

## 站 3 · Dense MLP：先把「不稀疏」讲清楚

`first_k_dense_replace = 3` —— V3 的前 3 层是普通 dense MLP，后 58 层才是 MoE。
**先讲这 3 层，因为不理解 dense 就理解不了 MoE 在省什么。**

**讲**
- 结构：gate / up / down 三个矩阵 + SiLU（SwiGLU 家族）
- **Dense 的特性，以及它对硬件到底有多友好**：
  - 每个 token 走完全相同的一条路 → **形状是静态的、可预测的**
  - 就是一个大矩阵乘 → **算力利用率天然高**，MXU / Tensor Core 最爱这种
  - **不需要任何跨卡通信来决定谁算什么**
  - 编译器能提前排好一切
- ⚠️ 这一条要说透，因为它是后面所有 MoE 麻烦的**对照组**：
  **MoE 省下来的算力，是拿这些好性质换的。**
- 为什么最前面几层偏偏不做 MoE

**算**
- 一层 dense MLP：3 × 7168 × 18432 = ?
- 跟下一站的一层 MoE 做对照

## 站 4 · MoE：671B 的主体

### 4a · 原理

**一句话比喻（贯穿整站）**：
> **护士分诊，专家看病。** 不是每个医生都给每个病人看一遍 ——
> 先分诊，再送到对口的少数几个专家那儿。**总的诊疗量因此降下来了。**

- 门控网络 = **分诊台**：给每个 token 打分，决定送去哪几个专家
- 专家 = 一个个独立的小 MLP，每个只擅长一部分
- 稀疏在哪：**参数全都在，但每个 token 只激活其中一小撮**
- 于是：**参数量和计算量解耦了** —— 这是 MoE 唯一的、也是全部的价值
- 为什么被稀疏化的是 MLP 不是 attention（回到站 3 的参数占比 + MLP 天然是"一堆独立的问题"）

**细粒度专家**
- `moe_intermediate_size` 只有 2048，而 dense 是 18432 —— **专家做小做多**
- 为什么小而多比大而少好：组合数变多，同样的激活预算能表达更多分工

**共享专家**（`n_shared_experts = 1`）
- 所有 token 都要过的那一个
- 原理：**通用能力不该被反复学 N 遍**。
  语法、常识这类每个 token 都要用的东西，交给共享专家；
  路由专家专心分工。**省的是冗余。**

### 4b · 路由：怎么选

- 打分：`scoring_func = sigmoid`（不是 softmax，为什么）
- **分组限制**：`n_group = 8`，`topk_group = 4` —— 先选组，再组内选专家
  > ⚠️ 这个设计**纯粹是硬件逼出来的**：限制一个 token 最多要跨多少台机器去取专家。
  > **通信约束被直接写进了模型结构里。** 这是全课主线最锋利的一个例证。
- top-8：`num_experts_per_tok = 8`
- `noaux_tc`：不靠辅助损失做负载均衡，靠一个可学习的偏置
  - 为什么辅助损失有害（它跟主目标打架）
  - 负载不均会怎样：**最慢的那张卡决定整层的时间**

### 4c · 分布式：挪 token，还是挪权重？

**这一小节是整课的系统高光。** 专家分散在不同卡上，那么算的时候：

| | 挪什么 | 通信原语 | 通信量正比于 |
|---|---|---|---|
| **Dispatch / Combine** | **把 token 送到专家那儿**，算完送回 | all-to-all ×2 | token 数 × hidden |
| **AG-RS** | **把专家权重取过来**，在本地算 | all-gather + reduce-scatter | 专家权重大小 |

**这是一个真实的二选一，答案取决于场景：**

- token 多、权重相对小 → 挪权重划算
- token 少（比如推理 decode，一次就几个 token）→ 挪 token 划算
- 还要看互联拓扑：跨机带宽比机内小得多，分组限制正是为了让 all-to-all 尽量留在机内

**要算的**
- 一层 MoE 的 all-to-all 通信量：token 数 × hidden × 2（去和回）× 精度
- 对照一层的计算量 → **算出通信/计算比**
- → 这个比值决定了通信能不能被计算盖住 —— 后面性能工程那一课的地基

**要提的**（不展开）：DeepEP、EPLB 负载均衡、dropless

### 4d · 算账

- 单个专家：3 × 7168 × 2048 = ?
- 一层（256 routed + 1 shared）= ?
- 58 层合计 = ? → **671B 的绝大部分**
- 每 token 实际过 8 + 1 = 9 个专家 → 激活多少？
- **总参数 671B vs 激活 37B，差 18 倍**
- ⚠️ 但显存要装的是 **671B**，算力只花 **37B** ——
  **MoE 省的是算力，不省显存。** 这个反直觉必须点破

## 站 5 · 层间：数据怎么流，以及残差连接

**讲**
- **残差流是一条总线**：每层从它读、往它写，一路贯穿 61 层
- 为什么必须有残差（梯度、以及"默认什么都不做"这个初始状态）
- RMSNorm 摆在哪（pre-norm），为什么现代模型都站到了这边
- 一层的完整数据流：`x → norm → MLA → +x → norm → MoE → +x`，然后 ×61

**mHC（Manifold-Constrained Hyper-Connections）**
- DeepSeek 在 V4 上用的新残差结构：**4 条残差流** + Sinkhorn 双随机矩阵约束
- 它想解决什么：单条残差流是所有层共用的一个瓶颈，
  信息在里面反复叠加、互相干扰
- 多条流 + 流形约束 = 让不同层能走不同的"车道"，同时约束住数值不发散
- ⚠️ 代价：**残差流变 4 倍宽 → 激活显存也跟着涨**。这笔账要算出来
- （V3 还没有，V4 才有。放在这里是因为它属于"层间连接"这个话题）

**算**
- 单层激活峰值
- **61 层的激活如果全留着**是多少？
  → 大得离谱 → 于是自然冒出：*凭什么要留着？*
  → 答案在反向里 —— **那是后面的课，这里只把问题立住**

## 站 6 · 出口：从向量回到文字

**讲**
- 最后一次 RMSNorm
- **反向嵌入**（`lm_head`）：7168 → 129,280，把向量映射回词表
  - 跟站 1 的嵌入矩阵是**镜像**关系，但 `tie_word_embeddings = false` ——
    **V3 的进出口是两份独立的大矩阵，不共享权重**
  - 为什么有的模型共享、有的不共享
- softmax → 概率分布；温度在这里起作用
- **MTP**（`num_nextn_predict_layers = 1`）：一次多预测一个 token
  - 训练时是额外的监督信号
  - 推理时可以拿来做投机解码 —— **同一个模块，训练和推理用途完全不同**

**算**
- lm_head 参数量（= 嵌入矩阵大小，且是独立的第二份）
- **logits 张量**：128K × 129,280 × 2 字节 = ?
  → 又一个容易漏掉的爆点：**出口这一下比中间任何一层都吓人**
  → 顺带引出：为什么实际实现里 logits 要分块算、loss 要 fuse 进去

## 站 7.5 · 我们真跑过：算出来的数，跟机器上量出来的数 ⭐

**前面七站都是推导。这一节把推导和实测对上。**

我们有一套工具（`tpu/tpuguru/`）能做到这件事：给定一份配置，
用 **AOT 提前编译**在**不占一张卡**的情况下算出它到底装不装得下 ——
编译器会在 HLO 里报出 `temp_size`（HLO 临时缓冲）和参数占用。

### 三条只有真跑过才知道的教训

**① 「编译过了」不等于「装得下」**

这是最贵的一条。编译成功只说明图合法，**不代表运行时不会 OOM** ——
我们见过 `temp_size` 报到 **142.30 GB** 的配置，编译一路绿灯，
而单 device 上限是 **94.74 GB**。

> ⚠️ 更糟的是**报错会误导**：真正的编译失败常常被工具报成「装不下」，
> 于是人去调小 batch —— 方向完全错了。
> **我们自己的工具就犯过这个错，后来把判据统一到一个地方才修好。**

**② `temp_size` 只是临时缓冲，不含参数**

第一次看这个数会误以为它就是显存占用。它不是 ——
**参数和优化器状态是另外一笔**（见[专题三](专题03-反向与优化器.md)）。
而且它**不随 FSDP 宽度缩小**：切得再宽，临时缓冲该多大还多大。

**③ ⭐ 94.74 GB 附近 ±5% 的配置，AOT 判不准，必须实跑**

这是最诚实也最有用的一条：**在上限附近那一条带里，静态判据会失灵。**
我们两次判错都落在这个区间。

> **讲课时要点破的**：不要把 AOT 当成神谕。
> 它在**远离边界**时非常可靠（能替你省掉大量排队等卡的时间），
> 但**贴着边界**时只能给你一个"需要实跑"的信号。

### 顺带：同一个配置，换个实现数字就变

同一个模型、同样的并行配置，只是把某个算子从 tokamax 换成原生实现：

| | `temp_size` |
|---|---|
| 原始实现 | 78.42 GB |
| 换实现之后 | 80.48 GB（**+2.06**）|

而另一个模型上，同样的替换是 **86.30 → 72.28 GB（−14.02，方向相反）**。

> ⭐ **结论：显存不是模型的属性，是「模型 × 实现 × 编译器」的属性。**
> 这一条会在[专题六](专题06-性能调优与工具链.md)里反复出现。

## 这个专题明确不讲

写清楚是为了让边界清楚，不是遗漏：

- **反向传播与优化器状态** —— 前向的账是事实，反向的账掺着策略，混讲会讲不清
- **并行策略** —— 本专题只负责把"装不下"这个事实算出来
- **FP8 训练** —— V3 的一大贡献，但那是精度与数值的话题，单独讲
- **推理**（prefill / decode 的差异、连续批处理）—— 全程按训练的前向算
- **训练数据、后训练、RL** —— 跟架构无关
