[focus] 前两章一直在拧同一个旋钮：让每一份小一点。这一章换一个完全没碰过的方向。每一份多大都不改，改的是每走一步，到底读进来几份。

[seriously] 先把话说在前面，这句话请记一整章：这条路，一个字节的显存都不省。而正因为它不省，第八章才非存在不可。

[friendly] 请看这五张图，先别一张一张看，五张一起看。从左往右，黑格子越来越少：全都算，只看身边，只看身边再加开头几个，挑着看，先压再挑。五张图其实就是一句话：这一支从头到尾，只在回答「这一步，到底哪些格子可以不算」。

[casually] 最容易想到的那一招，叫滑动窗口。每个字只看前面固定的几百个，再往前的一律不看。听上去很合理，对吧？说话本来就大多只跟附近有关。

[seriously] 可它有一个著名的崩法，而且崩得毫无预兆。这是全讲最好的一个侦探故事。

[focus] 请看这三根柱子。先说一句，它们是按对数画的。一个十三 B 的模型，窗口一千零二十四个 token，只留窗口，困惑度是五千一百五十八。把最前面四个 token 留住，窗口里少放四个，困惑度掉回五点四零。三个数量级。一个模型从能用到彻底胡说，中间只隔着四个 token。

[curiosity] 那这四个 token 是什么神仙？有人做了一个判决性的实验：把那四个 token，换成毫无意义的换行符。如果它们重要是因为内容，换掉之后应该照样崩。

[realization] 结果是五点六零，跟留着原来那四个字几乎一样。所以结论只能是这一个：起作用的是位置，不是内容。那几个字什么意思都没有，它们是个废票桶。

[thinking] 这个 bug 是一整类 bug 的样板。从公式上你看不出任何问题，是有人把注意力矩阵整个画出来，才看见开头那几个字上堆着一大片。

[friendly] 凭什么是开头？看左边这一格。每一行的票，一百分必须投满，而在场的候选人只有前面这些 token。开头那一个，是唯一一个人人都够得着的。它不是特殊，它只是永远在场。

[seriously] 那补一个可以弃权的格子行不行？行，但那一格必须是可学的。有人补了一个可学的桶，困惑度十八；有人补了一个恒定为零的格子，形状一模一样，困惑度涨到两万九。两个长得一样的方案，结果差了一千多倍。

[contemplative] 还记得第二章 Bengio 那句话吗？注意力必须是软的，要有一份总额固定的注意力。「总额固定」翻译过来就是：不许有人弃权。一个头这一步实在没什么想看的，也得把票投到某个地方去。窗口一滑过开头，废票桶被扔掉，那些票没地方去，模型当场崩掉。

[realization] 这正是第一章那句话，第二次应验：一个设计的毛病，十有八九跟它的好处是同一条性质。总额固定，是它能被训出来的原因，也正是这个 bug 的病根。第一次是那个盒子，这是第二次。第三次在第七章。

[casually] 好，滑窗会崩，得把开头那几个留着。那下一个想法就很自然了：别只看身边，去把重要的挑出来。听起来比滑窗聪明多了，对吧？

[seriously] 可这里有个死结。你要挑出重要的，就得先知道谁重要。而「谁重要」这件事，本身就是注意力分数。等你算完注意力再回头去挑，你想省的那一步，钱已经付过了。

[thinking] 破这个死结有三条路。第三条值得先记一笔：先把要挑的东西压短四倍，再在压短之后的格子里挑。死结没破，但那只鸡小了四倍。而这一条，两家不同的团队各自独立做了出来。一件事被独立做对两次，说明它不是谁的灵光一现，是这个死结自己逼出来的解。

[friendly] 我们重点讲第一条，DeepSeek 的 DSA。它的破法是师徒：让真正的注意力当老师，另外训一个极便宜的学生。

[curiosity] 学生凭什么便宜？因为它不学怎么算得准。它只去学老师那张分布的排序，只要知道谁排前面。这个要求低多了，所以它可以做得非常轻。这个套路大家在别处也见过，投机解码、模型蒸馏，都是同一个形状：贵的那个不用消失，它只要愿意当一次老师。

[focus] 请看这张图，一格一格来。第一格，一步之内发生了什么：一个很轻的打分器扫过全部历史，取分数最高的两千零四十八个位置，再只对这两千零四十八个做完整的注意力。注意那个红框：它必须扫过全部历史，一个都不能跳。不扫完，就不知道该跳谁。

[seriously] 第二格请多看一会儿。这条带子是按真比例画的。十三万一千零七十二个 token 里，每一步读进来两千零四十八个，百分之一点五六，就是橙色那一小条。灰色那一大片，百分之九十八点四，全都还在显存里躺着。它们只是这一步没被读，不是没被存。

[focus] 第三格是三栏账。第一栏省下来的：注意力那一段，从长度乘长度，变成长度乘两千零四十八，上下文越长赚得越多。第二栏一点没省的：显存。道理很硬，要能从历史里挑，就得把历史全留着。

[seriously] 而且说「没少」还算客气。那个打分器自己也得存一份东西，每个字一份很小的、专门给它打分用的记号。一百二十八维，FP8，六十一层，十二万八千个 token，合计零点九五个 GiB，比原来的 KV cache 还多了约一成。

[thinking] 第三栏是反而多花的，一笔比一笔疼。第一笔，这零点九五个 GiB 每一步都要整条读完，是挑中那两千零四十八个的七倍。所以这一支后来的新名字，都在缩这一笔，比如让好几层共用一个打分器。第二笔更疼：挑中的两千多个散落在显存各处，不是一整块，搬起来很碎。

[seriously] 省 FLOPs 谁都会，在纸上少算百分之九十八的格子而已。可只要那些格子是散的，要搬的字节就一点没少，时间也就一点没省。

[casually] 还有一个从定义直接推出来的细节：历史不足两千零四十八个的时候，挑两千零四十八个就是全选。所以短上下文下，DSA 就是普通的 MLA。它挑的那两千零四十八个，本来就是在 MLA 那份全量缓存上挑的。

[friendly] DSA 既不是这条路的起点，也不是终点。请看这张图，把它前后一共四步摆在一起。

[casually] 第一步是 NSA，三条支路并排跑：远处按块压成摘要，挑出最相关的几块，身边一段全留。三条里只有「挑哪几块」要跑起来才知道。而且它挑的是块，不是散落的单个 token。块是连续的一片，搬起来整齐。论文把这件事写进了标题：hardware-aligned，对齐硬件。

[thinking] 第二步是 DSA，不压，纯挑单个 token，更准，也最碎。第三步是 CSA，先把四个 token 压成一条，再挑，要挑的池子小了四倍。第四步是 HCA，一百二十八个字直接压成一条。注意，它不是在 CSA 的基础上再压，它是另一种层，自己直接从原始的字压过去。

[realization] 压到这个份上之后，它不挑了。这就是这张图真正要说的：压得够狠的时候，就不需要挑了。挑这个动作，本来是为了在一大堆里只看几个；你先把一大堆压成一小堆，全看也无所谓了。

[seriously] 代价是分辨率没了。所以 HCA 旁边还挂着一个局部滑窗，把身边一百二十八个 token 原样留着，不进压缩器。压缩块直接拼在这一段后面，一次注意力一起看。远处压得很糊，近处一个不落。

[curiosity] 这里大家一定会问：这东西用的时候要不要解压？像 MLA 那样吸收？不用解压。但原因跟 MLA 完全不是一回事，它俩压的根本不是同一个轴。

[thinking] MLA 压的是一个 token 有多宽，是维度方向。维度方向压完，逻辑上必须升回去，不然点积对不上，吸收就是为这个生的。CSA 和 HCA 压的是一共有多少个 token，是序列方向。压出来的那一条，本身就是要参与注意力的 K 和 V，根本没有还原这回事。

[seriously] 代价也跟着两个轴分开走。维度方向是有损的近似，可每个 token 都还在；序列方向是把一百二十八个字合掉，它们各自的身份永久没了。这才是那条滑窗非挂不可的理由，不然连刚说完的上一句都是一团摘要。

[curiosity] 那 DeepSeek 最新的 V4，一条 KV 里存的到底是什么？很多人第一眼会说：这不就是 MLA 吗？所有头共读同一条五百一十二维的东西。这个直觉是对的。它的正式名字叫共享 KV 的 MQA，一个 KV 头，一百二十八个查询头共读，而且 K 和 V 就是同一条。

[realization] 差在哪？MLA 存的是原料，下锅前得加工一道，展开成每个头的 K 和 V，吸收是把这道工序提前折进别的矩阵。V4 存的是成品，这道工序压根不存在。位置信息也收进了这五百一十二里面：只旋转末尾六十四个通道，所以从五百七十六降到五百一十二。代价是 V 也被转过了，算完注意力要反向再转回来。

[contemplative] 那二零一九年被判不行的 MQA，怎么又行了？论文没有正面回答，下面是我们的推导。MLA 吸收之后，本来就长成一个每头五百一十二维的 MQA。当年的 MQA 掉点，毛病不在共享，在删了不补：共享的那条只有一个头宽，没有任何东西接手。V4 共享的那条宽四倍，查询每头五百一十二维，输出侧还有分组投影。每个头的视角没有消失，它搬家了。

[thinking] 再算一笔账：两个轴能不能只上一个？假如不压宽度，标准多头每 token 每层存三万两千七百六十八个数，沿序列压四倍，还剩八千一百九十二，比 MLA 的五百七十六大十四倍。所以序列压缩不是可以叠在宽度压缩上，是必须叠。

[focus] 最后，为什么这一步在 TPU 上格外要紧？DSA 和 CSA 跑起来才知道挑谁，挑的结果只能运行时现算。HCA 窗口固定、压缩比固定，该看哪些格子在编译的时候就能定下来，打包好直接塞进片上。HCA 不是把动态稀疏做快了，是把动态取消了。

[realization] 把四步连起来看：挑块，挑单个 token，先压再挑，压到不用挑。每一步，都在把运行时的决策往编译期推。这又是那条暗线，硬件在反过来决定公式：按块挑，不按 token 挑。一个麻烦最好的结局，不是被解决，是不再存在。

[focus] 这一章的三句话，答案很不一样。省的是哪一样？不是显存，是算力和带宽。省了多少？每步只读两千零四十八个，一百二十八 K 下是六十四分之一。亏了多少？显存一个字节都没省，还多存了一份打分记号，而且搬起来更碎了。

[seriously] 请大家记住中间那一栏，显存不省。既然一个旋钮补不齐，后面就得几个一起拧。而现在，存得少、读得少，两条路都走过了，还有第三条。

[friendly] 这一节就到这里，大家有问题吗？
