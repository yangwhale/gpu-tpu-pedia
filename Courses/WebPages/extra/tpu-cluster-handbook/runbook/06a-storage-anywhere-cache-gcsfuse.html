06a 存储：Anywhere Cache、带宽配额、gcsfuse 怎么配合

06c §6.1 讲「桶怎么挂上」，本节讲「几千芯同时读，桶扛不扛得住」。实况取自实测集群。

💡三句话

  • 训练读数据靠的是 Anywhere Cache 带宽，不是桶的出口配额。 缓存按字节命中 99.96%；桶出口配额只有 1 Tbps，满打满算一天也远不够缓存实际出量。
  • 缓存带宽按 zone 给，每项目每 zone 封顶 20 Tbps。 实测 24 小时内 5 分钟均值冲到略超 20 Tbps。这条配额使用方自己提不了，开卡前要设好，Google 可协助。
  • 缓存只服务同 zone、且建在那个桶上。 10+ 片主训练都挂同 zone 有缓存的那个桶，全走缓存；没缓存的桶只剩一次性搬运和一个 1 片小任务在读（§1）。
  • 20 Tbps 卡所在 zone 的缓存带宽配额
  • 略超 20 Tbps 24h 内 5 分钟峰值
  • 99.96% 同 zone 缓存按字节命中
  • PiB 级 缓存当前容量（已超单缓存默认 1 PiB）
  • 1 Tbps 桶出口配额（不是瓶颈）

本节用词：

词 一句话
Anywhere Cache GCS 的 zone 级 SSD 只读缓存，同 zone 读自动走它；官方文档现改名 Rapid Cache，API / gcloud / 指标名仍叫 anywhere-cache
出口配额 桶往 Google 服务（含 GCE / GKE）出数据的带宽配额，按 region 计
producer override Google 后台设的配额覆盖值，使用方在 Console 看得到、自己改不了；使用方自己提的是 consumer override
file cache gcsfuse 在节点本地的文件缓存；tpu7x 无 Local SSD，只能放内存

1.实测现场：集群、桶、缓存

  • 集群：tpu7x 节点全部在同一个 zone。

  • 桶：训练数据桶在卡所在 zone 建了 Anywhere Cache；另有两个桶没建缓存。

  • 谁在读：24 小时内，同 zone 缓存按字节命中 99.96%。

  • 缓存参数：admission_policy: admit-on-first-miss、ttl: 604800s（7 天，上限）、ingest_on_write: true、state: running。

  • 「谁在读」来自 Monitoring anywhere_cache/sent_bytes_count，只算 ReadObject，标签 anywhere_cache_zone 是请求方所在 zone，anywhere_cache_hit 是否命中（§3 查询）。

📊没缓存的桶：一次性搬运 + 一个小任务

  • 主训练只挂有缓存的那个桶。
  • 没缓存的桶，24 小时里的读量大头集中在一个小时内，是一次性搬运，不是训练常态读。
  • 还在读的只有一个 1 片小任务，量级远在 1 Tbps 出口配额以内，不影响主训练。
  • 要它放大到多片时：数据先搬进有缓存的桶，或给那个桶在卡所在 zone 建缓存（多区域桶允许在其覆盖的 zone 建）。

2.配额：读哪几条、要设成什么

怎么读（gcloud alpha quotas 在部分账号权限下不可用；直接调 Service Usage REST）：

bash
curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://serviceusage.googleapis.com/v1beta1/projects/$PROJECT/services/storage.googleapis.com/consumerQuotaMetrics?view=FULL" > quota.json
# 每条 metric → consumerQuotaLimits[].quotaBuckets[]：dimensions 是 zone/region，
# effectiveLimit 是生效值，defaultLimit 是默认，producerOverride / consumerOverride 是谁改的

要设成什么：

配额 metric 维度 默认 要设到 谁能改
anywhere_cache_egress_bandwidth 卡所在 zone 无值 20 Tbps producer override，使用方自己提不了，Google 可协助
anywhere_cache_storage_size 桶 / zone — 按数据集大小 producer override
google_egress_bandwidth 卡所在 region 200 Gbps 1 Tbps 兜底 使用方在 Console「IAM → Quotas & System Limits」自助提；>5 Tbps 找 Google
  • 20 Tbps 是缓存带宽配额，不是桶出口配额。 官方：缓存带宽起步 100 Gbps，每存 1 TiB 加 20 Gbps，每项目每 zone 封顶 20 Tbps，同 zone 各桶共用；超出部分按桶出口配额计。
  • 出口配额兜的是缓存未命中、超出缓存带宽的读、checkpoint 恢复读；写入不计这个配额。多区域桶超过 1 Tbps 不支持。
  • 带宽 API 原值是 bit/s。consumerOverride: -1 是使用方不额外限制，生效值取 producer 那个。

开卡前做完：

  1. 先定卡在哪个 zone，再在同 zone 为训练数据桶建缓存（§5 命令）。建缓存最长要 48 小时，zone 一定就建。
  2. 缓存带宽和容量两条配额设好（Google 可协助）。
  3. 出口配额提到 1 Tbps。
  4. 上线当天用上面的 curl 读一遍生效值，和 01 §1.4 一起归档。

3.Dashboard 怎么看

Console 两处
  • 单桶：Cloud Storage → Buckets → 选桶 → Observability 页签 → Rapid Cache。
  • 全项目：Cloud Storage → Monitoring → Rapid Cache。

图里看四样：命中率（按字节 / 按请求）、命中与未命中吞吐、缓存容量与淘汰、Cache throughput benefit（缓存多给的吞吐 vs 配额用量）。源https://cloud.google.com/storage/docs/using-anywhere-cache

Metrics Explorer / API（前缀 storage.googleapis.com/）：

指标 用来看 关键标签
anywhere_cache/sent_bytes_count 吞吐、命中率 bucket_name、anywhere_cache_zone（请求方 zone）、anywhere_cache_hit、method
anywhere_cache/request_count 按请求的命中率 同上
anywhere_cache/ingested_bytes_count 进缓存速率（未命中回填 + 写入同步） —
anywhere_cache_metering/cache_storage_bytes_count 缓存当前容量 cache_zone；按小时采样，最多延迟 8 小时

实测 24 小时读数：

项 值 怎么算的
卡所在 zone 命中吞吐峰值 略超 20 Tbps sent_bytes_count 过滤训练数据桶、hit=true，5 分钟 ALIGN_RATE 后求和取最大
卡所在 zone 命中吞吐均值 约 3 Tbps 同上取平均（288 个点）
按字节命中率 99.96% 命中字节 ÷ (命中 + 未命中)
按请求命中率 约 85% 命中请求数 ÷ (命中 + 未命中)
进缓存 每天数百 TiB ingested_bytes_count
缓存容量 PiB 级（主训练 zone）、TiB 级（另一 zone） cache_storage_bytes_count 小时均值
  • 峰值略超 20 Tbps 配额：5 分钟均值，可能含突发宽限或协议开销 [需确认：超额部分是否已经转计入出口配额]。要看是否被限速，盯同时段该 region 的出口配额（google_egress_bandwidth）用量有没有跟着抬起来；未命中吞吐只作旁证——没命中的读本来就不算缓存带宽 [推断：依 §2 官方「超出部分按桶出口配额计」]。
  • 按请求命中率比按字节低：未命中的多是小请求（元数据附近的小读），字节上几乎全命中。
bash
# 复现峰值那条（只读）。表里是 24 小时窗；要复现当天的读数，把 START / END 换成当时的 UTC 时间
BUCKET=${BUCKET:-<你的数据桶>}                     # 换成要查的桶（不带 gs:）
START=$(date -u -d '-24 hours' +%FT%TZ); END=$(date -u +%FT%TZ)
F='metric.type="storage.googleapis.com/anywhere_cache/sent_bytes_count" AND resource.labels.bucket_name="'"$BUCKET"'" AND metric.labels.anywhere_cache_hit="true"'
curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://monitoring.googleapis.com/v3/projects/$PROJECT/timeSeries?filter=$(python3 -c 'import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1]))' "$F")&interval.startTime=$START&interval.endTime=$END&aggregation.alignmentPeriod=300s&aggregation.perSeriesAligner=ALIGN_RATE&aggregation.crossSeriesReducer=REDUCE_SUM"

4.gcsfuse 怎么和缓存配合

分工：gcsfuse 在 pod 里把桶挂成目录；它发出去的读请求从卡所在 zone 出发，GCS 自动交给同 zone 的 Anywhere Cache。gcsfuse 不需要任何「开缓存」参数，缓存对客户端透明。gcsfuse 自己的 file cache 是第二层，放节点内存，省的是重复读同一文件的往返。

实测集群的 PV（都是 gcsfuse.csi.storage.gke.io、RWX、Retain）：

PV mountOptions
主数据桶（有缓存） implicit-dirs、client-protocol=grpc、metadata-cache:negative-ttl-secs:0、metadata-cache:ttl-secs:-1、metadata-cache:stat-cache-max-size-mb:-1、metadata-cache:type-cache-max-size-mb:-1、file-cache:max-size-mb:204800
其余数据桶 上面全部 + profile:aiml-training、file-cache:cache-file-for-range-read:true、file-cache:enable-parallel-downloads:true

10+ 片主训练都只挂主数据桶那个 PV。

一个 1 片小任务用了两个 inline 卷（直接写在 pod spec 里，不经 PV）：

  • 只读的 chunk 缓存卷：only-dir: 指到本次 run 的目录，file-cache:max-size-mb:1024、file-system:kernel-list-cache-ttl-secs:0。
  • 读写的输出卷：enable-hns=false、metadata-cache:ttl-secs:0、kernel-list-cache-ttl-secs:0 —— 写目录关掉元数据缓存，保证多 pod 看到彼此新写的文件。
sidecar 与内存
  • 注解只有 gke-gcsfuse/volumes: "true"；sidecar gcs-fuse-csi-driver-sidecar-mounter:v1.24.5-gke.2，原生 sidecar（restartPolicy: Always），request 250m / 256Mi / 5Gi，不设 limit（1.29.1 起默认如此）。
  • file cache 卷 gke-gcsfuse-cache 是 emptyDir: {medium: Memory}，不限大小。
  • file-cache:max-size-mb:204800 的单位是 MiB：每个节点最多 200 GiB（≈ 215 GB）内存给文件缓存，再加 200 GiB 的 tmpfs ramdisk，合计约 430 GB，约占 960 GB 主机内存的 45% [推导：(200 + 200) × 2³⁰ ≈ 429.5 GB，÷ 960 GB ≈ 45%]。见经验教训第 22 条。
  • profile:aiml-training 把元数据缓存设成无限容量、无限 TTL；官方提示内存小于 1 TiB 的机器易 OOM。GCS 文档说 CSI 不支持 profile，GKE 文档却给了 StorageClass 写法 —— 两份冲突，实测集群在用且能挂上。

💡两层缓存各管什么

层 在哪 管什么 实测设置
Anywhere Cache GCS 侧、zone 级 SSD 全 zone 共享：第一台读过，同 zone 其他节点都命中 7 天 TTL、首次未命中即进
gcsfuse file cache 每个节点内存 本节点重复读同一文件 200 GiB、并行下载、range read 也缓存

全部节点数据并行读同一批 shard：第一层把回源压到 0.04%；第二层省每节点的重复往返。第一层决定能不能起量，第二层决定省多少内存换多少延迟。

gcsfuse 起步配置（照实测集群主数据桶 PV，去掉争议项）：

yaml
mountOptions:
  - implicit-dirs
  - client-protocol=grpc
  - metadata-cache:negative-ttl-secs:0
  - metadata-cache:ttl-secs:-1            # 只读数据集可以；写目录改 0
  - metadata-cache:stat-cache-max-size-mb:-1
  - metadata-cache:type-cache-max-size-mb:-1
  - file-cache:max-size-mb:204800         # 与 MTC ramdisk 一起核内存预算
  - file-cache:enable-parallel-downloads:true
  • 06c 的 PV 模板默认没有这些项：scripts/06-data-pv-pvc.yaml 只开了前两项（implicit-dirs、client-protocol=grpc），其余几项在文件里注释着。
  • 怎么用：起步照 yaml 默认；要开 file cache / 元数据缓存就去掉那几行注释，先按上面的内存预算核一遍。这几项组合在本书集群上没有实测。

⚠️新桶第一件事：挂载带 client-protocol=grpc

  • 新桶挂载漏了 client-protocol: grpc：DIRECT_PATH 流量为 0，GCSFuse 全部退回 HTTP/1.1 走 CLOUD_PATH。
  • CLOUD_PATH 撞上单桶的请求速率上限，返回 429。带 gRPC 的桶 98% 以上的元数据和读请求走 DIRECT_PATH，不受这条限额。
  • 扩配额无效：项目级 NonMultiregionRequests 提到默认值的约 2 倍也碰不到单桶的请求速率上限。修法只有补 gRPC。
  • 规模参考：数千芯冷启动按秒统计，GRPC_DOWNLOAD 峰值数十万 QPS、持续十几秒；稳态只有约万级 QPS。1 分钟均值图只显示二十多万，看不出尖峰。
  • max-retry-attempts:10 不是解法：HTTP 下无效，gRPC 下会把限流变成读报错。
  • 检查：建桶后先看挂载参数有没有 gRPC；429 按原因（项目配额还是单桶速率上限）分开监控。
  • 写检查点走 Orbax / TensorStore，默认是 HTTP（CLOUD_PATH，经 GFE），不受挂载参数影响。

只读挂载开元数据缓存（经验建议，本书集群未实测）：

挂载 参数 作用
数据集（只读） metadata-cache:negative-ttl-secs:-1 缓存 404，同一个不存在的路径不再反复问 GCS
file-system:kernel-list-cache-ttl-secs:-1 内核锁住目录列表
gcsfuseMetadataPrefetchOnMount: "true"（卷属性） 挂载时预取元数据，压冷启动请求量
检查点（读写） metadata-cache:negative-ttl-secs:60（≥0） MTC 场景 404 很多，缓存 60 s 削峰
metadata-cache:ttl-secs:-1 —
  • negative-ttl-secs：0 不缓存 404；-1 永久缓存，只适合只读；60 缓存 60 s，适合读写的检查点桶。
  • 上面起步 yaml 里的 negative-ttl-secs:0 照抄自实测集群主数据桶 PV，是保守值。只读数据集可按本表改成 -1。
  • 数据集和检查点同一个桶时，建两个 PV 分别设挂载参数。
  • 写目录（多 pod 互看新文件）仍按上文输出卷的做法关元数据缓存。
  • -1 的 kernel list cache 意味着挂载期间新增的文件看不见 [推断：锁住列表的直接后果]。数据集要在训练前写完。

用 CSI StorageClass 时可以让驱动替你建缓存：anywhereCacheZones: "<卡所在 zone>"、anywhereCacheTTL、anywhereCacheAdmissionPolicy 源GKE gcsfuse-profiles 文档。但缓存带宽配额仍要另外谈（§2）。

5.建、查、改缓存的命令

操作 命令
建 gcloud storage buckets anywhere-caches create gs://$DATA_BUCKET $ZONE --ttl=7d --enable-ingest-on-write
列 gcloud storage buckets anywhere-caches list gs://$DATA_BUCKET
看 gcloud storage buckets anywhere-caches describe $DATA_BUCKET/$ZONE
改 gcloud storage buckets anywhere-caches update $DATA_BUCKET/$ZONE --ttl=3d
停 / 恢复 ... disable $DATA_BUCKET/$ZONE（1 小时内可 resume）
  • 建是长操作，最长 48 小时，zone 没容量会一直重试；每项目每 zone 同时 creating 最多 20 个 [需验证：未找到公开出处]。
  • TTL 1–7 天，从最后一次读起算；按 2 MB 分块进缓存。
  • --ttl=7d 的取值：本机 gcloud SDK 587 的参数解析器把 7d 解成 604800 秒（3d → 259200），与实测缓存显示的 ttl: 604800s 一致；只核了本机解析，没对云端执行。
  • $DATA_BUCKET 是 env.sh 的数据桶变量（不带 gs://）；缓存要建在训练真正读的那个桶上。
  • gcloud 现行 FLAGS 里已没有 --admission-policy（参考页示例还残留），实测缓存显示 admit-on-first-miss。
  • 计费：进缓存 $0.0032/GiB、读出 $0.0006/GiB、命中读 $0.0002/千次（代替 Class B）；命中读免多区域传输费 源https://cloud.google.com/storage/pricing; 价格按地区与时间变化; 地区未记; 以 pricing 页为准。

本节可能踩到的问题：gcsfuse 挂载要 WI · Checkpoint 存储与 MTC · 没有 Local SSD，缓存吃内存

交棒：存储就绪后跑训练：公开配置 → 06b，大号 MoE 模型 JIT 对照 → 06c；大规模建议提前编译（AOT），Google 可协助。
