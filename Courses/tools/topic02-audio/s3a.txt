[focus] 前两节我们说了两边胃口一样大，也说了吃法完全不同，一边路上四个跑起来才知道的决定，一边零个。这一节把两颗芯片真的拆开，看那个不同长在哪儿。路线是从整颗芯片，到一个核，到核里那块地，再到并行层级，最后到一条指令。每一层都问同一个问题：这一层两边少了什么，多了什么，是谁的决定造成的。

[casually] 先看整颗。请看 B200 这张全景图。一个封装里是两颗 die，中间用一条每秒十个 TB 的桥连起来。每颗 die 物理上有八十个 SM，出厂禁用六个来提良率，所以全片是一百四十八个。但你在 CUDA 里看到的，是一个设备。缝被藏起来了。

[casually] 再看 TPU v7 这张。它也是两颗 die，但它如实暴露成两个 device。两半各有自己的九十六个 GiB HBM，地址空间互不可见，想用对面的，你得自己写一步。

[realization] 缝在明处，还是缝在暗处。这就是第二节那个决定，在封装这一层的样子。

[thinking] 藏起来的那一边，代价不会因为藏起来就消失。你付了钱，只是不知道自己付了。B200 的 L2 在本分区里实测大约每秒二十一个 TB，跨到对面那颗 die，就掉到十六点八，延迟也变高。而这件事，不出现在任何 API 里。

[suggestion] 缝在明处还有一个很实际的后果：框架日志一律按 device 报数。所以看到每个 device 一千一百五十三个 TFLOPS，别以为掉了一半，那正是一颗芯片两千三百零七的一半；看到一个叫一百二十八的切片，也别以为是一百二十八颗芯片，那是六十四颗。

[seriously] 顺手提醒一个数。TPU 这张图上写着两个 MXU 一共十三万一千零七十二个格子，这个数先别急着往峰值上乘。每个格子一拍做两次乘加，这一步图上没有。而一次乘加本身就是一乘一加，算两个 FLOP，所以一格一拍是四个 FLOP，不是两个。漏掉这一步，拿格子数乘两个核、乘两个 FLOP、乘二点二 GHz，得到一千一百五十三，刚好是官方两千三百零七的一半。完整那条链，我们到后面讲指令的时候再对。

[focus] 再往里一层，拆一个核。顺序很重要：先看 GPU 有什么，再看 TPU 没有什么。反过来看，你会以为 TPU 是个简化版。

[casually] 请看 SM 这张图。一个 SM 里有四个 warp 调度器，两百五十六 KB 的寄存器堆，两百二十八 KB 的 L1 加共享内存，还有记分板。这些部件加起来，只干一件事：在运行时动态地藏住延迟和分支。

[curiosity] 再看 TPU 那个核，右边那一栏有五个打叉的空格：warp 调度器，几十个 warp 槽，那么大的寄存器堆，共享内存的自动填充，记分板和乱序发射。这五样，它一样都没有。

[realization] 但重点不是少了五样，是这五样其实是一件事。问一个问题：要不要在运行时换任务跑？答要，你就必须同时驻留几十份上下文，必须有东西挑下一个跑谁，必须知道谁的数据到了，五样缺一不可。答不要，五样同时失去存在的理由。有没有 cache 和有没有 warp 调度器，不是两件事，是同一个决定的两个面。第二节主路上那四个红框，就是答了要之后的必然产物。

[contemplative] 那省下来的面积去哪了？先说它没去哪：没变成更多算力，乘加总量反而是 GPU 多百分之十六；也没变成更多片上存储，这个马上就数。它变成的是不做本身。能点名的有两样：L2 那一百二十六 MB 整整一层，TPU 没有；给几十份线程上下文准备的那三十七个 MiB 寄存器堆，TPU 也没有。GPU 的寄存器堆那么大，主要不是为了算得快，是为了同时装下几十份随时待命的上下文。再加上控制接口，五百九十二套对四套。电路更简单，复杂度从硅上挪进了编译器里。

[thinking] 拆完部件，下一个必然要问的是片上那块地。这里必须正面接一个反问：你说 TPU 省下了面积，可 GPU 片上的 SRAM 明明更多啊。他是对的。把两边的片上 SRAM 一格不漏地列出来：GPU 一共大约两百三十一个 MiB，TPU 大约一百三十四个 MiB，GPU 多百分之七十三。这一条别嘴硬。

[curiosity] 承认完，再翻面。同一张表，能读出三个方向不同的结论，看你在问什么。第一个口径，一共有多少 SRAM，GPU 赢。第二个口径，只数软件当数据暂存用的那一行，TPU 是一百三十对三十七，大约三点五倍。第三个口径，也是真正有用的那个：一个计算单元能当成一整块连续工作台用的，有多大？TPU 一个核是六十四 MiB，GPU 一个线程块最多是两百二十七 KiB，差两百八十九倍。

[thinking] 为什么差这么多？因为 GPU 那三十七个 MiB 不是一整块，是一百四十八个互相看不见的小岛，每个两百五十六 KiB，里面 L1 还占着一部分。这个两百八十九倍，后面两边决定把块切多大的时候会直接用上。当然，六十四 MiB 是这块地的总面积，编译器每次给一个融合开多大，另有一道额度管着。

[seriously] 还有一句必须说：第一个口径虽然对，却最容易把人带沟里。GPU 领先的那九十几个 MiB，几乎全来自 L2 那一行。而 L2 是这张表里唯一一格你没法安排的空间。你不能把一块权重放进 L2 待着，只能发访存指令，然后希望它还在。

[focus] 所以这三种口径不是并列的，得看你在问什么。问这颗芯片一共有多少 SRAM，用第一个。问我能把中间结果放在哪儿、不落 HBM，只有第三个算数。而后面这个问题，正是算子融合每一次都要回答的那个。

[focus] 上面回答的是有多大、归谁管。还差一半：跑多快。这里会撞出一个几乎所有人都猜错的结果。大多数人默认，cache 总该比显存快一个数量级吧。B200 的 L2 不是。HBM 每秒八个 TB，L2 只有二十一，两点六倍。

[thinking] 但两点六倍答的是一个很窄的问题：这一个字节，命中 L2 比去 HBM 快多少。换个问法，结论完全不同：每一字节容量能供多少带宽？L2 是用大约一千五百分之一的容量，做到了两点六倍的带宽，两者一乘，它的带宽密度是 HBM 的四千倍左右。说得更好想象一点：把 HBM 整个读一遍，要二十四毫秒；把 L2 整个读一遍，只要六微秒。

[realization] 这两个时间的比值，恰好就是容量比。也就是说，片上存储的本事，全在它小这件事上。它快，不是因为它是 SRAM，是因为它小、离得近、线短。

[suggestion] 但做优化的时候，还是只能用两点六倍那个数，因为你搬的是字节，不是容量。所以 L2 的价值不在它本身快，在省掉一趟 HBM 往返。命中了，你拿到两点六倍；没命中，你什么都没省，还多绕了一圈。这就是为什么，让它落在 L2 里就好了，不是一个能依赖的策略。

[thinking] 反过来，两点六倍其实还是个下界。峰值带宽是 HBM 最擅长的工况，一次连续搬很大一块。HBM 每次访问都要先付一笔固定的启动开销，还得靠很宽的总线并行取数才跑得满。块小的时候，这笔开销摊不掉，总线也填不满，实际带宽比峰值低得多。片上那一层没这个问题，所以块越小，命中片上的收益越大。这也是合并访存争的另一半：让每一次搬运够大。

[thinking] 它为什么慢？因为 L2 是全片共享的，数据得穿过片上互连，才到得了 SM。而共享内存大约是 HBM 的四点三倍，VMEM 按公开的说法高出一个数量级左右，它们都贴在计算单元旁边。VMEM 的带宽官方没有公开，我们只给量级。所以真正快的那两块，恰好都是软件说了算的那一类。

[curiosity] 那 VMEM 相当于 GPU 的哪一级？哪一级都不是。按性格，它是共享内存：软件显式搬，没有标签，不会未命中。按容量，它是 L2 那一级：一颗芯片一百二十八个 MiB，B200 的 L2 是一百二十六 MB，几乎一样大，而 GPU 全片的共享内存加起来才三十几个 MiB。最准的说法是：TPU 把共享内存那种性格的东西，做到了 L2 那么大，然后把 L2 整层删掉了。

[seriously] 但千万别把这两小节读成 TPU 赢了三局。每一条领先都有对价。暂存又大又快，代价是没有兜底：GPU 猜错了只是慢一点，TPU 编译器切错了，就是真的停在那儿等。GPU 那几十个 MiB 的寄存器堆看着没用在数据上，它买的是别的东西：形状不规则、长度会变、分支不确定的活，照样能跑得不太难看。

[contemplative] 所以真正的结论不是谁的片上存储更好，而是这一句：两边都在处理同一个东西，不确定性，只是把它放在了不同的地方。GPU 花硅去兜住它，TPU 把它消灭在编译期。

[focus] 容量讲完了，带宽也讲完了，还差第三个轴：等多久。而这个轴，是三个里面唯一一个 GPU 自己也答不上来的。大家先想一想：一个 warp 要一块数据，L1 里没有，去 L2 查，L2 也没有，再去显存搬，这一串下来要多久？

[casually] 请看这张延迟阶梯。L1 命中，三四十拍。L2 命中，两百七十三拍。一路到显存，六百五十九拍。同一条 load 指令，在源码里长得一模一样，耗时从三十拍摆到六百五十九拍，二十倍。这组数是在 H100 和消费级 Blackwell 上量的，B200 没有同类公开数据，量级可以借，别当成 B200 的实测值。

[seriously] 这里要拦一个几乎人人都会犯的算法：L1 查一次，加 L2 查一次，再加 HBM 搬一次。不能这么加。六百五十九是一次全没命中的端到端耗时，前面那两次扑空已经含在里面了。

[curiosity] 那真正该问的是：每种情况耗时都不一样，这东西怎么提前规划？答案很干脆：规划不了，所以 GPU 根本不规划。它的三条对策，没有一条在试图算准。第一，超量线程，一个 SM 上驻着几十个 warp，这个卡住就切下一个，延迟不是被消除的，是被别人的活盖住的。第二，记分板，硬件在运行时盯着操作数到没到，到了才发。第三，缓存本身就是一台猜测机器，它赌你还会再用一次。

[realization] TPU 走的是反方向：把不确定性从源头删掉。没有硬件缓存，就没有缓存缺失，也就没有可变延迟。VMEM 里的数在那儿，不是因为运气好，是因为编译器自己发的那条 DMA 把它放在那儿的，而且它也知道该在第几拍等。

[warmly] 这一句是上半段的落点：GPU 用总有别的活可干，来盖住不确定的延迟；TPU 用把不确定性删掉，来避免它。一个是统计学的答案，一个是确定性的答案。所以 TPU 没有 L2，不是缺功能。缓存是一台猜测机器，而一台编译期就把每一拍排好的机器，不需要猜。

[suggestion] 这也解释了为什么两边的调优没有一样东西是重合的。GPU 上你调的是怎么让别的活足够多：占用率、warp 数、访存合并。TPU 上你调的是怎么让编译器排得开：对齐、分块、双缓冲。不过也别把它读成两边越走越远。现在追峰值的 CUDA kernel，用异步拷贝、显式 barrier、自己管双缓冲，那就是在 GPU 上手写一个静态调度。一旦你真的要峰值，猜就不够用了。

[friendly] 这一节就到这里，大家有问题吗？
