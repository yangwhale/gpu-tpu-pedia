First, guess a number

Feed DeepSeek V3 a 128K-token document, one prefill: it reads everything, generates nothing yet.
After that pass, one thing must stay in HBM: every later token looks back at the K and V of every earlier token in every layer. That is the KV cache.
How large is the one this prefill leaves?
For scale: one TPU v7 device has ~94.74 GiB of usable HBM. (Throughout, “device” means one such device; each v7 chip holds two.)

The answer is 8.58 GiB: 9% of one device.
The other three are real too: four ways of storing K and V, four generations of attention. Same model, same document; only “values stored per token per layer” changes, and the answer spans 128×. All of Step 2 lives in the gaps between these four.

Why the KV cache, unlike everything else, scales with layer count Intermediate results die once used: layer 3's activations are useless after layer 4 consumes them. They live one layer, so no layer multiplier.
The KV cache is different. Token n+1 needs the K and V of all n earlier tokens in every layer. So it lives for the whole conversation, is multiplied by 61 layers, and grows linearly with length, never freed.
One-line test: does the next token still need it? Yes → KV cache. No → drop it.

The four options are four ways to store K and V, all at 128K, 61 layers, bf16:

MLA sits between GQA and MQA in size, yet should beat both on quality. (The paper never pits MLA directly against GQA or MQA; this is inferred by chaining two of its ablation tables. See Step 2.) 8.58 GiB is 9% of one device.
One means “first, find more machines.” The other just fits.

The point isn't the numbers but deriving them yourself, and the counterintuitive things on the way. This lecture follows one token end to end, doing the math at each step.

Why DeepSeek V3

The GPT-3 175B era is long gone.

The gold standard

Most later open models start from it. To show what a modern LLM looks like, dissecting this one beats surveying ten.

Three wins at once

MLA shrinks the KV cache, fine-grained MoE the active parameters, FP8 the training cost.

Each hits a hardware bottleneck

HBM, compute, bandwidth: three bottlenecks, three answers. This course builds that chain.

⭐ “The standard” is checkable, not an opinion Tencent's Hy3 (Hunyuan 3, 295B/21B), open-sourced in 2026, copies V3's MoE field by field: sigmoid routing, auxiliary-loss-free expert bias, a shared expert, MTP, even the same config field name for “keep the first k layers dense.” Only attention changed: GQA instead of MLA.

From text to vectors

No compute, one table lookup. Yet a chunk of HBM is gone.

Tokenization: why 129,280

First, context: on one axis with its contemporaries' vocabularies, it is nothing special.

Expand: what “two bigger tables” costs— why V3 can afford 129K, a small model can't

A vocabulary matrix's size depends only on vocab × d, not on the layer count. So the deeper and larger the model, the smaller its share.

// V3: embedding + output table (no weight sharing, tie_word_embeddings = false) 129,280 × 7,168 × 2 = 1.853B → of 671B: 0.28% // Counterexample: the same 129,280 vocab in a small model, d = 2,048, 12 layers 129,280 × 2,048 × 2 = 530M // both tables 12 × 12 × 2,048² = 604M // model body at 12d² per layer, order of magnitude only → vocab is almost half

So the “bigger tables” cost in the figure barely holds V3 back. The real costs are undertrained rare words and a more expensive output softmax.

What the research says A paper on vocabulary scaling laws (Scaling Laws with Vocabulary: Larger Models Deserve Larger Vocabularies, NeurIPS 2024, arXiv 2407.13623) concludes that most LLMs' vocabularies are too small. Its fitted formula puts Llama2-70B's optimum at 216K or more, against an actual 32K; at the same compute budget, raising the vocabulary from 32K to 43K lifts ARC-Challenge from 29.1 to 32.0.
⚠️ One limit: the paper fits dense models from 33M to 3B. Extrapolating it to a 671B MoE has no basis. It points toward “bigger,” not that 129,280 is optimal for V3.
Rare words that never get learned have a name: under-trained / glitch tokens (arXiv 2405.05417; the famous SolidGoldMagikarp is one).

Why the width is 7,168

Remember d = 7,168, the model's main highway width; every later step uses it. Why: 7,168 = 128 × 56 = 256 × 28. It divides evenly both ways, so neither TPU nor GPU wastes compute on padding.

Expand: hard constraint vs. DeepSeek's own call— easy to conflate

The constraint (hard): it must align with the hardware's matrix units. A TPU MXU is a systolic array, 256 × 256 on v6e and TPU7x, 128 × 128 on earlier generations. NVIDIA recommends dimensions in multiples of 8 for FP16 and of 64 on A100. 7,168 divides by both 128 and 256, so neither side pads. No one picking this number escapes it.

The trade-off (soft): for a fixed parameter budget, wider or deeper. Every model makes that call afresh, and DeepSeek has never publicly said how it arrived at 7,168.

Don't present a constraint as a reason Alignment explains only why it isn't 7,000 or 7,200, not why it isn't 6,144 or 8,192, which divide just as evenly. Merge them into “so they chose 7,168” on stage, and any expert will call you on it.

Embedding: a lookup, at least by default

Fetch the token id's row from the 129,280 × 7,168 table. On this path, compute is zero. But real frameworks don't always do a lookup; expand below.

// embedding matrix parameters 129,280 × 7,168 = 926.68M → 1.73 GiB // size of the tensor after the lookup 131,072 × 7,168 × 2 B = 1.75 GiB
Expand: how true is “a lookup, not a matmul”?— in production configs it is often a real matmul

Mathematically it is equivalent to a one-hot vector times the embedding matrix. Intuitively, nobody would do that multiply: it costs 129,280 multiply-adds per output value. Yet real training frameworks ship both paths, behind an explicit switch.

// MaxText layers/embeddings.py — both branches are in the source if cfg.use_iota_embed: iota = lax.iota(jnp.int32, self.num_embeddings) one_hot = jnp.array(inputs[..., None] == iota, dtype=self.dtype) output = jnp.dot(one_hot, embedding) // ← really does the matmul else: output = embedding.at[inputs].get() // ← gather, zero compute

In base.yml the switch defaults to false, i.e. gather. But 34 production configs in the repo explicitly turn it on, and none explicitly turns it off. So do GPU model configs (llama3, mixtral), not just TPU ones. Default and actual usage are opposites.

With it on, how much compute does this step cost? Exactly as much as lm_head in the summary table at the end of the page, because the two matrices have the same shape: one maps 129,280 → 7,168, the other 7,168 → 129,280. Later on we call them mirror images. With a lookup, the mirror holds only for parameter count; with a matmul, it holds for compute as well:
2 × 129,280 × 7,168 = 1.85 GFLOP / token // whole sequence = 242.92 TFLOP, of the full step's 52.50 PFLOP: 0.46%

Precisely: “zero compute” holds only for the gather path. The other compiled path isn't zero; the denominator is just large enough that 0.46% vanishes into the noise. Why spend that compute at all? It turns an irregular, sparse row fetch into a regular dense matmul, shardable along the vocabulary dimension, and makes the backward pass a matmul too. That is the most plausible explanation, not one stated in any public source; don't treat it as settled.

Memory is the same on both paths: the table stays resident and the fetched tensor takes space too (figure on the right).

⚠️ Easy to get wrong: d isn't tied to the head count by divisibility

In standard MHA, hidden = heads × head_dim must hold. In V3 it doesn't, by a wide margin.

Expand: this figure also explains a recurring fact— why o_proj is a layer's largest block

o_proj is the largest weight in an MLA layer (117.44M, 63% of the layer). Nothing special: it just spans the gap above, 16,384 in and 7,168 out.

o_proj = 16,384 × 7,168 = 117.44M MLA weights per layer = 187.11M → 117.44 / 187.11 = 62.76%

More important: once that gap opens, the head count and d can be set independently. That is what lets Step 2 keep all 128 heads.

The first number that makes you sit up Before layer 1, turning tokens into vectors already takes 1.75 GiB. And this tensor isn't discarded after use: it is the residual stream, read and written once by each of 61 layers.

MLA: attention and the KV cache war

The heart of the lecture and of V3. Budget 15 minutes.

The weak spot: a runaway KV cache

Attention lets every token look at all earlier tokens. To avoid recomputing their K and V, we keep them around. That is the KV cache. Its size:

KV cache = seq length × layers × values per token per layer × bytes ↑ linear ↑ linear

Multiply two linear terms and you get a disaster. 4K → 128K tokens is 32×, then × 61 layers. That is why long context forces attention to change.

“Disaster” is vague. Build it step by step.

Startling enough to memorize Stored this way, one conversation of 25,446 tokens fills a whole TPU v7 device (94.74 GiB) with cache alone. No weights are loaded yet, and that is one user.
With MLA, the same device holds 1,447,608 tokens.

Training's bill is activation memory, and at this scale recomputation is maxed: a layer keeps only its input residual stream; the 128-head K/V are recomputed, used, discarded. MHA and MLA store the same stream: a tie.
Not “MLA saves training memory too”, nor “useless for training”: it pays off in two other places. With recomputation relaxed a notch, store the 512-dim latent, not 32,768 values; context parallelism passes the latent around its ring instead of K/V: a communication saving, not memory. Both in Topic 4.

How MLA actually works

Compress on write, expand on read. Not 128 per-head copies of a token's KV but one 512-dim latent; at attention time a matrix expands it to 128 heads.

First, what RoPE is Attention is blind to order: shuffle a sentence, same result. Order must be supplied. RoPE rotates the vector by a position-dependent angle instead of adding to it: token 1 by 1°, token 100 by 100°. (A simplification: in reality the vector's dimensions are paired, and each pair turns at its own rate. The fastest pair turns 1 radian per position; the rates slow from there, and the slowest pair takes many positions to complete one turn.) A dot product then carries the angle difference: relative distance.

Why position needs its own path. The angle depends on position. Rotate, then compress, and position leaks into the latent; stuck between two matrices, the rotation can't be moved out: matmul doesn't commute.

Precisely: correctness survives; it trains and runs. A valuable inference shortcut breaks: each new token recomputes every earlier K. Which shortcut: see the shape chain below.

So V3 splits each head: 128 dims without position (compressed), 64 dims with it (stored raw).

576 = 512 + 64 All MLA stores per token per layer, independent of head count: 128 heads or 256, 576 values.

⭐ An easy trap: 7,168 and 16,384

Almost everyone first computes 7,168 ÷ 128 heads = 56. That hides two misconceptions; the second is deeper.

Misconception 1: V3 heads are 56-dim Each head is 128-dim. 128 of them give 16,384, 2.29× the residual width. On V3 the two differ.
Misconception 2: “128 slices of 56” (the worse one) The input is never split. Each head reads all 7,168 dims through its own 7,168 × head_dim matrix into its own space.
The “split” is on the output side: the heads' outputs concatenate, and that width is 7,168 or 16,384.
Even in a standard model the division means “the concatenation equals the input width,” not “the input was divided.”

The section rests on this. See it, and “why wider heads?” answers itself: each head's matrix is 7,168 × d_h; d_h was always free.

Where the rule came from

A choice, not a definition, in the 2017 Transformer paper. §3.2.2 writes W^O ∈ R^(h·d_v × d_model): the two never had to match.

The next sentence: “In this work we employ h = 8 … we use d_k = d_v = d_model/h = 64.” “In this work”: a chosen value, not a rule. The reason is plain:

The reason given in the paper (Vaswani et al., 2017 · arXiv 1706.03762) “Due to the reduced dimension of each head, the total computational cost is similar to that of single-head attention with full dimensionality.”
A compute budget, not a mathematical necessity.

Seven years of copying made it intuition. It was only a convention.

Why V3 can widen

In standard attention, wider heads cost cache: each head stores K and V, 2 × heads × head_dim. Width and cache are locked, linearly.

MLA cuts the lock. The MLA paper's Table 1 gives all four cache formulas; MLA's is (d_c + d_h^R) × layers, no head count, no head dim.

A new degree of freedom Attention as wide as you like; KV cache unchanged to the byte. Expressiveness and cache cost are, for the first time, separate knobs.

Evidence: DeepSeek-V2, MLA's debut, has a 5,120 residual stream but 128 × 128 = 16,384 attention, 3.2×, bolder than V3. (DeepSeek never claims causation, but two generations alike is hardly coincidence.)

⭐ The full shape chain: [128K, 7168] to Q / K / V

Now every step in the layer. In and out: [128K, 7168]. Between, three very different paths: Q, K, V.

① Q path: down, then up

Q: two projections, narrow waist. q_a_proj takes 7,168 to 1,536, Q's latent; after RMSNorm, q_b_proj lifts it to 24,576; a view makes 128 heads × 192.

Easy to misremember: 24,576, not 12,288 Each head is 192-dim, not 96 or 128. 192 = 128 (unrotated) + 64 (rotated).
So q_b_proj has shape [1536, 128×192] = [1536, 24576]. 128×128 = 16,384 is the output-side width (v_head_dim × heads), at o_proj's input, not here.

Then each head's 192 dims split: first 128 (q_nope) untouched, last 64 (q_pe) get RoPE. Rejoined, query_states is final: [128K, 128, 192].

No byte of Q is cached. Its compression only saves weights and training activations (see the cost table).

② KV path: store 576, compute the rest on the fly

K and V share one down-projection. kv_a_proj_with_mqa takes 7,168 to 576, split at once: first 512 c_KV (shared K/V compression), last 64 k_pe (the position strip).

⭐ The key sentence of the page Only these two blocks are cached: 512 + 64 = 576. Everything downstream (k_nope, value, key_states) is computed on the fly, never stored.
The MLA paper's formula: cached elements = (d_c + d_h^R) × layers, with neither head count nor head dim in it.

After RMSNorm, kv_b_proj lifts c_KV to 32,768; a view makes 128 heads × 256, halved: first 128 k_nope, last 128 are V. value_states is final: [128K, 128, 128], never touching RoPE.

k_pe, after RoPE, is broadcast, one copy, to all 128 heads and joined to each head's k_nope: key_states is final: [128K, 128, 192], matching Q.

③ Why RoPE needs its own 64-dim branch

MLA's most convoluted, most skipped part. Why not encode position across the whole vector? Because the cache just saved would be given right back.

If all of K carried RoPE Inference's elegant shortcut: fold K's up-projection into Q's matrix in advance. K is never materialized; Q scores directly against the cached 512-dim c_KV.
But RoPE, a position-dependent rotation, would sit between them. Matmul doesn't commute; the middle can't be moved out, so the fold breaks.
Result: every new token must recompute every earlier token's K.
Expand: the paper's words— DeepSeek-V2 §2.1.3
“RoPE is incompatible with low-rank KV compression … W^UK cannot be absorbed into W^Q any more during inference, since a RoPE matrix related to the currently generating token will lie between W^Q and W^UK and matrix multiplication does not obey a commutative law. As a result, we must recompute the keys for all the prefix tokens during inference …”

Note the last sentence, we must recompute the keys. The paper says “must recompute,” not “will compute the wrong answer.” What breaks is efficiency, not correctness. This matters at the podium: say “the result would be wrong” and anyone who knows the material will correct you.

The fix: position on a side path

Split each head's vector into two jobs:

Dot products add: [a;b]·[c;d] = a·c + b·d. One 192-dim dot product equals “content similarity” plus “positional relevance,” computed apart. No interference; each half keeps its math.

Nearly free The position strip is 64 dims, one copy for all 128 heads (hence [128K, 1, 64]).
64 cached values buy “no K recomputation”: the 64 in 576.
One per head would add 128 × 64 = 8,192: 576 → 8,704, and MLA would be pointless.
Expand: why Q's 64 dims aren't shared— cost, not math, decides
Position belongs to the token, not the head; the rotation angle is the same for every head. So why does K share one copy while Q has 128 (128 × 64 = 8,192)?
Because those 64 dims aren't pure position. Equation (14) of the paper is RoPE(W^QR · c_Q): first project a vector from the content, then rotate it. The 128 heads use different rows of that projection matrix, so the angle is the same, but what gets rotated differs.
Expand the position term's dot product to see it (rotation matrices are orthogonal, so R_t transpose × R_s = R_(s−t)):
// head i, query at position t, key at position s (R_t · a_i) · (R_s · b) = a_i transpose × R_(s−t) × b // middle term depends only on relative distance
The middle depends only on relative distance; the two sides are content. a_i differs per head, so each head gets a different “distance → score” curve. Some heads can focus on the nearest tokens; others can look far back for a match. Share one copy and all 128 heads get an identical position term.
⭐ But what actually decides it is cost, not expressiveness: Q never goes into the cache, so sharing saves nothing: you'd lose expressiveness for free. K does go into the cache, and sharing shrinks 8,192 to 64: a loss worth accepting.
So the asymmetry is not a mathematical requirement but a cost decision: compromise only on the side that costs money.
Caveat: the fold is an inference optimization, not the model definition The reference implementation (Hugging Face's modeling_deepseek.py) materializes K and V, then runs attention. The figure draws that path: the math definition.
Absorbing the up-projections into Q and o_proj is an equivalent rewrite done only by fast inference engines. Leaving room for it is why RoPE was isolated at design time.
The paper (V2, end of Appendix C): “due to the associative law of matrix multiplication, we can absorb W^UK into W^UQ, and W^UV into W^O. Therefore, we do not need to compute keys and values out for each query.”
Expand: are the “128 heads” real or bookkeeping?— heads have a lifecycle

A natural question after the chain: the weights are a few big matrices from start to finish, and view never moves a single value. So are the 128 heads just bookkeeping?

In the projections: yes, pure bookkeeping q_b_proj is one block, 1,536 × 24,576; kv_b_proj is one block, 512 × 32,768; o_proj is one block, 16,384 × 7,168.
No 128 small matrices, just three big ones. view / reshape only changes how data is read: zero data movement, zero compute.
“Head i's projection matrix” is just the i-th column group of the big matrix.
In scoring: heads are physical, and they can't be merged Without heads, one dot product of the full 24,576-dim Q and K gives each token pair one score.
With 128 heads, each token pair gets 128 scores, each head then runs its own softmax and weights its own slice of V.
The results differ completely, and the second can't be written as one big matmul, because softmax is nonlinear and runs inside each head separately. Linear operations merge in any arrangement; once a nonlinearity is applied per group, the groups can't be stitched back.

Precisely: a head has a lifecycle. At the view it only gets a name. It is truly alive during scoring and softmax. At o_proj it dies: that 16,384 × 7,168 matrix is the only place the 128 heads ever exchange information. Both ends are single blocks; only the short stretch in the middle is real.

The hardware shows it too: the projections are large, regular matmuls, the kind accelerators like best. Scoring is batch × 128 small matmuls batched together, with inherently lower arithmetic intensity, one reason attention has long been a performance bottleneck.

⭐ Why so much compression? The 32,768 never existed

56.9× looks like magic; magic has a trick. Most of it isn't compression, just not being wasteful.

Cut 1: 32,768 values, 7,168 degrees of freedom

Standard MHA stores 2 × 128 heads × 128 dims = 32,768 values per token per layer. Where do they come from?

All from the same 7,168-dim input. K and V are each a 7,168 × 16,384 matrix times h. A 7,168 × 16,384 matrix has rank at most 7,168.

Provable, not a hunch The 32,768-dim vector always lies in a ≤7,168-dim subspace.
Store those 7,168 values (the input) and K and V rebuild bit for bit.
So 4.57× of standard storage is pure redundancy; cutting it isn't compression.
Why did nobody store just the input? Recomputation. Store only h and each new token re-multiplies every earlier K and V. Memory saved, compute paid.
MLA's real contribution: that recomputation almost never happens (matrix absorption), so the 4.57× is collectible at last.

Cut 2: cap the rank at 576, the real compression

The rest, 7,168 → 576, 12.44×, is real and lossy, but compresses rank, not value count.

MLA's bet: the 128 heads together need at most 512 information channels.

⭐ Q, K, V in hand: how attention plays out

Everything so far prepared these three tensors. Now attention does its actual work.

Intuition: at a sentence's fifth word you glance back at the first four and judge which matter most. Scoring computes that, with 128 heads applying their own criteria at once.

① Dot product: who should look at whom Dot the current Q with every K. Aligned: large (“look closer here”); unrelated or opposite: small or negative.
Each head separately: 128 matrices of 128K × 128K.
② ÷ √192: no magic, anti-saturation A sum over 192 dims grows with dimension. Raw into softmax, it saturates: one position takes nearly all weight, the rest go to 0, and gradients vanish.
√d restores the range. 192, not 128: each Q/K head is “128 unrotated + 64 rotated.”
Expand: two details of “÷ √192”— skippable in class, but don't get them wrong
Two details worth being pedantic about ① The original paper phrases this step as “we suspect,” not “we prove.” Attention Is All You Need §3.2.1: “We suspect that for large values of d_k, the dot products grow large in magnitude, pushing the softmax function into regions where it has extremely small gradients”. A footnote argues heuristically: with independent components of mean 0 and variance 1, the dot product has variance d_k, so dividing by √d_k restores standard deviation 1. A useful intuition, but a conjecture, not a theorem.
② In V3's actual code the factor is not 1/√192. With YaRN enabled for length extrapolation (original_max_position_embeddings = 4096, factor = 40, 4,096 × 40 = 163,840), the scale is also multiplied by mscale²:
mscale = 0.1 × ln(40) + 1 = 1.3689, 1/√192 × 1.3689² = 0.1352, not 0.0722: a 1.87× difference. Same principle; the constant is tied to long-context extrapolation.
Source: the * mscale * mscale after softmax_scale = q_head_dim^(-0.5) in the reference implementation modeling_deepseek.py, and the definition of yarn_get_mscale(). Also, 163,840 is the config's position limit, while 128K is the advertised usable length; they differ.
③ Mask: correctness, not optimization Position 5 can't see 6: upper triangle = −∞, which softmax zeroes.
Unmasked, the model copies the answers: training converges beautifully; inference, lacking later tokens, collapses at once.
④ Softmax: scores into “how much to take” Rows normalized to sum to 1: each a probability distribution, “29% of my info from position 1, 47% from position 5.”
Softmax is nonlinear, per row and per head, so the 128 heads can never merge back (the previous section's point).

⑤ Weighted sum, ⑥ concatenate, exit. Step ④'s weights sum V; each head emits 128 dims. Concatenated: 16,384, which o_proj folds to 7,168 into the residual stream. o_proj is the largest matrix in the layer (117.44M, about 60% of an MLA layer), and the only place heads exchange information; before it, each computes alone.

A different kind of compute Projections (Q/K/V, o_proj) are big regular matmuls, [128K, 7168] × [7168, N]: static shapes, high arithmetic intensity, accelerator heaven.
Scoring is 128 small batched matmuls around a row-wise reduction (softmax), and quadratic in length: 2× sequence, 4× work.

FLOPs: when the square term takes over

Two parts of attention are quadratic in length: scores (QKᵀ) and the weighted sum (AV). All else (projections, MLP, MoE) is linear.

Negligible when short, all-consuming when long. The crossover is computable.

At 128K, the attention quadratic term takes 81.8% of forward compute. At this scale, sequence length, not parameter count, dominates compute. Push the slider at the top to 1M and it becomes 97%.
What happened next The curve dictates the next move: if attention eats more than 80% of compute (82% at 128K, 97% at 1M), stop every query seeing every token. V3.2's DSA: each query picks its 2,048 most relevant tokens and attends to those (index_topk = 2048, in V3.2's own config). At 128K that's 1.6%; quadratic becomes linear.
V4 is a hybrid of two attentions: Compressed Sparse Attention (compression + sparse selection) and Heavily Compressed Attention (harder compression, no selection, global view). At 1M tokens, V4-Pro needs 27% of V3.2's per-token inference FLOPs and 10% of its KV cache. (DeepSeek-V4 paper abstract, arXiv 2606.19348. Two kinds, not three; an earlier version erred.)

Their designs and trade-offs belong to Topic 3. This lecture only shows why change was unavoidable: the curve above.

Dense MLP: what “not sparse” looks like

first_k_dense_replace = 3: V3's first 3 layers are ordinary MLPs. Dense first: it shows what MoE saves.

Three matrices + one gate

Widen, open a valve, project back. Three matrices, each 7,168 × 18,432: 396.36M parameters per layer, 1.19B for all three.

The shapes are fixed, independent of input and sequence length. All four advantages below follow.

Expand: the formula— the gold × sign, written out
gate = W_gate · x // 7168 → 18432 up = W_up · x // 7168 → 18432 h = SiLU(gate) ⊙ up // elementwise multiply out = W_down · h // 18432 → 7168

⊙ is an elementwise multiply, not a matmul: two 18,432-dim vectors multiplied position by position give another 18,432-dim vector. SiLU(z) = z · σ(z); the config field is hidden_act: "silu".

Four hardware-friendly properties

① Every token takes the same path→ static shapes
② One big matmul→ high utilization, MXU's favorite
③ No communication to assign work→ no scheduling overhead
④ Compiler plans it all ahead→ no runtime uncertainty

MoE keeps none of them; we'll revisit each. In Step 4 they become: shapes unknown until routing ends (the dropless section wins this back); one matmul shattered into 257; two extra all-to-alls; a compiler reserving for the worst case.

Why three matrices, not two?

The most common interruption here, and a fair one. A classic MLP has only two: widen, fixed nonlinearity, project back. But that nonlinearity is fixed: one rule for every input and channel.

SwiGLU widens twice: one copy is the valve, one the flow, multiplied elementwise. Which channels pass, and how much, becomes learned and input-dependent.

The key isn't SiLU. It's the multiply. The same paper's Bilinear variant multiplies two paths with no activation: a strict quadratic form in x. It still beats every activation-only swap. Expressiveness comes from multiplying two linear maps, not a cleverer activation.

One experimental table backs this. Eight variants, equal parameters and compute: watch the two groups.

Honestly: even SwiGLU's authors can't say why it works The paper's conclusion, verbatim: “We offer no explanation as to why these architectures seem to work; we attribute their success, as all else, to divine benevolence.”
Plainly: no explanation. So “the multiply adds interaction terms” is plausible intuition, not proven cause. The table shows only this: gating wins, and not via the activation.

Expand: why the first layer?— labeled speculation

Up front: this explanation is not in the paper; it is our inference.

A router is a linear projection of the hidden state followed by top-k, so tokens with similar hidden states necessarily go to the same experts. In the first layer the hidden state, not yet mixed by attention, is essentially the embedding plus some positional information. The same word looks nearly identical in any context.

So in the first layer the router degenerates into assignment by vocabulary ID. High-frequency words (commas, the, “of”) dominate and flood the same expert in batches. The load can't balance; the cause is the data distribution itself. The aux loss has to fight it, so slow convergence is no surprise.

⚠️ It has a single source; don't treat it as a law “The first layer is hardest to balance” comes only from DeepSeekMoE's own experiments; this course found no public cross-model, cross-dataset comparison that confirms it.
So all we can say is “in that setup, the first layer was hardest to balance.” Change the model, the data or the aux-loss coefficient and it may no longer hold: which layer is hard to balance can't yet be taught as a general rule. That also explains why labs keep 0 to 3 dense layers: their experiments really did differ.
Wrap-up: what is this design for? ① The only public starting point: DeepSeekMoE observed that first-layer load balance converges especially slowly.
② No one has explained the mechanism; V3's move from 1 to 3 is unexplained too.
③ Far from consensus: at least three mainstream peers keep no dense layer.
④ One free benefit: shallow dense layers need no all-to-all, so they can be deployed separately at 1-way tensor parallelism, saving communication.

4a · Where the sparsity lies

The only thing MoE buys you It decouples parameters from compute. Parameters grow to 671B (more knowledge); per-token compute stays dense-level (affordable).

⭐ Each token takes its own path

That is what “the life of a token” means: all 58 MoE layers triage afresh, so each token traces its own path.

Why sparsify the MLP and not attention

First, the MLP holds most parameters: per the tables above, 187M per MLA layer, 396M per dense MLP, 11.32B per MoE layer. Second, the MLP is a pile of independent problems: it acts on each token alone, so tokens can safely take different routes. Attention exists to let tokens see each other; it can't be split.

4b · Routing: how the 8 are chosen

⭐ Keep this: scheduling stays out of the output Load balancing is scheduling; quality is learning. V3 puts them on disjoint paths.

Three consequences: ① push the bias as hard as you like, the output stays true; ② outside backprop, it steals no gradient from the main objective; ③ it acts outside the training loop, so policy changes leave the model alone.

(The paper, verbatim: “Note that the bias term is only used for routing. The gating value, which will be multiplied with the FFN output, is still derived from the original affinity score.” —arXiv 2412.19437, Section 2.1.2. Two scores, two paths.)
Expand: sigmoid scores “don't sum to 1,” yet the 8 final weights sum to 1. Contradiction?—you will be asked

No, because they happen at two different moments. “Doesn't sum to 1” refers to scoring: each of the 256 scores is computed on its own, and none affects another. “Normalized to 1” refers to after selection: the proportions are redistributed among the chosen 8 only.

// ① Score: 256 independent sigmoids, unrelated to each other, any total is fine s_i = sigmoid(u · e_i) i = 1 … 256 // ② Select: add the bias only for ranking, pick 8 indices (the bias stops here) // ③ Weight: normalize over these 8 only, then multiply by routed_scaling_factor g_i = s_i / Σ(s of the 8 selected) × 2.5

So what actually changes between softmax and sigmoid? Step ①. Softmax's denominator covers all 256 experts, so raising any one expert's score pushes down the other 255: a forced zero-sum competition. Sigmoid has no such denominator; each expert independently says “I'm good at this token.”
Competition is deferred to the “rank and take the top 8” step instead of being baked into scoring. V2 used softmax; V3 switched to sigmoid, as the paper states explicitly.

Where the 2.5 comes from: routed_scaling_factor in the config. Normalization pins the sum of the 8 weights to 1, and the shared expert's branch has a coefficient of 1, so the combined output is small relative to the residual stream; a constant greater than 1 restores the branch's magnitude. That is our reading. The coefficient appears only in the open-source config and implementation, not the paper's formulas.

Expand: the rule in the paper, and where the 2 in “top 2 per group” comes from—a number you can derive
The paper, verbatim “Like the device-limited routing used by DeepSeek-V2, DeepSeek-V3 also uses a restricted routing mechanism to limit communication costs during training. In short, we ensure that each token will be sent to at most M nodes, which are selected according to the sum of the highest Kr/M affinity scores of the experts distributed on each node.”
—DeepSeek-V3 Technical Report, arXiv 2412.19437, Section 2.1.2. The stated reason leaves no ambiguity: “to limit communication costs.”

The “top 2” isn't arbitrary; plug in the numbers. The paper writes Kr/M, where Kr is the number of activated routed experts and M is the maximum number of nodes a token may reach:

// K_r = num_experts_per_tok = 8 M = topk_group = 4 K_r / M = 8 / 4 = 2 ← hence “sum of the top 2 in each group” as the group score

The rule makes sense: if a token can reach at most 4 nodes and must pick 8 experts, each node has to contribute 2 on average. Scoring a group by the sum of its top 2 asks, “if I pick this node, how much do its best 2 give me?” That is exactly the share you will take from it.

A telling aside: this communication design has headroom The paper, verbatim: “although DeepSeek-V3 selects only 8 routed experts in practice, it can scale up this number to a maximum of 13 experts (4 nodes × 3.2 experts/node) while preserving the same communication cost.” The same passage: this IB/NVLink overlap scheme needs only 20 SMs.
Read it as: set “at most 4 nodes” from the shape of the machines, then see how many experts fit in that box. They filled it with 8; the box holds 13. The plainest instance of “hardware draws the line, the model picks its parameters inside it.”
Why this design matters The old way adds an imbalance penalty to the loss. That makes the model optimize two unrelated goals at once, “answer correctly” and “spread evenly.” They pull against each other; both lose. The paper agrees: a large auxiliary loss impairs model performance.

V3 moves the main burden of balancing out of the loss, into scheduling outside the training loop, independent of what the model learns. Good engineering instinct: a constraint that isn't the objective stays out of it.
⚠️ “Auxiliary-loss-free” is tidier than the truth This page once said V3 uses no auxiliary loss; per the paper, that overstates it. The paper: “Although DeepSeek-V3 mainly relies on the auxiliary-loss-free strategy for load balance, to prevent extreme imbalance within any single sequence, we also employ a complementary sequence-wise balance loss.” Its factor α “will be assigned an extremely small value for DeepSeek-V3.”
Accurately: the bias does the main work; a tiny auxiliary loss is the backstop. Not “none at all.”

⭐ Imbalance: one device busy, all wait

Experts live on different devices. If a few are hot, their devices take more tokens while the rest idle. The layer ends when the slowest device does.

4c · Move tokens, or weights?

The systems highlight of the topic. Experts sit on different devices; a token needs expert #137. Two options: a genuine either/or.

⚠️ An easy misnomer: Scheme B is not AG‑RS All-gathering expert weights to every device is real, and right on TPU, but it is called “EP = 1 + FSDP,” or just “no expert parallelism.”
In MoE, AG-RS is something else: an all-to-all alternative that also moves tokens, replicating every token to every device, routing locally, then reduce-scattering results back. Two independent implementations agree: in Megatron-Core's flag --moe-token-dispatcher-type, all three values, allgather / alltoall / flex, are token dispatchers; MaxText calls this path ring of experts.

The “move tokens or weights” split stands; only the second label was wrong. All three paths' mechanics and traffic, and why TPU picks the most-bytes one, get a full appendix section (Chinese edition): §14 How tokens meet their experts →

⭐ 4 copies, not 8: the unit of movement is the destination, not the expert The tempting intuition: 8 experts selected, so send 8 copies. Wrong.
The copies sent depend on how many places a token lands. Two selected experts on the same node share one copy. Once there, it is fanned out over the intra-node interconnect, not across nodes.
And the number of destinations is fixed: group routing (topk_group = 4) guarantees a token lands on at most 4 nodes. So the multiplier is 4, not 8.
One-line test: it doesn't depend on top-k. Top-k 8 → 16, still at most 4 nodes: cross-node traffic grows not one byte.
The paper settles it—8 to 13 experts, same communication cost

“…we limit each token to be dispatched to at most 4 nodes, thereby reducing IB traffic. For each token, when its routing decision is made, it will first be transmitted via IB to the GPUs with the same in-node index on its target nodes. Once it reaches the target nodes, we will endeavor to ensure that it is instantaneously forwarded via NVLink to specific GPUs that host their target experts… This implies that, although DeepSeek-V3 selects only 8 routed experts in practice, it can scale up this number to a maximum of 13 experts (4 nodes × 3.2 experts/node) while preserving the same communication cost.”
—DeepSeek-V3 Technical Report, arXiv 2412.19437, Section 3.2.2.

The last sentence decides it: 8 → 13 for free. Were traffic proportional to experts, 5 more couldn't be free. It must be proportional to nodes, locked by M = 4.

The same section gives the layout: 256 routed experts evenly over 64 GPUs on 8 nodes (4 per GPU, 32 per node), with M = 4. So the “8 groups” are the 8 nodes, and a token goes to at most 4 of them.

One refinement: one of those 4 destinations may be the token's own node, and that copy never touches the network. Choosing 4 of 8 nodes, the chance the home node is chosen is 1/2, so the expected number of cross-node copies is 3.5, not 4. The calculation above conservatively uses 4: an upper bound that never understates the traffic.

Over the layer's compute, it gives the communication-to-compute ratio: can compute hide communication? It underpins Topic 7's performance lecture.

⭐ Why it's a real either/or: two slopes

Where the crossover comes from: two steps
// A: bytes moved per token per layer (there + back) // 4 = max nodes a token lands on (topk_group), not 8 experts; see the red box above 2 × 4 copies × 7,168 × 2 B = 112 KiB // B: one layer's expert weights (256 routed + 1 shared, three-matrix SwiGLU) 257 × 3 × 7,168 × 2,048 × 2 B = 21.08 GiB // token count where they're equal 21.08 GiB ÷ 112 KiB = 197,376
Mind the limits: a rough comparison reducing both to “bytes moved per layer.” Real all-to-all and all-gather differ in efficiency, and it depends how many devices hold the experts: wider spread, thinner A traffic, crossover further right.
So don't treat 197,376 as an engineering threshold. It shows the two schemes share an order of magnitude, which is what makes it an either/or.

⭐ Dropless: how static shapes were lost and won back

📄 This section has an appendix (Chinese edition) Dropless and grouped matmul On one device, both approaches with realistic numbers (16,384 rows per expert per step): why shapes must be regular, what MegaBlocks changed, whether to call it block-sparse or grouped GEMM, how padding to 128 relates to PagedAttention pages, and how far the evidence for V3's “no token dropping” goes.
Then three levels down: how the MXU stays fed (the HBM → VMEM → VREG pipeline), how tokens meet their experts (all-to-all / AG-RS / no EP, and why TPU picks the most traffic), and how much memory “rows × 8” takes, which few people compute.

Back to the dense MLP's first virtue: static shapes. Knowing all matrix sizes and buffers up front, the compiler schedules the whole graph.

MoE breaks that. How many tokens hit expert #37 is known only after routing, and changes next batch. But hardware wants it fixed up front.

The old fix is blunt: a fixed-size box per expert, and shapes are static again. The price: overflow is discarded, empty slots zero-padded.

Three MegaBlocks numbers (arXiv 2211.15841) ① Dropping tokens really hurts quality. In one controlled comparison, capacity factor 1 (drops) cut validation loss by only 0.15; no drops cut it by 0.26, 1.73× as much.
② Avoiding drops with a bigger box is expensive. The paper: “MoE-layer math operations increased by over 2× in order to avoid dropping tokens.”
③ And you can't know how big. Per Tutel: some models need capacity factor 11 to avoid drops; in others it spikes without warning mid-training.
So it isn't “just tune a parameter.” It is a hyperparameter you can't set, costly if wrong either way. Dropless deletes it.

4e · Sparse per token, dense per batch

“Compute pays only for 37B” needs one more twist: that is per token, and machines never process one token at a time.

Both true, about different things One token passes only 9 experts, not 257: sparse.
A batch, if large enough, lights up all 256: dense.
No single token activates every expert; the batch does.
So “MoE is fully activated after all” is exactly right on “must the weight bytes be read,” exactly wrong on “how many multiplies.” Every byte of the 671B weights crosses HBM; the FLOPs really are only 9/257.

Turning “dense” into a number

Density is a division, not an adjective. Rows per expert set the shape of its matmul:

// rows one expert receives this step rows per expert = total tokens in this step × 8 ÷ 256 = total tokens ÷ 32 // and what makes up “total tokens” training / prefill = batch × sequence length ← both count decode = batch × 1 ← the sequence-length leg is gone
32: this configuration's “dilution factor” 256 experts, 8 per token: each expert sees just 1/32 of the tokens fed in. More experts or smaller top-k dilute further: 384 experts, top-8, gives 48.

The hardware threshold: 128 rows

Matmuls run in tiles, not rows. In TPU's grouped matmul kernel, the bf16 tile height is 128 rows, hard-coded in the public source:

// MaxText megablox Pallas kernel (v2), calculate_tiling() bf16_bf16_tile_m = 128 // comment, verbatim: "128 is the largest tile_m value that is safe to use // for most scenarios" (raised for lower bit widths)

Back to 4c: EP changes segment length, not communication

This math settles something 4c left open. Per-device work in the two schemes has identical row counts:

// A · with EP: 4 experts per device, tokens gathered from 64 devices via all-to-all rows per device = 16,384 × 4 = 65,536 in 4 segments of 16,384 rows // B · without EP (EP=1 + FSDP): every device holds all 256 experts, computes only its own 8,192 tokens rows per device = 8,192 × 8 = 65,536 in 256 segments of 256 rows // exactly the same 65,536 rows; the only difference is how many segments
Why seams cost: TPU revisits tiles instead of padding Segment boundaries rarely land on multiples of 128. GPUs pad with zeros to the tile edge; TPU's megablox runs the straddling tile twice, with the left and then the right expert's weights, accumulating into one output.
The cost changes form: not “pad ≤ 127 zero rows per segment” but “≤ (segments − 1) extra tiles in total,” a bound stated in the source comments. Mechanism: appendix (Chinese edition) §11 · No padding on TPU.
// bound: tiles_m ≤ tiles executed ≤ tiles_m + segments − 1 tiles_m = 65,536 ÷ 128 = 512 A · EP ≤ 512 + 3 = 515 tiles → +0.59% B · FSDP ≤ 512 + 255 = 767 tiles → +49.8% ← upper bound
49.8% is an upper bound, not a given, but dropless can't escape it If all 256 segments were exactly 256 rows, every boundary would land on a multiple of 128: overhead 0. But equal segments are exactly the assumption dropless gives up. Segments are ragged, so nearly every boundary misaligns. The real value sits near the bound, not 0.
The takeaway EP's first value is long segments, not saved communication. It regathers each expert's tokens from 64 devices, growing each segment from 256 rows back to 16,384: 64× the segment length.
(64× is segment length, not efficiency: 0.59% versus a 49.8% upper bound is about 1.5×, far less, since in-tile waste was bounded anyway.)
FSDP's truly fatal cost lies elsewhere: each device assembles all 256 experts' weights, 21.00 GiB per layer (256 × 44.04M × 2 bytes), versus 336 MiB under EP.

Step 5

Between layers: the residual bus

So far, all inside one layer. Now: how 61 layers connect.

Snag: the middle line is the trunk, so why “residual” stream? Instinct says the added-back loop deserves the name, not the trunk. By the original definition, instinct is right. ResNet (He et al., 2015) has each layer learn residual functions with reference to the layer inputs. The residual is the branch, H(x) minus x; the trunk is the paper's shortcut connection (identity path).
“Residual stream” comes from another tradition, interpretability, which defines it as “simply the sum of the output of all the previous layers and the original embedding.”
So it isn't “residual = trunk”; it's “the stream of residuals,” possessive dropped. The trunk is the sum of the residuals, not a residual: x = embedding + layer 1's residual + layer 2's + … + layer 61's. Precise, just compressed.
Don't read “residual” as “leftover” Everyday “residual” means what remains; here it means “difference from the identity mapping”: an increment, not a remainder. Read “increment stream” and the section clicks: each layer adds an increment to a shared ledger, which is the sum of all increments.
Expand: both sources verbatim, and the trunk's other name—“residual stream” was chosen on purpose; its rival was “embedding”

① Residual = the branch. He et al. 2015, Deep Residual Learning for Image Recognition (arXiv 1512.03385), from the abstract:

"We explicitly reformulate the layers as learning residual functions with reference to the layer inputs, instead of learning unreferenced functions." // what the main text calls the trunk: "The formulation of F(x)+x can be realized by feedforward neural networks with ‘shortcut connections’."

② Residual stream = the sum of the residuals. Elhage et al. 2021, A Mathematical Framework for Transformer Circuits:

"each layer adds its results into what we call the ‘residual stream.’" "The residual stream is simply the sum of the output of all the previous layers and the original embedding."
Bonus: the trunk's other name is “embedding,” and they avoided it on purpose The same paper also says: “In transformers, the residual stream vectors are often called the ‘embedding.’ We prefer the residual stream terminology, both because it emphasizes the residual nature ... and also because we believe the residual stream often dedicates subspaces to tokens other than the present token, breaking the intuitions the embedding terminology suggests.”
So the trunk does deserve its own name, and it already had one: embedding. They dropped it on purpose: to stress that the stream holds residuals, and because it often reserves subspaces for other tokens, while “embedding” implies it describes only the current token.

Lineage: the same paper traces models built around a residual stream back to Schmidhuber's line (highway networks, the LSTM); ResNet brought their modern success.

The residual stream is a bus, not a pipeline

The usual picture is an assembly line: layer 1 → 2 → 3. It's closer to a bus. One 7,168-wide vector runs through the whole network; each layer reads it, computes, and adds the result back.

x = x + MLA(norm(x)) // add back, don't replace x = x + MoE(norm(x)) // ↑ these two lines × 61

Why addition. For gradients, it gives backprop a direct highway that doesn't fade across 61 layers. For meaning, it makes “do nothing” the default: a layer that hasn't learned yet outputs ≈0, and existing information survives.

Where RMSNorm sits: one placement decides whether you need warm-up

V3 uses pre-norm: normalize, run the sublayer, add its output straight to the trunk. Post-norm adds first, then normalizes the sum. That puts the norm on the bus, cutting the figure's “direct highway.”

Not taste: proven, and far more precisely than “it trains unstably.”

Expand: what the verifiable version of “post-norm is unstable” looks like—the finding is “do you need warm-up,” not “does it converge”

The source is Xiong et al. 2020, On Layer Normalization in the Transformer Architecture (arXiv 2002.04745). They analyzed both placements' gradients at initialization, with two parallel conclusions:

post-normAt initialization, gradients near the output layer are large. In the paper's words, this explains “why the learning rate warm-up stage is essential in training the Post-LN Transformer”: warm-up isn't a tuning trick, it's a requirement
pre-normGradients are well-behaved. The paper claims to be “the first to show that the learning-rate warm-up stage can be removed for the Pre-LN Transformer”: warm-up can be dropped entirely

So the claim isn't “post-norm can't be trained”; it's “post-norm adds one more thing you must get right.” A setting that blows up if wrong and gets harder to tune with depth is, at tens to hundreds of layers, “unstable training” in practice. When you repeat the claim, say which one you mean.

An often-unmentioned side benefit: with the norm off the trunk, the residual stream is pure addition end to end, and the backward gradient reaches layer 1 unchanged. The “bus vs. pipeline” figure above draws exactly this path. Post-norm puts a norm in every segment of the bus and breaks it.

A number that poses a question and half-answers it Saving the residual stream at all 61 layer boundaries takes 106.75 GiB: more than a single device, before any intermediate inside a layer. So why keep them?
Half the answer is in the V3 paper: it doesn't. Verbatim: “We recompute all RMSNorm operations and MLA up-projections during back-propagation, thereby eliminating the need to persistently store their output activations.” If it doesn't fit, don't store it; buy it back with compute in backward. That's trading time for space, not free. The other half (why backward needs these intermediates, how to price the trade) is in Topic 4. The reflex: when activations don't fit, ask not “how do I add devices?” but “must this be stored?”

A short detour: mHC, or how V4 widens the bus

So far: “one 7,168-dim bus.” The bus itself is a design choice you can change.  In V4, DeepSeek replaced it with mHC (Manifold-Constrained Hyper-Connections). The topic's one excursion beyond V3; it sits here because you need the bus to see what changes.

① What it actually changes

Residual state goes from Rd to R4×d. But each layer's input and output stay d-dimensional (“still 7,168-dim” above). Width is decoupled from hidden size: a new knob.

② What “doubly stochastic” buys

Rows and columns sum to 1: mixing is a convex combination, mean conserved, norm bounded. Products stay doubly stochastic, so 61 layers don't blow up. Sinkhorn-Knopp projects onto the set; V4 runs 20 passes.

③ ⚠️ The cost isn't where you'd expect

“4× wider → 4× activation memory” skips the engineering section. Per V4's paper, mHC raises activation memory and pipeline traffic; fused kernels, selective recompute and a reworked DualPipe overlap cut wall-clock overhead to 6.7%.

Expand: every number's source, and why V4-Pro maps directly onto this page—61 layers, 7,168 dims, identical to V3

First, a coincidence that makes the numbers directly comparable. V4 comes in two sizes. V4-Pro has 61 layers and hidden 7,168, exactly as V3; V4-Flash has 43 layers and hidden 4,096. Both use nhc = 4 and 20 Sinkhorn-Knopp iterations. So the 1.75 GiB bus above is exactly V4-Pro's.

// source: DeepSeek-V4 technical report (arXiv 2606.19348) §4.2.1, model configuration V4-Pro layers = 61 d = 7168 n_hc = 4 t_max = 20 1.6T total / 49B active V4-Flash layers = 43 d = 4096 n_hc = 4 t_max = 20 284B total / 13B active // source: mHC paper (arXiv 2512.24880), experimental setup expansion rate n = 4 for both HC and mHC; main experimental model 27B

So how much memory does “4× wider” add? This course gives no number, because none can be given. The naive arithmetic is 1.75 GiB × 4 = 7.00 GiB per layer, but that assumes all four streams' activations are kept at every layer. The V4 paper says: “we recompute most hidden states between layers and all normalized layer inputs, while avoiding recomputation of compute-intensive operations.” Most between-layer hidden states are not stored but recomputed in the backward pass. How much to store versus recompute is an engineering setting, not an architectural constant, so the real increase depends on that setting, and the paper gives no absolute memory figure.

The only cost the paper quantifies in absolute terms is time: “Collectively, these optimizations constrain the wall-time overhead of mHC to only 6.7% of the overlapped 1F1B pipeline stage.” The denominator of 6.7% is the overlapped 1F1B pipeline stage, not total training time. Quote the number with its denominator, or you quote it out of context.

The inverse of the embedding

A final RMSNorm, then a 7,168 → 129,280 matrix scores every token in the vocabulary. It mirrors Step 1's embedding matrix; if Step 1 compiles to a matmul (see its expandable note), even the FLOPs match.

tie_word_embeddings = false, yet one thing is shared Many models make input and output share one weight matrix (one less copy; “representing” and “predicting” a token feel like one job). V3 does not. Reading and writing get separate weights: 926M extra parameters.
The trap: V3 does have a “shared output head,” but it's shared with MTP, not the embedding table. The paper puts the shallowest layers (with embedding) and deepest (with output head) on one pipeline rank, so MTP and the main model physically share those parameters and gradients. So at MTP below, don't add another 926M.

MTP: built for training, a windfall for inference

num_nextn_predict_layers = 1: depth 1, meaning it predicts one extra token (the one after next). Not two: this number is the depth.

Why build it
(training)		Extra supervision. Trained only on the next token, a model can coast; predicting the one after too forces it to plan ahead. The V3 paper names this the main purpose of MTP: “we utilize MTP to improve training”
At inference you can
simply drop it		“during inference, we can directly discard the MTP modules and the main model can function independently and normally”: it's training-time scaffolding. The ablations drop it, so both arms have identical inference cost
But dropping it is a waste
(speculative decoding)		Use it as a draft model: cheaply guess the token after next; the main model verifies both at once. A hit is a free token; a miss costs nothing.
V3, measured: 2nd-token acceptance 85%–90%, end-to-end speed 1.8× TPS

Speculative decoding pays off because of Topic 6: decode is bandwidth-bound, not compute-bound. With the weights already read, one more token is nearly free to verify. Acceptance hits 85%–90% because the draft isn't a separate model: it reads the main model's hidden state.

Another easy-to-miss blow-up The logits tensor is 31.56 GiB: scarier than any middle layer, and purely temporary. Real implementations compute logits in chunks with the loss fused in, never materializing it. Same trick as FlashAttention: don't write intermediates to memory.

⭐ Three questions nearly everyone trips on

① Why are training logits 131,072× larger? Positions, not vocabulary Both sides have a 129,280 vocabulary. What differs is how many positions are scored.
Training uses teacher forcing: the whole sequence goes in at once, and every position predicts. Position 5 predicts token 6, 6 predicts 7, all in parallel: one forward pass, 131,072 losses, none skippable.
Inference samples only the last position; the 131,071 before it need no logits. 131,072 : 1. That's the whole difference.
An easy ratio: the logits are “18 residual streams stacked”
// at the output, width jumps from 7,168 to 129,280 129,280 ÷ 7,168 = 18.04 // so one residual stream 1.75 GiB × 18.04 = 31.56 GiB ← exactly the number above
Everything else is “positions × 7,168”; only the output is “positions × 129,280.” Same positions, 18× the width: hence it stands out.
② Inference samples from the top-k anyway; why compute the small scores? True, but order matters: you need all 129,280 scores to find the top 64. Top-k selects after computing; it skips no compute.
Inference needn't save anyway: one position's full logits are just 252.5 KiB.
The pressure is in training, which can't use top-k. The cross-entropy denominator sums the entire vocabulary; drop a term and it's wrong. (Older approximations like sampled and hierarchical softmax pay with biased gradients.)
The modern fix is chunking: logits for a small slice of positions, take the loss, discard. It's exact, and saves peak memory, not compute.

With a real training config: why chunking is mandatory

The 31.56 GiB above uses the control panel's setting at the top (128K). Switch to a common training shape, sequence length 4,096 with a per-device batch of 12:

// positions that need logits in this step 4,096 × 12 = 49,152 // the logits tensor itself bf16 49,152 × 129,280 × 2 B = 11.84 GiB fp32 49,152 × 129,280 × 4 B = 23.67 GiB ← cross-entropy is numerically unstable; usually upcast to fp32 // for scale: one residual stream at the same positions 49,152 × 7,168 × 2 B = 0.66 GiB ← that 18× again
On one device, this temporary tensor takes a quarter of HBM Of 94.74 GiB HBM per device, bf16 logits take 12.5%; fp32 for the loss, 25.0%. Yet it's absent from the parameter table, costs about 2.2% of compute (at this 4K shape; 0.46% at 128K), and is dropped the next step.
Why chunking works: positions are fully independent The loss is a sum of per-position terms: position i's logits don't depend on position j's. So stream: slice logits → loss → discard → next slice.
slices of 1,024 → peak 1,024 × 129,280 × 2 B = 252 MiB // 11.84 GiB → 252 MiB, down to 1/48
And you save twice. The backward gradient tensor is as large as the logits (just p − y, elementwise, same shape). Fused, it never hits memory either: computed in the slice, immediately contracted to the “1,024 × 7,168” hidden-state gradient.
Cost: near zero. lm_head is about 2.2% of total compute; recomputing it barely registers.

Where does “the next token” come from? Almost everyone asks

At layer 0, the vector is the embedding of the current token. How does it become the next token after 61 layers? Is the “shift by one” rule written into lm_head's parameters?

No. It lives in the loss; nothing in the architecture shifts lm_head is trivially simple: a table, one row per token, each a direction in 7,168-dim space.
row w of lm_head = a direction for token w in 7,168-dim space score of token w at position i = top vectorᵢ · row w // just a dot product ↑ whichever direction aligns best scores highest
So lm_head stores only “what each token looks like,” nothing about “next.”
The guessing happens in the 61 layers below. Attention lets position i see all earlier ones, so at the top the vector means not “what token i is” but “given the first i tokens, what comes next.”
“Next” comes from shifting the training labels by one.
// corpus: it is a fine day today pos 1 2 3 4 5 input it is a fine day ↓ ↓ ↓ ↓ ↓ 61 layers + lm_head, every pos ↓ ↓ ↓ ↓ ↓ label is a fine day today ← input: always from the corpus ← label: same row, shifted left by one
Best evidence: MTP shifts labels by two, no code change MTP above predicts the token after next. Same structure, same scoring; labels shift by two. If “shift by one” lived in the architecture, this couldn't be so cheap.
③ So in training, is each position's loss computed on its most probable token? No. Training neither samples nor takes the argmax; it never “picks” a token.
It takes the corpus's true next token and the model's probability for that token; loss = −log(that). The model's own favorite plays no part.
Crucially, predictions are never fed back. Position i+1's input is the true token i+1, whatever position i guessed. Hence teacher forcing: the teacher resets you every step.
Why it mustOtherwise
Parallelism: all 131,072 positions are computed in one forward pass Feed predictions back and position i+1 waits for position i: serial training, 131,072× slower
Differentiability: cross-entropy is smooth over the whole distribution argmax isn't differentiable; backprop can't pass
Gradient covers the whole vocabulary: true token's score up, the other 129,279 down Look only at the argmax and you lose the denominator, which is why ② above rules out top-k
The price: exposure bias Training always shows a correct prefix; inference shows the model's own, possibly wrong, output. That gap is exposure bias. Scheduled sampling and the like once tried to ease it; today's large models mostly fix it in post-training, with real rollouts.

④ Isn't a 0/1 label far from the real probability distribution?

After “The weather today is,” “nice,” “great,” “lovely” all work. Why does the label give one 1, the others 0? Fair point: for any single example, the label is wrong.

Key point: a label isn't a claim about the distribution; it's one sample from it Flip a coin: always 0 or 1, never 0.5. Average ten thousand flips and you get 0.5.
“The weather today is” recurs in the corpus, followed by “nice,” “great,” or “lovely.” Each pushes its own way; the averaged gradient is the empirical frequency. Each label is hard; their sum is soft.
// why this objective is right in expectation minimize E(x,y)~data [ −log pθ(y|x) ] ≡ minimize KL( Pdata(·|x) ‖ pθ(·|x) ) + H( Pdata(·|x) ) ↑ constant, independent of θ // so the optimum lands exactly at pθ = Pdata ← the true conditional distribution, not one-hot
Corollary 1: the model never reaches 1; gradient descent holds it back Say the model gives “nice” probability 1 after “The weather today is.” Every example followed by “great” then has loss −log(0) = ∞.
So the prefix's other occurrences rein in the push to 0 or 1. The equilibrium is the empirical distribution, not one-hot.
Corollary 2: the loss floor isn't 0; it's the entropy of language KL can at best reach 0, but H(Pdata) can't be reduced: it doesn't depend on the parameters. Loss leveling off above zero isn't failure; it measures how many sensible next words there really are.
Loss heading to 0 means memorizing the corpus, not learning language.

What if I have better soft labels? There are two routes, and their very existence admits one-hot loses information:

MethodWhat it doesCost
label smoothing 1 → 1−ε, rest share ε Transformer used ε=0.1; modern LLM pretraining mostly doesn't (hurts calibration)

The original paper states what the trade buys “During training, we employed label smoothing of value εls = 0.1. This hurts perplexity, as the model learns to be more unsure, but improves accuracy and BLEU score.” —Vaswani et al. 2017, Attention Is All You Need §5.4
“Learns to be more unsure” flips your worry: one-hot doesn't teach confusion; it teaches overconfidence, which smoothing pulls back.
In one sentence One-hot says only “this time, this token.” A teacher's soft labels add “cat is a bit like dog, nothing like car.”
One-hot recovers that by averaging vast data: slow, but teacher-free. That's pretraining vs. distillation.

⑤ Distillation in depth: why it beats one-hot, and by how much

One-hot is correct in expectation. Its only flaw is that it's slow. Distillation does one thing: it replaces the hard label with the teacher model's full output distribution. That buys more than intuition suggests. Every number below comes from Hinton / Vinyals / Dean 2015, Distilling the Knowledge in a Neural Network (arXiv:1503.02531).

First: the teacher really teaches ratios between “negligible” probabilities “one version of a 2 may be given a probability of 10−6 of being a 3 and 10−9 of being a 7 whereas for another version it may be the other way around. This is valuable information that defines a rich similarity structure over the data.”
One-in-a-million and one-in-a-billion are both negligible, but their ratio means something: “this 2 leans toward 3, not 7.” This became known as dark knowledge: beyond the answer, the teacher hands over a map of what resembles what.
One-hot throws the whole map away.
// the same position, gradients under the two kinds of label one-hot ∂L/∂logiti = pi − yi y is 0/1 → the target for all 129,279 wrong tokens is 0, and the model already gives them ~0 ⇒ they get almost no gradient this step soft ∂L/∂logiti = pi − qi q is the teacher's value ⇒ each token off the teacher's value gets a push some up, some down; not a single winner
Second: one-hot is a sample, so it's noisy; the teacher's distribution isn't “When the soft targets have high entropy, they provide much more information per training case than hard targets and much less variance in the gradient between training cases, so the small model can often be trained on much less data than the original cumbersome model and using a much higher learning rate.”
Back to the coin: one-hot is one flip each time. The same prefix draws “nice,” then “great,” so the gradient swings until vast data averages it out. The teacher just states the coin's bias: identical every time, no noise to average.
Hence the paper's “a much higher learning rate.”
Aside: an information estimate (my derivation from vocabulary size, not the paper's)
one-hot carries at most log2(129,280) ≈ 17 bits per position // “which of these 129K tokens” soft distribution carries the full 129,280-dim shape per position // every dimension is a constraint
Same forward pass, same 31.56 GiB of logits, a supervision signal orders of magnitude richer. No extra FLOPs, far more information: that's the speedup.

Where the 41.89 GiB of peak activations comes from

The opening question counted only the KV cache: its cost is deterministic; what's stored, and how long, is clear at every step. Activations need a full trip to cost. Now we've made one.

Two terms people keep confusing KV cache = kept. Token n+1 needs K and V of all n before it. It lives all conversation, multiplies by layer count, grows linearly, never freed.
Activations = discarded after use. Layer 3's intermediates die when layer 4 starts: they live within one layer. So they don't multiply by layer count; only the fattest layer counts. Hence 61 layers peak at just tens of GiB.
(Training keeps activations for backward, so they dominate memory. We count only forward, so the two separate cleanly.)

The scariest item isn't attention; it's the output. Times a 129K vocabulary, logits exceed 3× the whole KV cache. (Assumes logits at all positions; pure generation needs only the last, so ignore it there. Activations vary with implementation; magnitudes, not exact values.)

The table's three “×2”s have three reasons Q and K: two same-size tensors, 128 heads × 192.
V and output: two same-size tensors, 128 heads × 128.
Residual stream ×2 differs. The incoming x must be kept, since the layer ends by adding it back; its layer-normed copy is a separate buffer. From norm to addition, two copies live, each 1.75 GiB.
MoE repeats the structure, so also ×2; the output step has no add-back: one copy.
Aside: why pretraining usually uses 4K, not 128K—what it saves isn't logits, it's attention

It doesn't save on logits. Logits depend only on the total token count (= sequence length × batch), not per-sequence length:  128K × batch 1 and 4K × batch 32 are both 131,072 tokens, and the logits are 31.56 GiB either way.

What short sequences save is attention: its cost is batch × the square of sequence length. For the same 131,072 tokens, the 128K split pays 32× what the 4K split does.

In V3's config, original_max_position_embeddings is 4,096 and YaRN's factor is 40; 4,096 × 40 = 163,840. The base model was trained at 4K and extended to 128K afterward. Also, training usually upcasts logits to fp32 for cross-entropy, doubling them again; hence chunked cross-entropy is now standard: compute a slice, discard it, never materialize the full table.

Step 7.5

Computed vs. measured numbers

Seven steps of derivation. One question: can you trust it?

You can check it without occupying a device The compiler is a static analyzer: compile model plus parallelism config ahead of time (AOT) and it reports the memory without allocating an accelerator. You get the answer before queuing. Cross-checking the table above is the cheapest step.
Below is no AOT how-to; we don't cover running it. It asks how far to trust a tool that answers without running. Any performance model or capacity sheet gets the same verdict.

Run it for real and you learn three things, the hard way, not from a book.

① Compiles ≠ fits

A clean compile means only a legal graph. We've seen green builds far exceed device memory.

Worse, errors mislead. Real compile failures often surface as “out of memory,” so people shrink the batch: exactly wrong. A wrong error is worse than none.

② The number isn't everything

Only temp buffers; parameters and optimizer state are separate (see Topic 4).

And it doesn't shrink with parallelism: shard as wide as you like, temp buffers stay put. It's the easiest to miss.

③ ⭐ It fails right near the limit

Far from the limit, very reliable. Near the limit, in a narrow band, it can't tell.  All our wrong calls fell there.

Static analysis is no oracle. It rules out most obviously bad configs; the final call is yours.

One more surprise Same model, same parallelism: swap one op's implementation and memory changes, in no fixed direction, up or down.
Memory isn't a model property; it's a property of model × implementation × compiler. This point recurs throughout Topic 7.

Takeaways

Numbers fade. Keep these counterintuitive conclusions: every later lecture uses them.

01 · MoE

It saves compute, not memory.

“Only 37B active” doesn't mean 37B-dense cheap: HBM still holds all 671B.

02 · Long context

Long sequences move the bottleneck from parameters to length.

Attention is 12% of compute at 4K, 82% at 128K, 97% at 1M. Same model, new length, new optimization target.

03 · “Blowups”

The scariest tensors: temporaries, not weights.

Attention scores and output logits aren't even parameters. Discarded after use, they outpeak any layer's weights. Weights-only memory math is wrong.

04 · Architecture

Some architecture numbers are set by hardware, not quality.

“4 groups first, then experts” only caps how many machines traffic spans. Separate what makes a model smart from what makes it run.

05 · “Experts”

In the only publicly measured model, experts don't split by domain.

Mixtral's authors, searching by topic, found no obvious patterns. Yet consecutive tokens repeat an expert 26.4% of the time in middle layers (random: 12.5%). Routing seems to track syntax and token, not subject.
⚠️ Mixtral is top-2 of 8; V3 is top-8 of 256: no direct transfer. Only this is certain: across 58 MoE layers, each token takes its own path.

06 · The accounting itself

Memory belongs to model × implementation × compiler, not the model.

Same config, new kernel: memory changes, either way. Static analysis prunes most non-starters but doesn't make the final call.
