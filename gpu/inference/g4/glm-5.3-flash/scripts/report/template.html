结论先行

  • 能跑，而且不用打补丁。 vLLM nightly（0.33.0rc1.dev484）原生支持 GLM-5.3-Flash 在 RTX PRO 6000（SM120）上运行，自动选用 SM120 的 sparse MLA 后端。单路生成约 100 tok/s，输入从 1K 到 32K 几乎不变。
  • NVFP4 中高并发快 23–30%，模型能力看不出损失。 同样的 1P1D 部署，8–64 并发时 NVFP4 吞吐比 FP8 高 23–30%、TPOT 低约 30%，KV 容量翻倍；GSM8K 全量 1,319 题差 0.38 个百分点，配对检验 p = %%PVAL%%，统计上无差别。单路没有收益（−3%）。
  • PD 分离要配对比例，否则吃亏。 1P1D 的 D 大部分时间在等 P：同样 16 张卡，NVFP4 1P1D 在 128 并发只有 %%H1P1D_OUT%% tok/s。按实测容量把 P、D 配成 1:1 并都用 TP4（2P2D），吞吐提升到 %%H2P2D_OUT%% tok/s（%%IMP_2P2D%%）。2P2D 没有多用一张卡：还是同样两台机器、16 张卡，只是把每台机器切成两个 TP4。
  • PD 分离在 G4 上换来的只有「不卡顿」。 同样 16 张卡，2P2D 吞吐比不分离的 4×TP4 低 %%GAP_DP4%%；按真实的随机到达压测，首字反而是不分离更快（TTFT 中位数 0.8–1.1 s 对 1.2–1.7 s，PD 每个请求多一次代理转发和 KV 跨机传输）。2P2D 唯一的明确优势是生成平稳：P99 ITL 稳定在约 110 ms，不分离从每秒 1.5 个请求起就到 640 ms 以上。只有对生成卡顿敏感的业务（流式语音、数字人、实时字幕）值得上 PD。
  • G4 上的两条硬约束： 这个模型做 PD 时 P 和 D 必须用相同的 TP（KV 块大小随 TP 变化，不同则 NIXL 握手失败）；prefill 能力不随 TP 增长（TP4 与 TP8 都约 9K tok/s），所以 TP4 比 TP8 每卡效率高一倍。

两种压测方式

  • 并发扫描：固定同时在飞的请求数（1 → 256），每档请求数 = 并发 × 4。测的是吞吐和 TPOT 的上限。注意每档开头会一次性涌入「并发数」条请求，TTFT 的 P99 会被这一波排队放大，看 TTFT 以中位数为准。
  • 速率扫描：按泊松分布随机间隔发请求（0.5 → 2.5 请求/秒），更接近真实线上流量，用来回答「这个负载下用户等多久出第一个字」。

负载统一为 8K 输入 / 1K 输出（随机 token，--ignore-eos 保证每条都生成满 1,024 个 token）。所有场景失败请求数为 0（单独注明的除外）。

两个关键发现

  • prefill 能力不随 TP 增长：TP8 实例约 %%PRE8%% tok/s，TP4 实例约 %%PRE4%% tok/s。一台机器跑两个 TP4，prefill 能力约 %%PRE4X2%% tok/s，是 TP8 的两倍。
  • 1P1D 的 D 一直没吃饱：一个 TP8 的 D 单独能在 128 并发下出约 2,650 tok/s，而 1P1D 实测只有 1,274 tok/s。

配比计算

8K 输入 / 1K 输出的请求，每生成 1 个 token 要先 prefill 8 个 token。

  • 一台 P 机器（2 × TP4）：约 18K tok/s ÷ 8.2K ≈ 每秒 2.2 个请求；
  • 一台 D 机器在 TPOT 约 45 ms 时：约 2,600 tok/s ÷ 1,024 ≈ 每秒 2.5 个请求。

两者接近，按机器算 P : D ≈ 1 : 1。两台机器就是：一台放 2 个 TP4 的 P，一台放 2 个 TP4 的 D，即 2P2D。

为什么不是「2 个 TP4 的 P + 1 个 TP8 的 D」？ 实测这个组合所有请求都失败：GLM-5.3-Flash 的 KV 块大小要和每卡的 KDA 状态页对齐，TP4 时是 2,304 token、TP8 时是 1,280 token，块大小对不上，NIXL 握手失败（日志 Not pairing remote 2304-token blocks with local 1280-token blocks）。这个模型做 PD 时，P 和 D 必须同 TP。

为什么不是 3P1D？

两台机器也能放下 3 个 TP4 的 P 加 1 个 TP4 的 D，但按上表算：3 个 P 每秒能喂约 3.4 个 8K 请求，1 个 TP4 的 D 在 TPOT 约 45 ms 时每秒只能消化约 1.3 个（放宽到 TPOT 约 93 ms 也只有约 2.4 个）。对 8K 输入 / 1K 输出，3P1D 会变成 P 闲、D 被压垮，吞吐和每路速度都不如 2P2D。

配比依赖输入输出长度：输入越长、输出越短，越需要更多 P（例如 32K 输入 / 256 输出的 RAG、摘要类业务，3P1D 这类「P 多 D 少」的配置才合适）。按本节方法，用业务的真实长度分布代入即可算出比例。

八、硬件视角：为什么是这样

1. FP4 的长处在 decode，不在 prefill

RTX PRO 6000 的第五代 Tensor Core 原生支持 FP4，标称算力是 FP8 的两倍（4 vs 2 PFLOPS）。但这次实测里，FP4 的收益主要来自省显存、省带宽，而不是算力：

  • decode 是读权重的活。 高并发时一步 decode 几乎会用到全部 288 个专家，每卡要把自己那份权重读一遍。按实测每卡权重估算：FP8 39.38 GiB ÷ 1,597 GB/s ≈ 26 ms，NVFP4 23.69 GiB ÷ 1,597 GB/s ≈ 16 ms，每步省约 10 ms。实测 128 并发 TPOT 63.8 → 42.8 ms，方向和量级吻合（推导值，未计 KV 与注意力读取）。
  • 省下的显存全部变成 KV。 每卡可用 KV 从 38 GiB 涨到 55 GiB，KV 池翻倍，同样的卡能同时服务的长上下文请求翻倍。G4 每卡 96 GB 显存而带宽只有 1.6 TB/s，FP4 正好补的是带宽这块短板。
  • prefill 和单路几乎没收益。 prefill 每实例约 9K tok/s，折合每卡算力约 2 × 18B × 9.3K ÷ 8 ≈ 42 TFLOPS（TP8，未计注意力），只占标称峰值的个位数百分比——瓶颈不在矩阵乘，而在 SM120 上还不成熟的 sparse MLA 索引器、KDA 等非 GEMM kernel 和调度开销。单路时每步约 9.5 ms，按带宽算读一遍激活参数（约 18 GB ÷ 8 卡）只要约 1.4 ms，时间主要花在 PCIe 上的 all-reduce 和 kernel 启动。这两部分 FP4 都帮不上。
软件还在快速演进：随着 SM120 的注意力 kernel 成熟，prefill 能力会上升，最优 P:D 比例会随之向「更少 P」移动。建议每次升级引擎后用第五节的方法重测两个容量。

2. PCIe 拓扑决定了 TP4 比 TP8 划算

G4 的 8 张卡两两挂在同一个 PCIe 交换芯片下，每 4 张一个 NUMA 节点，没有 NVLink。TP8 的每次 all-reduce 都要跨 NUMA；TP4 可以留在一个 NUMA 内。实测 prefill 每实例吞吐 TP4 ≈ TP8，等于 TP4 每卡效率高一倍；decode 在 TPOT 约 45 ms 时两者整机吞吐相当，更高负载时 TP4 略好。代价是 TP4 单路略慢（每卡分到的权重更多）。

3. 网络不是 PD 的瓶颈

G4 跨机没有 RDMA，KV 走 TCP。这个模型只有 11 层是 MLA，KV 很小；单路实测 PD 只比单机多约 0.2 s TTFT，整个测试里 PD 的瓶颈始终是 P 的算力，而不是网络。本次只用了一块网卡（实测 173 Gbit/s），机型上限是两块网卡 400 Gbps，还有余量。
