# 二、同名不同义 —— 会让我理解反的地方

## ⛔ 1. 「重算」：这是最危险的一个，全文 60+ 次，零次消歧

**位置**：§2 整节（`s2-1`~`s2-6`）、`fig-recompute`、§7.0 表。

在我的日常里，`recompute` 是一个**有明确技术含义的反义词**：vLLM / SGLang 的抢占策略之一 —— KV cache 打满时**把一个正在跑的请求的 KV 整个丢掉、以后重新 prefill**。它的性质跟这里讲的完全相反：

| | 推理侧的 recompute | 本讲的重算 |
|---|---|---|
| 是什么 | 调度/驱逐策略 | 静态配置 |
| 何时触发 | 显存打满时的**最后手段** | **默认就开着**（§2.2 原话） |
| 代价 | 重跑一整个请求的 prefill | +33% FLOPs |
| 对手 | `swap`（换出到 CPU） | 无 |

§2.1 的"游戏存档"比喻其实很好，但它解释的是**机制**，救不了**词**。我读 §2.2「它默认就是开着的」时的第一反应是"什么？默认开抢占？"——愣了一下才切回来。

**建议**：§2.1 开头加一句「⚠️ 这个词跟推理引擎里的 `recompute`（KV 满了驱逐请求、之后重新 prefill）**不是一回事** —— 那是应急调度，这是静态配置」。一句话解决。

顺带：**§7.0 的 `torch.utils.checkpoint` 和 §3.7 的 checkpoint（7.3 TiB 那个文件）是两个完全不同的 checkpoint**，隔三页，都在读者眼前，也没有一个字消歧。

## ⛔ 2. 「激活」：4.15 TiB 这个数让我当场怀疑整份材料

**位置**：`fig-act-bill` Ⓑ（§1.6），标题是「**一条 128K 序列，V3 那个规模**」，batch = 1。

"一条 128K 序列、batch 1"在我这行是**请求的形状**，不是任何人的预训练形状。所以我读这一格时脑子已经切到长上下文推理的显存账了 —— 然后看到 **4.15 TiB**。

而我按 V3 config 推的同一条序列的 KV cache 是：

```
61 层 × (kv_lora_rank 512 + rope 64) × 2 B = 70,272 B/token = 68.6 KiB/token
× 131,072 token = 8.58 GiB
```
（这是我自己按 config 推的，请复核；关键前提是 V3 全部 61 层都走 MLA，dense/MoE 的区别在 FFN 不在 attention。）

**8.58 GiB vs 4,250 GiB —— 差 495 倍。**我的第一反应不是"训练好贵"，是"这个数算错了"。**整份材料对我的可信度就是在这一格掉的**，而它出现在第一节。

图的底部注释确实有那句救命的话：「推理根本没有这座山 —— 它算完一层就把中间结果扔了，只留 KV cache」。但它是**全文唯一一次**提 KV cache，藏在 SVG 最底下一行，而且**没给数**。给了数，这一格就从"劝退"变成"全讲最有说服力的一格"。

## ⚠️ 3. 「batch」：三页之内换了三种单位

**位置**：§1.8 的项目符号（`12.6M → 62.9M token`）、`fig-batch`、`fig-step` Ⓑ（`global batch = 94 条`）、§5.4（`batch 8 × 序列 1024`）。

- §1.8：`GPT-3 从 32K 爬到 3.2M`（**token**）、`V3 从 3072 条爬到 15360 条`（**4K 序列**）—— 同一个项目符号里
- §5：`global batch = 1 条` / `94 条`（**128K 序列**）
- §5.4：`batch 8`（**序列条数，S=1024**）

对一个"batch = 并发请求数"的人，这四个数没有一个能直接读。而且语义也反了：推理侧 batch 大小由**延迟 SLO**封顶，这里由**梯度噪声尺度**决定（§3.5 引 GPT-3 原话时提了一句 `梯度噪声尺度`，但没解释）。

`fig-batch` 本身讲得很好（"batch 不是为了跑得快才有的，它首先是别只听一个人的"），但它讲的是**为什么要有 batch**，没讲**它在两侧被什么封顶**。

## ⚠️ 4. 「显存峰值」：形状完全不同，§5.3 只讲了一半

**位置**：§5.3 `s5-3`、`fig-step`、`anim-memtime`。

§5.3 那条判据（"先问哪一项的峰"）本身是通用的、很好。但两侧的峰**在时间上是不同物种**：

- 训练：一个 step 内的**瞬间**，每个 step 完全重复，可以静态规划
- 推理：KV 在一个请求的生命周期里**单调涨**，峰值在请求**结束时**，而且跨请求叠加、不可预测 —— 所以才有 paged attention 和 preemption

§5.3 的落点写「你去查 OOM，光知道峰值 xx GiB 没用」—— 这句话对两侧都对，但**原因完全不同**，而读者会拿自己那一侧的原因去套。

## ⚠️ 5. 精度 / 量化：判据是通用的，却只按训练侧写

**位置**：§3.2 `fig-precision` Ⓒ、§6.6 `fig-underflow`。

§3.2 的判据（「老的贡献会不会永远不走」）是这一讲最漂亮的一条，而且它**本来就能一次性解释推理侧为什么敢量化到 4 bit**：推理里**没有任何一个量是"永远不走"的** —— 权重只读、KV 只在一个请求内活、激活单层即弃。这一句没有。

结尾只反向说了一半：「FP8 训练为什么难，问的就是同一句」（§3.2 末）。方向反了 —— 对我而言"w4a16 能跑"是已知，"训练不行"才是新知。

`fig-underflow`（§6.6）更明显：它讲的是**梯度**下溢，可全图一个"梯度"字都没在轴上。我读到「fp16 要 loss scaling」会想"我推理跑 fp16 从来没做过 loss scaling 啊"—— 答案当然是"因为没有梯度"，但文中不说。

### §6.5 有一处是反的：它混了「架构」和「训练开关」

这一分界线一个字都没有。§6.5 里 QK-norm 那段对我其实是**最有用的一段**（它决定我的 attention kernel 长什么样），却被放在「让它天生不容易飞」这个纯训练标题底下。

# 四、可以借用的桥（这条最有建设性，给具体建议）

## 桥 1 ⭐⭐⭐ KV cache 的增长 ↔ 激活的堆积
**落点：§1.6 末尾，`fig-act-bill` 之前，一段 + 一张三行表。**

两者**本质是同一件事**：前向算出来的东西不能扔。差别只在**谁在等它**。

> - **推理**：第 t 个 token 的 K/V 要留着，因为**未来的 token** 要 attend 它。留 2 项，跨 step 累积，请求结束才释放。
> - **训练**：每一层的输入要留着，因为**反向**要乘它（§1.3 第①笔）。留每层每个中间张量，**一个 step 之内**堆完又拆完。

| 同一条 128K 序列 | 显存 | 相对 |
|---|---|---|
| 推理 KV cache | ~8.6 GiB | 1× |
| 训练激活（不重算） | 4,250 GiB | **~500×** |
| 训练激活（全量重算） | 107 GiB | ~12× |

而这张表自带下一节的钩子：**重算的本质，就是把激活压回 KV cache 那个量级** —— 从 500× 压到 12×，而不是压到 0。**这一句能让 §2 整节对推理读者立刻有参照系。**

## 桥 2 ⭐⭐⭐ prefill / decode 的算力结构 ↔ 前向 / 反向
**落点：`fig-3x` Ⓒ 那一格再加一行注脚（图已经在那儿了，改动最小、收益最大）。**

读者已经拥有「同一份权重、两种截然不同的算力形态」这个直觉：

> prefill = 大 GEMM、算力受限；decode = GEMV、带宽受限。
> **而训练的 1 ＋ 2 全都是"prefill 形状"** —— 前向和两笔反向都是大 GEMM、都算力受限。**训练里根本没有 decode 这一半。**

这一句能一次性解掉两个推理直觉的误用：
1. "训练是不是也被带宽卡住？" —— 基本不会，batch×seq 永远够大。
2. "为什么训练 MFU 40% 算高，而我的 decode 5% 也算正常？" —— 同一个分母，一个在 GEMM 区、一个在 GEMV 区。

## 桥 3 ⭐⭐ chunked prefill ↔ 梯度累积
**落点：§1.8「📌 顺带把 ④ 说清楚」那五条的末尾，一句话。**

梯度累积 = 把一个大 batch 拆成 K 份**串行**跑，只为了让同时在场的激活只有 1/K。推理侧一模一样的动作叫 **chunked prefill**：把一个长 prompt 拆成 chunk 串行跑，只为了让同时在场的中间张量小一份。**同一个动作、同一个动机、同一条"改时间线不改总量"的结论**（§1.8 已经写了这句话，只差点名）。

## 桥 4 ⭐⭐⭐ `fig-zero` Ⓑ 那张散点，反过来照亮推理
**落点：`fig-zero` Ⓑ 落点带，一句话。**

Ⓑ 那张「每参数几字节 × 每步用几次」的图是全讲最可迁移的一张，而且它正好能解释推理侧的一件事：

> 图上写着「**这一角是空的：又大又忙的东西**」。
> ⭐ 在推理侧，**那一角不是空的 —— 坐着 KV cache**（每个 decode step 全量读一遍）。所以它切不动、只能分页管理；而优化器状态落在"又大又闲"那一角，所以它第一个被切。
> **同一张判据图，两侧读出完全不同的策略。**

这是唯一一处能把训练侧判据反向照亮推理侧的地方，而且**图已经画好了，只差一句**。

## 桥 5 ⭐⭐ 量化判据的对称
**落点：§3.2 末尾那句「FP8 训练为什么难」的前面。**

> 把这条判据代进推理：推理里**没有任何一个量是"老的贡献永远不走"的** —— 权重只读、KV 只活一个请求、激活单层即弃。**所以 w4a16 / kv8 敢压到训练根本不敢的位数。**
> 同一条判据，一边给出"这 12 字节必须 fp32"，一边给出"4 bit 就够"。

## 桥 6 ⭐ 通信不随 batch 变 ↔ 连续批处理的算术强度
**落点：§1.8「⭐⭐ 第 ② 步那笔通信，有个很反直觉的性质」。**

「梯度通信量 = 参数量 × 字节数，**跟 batch 完全无关**」—— 这正是推理侧 continuous batching 的那条论证：**权重搬运量跟 batch 无关，所以 batch 越大每 token 摊得越薄**。同一个形状，只是一边搬的是梯度、一边搬的是权重。读者已经会算这个了，白捡一个锚点。

## 桥 7 ⭐ LoRA 欠推理侧半句
**落点：§3.8 收口处。**

§3.8 三本账讲得很好，但推理侧最关心的半句缺了：**adapter 可以 merge 回权重，合并后推理零开销；不合并则每层多两个瘦 GEMM —— 多租户 serving 才会不合并。** 完全在已有框架内，一句话。

## ⚠️ 空降或口径不一致的

### ① `106.75 GiB` 少算了「当前正在重算的那一层」—— 而 §5.4 算了

这是最实质的一处。同一本账，两个地方口径不同：

- **§5.4（125M）**：明写「每层只留入口那一份，外加**当前正在重算的那一层的完整一份**」。数字对得上：`0.144 + 0.176 = 0.32 GiB` —— **在场那一层占了 55%**。
- **§1.7（671B）**：`106.75 = 61 × 1.75`，**在场那一层一分都没算**。而 V3 一层 MoE 块是 **71 GiB**。

补上之后 ≈ 178 GiB，于是：**40 倍 → 24 倍**、**2.5% → 4.2%**（`fig-recompute` Ⓐ 那根"短到几乎看不见"的条）、**94 条 → 56 条**（§5.1 分水岭）、`fig-step` Ⓑ 的三行也跟着动。

⭐ 不一致的方向是**让 671B 那笔交易看起来更划算**。这一讲自己在 §2.3 自曝过「早先那两个百分比分母不一样，并排比不能比」—— 这是同一类问题的第二例，只是换到了分子上。

### ② `一个 step ≈ 2,571 TFLOP` —— 全文最关键的空降数

§2.3 的整个落点（「**只多付 1.9%**，换掉 77%」）全靠这个分母，而它从哪来一个字没说。而且读者**无法自己复算**：6ND 在 128K 上低估 5–6 倍（§5.2 自己说的），所以标准公式给不出它。

⭐ 讽刺的是同一段还写着「**这张表你拿 config 自己也能排一遍**」——**前八行确实能，最后那一步偏偏排不出来。**

### ③ `fig-step` 与 `anim-memtime` 相邻，激活口径差 40 倍，却都声称「同一套口径」

- `fig-step` Ⓐ：激活 = **106.75 GiB**（重算开着）
- `anim-memtime`（紧接其后）aria：`八点五四 ＋ 四点一五 ＝ 十二点六九 TiB` → 激活 = **4.15 TiB**（重算**关着**），且常驻基座 8.54 TiB = 14 B/参数（把梯度单独拆出来了，是**另一套分解**）
- 而 `anim-memtime` 的 figcaption 明写：「三条带的高度按真实字节数算，**跟上面那张图同一套口径**」

两张相邻的图，同一个训练步，激活差 40 倍、常驻分解法也不同，却宣称口径一致。

### ④ `一层 dense 块约 40 GiB` —— 唯一没拆的那一行

§1.7 给了 MLA 表和 MoE 表，dense 块的 MLP（宽 18,432）那一份从来没拆过，40 直接落下来。它参与 4.15 TiB 的总和。这一节的立意就是「给要自己算的人看」，这一行破了自己的规矩。

### ⑤ `专题一算过它在 128K 上是 4 TiB／层` —— 口径与本讲相反

我复算：`131,072² × 128 头 × 2 B = 4.0 TiB`（**未 causal 折半**）；折半是 2 TiB。而本讲从 §2.4 起明确统一到 **causal 折半口径**，还在 §2.5 专门警告「跨文献比这类比例前，先确认对方折没折半」。**这一处引用的正是未折半的数**，放在一份自己立了折半规矩的材料里。

### ⑥ 小问题
- `按每张卡 80 GiB 算要 125 张`（§5.1）：§7.2 老实承认是随手基准，但正文读起来像硬件事实。
- `fig-act-bill` Ⓑ 声称「两个框的高度按真实比例画」（40:1），而 `fig-recompute` Ⓐ 是「两边都归一到 100%」—— 同一组数在两张图上长得完全不同，读者会以为是两组数。

# 六、⭐ 特别盯：长度口径的切换，在哪几处让我以为在讲长上下文推理

先把事实摆清楚。这门课的基准是 **4K**（V3 的真实预训练长度 —— 而且**这份文件自己写了**，§1.8 那一行：「V3 从 3072 条序列爬到 15360 条（**4K 上下文**，折合 12.6M → 62.9M token）」）。

但文件的**实际工作基准是 128K**，在 §1.7 立下：「（序列 **131,072**、batch **1**、bf16。）」

⛔ **而 §1.7 的第一句话是：「⭐ 这一小节可以整段跳过。」**

> **整份材料所有数字赖以成立的那个前提，被声明在唯一一节作者叫你跳过的小节里。**

下游全部继承它，而且**没有一处标注适用区间**：

| 位置 | 数字 | 隐含 S | 在 4K 上会怎样 |
|---|---|---|---|
| §1.6 `fig-act-bill` Ⓑ | 4.15 TiB / 106.75 GiB | 128K | ÷32 |
| §2.2 | 「约 40 倍」 | 128K | 不变（都 ÷32） |
| §2.3 排序表 + 「1.9% 换 77%」 | 全表 | 128K | 前七行**不变**，attention 行 ÷32 |
| §2.4 | 「attention 是最不该重算的」 | 128K | **结论翻转** |
| §5.1 | 「94 条」分水岭 | 128K | → 3,000 条 |
| §5.2 | 「6ND 低估 5–6 倍」 | 128K | → **低估 14%，完全够用** |
| §7.2 | 「82.1%」 | 128K | → 约 12.5% |

## 具体是哪几处把我带到"长上下文推理"上

### ⛔ A. `fig-act-bill` Ⓑ（§1.6）—— 「一条 128K 序列，batch 1」
这**不是任何人的预训练形状**（预训练 batch 是几千条），它恰好就是**一个长上下文推理请求**的形状。我在这里第一次切错参照系，然后带着 4.15 TiB 这个在我看来"不可能"的数往下读了一整节。**这是整份材料对推理读者最先崩的一处。**

### ⛔ B. `fig-per-byte`（§2.4）—— 横轴 1K–256K，两根竖线立在 2,048 和 131,072

这张图被 figcaption 称为「全专题最值钱的一张」，我同意它的**几何**（斜率不同必然相交）。但它把 **V3 的 config** 和 **一个 V3 预训练时根本不用的长度** 绑在了一起，然后用这个组合去论证一场 V3 实际上没遇到过的翻转。

按图自己的判据代 4K 进去：`1.25 × 4,096 = 5,120 < 7,168` —— **4K 落在交点 5,734 的左边**，也就是说在 V3 的真实预训练长度上，**attention 仍在"该重算"那一侧**。图上却只画了 131,072 那根线。

⭐ 而下面那条第一方证据其实**不依赖 128K**：表里前七行是线性层，闭式解里 `S` 约掉了，**这份名单在 4K 上一字不变**，唯一会动的是 attention 那一行。所以只要补一句就同时修好两件事：

> 「⭐ 注意：前七行跟序列长度**无关**（闭式解里 S 和 n 全约掉了），所以这份名单在 V3 真实预训练的 **4K** 上**一字不变** —— 唯一会挪的是 attention 那一行。**128K 这根竖线画的是长上下文微调 / 长上下文推理的场景**，不是 V3 的预训练。」

这一句让"1.9% 换 77%"从一个 128K 专用结论变成一个普适结论，**反而更强**。

### ⛔ C. §5.2 标题：「6ND，在**长上下文**下严重低估」

"长上下文"这四个字在我这行专指推理场景。读到「低估五到六倍」我以为在讲长上下文 prefill 的算力估算。

而**在这门课的基准 4K 上，6ND 完全够用** —— 我按文中给的 82.1% 外推：attention/linear 比正比于 S，`4.587 × (4096/131072) = 0.143` → attention 占 **12.5%**，6ND 低估约 **14%**。这一节的适用区间是 128K，标题没写，正文只在末尾用 GPT-3 的 2,048 反向提了一句。

### ⚠️ D. §5.1 —— 唯一一次把口径换回 4K，却当成补充塞在后面

「**94 条 128K，还是 3,000 条 4K —— 对显存是同一件事**」

这是**全文唯一一次**主动做长度换算，而且 3,000 条 4K 才是像预训练的数。它应该**前置成整节的口径声明**。

⭐ 而且这里有一个这份材料自己算出了两半、却没接上的巧合：**V3 开训时的 global batch 是 3,072 条 4K = 12.58M token**，而这一节算出的分水岭是 **1,230 万 token**。

> **V3 开训那一刻的 global batch，几乎正好落在「激活追平常驻」那个点上。**

这是全讲最好的一个落点，两个数都在文里，中间只差一句话。

### ⚠️ E. §4.3 的 CP，理由跟 §5.1 打架

§4.3：「CP（上下文并行）—— 针对激活里**随序列长度涨**的那一部分」

可 §5.1 刚刚证明了（在 FlashAttention 前提下）**激活只认 token 总数，不认序列长度** —— 没有 S² 项。固定 token 数下，94×128K 和 3,000×4K 的激活一样大，DP 已经沿 batch 轴切了。CP 存在的真实理由是**一条序列本身切不进 DP**。

对一个从长上下文 serving 那边认识 sequence/context parallel 的人，这一句读起来是乱的。
