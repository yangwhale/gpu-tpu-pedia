## 这个专题要回答的一个问题

模型跑起来了，MFU 只有 20%。

**剩下那 80% 的时间，去哪了？**

绝大多数人的做法是开始试参数 —— 换 batch、换并行度、翻别人的配置抄几个 flag。
**这不叫调优，这叫碰运气。**

真正的调优只有两步：

1. **定位** —— 用一套判据和一套工具，找出时间到底花在哪、谁在闲着
2. **动手** —— 针对定位到的那个瓶颈，选对应的手段

这个专题讲的就是这两步。**顺序不能反。**

## 一 · 先建立判据：屋顶线

**没有判据就没有调优。** 屋顶线（roofline）是最基本的那个。

- 横轴：**算术强度**（arithmetic intensity）= 计算量 ÷ 访存量，单位 FLOP/Byte
- 纵轴：实际达到的算力
- 屋顶由两段构成：**带宽斜坡** + **算力平顶**
- 拐点 = 峰值算力 ÷ 峰值带宽 —— **每种硬件有自己的拐点**

**这张图的用法**：把你的算子一个个点上去，落在斜坡上就是**带宽受限**，
落在平顶下就是**算力受限**（或者根本没优化好）。

**要对号入座的**：
- 大矩阵乘（MLP、专家）→ 算术强度高 → **算力受限**
- Attention 的 decode 阶段 → 反复读 KV → **带宽受限**
- norm、激活函数、element-wise → **强带宽受限**，而且量还不小
- 通信 → 另一条轴，屋顶线不直接管，要单独看

> ⭐ **算术强度是这个专题的核心概念。** 有了它：
> - 「为什么长序列解码卡带宽」→ 算一下 KV cache 的强度就知道
> - 「为什么 batch 越大越划算」→ 强度随 batch 线性涨
> - 「FlashAttention 到底改了什么」→ 它改的正是访存量，也就是横坐标
>
> **它把「感觉慢」变成了「落在图上哪个位置」。**

## 二 · 硬件：知道有哪些资源，才知道谁在闲着

调优的本质是**让尽量多的部件同时忙着**。所以先要知道有哪些部件。

| 部件 | 干什么 | 什么时候是瓶颈 |
|---|---|---|
| **MXU** | 矩阵乘 | 大 GEMM 密集时 |
| **VPU** | 向量运算：norm、激活函数、element-wise | 小算子多、融合不好时 |
| **SparseCore** | 嵌入查找、**集合通信卸载** | MoE / embedding 重的时候 |
| 标量单元 | 控制流、索引 | 很少 |
| **HBM 带宽** | 喂数据 | 访存密集型算子 |
| **VMEM** | 片上缓冲 | tile 太大会 OOM，太小会反复搬 |
| **ICI** | 跨芯片通信 | 通信没被计算盖住时 |

⭐ **关键认识：这些部件可以并行工作。**
所以「MXU 利用率 90%」不等于好 —— 也许 VPU 全程闲着，
而那些 element-wise 算子本可以和矩阵乘重叠。

**反过来最常见的浪费**：一个纯访存的小算子夹在两个大 GEMM 中间，
没被融合掉，于是 MXU 停下来等它。

## 三 · 编译栈：从 Python 到机器码，中间发生了什么

不理解这条链路，就看不懂 profile 里那些名字。

```
JAX / Python
   ↓  trace
jaxpr
   ↓
HLO（High Level Optimizer IR）        ← 算子级，可读，是调优的主战场
   ↓  XLA:TPU 一堆 pass（融合、布局、调度、内存规划）
优化后的 HLO
   ↓
LLO（低层表示，贴近硬件）              ← 待核实全称与确切边界
   ↓
机器码
```

**要讲清楚的**：

- **HLO 是什么**：一张算子图。每个节点有形状、有布局、有内存占用。
  **`temp_size` 就在这儿读出来** —— 专题一算的显存账，落地就是看它
- **怎么 dump HLO**、怎么读一个巨大的 HLO
- ⭐ **融合（fusion）是编译器最重要的优化**：
  把一串小算子合成一个 kernel，中间结果不落 HBM。
  **融合成不成，常常就是快慢的分界**
- **布局（layout）**：数据在内存里怎么摆，会影响 MXU 能不能对齐吃满
- **调度**：编译器决定通信和计算怎么交错 —— 通信能不能被盖住，就在这里定
- **LLO** 什么时候需要看（大多数时候不需要，但要知道它存在）

## 四 · 抓 profile：XProf

**工具部分。** 我们有一份把 XProf 十几个工具页逐个走通的记录，
这里要做的是**提炼成"什么时候看哪一页"**，而不是逐页说明书。

- 怎么抓（训练中打点、抓几步、抓多大）
- **Trace Viewer**：时间线，看每个 device 每一刻在干什么
  - 怎么找到一个 step 的边界
  - 怎么看出「这里有个空洞」
  - 通信和计算是不是重叠的，一眼就能看出来
- **Op Profile**：按算子排序，谁最贵
- **Memory Viewer / Memory Profile**：峰值在哪一刻、哪个 buffer
- **Roofline 页**：直接把第一节那张图画出来
- 其余工具页各自的用途，以及**大多数时候用不上哪些**

## 五 · 看什么数：指标与它们的陷阱

| 指标 | 怎么算 | 陷阱 |
|---|---|---|
| **MFU** | 实际 FLOPs ÷ 峰值 ÷ 时间 | ⚠️ FLOP 公式的口径不一致就没法比；**漏了模型白名单会虚高数倍** |
| **HBM 带宽利用率** | 实际字节 ÷ 峰值带宽 | 跟 MFU 一起看才有意义：两个都低 = 有空洞 |
| 各单元利用率 | profile 里读 | 单看一个会误判 |
| **通信/计算重叠率** | 时间线上量 | **这是长期最容易被忽略的一项** |
| step time 构成 | 拆成前向/反向/更新/通信 | 拆不开就没法归因 |

⚠️ **单位陷阱**（TPU 特有，反复有人踩）：
- **v7 是 2 device / chip**，而框架日志一律按 device 报
- per-chip TFLOP/s = 日志值 × 2；MFU = per-chip ÷ 峰值
- 同样的 `per_device_batch_size`，v7 的 global batch 是 v5p 的两倍

## 六 · 定位：一个固定的顺序

**别乱试。按这个顺序走：**

1. **先看 step time 稳不稳** —— 抖动说明有别的问题（数据、抢占、掉卡）
2. **看时间线有没有大空洞** —— 有空洞先解决空洞，别去抠算子
3. **看通信有没有被盖住** —— 没盖住的话，动的是并行策略不是 kernel
4. **看 MFU 和 HBM 利用率的组合**
   - 算力高、带宽低 → 已经不错，看还有没有算力浪费
   - 算力低、带宽高 → **带宽受限**，去找访存
   - 两个都低 → **有空洞或在等** —— 回到第 2、3 步
5. **最后才看单个算子** —— 排序找最贵的那几个

> ⭐ **这个顺序本身就是这个专题最值钱的东西。**
> 大多数人从第 5 步开始，然后在错误的地方投入几周。

## 七 · 动手：手段按代价从低到高排

1. **XLA flag** —— 最便宜，改一行重跑
   - 我们维护了一份 flag 知识库（`tpu/tpuguru/backend/flags.py`），
     17 条，每条都标了**在哪一代上验过**、开了会怎样、有什么依赖
   - ⚠️ **flag 有依赖关系，不能挑着开** —— 比如延迟隐藏调度器
     必须同时开 SparseCore 聚合器，否则编译器直接拒绝
   - ⭐ 有些 flag 是**纯赚**的：比如锁频，能白拿百分之几的吞吐，
     **一个字节显存都不涨** —— 这类应该默认开
2. **tile / block size** —— 对付 VMEM OOM 和访存效率
   - ⚠️ scoped vmem 抬太满会把 prefetch 挤掉：**编译过了但吞吐掉**
3. **recompute 策略** —— 用算力换显存（见[专题三](专题03-反向与优化器.md)）
4. **并行策略 / 拓扑** —— 见[专题四](专题04-并行策略.md)。
   ⭐ **先选对拓扑再调参**：调参顶多再挤百分之几十，换拓扑可能是数倍
5. **改模型实现** —— 算子替换、融合友好的写法
6. **自己写 kernel** —— 最贵，见下一节

## 八 · kernel 层：什么时候不得不自己写

**前提**：前七节都做完了，瓶颈定位到某一个算子，而编译器就是生成不出好代码。

- **Pallas**：在 TPU 上用 Python 写 kernel
- 写 kernel 要想清楚的：数据怎么分块进 VMEM、循环怎么排、
  怎么让 MXU 吃满、怎么把访存和计算重叠
- **怎么看自己写的 kernel 好不好** —— 这就需要另一个工具

### Percale

- 比 XProf 更深一层的工具：**看 kernel 内部**发生了什么
- XProf 告诉你"这个算子花了 300 微秒"，
  Percale 告诉你"这 300 微秒里，MXU 忙了多久、在等什么"
- ⭐ 我们做过一次完整的 Percale 调优实战（RPA 那次），
  过程和结论都记着 —— 可以直接改编成这一节的案例
- 待补：Percale 的 trace 有时效性（artifact 会过期），
  要在课程材料里存下截图

### 我们的 kernel 实战

- **KDA 的 Pallas kernel**（Tokamax）—— 线性注意力的状态更新怎么并行化
- Splash Attention 的调优（块大小、`use_max_logit_estimate`）
- ⚠️ 一条实测教训：**「块越大越好」是错的**。
  seq=16384 时最优块仍是 2048，seq/2 编译都过不去 ——
  **共同点是绝对值 2048 而不是比例**，疑似撞硬件常数

## 九 · 方法论（贯穿全课，但这里要正式讲一遍）

- **一次只改一个变量。** 一次改三个，涨了也不知道是谁的功劳
- **跑三次取中位数。** 单次结果不可信
- ⚠️ **压测必须固定随机性**（比如 temperature=0）——
  否则投机解码的接受率会崩到 1%，你会得到一个完全错误的结论
- **别照抄别人的比例。** 重算的收益、flag 的收益，同一个开关在不同模型上差别很大
- **有判分接口先查分再改代码**
- ⭐ **调参是有天花板的。** 我们在混元 3 上从 445 调到 645 TFLOP/s，
  然后**八格参数扫下来零收益** —— 那时候该做的不是继续扫，
  是换思路（换拓扑、换实现、改 kernel）。
  **知道什么时候停下来，跟知道怎么调一样重要**
