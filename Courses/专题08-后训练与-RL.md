# 专题八 · 后训练与 RL

> **RL 把推理引擎塞进了训练循环 —— 这是它跟预训练最根本的不同，
> 也是它对系统提出的所有新要求的源头。**

## 这个专题要回答的一个问题

前七个专题讲的都是预训练：一个模型、一份数据、前向反向更新，循环。

**后训练不一样。** 而且它的不一样，不在算法上 —— 在系统上：

> **预训练的循环里只有训练。
> RL 的循环里，训练和推理是交替的。**

模型要先**生成**一批回答（这是推理），再根据这些回答的好坏去**更新**自己（这是训练）。
于是一套 RL 训练系统里，同时住着一个训练框架和一个推理引擎，
它们共享同一批权重、抢同一批卡。

**这一句话就是这个专题的全部难点来源。**

---

## 一 · 脉络：每一代在砍什么

**先划一条线：SFT 不在这个专题的难点里。**
它就是换了份数据的预训练 —— 同样的前向反向、同样的账、同样的并行策略。
[专题三](专题03-反向与优化器.md)那套东西直接照搬即可。

**真正的分水岭在 SFT 之后 —— 进入 RL 那一刻。**

下面不按时间讲算法细节，**按「砍掉了什么」讲** —— 因为砍掉的正是系统负担。

| 方法 | 核心思路 | **同时要在显存里的模型** |
|---|---|---|
| **SFT** | 直接拿标注数据微调 | 1（actor） |
| **PPO / RLHF** | 训一个奖励模型打分，用 PPO 更新 | **4** ⚠️ actor + critic + reward + reference |
| **DPO** | 跳过奖励模型，直接从偏好对里学 | **2** actor + reference |
| **GRPO** | 一个问题生成一组答案，**组内互相比**，砍掉 critic | **2-3** |
| **DAPO / KTO / SimPO 等** | 各自再简化或改进目标函数 | 视方法而定 |

> ⭐ **看最后一列。** 算法演进史，从系统角度看就是**一部削减模型数量的历史**。
>
> PPO 要四个模型同时驻留 —— 对一个 671B 的模型意味着什么？
> 用[专题三](专题03-反向与优化器.md)那张账单算一遍就知道有多疯狂。
> **DPO 和 GRPO 的流行，很大程度上是被系统成本推动的，不只是效果更好。**

### 各自要展开的点

- **RLHF 三阶段**：SFT → 奖励模型 → PPO。为什么当初要这么复杂
- **PPO** 里 critic 是干什么的、为什么它那么贵
- **DPO**：把强化学习问题重写成一个分类问题 —— 简约革命
- **GRPO**：用**组内相对比较**代替 critic 的绝对估值。
  这一步在 DeepSeek R1 上被验证得很彻底
- **规则奖励（RLVR）**：数学题、代码有标准答案 → 连奖励模型都不要了
  → 系统上又少一个模型

## 二 · 系统视角一：显存账怎么变

拿[专题三](专题03-反向与优化器.md)那套口径重算一遍：

- actor 要训练 → **全套 16 字节/参数**
- reference 只做前向 → 只要权重
- reward 只做前向 → 只要权重（如果有）
- critic 要训练 → **又一套 16 字节/参数**

**PPO 的账**：两套完整训练状态 + 两套推理权重。
对 671B 来说这是什么概念？—— 这一节就算这个数。

**GRPO 的账**：一套训练状态 + 一套推理权重。

> 这一算就明白：为什么大模型上做 RL，几乎没人用原教旨的 PPO。

## 三 · 系统视角二：rollout —— 推理引擎进了训练循环 ⭐

**这一节是整个专题的核心，也是别处讲不到的部分。**

RL 的一轮长这样：

```
    ┌──────────────────────────────────────────┐
    │  1. rollout：让模型生成一批回答（推理）      │  ← 这一步占大头
    │  2. 打分：规则或奖励模型                    │
    │  3. 更新：算梯度、更新权重（训练）           │
    │  4. 把新权重同步回推理引擎  ←──────────────┘
```

**四个由此产生的系统问题：**

### 3.1 训练框架和推理引擎必须共存

- 训练侧是 MaxText / Megatron，推理侧是 vLLM / SGLang
- 两套系统对权重的**布局、分片方式、精度**要求都不一样
- 谁跑在哪些卡上？共置还是分离？

### 3.2 权重同步是个真问题

- 每更新一次，就要把新权重推给推理引擎
- 671B 的权重同步一次要多久？走什么通路？
- 能不能只同步变化的部分？

### 3.3 ⭐ generation 占 80-90% 的墙钟时间

**这是整个 RL 系统设计的出发点，也是最该先讲的一个数。**

2026 年 3 月 HuggingFace 对 16 个开源 RL 后训练框架做过横评，
一个共同发现：**generation（也就是 rollout）吃掉 80-90% 的墙钟时间。**

也就是说：**RL 训练系统首先是一个推理系统。**
你花在优化训练那一侧的力气，天花板只有 10-20%。

### 3.4 rollout 阶段的利用率通常很低

- 生成是**逐 token 的 decode** —— [专题七](专题07-性能调优与工具链.md)讲过，
  这是**带宽受限**，MFU 天然低
- 而训练阶段是算力受限
- **同一批卡，两个阶段的瓶颈完全不同** —— 怎么配才不浪费

### 3.5 于是有了异步 RL

- 让 rollout 和训练解耦，各跑各的，不互相等
- 代价：用的策略稍微旧一点（off-policy 程度加深）
- **这是一个纯粹为了硬件利用率而做的算法妥协** —— 又一个「硬件塑造算法」的例子

## 四 · RL 引擎：四个要介绍的

这些不是"又一个训练框架"，它们是**编排器** —— 管训练、推理、打分几个角色之间的
数据流与权重流。复杂度比单纯的训练框架高一个量级。

| | 出品 | 定位 | 后端 |
|---|---|---|---|
| **veRL** | 字节 volcengine | **事实标准**，生态最大 | PyTorch + Ray，GPU |
| **AReaL** | 蚂蚁 + 清华 | **全异步**，Decoupled PPO | GPU |
| **slime** | THUDM（清华） | 面向 RL Scaling | GPU |
| **Tunix** | Google | 轻量级 post-training 库 | ⭐ **JAX —— TPU 侧的答案** |

### 4.1 veRL

- 生态最大、被引用最多，很多论文的复现基线
- HybridFlow 的编排思路：把角色（actor / critic / rollout）解耦成可独立放置的单元
- 我们关心：**它在 TPU 上能不能跑、要改什么** ← 待现查，别凭印象讲

### 4.2 AReaL

- **全异步**是它的旗帜：行为策略和近端策略解耦，容忍高 staleness
- 两个具体机制值得讲：
  - **Decoupled PPO** —— 把"用哪个策略生成"和"更新哪个策略"分开
  - **Interruptible Generation** —— 生成可以被打断，重算 KV cache 接着来
- 1024 GPU 上实测 **5.48× 加速**
- ⭐ 蚂蚁出品，跟我们的合作项目相关

### 4.3 slime

- 定位在 RL Scaling —— 规模化那一头
- 要补：它跟 veRL 的架构差异、擅长什么

### 4.4 Tunix ⭐

**这是 TPU 侧最相关的一个，要重点讲。**

- Google 出品，**JAX 原生** —— 不是把 PyTorch 方案往 TPU 上移植，是原生长在 JAX 上
- 覆盖 SFT + RL
- 跟 MaxText 的关系、跟 vLLM 的配合
- 我们仓库里已经有它的痕迹（依赖、GA 配置、checkpoint 转换）
- ⭐ **这个专题里我们唯一可能有一手经验的框架** —— 要把手上的东西盘清楚

### 4.5 横向看：所有人收敛到了同一个架构

HuggingFace 那份 16 框架横评的核心结论：

> **推理和训练拆到不同的资源池，中间用一个 buffer 连接，权重异步同步。**
> **异步解耦已经成为行业共识。**

其它共同点：
- **Ray 占 8/16** —— actor model 跟 RL 的角色编排天然契合
- 横评的七个轴（编排 / buffer / 权重同步 / staleness / partial rollout /
  LoRA / 分布式后端）**可以直接拿来当我们对比表的列**
- ⭐ **staleness 管理是公认的核心难题** ——
  用多旧的策略生成还能保证收敛，这是算法和系统的交界处

> 讲到这里应该点破一件事：**这四个引擎的差别，本质上都是在
> 「同步的确定性」和「异步的利用率」之间选了不同的点。**
> 跟[专题四](专题04-并行策略.md)里「用一种通信换一份显存」是同一类取舍。

## 五 · 长推理链带来的回旋

R1 之后，模型的思维链动辄几千上万 token。这把前面几个专题的问题**又拉回来了**：

- 生成的序列很长 → **KV cache 又成瓶颈**（回到[专题二](专题02-注意力演进.md)）
- 训练时这些长序列要进 batch → 激活又涨（回到[专题三](专题03-反向与优化器.md)）
- 长度还**不固定** → 静态形状的老问题（回到[专题六](专题06-TPU-与-GPU.md)）

> ⭐ **这一节的意义是收束**：RL 不是一个孤立的话题，
> 它把前面所有的账重新算了一遍，而且条件更苛刻。

## 六 · MoE + RL：我们特别关心的一个组合

- MoE 的 all-to-all + RL 的 rollout/训练交替 → 通信模式比预训练复杂得多
- 推理时的专家负载分布跟训练时不一样 → EPLB 之类的方案要重新考虑
- 我们有这方面的材料
