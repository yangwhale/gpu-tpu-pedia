# tokamax vs native megablox —— 特性、优劣、怎么选

> 出处：2026-08-15/16，64 芯片 TPU v7，Hunyuan3-295B-A21B。
> **这是本知识库里被问得最多的一块**，单独成篇。

## 先破一个误解：「tokamax」不是一个东西

同一个开关，**两个精度下走的是完全不同的代码**：

| 精度 | 开关打开后实际走到哪 | 有没有跨卡量化收集 |
|---|---|---|
| BF16 | `tokamax.ragged_dot(implementation="mosaic")` —— **裸路径** | ❌ 没有 |
| FP8 | megablox 封装 + tokamax 后端 | ✅ 有 |

所以「BF16 下 native 赢、FP8 下 tokamax 赢」不是矛盾 —— **它们比的根本不是同两样东西**。

---

## 逐项对比

| 维度 | native megablox | tokamax |
|---|---|---|
| **kernel 形态** | 自带 Pallas kernel，CSR 式组元数据 | BF16 走裸 ragged_dot；FP8 走 megablox 封装 |
| **权重收集** | **不写在代码里**，由编译器按分片规格插 | **手写在 kernel 入口**（`jax.lax.all_gather`） |
| **收集时机** | 权重刚读出来就发，**离用它还隔着好几层计算** | 临到用才发，**距离只有一行** |
| **能否被藏住** | ✅ 每步暴露 **34.6 ms** | ❌ 每步暴露 **6,170 ms** |
| **提升出循环** | ✅ 每步只发一次（80 层合并） | ❌ 每层发一次，一层都提不出去 |
| **收什么格式** | 未量化权重（字节 ×1） | **量化后**权重（字节 ×0.5） |
| **BF16 实测** | 基准 | **慢 12 倍**（裸路径本身就烂） |
| **FP8 实测** | 见下 | 677.0 per-chip |
| **静默出错风险** | ⚠️ **有**（见下） | 无 |

---

## native 的致命短板：会静默漏算

**触发**：专家维分片 + `fixed` 校准 + native kernel，三者同时成立。

`weight_gather_axes` 这个参数**两条分支都会拿到**，但只有 tokamax 分支真的去执行收集；
native 分支调的那个 kernel **函数签名里根本没有这个参数**。
反向的 `psum_scatter` 同样只有 tokamax 分支有 —— **前向漏收、反向漏散，成对出现**。

后果：kernel 只对本地那几个专家建组元数据，**其余专家完全不参与计算**。
不报错、loss 照常降，唯一症状是「快得离谱」（曾报 ~~1,014.8~~ **已作废**，补齐后 637.0）。

**规避**：不要开专家维分片。按 embed 维切（正经 FSDP）时每卡拿到的是**残缺**专家，
编译器**被迫**收齐才能算 —— 结构上不可能漏。

---

## tokamax 的致命短板：通信藏不住 + kernel 可能退化

**通信藏不住**：手写的集合通信钉死在依赖链中间，调度器没有腾挪空间。
它的字节数只有 native 的一半，**结果仍然慢 178 倍**（就暴露耗时而言）。

> **手写集合通信会牺牲调度自由度。** 声明式表达分片、让编译器插通信，
> 通常比手动优化更快 —— 哪怕手动那条在字节数上更省。

**kernel 退化**：不带 `input_buffer_count` 之类的 Mosaic 参数时，
实测 kernel 只跑出峰值的 **0.67%**（8 TFLOP/s vs 峰值 1,154），
整步时间被它吃掉 97.5%。加上参数能救回约 32 倍。

**这是个隐患**：谁切回 tokamax 路径而不知道要设这个参数，性能掉几十倍，而且不报错。

## 怎么选（决策树）

```
BF16 ?
  └─ 是 → native。tokamax 的裸路径慢 12 倍，没有任何理由用
  └─ 否（FP8）
       └─ 要开专家维分片吗？
            ├─ 不开（推荐）→ native + FSDP 吃满 + absmax 校准
            │                 实测 670.8（生产）/ 727.0（峰值 fixed）
            └─ 开   → **必须**同时开 tokamax，否则静默漏算
                      实测 677.0，但 FSDP 被整除约束锁在一半宽度
```

**结论：默认 native，不要开专家维分片。**
这条路同时避开了两边的短板 —— 没有漏算风险（编译器兜底），通信也藏得住（编译器插的）。

## 数字汇总（64 芯片，80 层，seq 4096）

| 配方 | 路径 | 专家维分片 | 校准 | FSDP | pdbs | per-chip |
|---|---|---|---|---|---|---|
| 峰值（仅 benchmark） | native | ❌ | `fixed` | 128 | 13 | **727.0** |

| 旧配方 | tokamax | ✅ | `fixed` | 64 | 7 | 677.0 |

## 排查提示

判断当前走的是哪条路，**不要看配置，要看实际行为**：

- 打 trace 期探针，看 kernel 收到的权重第 0 维是完整专家数还是分片后的数
- 看 profile 里权重收集的**执行次数**：每步一次 = 编译器提升出循环了；
  每层一次 = 手写的，没提出去
- 看收集算子的 dtype：量化后的格式 = 走了跨卡量化收集
