## 一、循环接缝（最贵的一类）

页面里这些 mp4 都挂 `loop`。**首末帧对不上，每一轮都跳一下**，
比没有动画还廉价。而它的隐蔽之处在于：**你在编辑器里播一遍是看不出来的**，
得等它循环到第二遍。

### 1.1 ⛔⛔ 不要用「平均像素差」判一致

2026-09-18 实测翻车三次，**每次都是同一个病换皮**：

| 用的判据 | 为什么瞎 |
|---|---|
| 首末帧**平均像素差** = 1.26 → 判「✅ 一致」 | 画面 98.5% 是白底，差异被稀释两个数量级。实际首帧是曲线、末帧是一列条 |
| **差异像素 ÷ 墨水** | 棋盘格曲面只转了不到半度就量出 **51.2%**，跟「差着一整幕」同档 |
| **墨水总量相对差** | 一条恒定的灰带占 19 万像素，把真变化稀释成 **17.4%**，比正常片子还低 |

⭐⭐⭐ **结论不是再换一个指标 ——&nbsp;一个标量分不开
「末帧是另一幕」和「末帧偏了一像素」，而人眼一秒就能分开。**

所以 `scripts/check-loop.py` 做成**基线回归 + 必落一张上下拼接图**：
只问「有没有比记录的更糟」，判定交给人，判完的结论写进 baseline 的 `note`。
新片子没有基线就报红，逼你看一眼再登记。

### 1.2 ⭐ 「复位」的目标是**第一帧**，不是「空」

这两个只有在第一帧真的是空的时候才重合。有一支片子的注释写着
「首尾都是全灭」——&nbsp;而它的第一帧其实有一个亮节点、两个球、两块计数。
**正因为把首帧想成「空」，复位才被写成「末尾全部关掉」，于是永远对不上。**

### 1.3 ⭐⭐ 复位只能定义在一个地方

有支片子把 `if t >= T_END - 0.6: 全灭` **在四个绘制函数里各写了一份**，漏了两份。

**判据：同一条不变量复制 N 份，N 越大越必然漏。**
正确形状是**在时间轴上做一次映射**：

```python
def clock():
    t = tr.get_value()
    return 0.0 if t >= T_RESET else t      # 复位段把时钟拨回 0
```

然后所有绘制函数一律读 `clock()`，并加一条断言兜住：

```python
assert src.count("tr.get_value()") == 1, "有绘制函数绕过了 clock()"
```

这样「末帧 ≡ 首帧」**不是靠 N 个分支凑出来的，是按定义成立的**。

### 1.4 内容是累积的时候，清零只是把跳帧挪进片内

一张「随时间填满」的图，末尾直接清零，观众看到的还是一次硬跳 ——
只不过跳的位置从接缝挪到了片尾。⭐ 正确做法是**让时钟倒着走回去**：

```python
def clock():
    t = tt.get_value()
    if t <= T_RESET:
        return t
    return T_RESET * (1.0 - (t - T_RESET) / T_REW)     # 线性倒放
```

读起来是「画一遍 → 看一眼 → 退回去 → 重画」，接缝自然，而首末帧是同一帧。
⛔ 注意横轴的归一化要改成除 `T_RESET` 不是 `T_END`，否则回退段会分走一截宽度。

### 1.5 良性局限：不要追最后那一两个像素

细线 / 小球 / 字的**抗锯齿边**会在小墨水基数上放大成 20–30% 的「不一致度」。
量出来高、肉眼一样 ——&nbsp;**登记进基线、写清楚原因，然后别追**。

⛔⛔ **怎么判它是不是噪声，这里我写错过一版，值得看清楚：**

| | 判据 | 结论 |
|---|---|---|
| ❌ 旧版 | 取**相邻两帧**（内容必然相同）量一次，若只有 1% 就说明那 20% 是真差异 | **没有判别力** |
| ✅ 现在 | 拿**压缩前的 manim 直出** 跟 **压缩后的成品**，量同一对首末帧 | 有判别力 |

旧版为什么瞎：静止段的相邻帧会被 h.264 编成 **skip 宏块，逐位相同**，
于是恒等于 0.0% ——&nbsp;**它测的是「编码器有没有偷懒」，不是「噪声地板有多高」。**

新版为什么有判别力：**首帧是 I 帧、末帧在静止 GOP 深处**，两者的量化待遇完全不同，
所以这一对的差值正好把「压缩引入的量」单独拎出来。实测（`anim-reverse`）：

```
压缩前 1080p60      不一致度  3.4%   幅度 >64 的差异像素    0 个
压缩后 960/crf30    不一致度 29.4%   幅度 >64 的差异像素   21 个
```

⭐ 26 个百分点全是压缩带来的，而且差异都是**低幅蚊式噪声**（围着文字和圆环）。
⭐⭐ 顺带一个副产品判据：**看差异像素的幅度分布。**
内容不同 → 高幅像素成片；压缩噪声 → 几乎全是低幅，高幅的个位数。

## 二、图层与可见性 · 镜头

### 2.1 `FadeOut` 会把 mobject **移出 scene**

`set_opacity(1)` 只改属性不改归属 ——&nbsp;淡出过的东西要回来，必须重新 `add`。

### 2.2 `Scene.add` 是**追加到最上层**

于是「把曲线加回来」会让曲线**盖住原本在它上面的球**。

⭐ **「加回 scene」和「加回原来的图层」是两件事。**
这个版本的 `Scene` **没有 `add_to_back`**（直接 AttributeError）。
可靠做法是**留着引用，按最初那一行同样的顺序重新 `add` 一遍** ——
`Scene.add` 会先 restructure 去重再追加，所以顺序自然复原，而且不依赖版本：

```python
ball_a, ball_b = ball(...), ball(...)
self.add(act1, ball_a, ball_b)      # 开头
...
self.add(act1, ball_a, ball_b)      # 复位时原样再来一遍
```

### 2.3 `self.wait()` 不一定驱动 `always_redraw`

改完 tracker 直接 `wait`，画面可能**停在旧帧**。
**只有 `play` 一定会走一遍 updater**，所以复位后补一个恒等动画：

```python
t.set_value(0.0)
self.play(t.animate.set_value(0.0), run_time=1 / 30)   # 强制刷一帧
self.wait(0.5)
```

⭐ 这么写对「wait 到底驱不驱动 updater」这个不确定点是**鲁棒的** ——
两种情况都得到正确末帧。比去查清楚机制再赌一把划算。

### 2.4 ⭐⭐ 「长度 ∝ 数据」的元素，在有镜头运动的片子里必须封顶

速度箭头画成「长度正比于 |v|」，平时很好看；镜头推近到 0.45 倍时
画面等比放大 2.2 倍，那根箭头**当场比球大五倍、还冲出画框**。

⭐ 判据：**它的视觉尺寸是「数据 × 镜头倍率」两项相乘** ——&nbsp;
数据那一项你控制得住，镜头那一项是后加的，所以要给最终长度设上限。

### 2.5 钉在位置上的标注，寿命不能超过它指的那个东西停留的时间

「冲过了头」这个标注钉在轨迹最远那一点上，跟着后面整段一起淡出 ——&nbsp;
可球一秒之内就荡回去了，于是有一秒多的时间它指着一块空地。

### 2.6 场景里一个 `play`/`wait` 都没有 → manim 只出 PNG，不出 mp4

`render.sh` 会明确报这一条。

## 三、造数据时的自欺

### 3.1 ⭐⭐ 断言挡住时，先看它挡的是什么

造了一条一维 loss 想演示「起点不同、落进不同的谷」，
写成 `0.10x² + 0.95cos(1.15x)` ——&nbsp;**这是偶函数**，
两个谷必然左右对称、深浅一模一样，论点当场不成立。

断言 `f(shallow) > f(deep) + 0.2` 把它挡下来了。
⛔ 当时的诱惑是「阈值太严，改成 0.05」。
⭐ **正确反应是去看它挡的是什么** ——&nbsp;挡的不是阈值，是我造的函数本身对称。
加一个奇次项 `+0.13x` 破对称即可。

同源的一条：断言 `>10×` 实测只有 8.6×，**正确反应是把实测值打印出来，不是把 10 改成 8**。

### 3.2 数据全部当场算，别手摆

等高线要真的二分找等值点，梯度轨迹要真的迭代，
精度边界要真的从 `numpy.float16` 的位模式读出来。
**手摆的坐标没有人能复核，算出来的有断言兜着。**

### 3.3 注释里的数也是一种断言

docstring 里那句「大约 20 倍」、图注里那句「12.8 秒无声循环」——
改了代码它们会**一声不响地过期**。
能做成 lint 的就做成 lint（本 skill 的 `check-loop.py` 就带了图注秒数体检）。

⛔ 写那条 lint 时第一版正则锚在**左括号**上（要求括号紧挨数字），
于是两条过期只抓出一条。⭐ **锚点要选语义短语，别选标点** ——
标点的位置随排版漂，「秒无声循环」这五个字才是这句话的身份。

### 3.4 ⭐⭐ 参数也是数据，别手调

要画「一个浅坑 ＋ 一个深谷，无动量的球卡住、有动量的球冲过去」，
第一版手写地形，那个线性项**符号写反了** ——&nbsp;整条曲线往右上抬，
于是起点左边那个坑反而最深，球一进去就到底，「冲过去」无从谈起。
断言挡下了，但**接下来才是关键**：诱惑是再手改几个数试试。

⭐ 正确做法是**把「要满足的条件」写成筛子去搜**。这一次的筛子是：
地形上至少两个极小、先遇到的明显浅、深谷在右边、无动量的球停在浅坑、
有动量的球落进深谷、速度峰值高出 1.3 倍。
3×3×3×3×3×3 的网格跑一遍，**454 个可行解**，按「深浅差 × 速度峰值比」取头名。
搜一次十几秒，比手凑快，而且**选出来的参数自带理由**。

### 3.5 ⭐ 断言要断在同一个坐标系里的量上

顺手写过一条 `assert K_CROSS < K_STUCK < K_LAND` ——&nbsp;看着像在检查时序，
其实它拿**两条独立轨迹**的步号在比大小，而那两幕是分开播的，
谁的第 19 步在前**没有任何物理意义**。换成同一条轨迹内部的顺序才成立。

### 3.6 时长要按**实际动作区间**定，不按循环次数定

轨迹跑了 120 步，就按 0→120 线性播 ——&nbsp;结果**戏全在头 20 步**，
镜头推近的时候球早过去了。先把关键步号算出来
（什么时候冲过去、什么时候卡死、什么时候落地），再按它们排时间。

## 五、渲染成本

实测（cc-tw，2026-09-18）：

| | 分辨率 | 简单场景（一条曲线＋几个点） | 重场景（几百个 mobject） |
|---|---|---|---|
| `--draft`（`-ql`） | 480p15 | **4–8 秒** | **3–4 分钟** |
| 正式（`-qh`） | 1080p60 | **2–5 分钟** | **5–10 分钟** |

⛔⛔ 「重场景」指的是**同时在场的 mobject 数量**，不是时长也不是分辨率。
一段 15 秒的图里如果有 540 条等高线线段、外加每帧重建上百条轨迹线段，
它在 **480p 草稿下都要三分半** ——&nbsp;比一段简单场景的 1080p 正式渲染还慢。

⭐⭐ 一条更贵的教训：有一次我觉得「加了字幕之后渲染变慢了」，
于是连续猜了两个原因（updater 每帧重设属性、Text 每帧光栅化），
各改一版、跑一次三分半的实验 ——&nbsp;**结果两个都不是**。
真相是那三分半本来就是这个场景的固有成本。
⛔ **问题出在前提：我从来没记录过它原来要多久。**
⭐ 判据：**「感觉比以前慢」在没有旧基线数字时不是可靠信号。**
所以这张表存在的意义，不只是让你预估等多久，**更是给下一次「是不是变慢了」一个可比的数**。

⭐ **迭代阶段一律 `--draft`。** 构图、时序、接缝这些在 480p 上全看得出来，
而一次 `-qh` 够你在草稿上试二十轮。

压缩到 960 宽 / crf 30，十几秒的教学动画通常落在 **50–300 KB**，可以直接进仓库。

⛔ 渲染要放后台跑（`nohup` / `setsid`），**并且给它配个 watch-task** ——
turn 结束你就不在了，"渲完我再报"说出口即落空。

## 六、换底色（2026-09-19 一次转七段攒的）

白底转黑底看着只是换几个十六进制，实际上有**八条**会咬人。全部来自那一轮的实测。

### 6.1 ⭐⭐⭐ 别名按「语义」建，不按「色值」建

`INK_ = 深色` 是**色值**别名；`DOT_ = 那颗黑点` 才是**语义**别名。

翻底色时，色值别名会当场炸：有一段里 `INK_` 同时喂着标题、说明文字、
和一颗**被画面文案点名叫「黑点」**的点。正文该改白，而那颗点一改白，
旁边那句「黑点：这里梯度为零」就成了假话。

⛔ 所以换底色前先盘一遍：**谁在用这个别名，它们是不是同一个语义。**

### 6.2 ⭐⭐ 灰的明暗关系会整个倒过来

白底上 `#c3c7cb` 比 `#80868b` **浅**，所以它是**更弱**的那个。
黑底上「更浅 ＝ 更强」——&nbsp;**不能按亮度照搬映射**，
要按「谁该更弱」重新指派。实测那一段里，等高线拿了暗灰、±5% 细线拿了亮灰，
跟白底版正好反过来。

### 6.3 ⭐⭐ 一个灰别名身兼两职，黑底上必须拆开

白底版常有一个 `GY_` 同时管**辅助线**和**大面积填充**。黑底上这两件事对亮度的
要求是**相反**的：

> **够亮的灰放大成一整块就是脏；够暗的灰缩成一条线就是没有。**

拆成两个常量（`GY_` 管线、`FILL_` 管面）。

### 6.4 大面积填充要问「它表达的是厚还是亮」

一块占画面四分之一的「常驻显存」基座，最后选的是**暗填充 ＋ 亮描边**：
厚度已经由高度说完了，填充只需要「这块地有东西」这一点信号，
真正该被看见的是它的**上沿**（别的东西从那条线上长起来）。

⛔ 试过「只留描边不填充」，抽帧后否掉：内部纯黑会跟画面外的黑**连成一片**，
体量感当场消失 ——&nbsp;而那正是那一幕的前提。

### 6.5 ⛔ 「线宽不低于 4」不是无条件的

manim 默认线宽是 4，黑底上细线容易消失，所以有「往上提」这条经验。
**但元素小到只有二十来个像素时，4 px 的边框会把它吃掉。**
一排 61 个小格，一格 21 px 宽 ——&nbsp;正确解是**去掉描边、靠实心填充和间距**，
既不是留一条 0.8 的细线，也不是硬塞 4。

### 6.6 `fill_opacity` 是配色的一部分，不是独立参数

同一对颜色在白底和黑底上的最佳不透明度**不一样**。棋盘格曲面用 0.62：
白底上半透明显得轻盈；黑底上同样的 0.62 把暗格拉到接近背景，
**轮廓在暗格处断掉**，看着像渲染缺了一块。

⭐ 所以「换一对颜色」要**连不透明度一起扫**。只扫颜色会得出「哪对都糊」的错误结论。
（那次扫了 3 对颜色 × 3 档不透明度共六版，才定下 `BLUE_D`/`BLUE_E` @ 0.85。）

### 6.7 ⭐ `stroke_width` 是**分辨率无关**的，别拿像素写断言

`camera.cairo_line_width_multiple = 0.01`，所以 `stroke_width w` 就是
**0.01 × w 个场景单位**（扒 `camera/camera.py` 确认）。
拿像素换算去跟它比，会出现「`-qh` 过、`--draft` 挂」。两边都换成场景单位才对。

### 6.8 零高度的 `Polygon` 照样会描边

一条随时间变化的带子，在某一段里高度恒为 0 ——&nbsp;它退化成一条线，
**但描边还在**，于是一条红边贴着旁边那块蓝色的斜边跑，
读起来像「这个量此刻已经存在」，而事实是它还是 0。

⚠️ 这条是旧版就有的，但**把描边从 2 加到 4 之后它响了一倍** ——&nbsp;
⭐ 判据：**自己的改动放大了别人的旧缺陷，那就归自己修。**
最小修法是调 z 序，让它被上面那块的描边盖住。

### 6.9 顺带：`assert` 消息里的 `%` 会被当成格式符

`assert x, "±5% 两条线…" % (...)` 报的是
`unsupported format character` **而且指向一个中文字符** ——&nbsp;
错误正文跟本意毫无关系。要写 `%%`。
（跟「commit message 里的 `%` 会腰斩」同源。）
