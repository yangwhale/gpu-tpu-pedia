08 日常运维：监控、维护、升级、巡检、找谁、事故手册

这一章要解决什么问题：交付后怎么天天跑——看什么信号、每天每周查什么、怎么分批维护和升级、出事翻哪本手册、做不动找谁。 为什么难：平台侧告警不一定比你先发现问题；健康信号会说谎；维护和升级本身会打断切片。检测必须自己做。

  • 29 条告警（7 条首个生产任务前必须有）
  • 7 种「看着健康」的假象
  • ≥132 自触发维护每批之后的健康 cube 下限
  • 306 s 日报完整 8 段跑一遍
  • A–G 7 本事故手册

变量：source ~/runbook-env.sh && rb_env_check PROJECT REGION ZONE CLUSTER RESERVATION（全书唯一变量块 scripts/env.sh）

  • 另用 $BLOCK $NS $CLUSTER_QUEUE $CUBES_SLO $SPARE_CUBES $STATE_DIR；集群是 zonal，一律 --location=$ZONE。
  • 脚本：scripts/08-alert-sources.yaml（29 条告警同号）、scripts/08-daily-check.sh；复用 05-triage-slice.sh、05-isolate-cube.sh、05-delete-slice-chain.sh、05-avoid-manual-slices.py。

掉队阈值要按功耗档分开

默认档和 P7 的跨 host 离散差一个数量级（同一批 host 上默认档、P7 交替跑的 ABBA 对照）：

功耗档 跨 host 极差 =（最高 − 最低）÷ 中位，单次运行；括号里是两次运行合起来的 min–max（bf16 N=32768，折算每芯片） 逐 host 固定吗 建议判据 [推断]
默认（P3） 4x4x4 0.7%（1,802–1,815）；4x8x8 0.8%（1,802–1,817） 否（噪声） 低于同片中位 > 2% 疑似掉队
P7（--xla_tpu_dvfs_p_state=7） 4x4x4 约 6%（1,821–1,926）；4x8x8 约 7%（1,808–1,939） 是：两次逐 host 相关 1.00 / 0.999 和这台自己的 P7 基线比，偏离 > 2% 报；跨 host 只报 > 8%
P7 下的 fp8 不到 2%，两次相关 −0.26 / −0.14 否 同默认档
  • P7 离散大：满载时被功耗 / 散热顶住，每台涨幅固定；最慢那台（4x8x8、bf16 N=32768，同一台 host 自比）P7 1,808 vs 默认 1,807；两种模式各取最慢 host 相比（1,802 → 1,808）的话，比的不是同一台 源「功耗顶住」为推断。
  • 片级掉队：拖后腿那片 collective 延迟最低、duty cycle 最高（按片看这两项找慢片，见经验教训第 45 条）。准入、周期测、在岗发现到送修的整条流程见 08a 慢节点标准流程。
  • 训练中只有分钟级 tensorcore_utilization 和 container/multislice/* 延迟；逐 host 靠每周 soak（04-bench/c1_chip_bench.py，P7 阈值见 thresholds.csv）。容器内读不到功耗 / 频率 / 温度（vfio，tpu_throttle_score 为空）。

7 升级 Google 支持时附上：实例 ID / 名、MIG 与 MMIG 名、multiMig 字段 05-delete-slice-chain.sh <slice>（dry-run）；--scan-orphans
8 缺货：精确错误串（GCE_LOCATION_OUT_OF_RESOURCES|GCE_RESERVATION_OUT_OF_RESOURCE|GCE_RESOURCE_EXHAUSTED|TPU_OUT_OF_RESOURCES|TPU_OUT_OF_RESOURCES_RESERVATION）、operation ID Q11

  • 维修卡单类升级，附上 §8.4「已修未回池」日表当天那几行：主机 + 送修时间 + 挡住的 cube 里坏几台。
  • 维修原因目前只给到 FAILURE_TPU / FAILURE_INFRA / hostError 这一级，看不出是哪类硬件故障；要细分得单独提需求。紧急修复几乎没有提前量，非紧急的硬件预警有 7 天窗口，所以检查点要按「随时会丢主机」设计 [推断]。

开 case 与推进升级

定优先级
  • 优先级跟影响走，不跟紧迫感走：交付日被挡、容量掉出 SLA 线标最高级；单台主机变慢但已隔离标低级。
  • 不打算要求对方立即响应就别标最高级；拿不准先标次一级，再找 account team 确认。
  • 缓解了就主动降级，写清缓解了什么、还剩什么，剩下的拆成后续 case。
  • 是你的头号优先级可以要求升级，但要在 case 里写明业务原因。

8.6事故手册

上线周会出哪些事故、交付前怎么防、出了怎么判，按类整理在 08c 上线周的生产事故。本节是止血步骤。

每本都是「止血 → 取证 → 修 → 升级」，取证在破坏性操作之前（遥测会过期）。

A. 跑着任务的 cube 变 UNHEALTHY

触发：Kueue 日志 EvictedDueToAdmissionCheck 或 Workload was evicted as there was no replacement for unhealthy node(s)。

  1. 按图判断：VM 坏不会自动 deform，只靠 pod 挂驱逐；重切耗时见 07 §7.4。
  2. 恢复的坑：新 pod 跑分区一致性检查（C 第 1 步）；新 cube 上本地检查点被拒、退回持久层（丢到上一个 40 步倍数）→ 见经验教训第 24 条。
  3. 隔离：05-isolate-cube.sh --reason "<case 号>" --execute <partition-id>。
  4. 取证：kubectl get nodes -l cloud.google.com/gke-tpu-partition-4x4x4-id=<id> -o wide -L cloud.google.com/gke-tpu-partition-4x4x4-state；sub-block healthInfo；REPAIRING / UNSCHEDULED 维护。
  5. 修：原地修复无 holdback 经验教训第 3 条；REPAIRING > 12 h 或反复坏 → §8.5。修好、16 Ready + HEALTHY → --undo --execute <id>。

B. SliceCreationFailed 风暴 / Slice 卡在过渡态

触发：日报第 5 段。

  1. 分类：05-triage-slice.sh <slice>，对 05 §5.6：
    报错片段 含义 会自愈吗
    AttachMIGsToMMIG failed ... already attached to '...' cube 还被上一个切片占着（多为删完立刻重建） 通常会（实测集中在约 20 min 内）
    ... active sub slice in it with external slice ID <名>-<hash8>，<名> 不是 default-jobset-… 手工 Slice 占着 cube 常驻的不会（实测被常驻手工片挡住的任务重试到第 11 次、650 s 仍失败）；跑完就删的会（实测各重试 4–5 次，267 s 准入）
    FormSubsliceStep failed ... has an active sub slice / ConfigureAcceleratorTopology ... not supported ... Multi-MIG 大片和 2x2x1 互相挡 删挡路的 sub-slice
    Error 412 ... not stable / 400 resourceNotReady 与 GCE 后台操作竞争 等 2–5 min
    SliceCreationFailed ↔ INCOMPLETE 一分钟内来回 cacheSyncUp bug 不会；已有修复，所需版本向 Google 确认
  2. 手工片：删 JobSet，用 05-avoid-manual-slices.py 重提；找主人删片 → 见经验教训第 33 条。
  3. 过渡态 > 60 min：带 deletionTimestamp 卡 ACTIVATING 的别自己改 status，找 Google；FAILED 不驱逐 → 删 JobSet 重提 → 见经验教训第 39 条、经验教训第 35 条。
  4. 删不掉：05-delete-slice-chain.sh <slice> 按顺序删；卡在 DETACH_MIG_FROM_MULTI_MIG 只有 Google 能清 → §8.5 附件 7。
  5. 风暴：先查告警 #7 和 #13，逐片处理没用。

C. 重切后 TPU 初始化挂住

触发：新 pod 全打出 TPU backend initialization is taking more than 60.0 seconds 后无输出；或 START_SESSION failed / Mismatch barrier id … PRE_START_SESSION_BARRIER。

  1. 30 秒确认（每个 replica 只应有 1 个 partition ID）：
    bash
    JS=$JOBSET_NAME     # 别的任务：kubectl get jobset -n $NS 的 NAME 列
N=$(kubectl get jobset $JS -n $NS -o jsonpath='{.spec.replicatedJobs[0].replicas}')     # replica 数（= 片数）
for r in $(seq 0 $((N-1))); do
  echo "replica $r: $(kubectl get pods -n $NS -l jobset.sigs.k8s.io/jobset-name=$JS,jobset.sigs.k8s.io/job-index=$r -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{end}' \
    | xargs -I{} kubectl get node {} -o jsonpath='{.metadata.labels.cloud\.google\.com/gke-tpu-partition-4x4x4-id}{"\n"}' | sort -u | tr '\n' ' ')"
done
kubectl logs -n kueue-system -l app.kubernetes.io/name=kueue --since=15m --tail=-1 | grep -c "conflicting rank"
  2. 别等 12 min barrier 超时，也别指望 RestartJobSet（大概率再跨 cube）：删 JobSet，kubectl get pods -n $NS -l jobset.sigs.k8s.io/jobset-name=$JS 为空后再重提（同 run 名续检查点）。
  3. 一片一个 cube 仍挂（演练中见过 1 次）：拿 GCE UUID 按经验教训第 43 条分诊。

💡C、D 同一根治：交付 JobSet 模板启动命令必须带 ulimit -c 0旧 pod 在宽限期内退干净，也不落 core 撑满启动盘。

D. DiskPressure 驱逐

触发：EvictedDueToNodeFailures。

步骤 做法
1. 确认链条 按图核对驱逐链条（链条本身见经验教训第 42 条）
2. 等压力解除 kubectl describe node <n> | grep -A2 DiskPressure；重切后照 C 第 1 步查
3. 根治 ulimit -c 0（或不落盘的 core_pattern；要 core 就写带 sizeLimit 的 emptyDir）；启动盘仅 94.3 GiB、无 Local SSD 经验教训第 22 条
4. 验证 kubectl auth can-i create events -n $NS --as=system:serviceaccount:kueue-system:kueue-controller-manager 为 yes（告警 #29）

E. DCN 挂住（疑似网卡复位）

触发：多片任务卡在首次跨片 all-reduce（Deadline Exceeded），单片正常；或 #17 响而无节点告警。

  • 查：串口搜 NETDEV WATCHDOG|gve.*Performing reset；节点上 ethtool -g eth0 | grep -i "tcp data split"、dmesg -T | grep -i "gve.*reset"（04-nic-check.sh 批量做）。没命中就按主机网卡硬件排查（上图右支，见经验教训第 19 条）。
  • 别做：运行时 ethtool -K 关 tcp-data-split；调大 --node-monitor-grace-period。修复版 1.35.13-gke.0+ / 1.36.4-gke.0+。
  • 慢而不是挂：按经验教训第 45 条先取证再重建，区分经验教训第 20 条。

F. OCS drain：很多 cube 同时翻 DEGRADED / UNHEALTHY

触发：degradedInfraCount: 1 大面积出现；同组机位号（如每 cube 的 1、6、9、14 号机）有 drained link。

  • 先开一个 case 交给 Google，再看 sub-block healthInfo。
  • 一个机箱 DEGRADED：可用（需 ICI resiliency），SLO 算健康，照常调度；任务起不来就暂停提交。
  • 一对交换机都 drain：全部 UNHEALTHY，整 pod 不可用。
  • 事后：回 HEALTHY 后重建受影响切片。

实测集群标签把 DEGRADED 显示成 UNHEALTHY，只有 healthInfo 分得清。

  • 一个事件一张 case，别开 144 张。
  • 照常调度前提：书面约定 --default-slice-health-node-affinity=HEALTHY_AND_DEGRADED（09 D03）。暂停提交信号：TPU backend initialization is taking more than 60.0 seconds / STOP_SESSION failed；别按 cube 快速连发（先例致全 pod UNHEALTHY）。
  • 事后：healthyInfraCount 恢复后重建，让 resilient routing 生效[需确认]。

G. 配额耗尽

触发：Quota exceeded for quota metric 'Read requests' and limit 'Read requests per minute per region'；Invalid slice state transition 'ACTIVE' -> 'MMIGHealthProbeFailed'。

配额 症状 先做 根治 页
GCE 读请求 / 分钟 / region 健康切片成批 Ready=Unknown、Unexpected partition state 别批量删切片（先例：删了反把 detach 卡死，作业长时间停摆）；开 case；停自己的轮询器 控制器升到含修复的版本；交付前抬读配额（(MIG+MMIG)×12，144 cube 仅控制器约 3,456 reads/min [推断算术]） 经验教训第 52 条
multi-MIG 配额 新 super-slice 建不起 看用量 交付前 override 到千级 经验教训第 5 条
HDB（启动盘）/ IP 新池 / 新节点起不来 读 limit 也读 usage；清 Released PV Cloud Quotas API 提额（最慢） 经验教训第 5 条、经验教训第 21 条
etcd / pod 数 mvcc: database space exceeded、新池 0 节点 批量删完成态 pod；别成批建池 JobSet 加 ttlSecondsAfterFinished；已满时控制面存储配额只有 Google 能调 经验教训第 53 条

说得出（先自己答，再点开对答案）

  • 为什么告警要自己做？
    平台侧告警不一定比你先发现；健康信号会说谎
  • 举三种「看着健康其实不健康」。（网卡 2 s 复位节点不 NotReady；sub-block 每 4 h 假 DEGRADED；驱逐原因不在 events；429 把健康切片标 Unknown；池 RUNNING 但一台 unreachable）
  • P7 下为什么不能用默认档的掉队阈值？
    P7 跨 host 极差 5.6–6.8% 且逐 host 固定，默认档 < 1%；和每台自己的 P7 基线比
  • 自触发维护一批要先做哪三件事？
    排空任务、删 Slice、配额减去批量×64
  • 维护前删 Slice 还是删节点池？
    只删 Slice，删池会丢主机映射
  • 节点池升级前为什么要先删切片？
    升级会把 ACTIVE 切片变 FAILED 且不恢复
  • 重切后 TPU 初始化挂住，第一步查什么？
    每个 replica 的 pod 是否在同一 partition；跨了就删 JobSet，旧 pod 删净再重提
  • 读配额打满时最不该做什么？
    批量删切片
  • 出了问题第一步做什么？
    按 §8.6 止血、取证，同时开 case 交给 Google，带齐 §8.5 附件表
